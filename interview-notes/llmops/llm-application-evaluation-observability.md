# AI 应用开发面试主题：LLM 应用评估与可观测性

## 主题选择记录

- 主题：LLM 应用评估与可观测性
- 分类：AI 应用开发 / LLMOps
- 已回顾主题：RAG、AI Agent、Prompt 工程与结构化输出，本主题不重复
- 适用：AI 应用开发工程师、LLM 应用工程师、AI 平台工程师

## 一、核心概念

LLM 应用上线后，质量不会自动稳定。模型版本、Prompt、知识库、用户问题分布都会变化，因此必须建立评估与可观测性体系。面试常考：如何证明应用变好，如何发现幻觉、延迟、成本、拒答异常，以及如何定位到检索、Prompt、工具调用或模型本身。

评估关注“效果是否达标”，可观测性关注“线上发生了什么”。二者结合才能持续迭代。

## 二、关键指标

### 1. 质量指标

- 正确性：答案是否解决问题。
- 忠实度：答案是否基于给定上下文，是否编造事实。
- 相关性：回答是否围绕用户意图展开。
- 完整性：是否遗漏关键步骤、条件或限制。
- 格式合规率：JSON、表格、字段是否符合协议。
- 工具调用成功率：Agent 是否选择了正确工具并传入正确参数。

### 2. 工程指标

- 首 token 延迟、端到端延迟、超时率。
- 单次请求 token 数、模型调用成本。
- 错误率、重试率、限流次数。
- 用户采纳率、追问率、人工转接率。

面试要强调：不能只看模型输出，还要看成本、稳定性和业务结果。

## 三、关键步骤

1. 建立评测集：收集高频问题、边界问题、失败案例和安全样本。
2. 定义标准答案：给出参考答案、评分规则、必含事实点和禁用内容。
3. 自动化评测：每次改 Prompt、模型、检索策略或工具逻辑后跑回归。
4. 人工抽检：对高风险场景保留专家评审，避免完全依赖模型裁判。
5. 线上监控：记录输入、输出、检索结果、工具调用、延迟、token 和错误。
6. 问题回流：把线上差评、无答案、高成本请求加入评测集。

简单评测记录可以这样设计：

```python
case = {
    "question": "如何重置企业账号密码？",
    "expected_facts": ["进入账号中心", "验证手机号", "设置新密码"],
    "forbidden": ["联系数据库管理员"],
    "tags": ["高频问题", "账号"]
}
```

## 四、常见问题

### 1. 为什么离线评测通过，线上仍然效果差？

通常是评测集覆盖不足，缺少真实用户表达、长尾问题、多轮上下文和异常输入。解决方法是持续从线上日志采样，并按场景分层评估。

### 2. 可以完全用 LLM-as-Judge 吗？

不建议。LLM 评分适合初筛和规模化回归，但会受提示词、模型偏好和标准不清影响。关键业务要结合规则校验、人工评审和业务指标。

### 3. 如何排查幻觉？

先判断上下文是否包含正确答案；如果没有，问题在检索或数据。若上下文正确但答案编造，重点检查 Prompt 约束、模型能力、输出校验和拒答策略。

### 4. 如何控制成本？

监控 token 分布，识别超长上下文和重复调用；对简单任务使用小模型；缓存高频请求；限制工具重试次数；把长链路拆成可观测步骤。

## 五、实践建议

- 每个改动都要能用指标证明收益，避免“感觉更好”。
- 评测集要按场景打标签，如客服、代码、合同、权限、安全。
- 日志要保留 request_id，方便串联检索、模型和工具调用。
- 敏感数据要脱敏，不能为了观测泄露用户隐私。
- 上线前看离线评测，上线后看真实反馈，两者缺一不可。

## 六、一分钟总结

LLM 应用评估与可观测性是面试高频工程题。优秀答案应覆盖评测集、指标体系、自动化回归、线上日志、成本延迟监控和问题回流。核心思路是：先定义什么是好，再持续记录发生了什么，最后用数据驱动 Prompt、模型、检索和工具链优化。
