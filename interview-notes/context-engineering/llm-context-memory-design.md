# LLM 上下文工程与记忆设计

## 主题选择记录

- **主题**：LLM 上下文工程与记忆设计
- **分类**：AI 应用开发 / Context Engineering
- **仓库去重**：RAG 偏外部知识检索；本主题偏**窗口内信息选择与记忆治理**
- **适用岗位**：AI 应用开发、Agent/对话系统工程师

## 核心概念

**上下文工程**是在有限 context window 内，选择、组织、压缩对当前任务最有价值的信息——不是把全部聊天历史塞给模型。

**记忆**分三类（面试高频）：

| 类型 | 内容 | 生命周期 |
|------|------|----------|
| 短期记忆 | 当前会话最近几轮 | 会话结束可丢 |
| 工作记忆 | 当前任务中间结论、工具结果摘要 | 任务结束可丢 |
| 长期记忆 | 经确认的用户偏好、稳定事实 | 跨会话，需治理 |

记忆是**可检索、可更新、可删除**的数据资产，不是无限 append 的聊天记录。长窗口模型也不保证会用好全部输入——噪声、冲突、指令被淹没都会导致答错。

## 核心知识点

### 1. 上下文来源拆分

系统规则、用户当前问题、近期对话、会话摘要、结构化状态（槽位）、工具返回、长期记忆检索结果、RAG 片段——应分开管理，避免一锅炖。

### 2. Token 预算分配

为 system、检索/RAG、历史、用户问题、**模型输出预留**分别设上限；超长时优先砍早期闲聊和低分记忆，保留当前问句和硬约束。

```python
BUDGET = {"system": 800, "rag": 2500, "history": 1200, "user": 500, "output": 1500}

def build_messages(user_msg, recent, summary, memories, rag_chunks):
    mem = [m for m in memories if m["score"] > 0.8][:5]
    return [
        {"role": "system", "content": SYSTEM_RULES},
        {"role": "user", "content": format_block(summary, mem, rag_chunks, user_msg)},
    ]
```

### 3. 历史压缩策略

- **最近 k 轮**原文保留（k 常取 4～8）。
- **更早内容**做任务导向摘要（保留实体、约束、待办、已确认事实）。
- 金额、日期、订单号等**精确信息用结构化字段**，不要只压在摘要里。

### 4. 长期记忆写入规则

写入前：是否用户明确或反复确认、是否可复用、是否允许存储、置信度是否够。禁止把模型猜测、一次性情绪、未验证事实写入。字段建议：`content, source, created_at, confidence, user_id`。

### 5. 遗忘与隐私

支持过期 TTL、用户删除、撤销错误记忆；敏感字段默认不落长期记忆或脱敏存储。冲突时优先级：**系统规则 > 最新用户确认 > 旧摘要 > 低置信记忆**。

### 6. 与 RAG 的边界

RAG：外部知识库事实；上下文工程：当前任务所需的**全部输入编排**（含历史、状态、工具结果、记忆）。二者可同时出现，但要避免重复灌相同段落浪费 token。

### 7. 可观测性

记录每次请求最终拼进模型的上下文摘要（脱敏），便于复现「为什么这次答错」。

## 高频面试问题与标准答案

### 1. 什么是上下文工程？

就是在 token 预算内做信息治理：选什么、以什么顺序放、什么时候压缩或丢掉。和「加长上下文」不是一回事——窗口大了更要防噪声和冲突。

### 2. 长上下文为什么还会答错？

常见原因：无关历史太多、两份材料矛盾、关键约束埋在中间、工具返回太长把 user 问题挤掉。我会用预算和分层结构缓解，而不是无脑加长度。

### 3. 短期记忆和长期记忆怎么区分？

短期就是本轮对话和工作区状态，关掉会话可以不要。长期是跨会话还要用的偏好或事实，写入要严格，且要能查、能改、能删。面试里我会补：**长期记忆写入要有门槛**，否则错误会被永久放大。

### 4. 摘要不要丢信息怎么办？

摘要要面向任务，不是写散文。精确字段结构化存；摘要只承担叙事和决策背景。对客服场景，订单号、金额、是否已退款这类绝不只靠摘要。

### 5. 如何避免记忆污染？

写入前打分或规则过滤；高风险记忆可要求用户确认；提供「忘记/更正」入口；定期清理低置信条目。Agent 自动总结的对话不要默认全部进长期记忆。

### 6. 多轮对话里检索和记忆怎么配合？

检索 Query 往往要先**改写**（补全指代），用的是对话状态；长期记忆若有关键实体也可拼进改写。生成阶段才需要完整最近几轮。我会避免把 50 轮原话同时送给 Embedding 检索。

### 7. 上下文和 RAG 有什么区别？

RAG 解决「知识库里的事实从哪来」；上下文工程解决「这一次调用窗口里放什么」。RAG 结果只是上下文的一块拼图。

### 8. 如何设计 token 预算？

我会先保证 system 和当前 user 问题，再给 RAG/工具结果，然后历史，最后才挤长期记忆。输出要留足 max_tokens，否则回答半截被截断。上线后看实际 token 分布再调。

### 9. 用户说「忘掉我的手机号」怎么处理？

长期记忆里按 key 删除或脱敏；缓存和日志一并清理；若已进向量库要触发重新索引或过滤。这题考的是**记忆不是只写不删**。

### 10. 你会如何排查「模型好像忘了上文」？

看最终 prompt 里是否包含关键轮次、摘要是否抹掉了实体、是否被 RAG 长文挤掉、是否用了错误的 session id。用 request 日志还原上下文比盲调 temperature 有用。
