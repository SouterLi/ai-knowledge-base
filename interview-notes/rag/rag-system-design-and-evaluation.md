# RAG 系统设计与评估

## 主题选择记录

- **主题**：RAG（Retrieval-Augmented Generation）系统设计与评估
- **分类**：AI 应用开发 / RAG
- **仓库去重**：与 Agent、Prompt、上下文工程、流式架构、安全、成本、评估等主题互补，不重复
- **适用岗位**：AI 应用开发、LLM 应用、RAG/Agent 工程师

## 核心概念

RAG 是「先检索、再生成」：从外部知识库找出与问题相关的片段，拼进 Prompt，让大模型在**有依据的上下文**里作答。

它主要解决三件事：**知识过时**（参数里没企业最新文档）、**幻觉**（需要可引用证据约束）、**私有知识无法全量微调**（用索引低成本接入）。

面试里 RAG 很少只考「向量库 API」，而是考整条链路：切分、Embedding、混合检索、重排、上下文预算、引用溯源、评估与权限。要把**检索质量**和**生成质量**分开看——答错可能是没搜到，也可能是搜到了但模型没遵守上下文。

## 核心知识点

### 1. 标准链路（离线索引 + 在线问答）

**离线**：接入 → 清洗 → 切分 → 元数据 → Embedding → 建索引 → 增量更新。  
**在线**：鉴权 → Query 改写 → **权限过滤** → 召回 → Rerank → 拼上下文 → 生成 → 引用 → 日志与评估。

```python
# 简化在线链路：权限必须在检索前
def rag_answer(user, question):
    q = rewrite_with_history(question, user.recent_turns)
    chunks = hybrid_search(
        q,
        filters={"tenant_id": user.tenant_id, "acl": user.roles},
        top_k=20,
    )
    ranked = rerank(q, chunks)[:5]
    context = pack_context(ranked, max_tokens=3000)
    return llm.generate(system=GROUNDED_PROMPT, context=context, question=q)
```

### 2. 文档切分（高频考点）

| 策略 | 要点 | 面试怎么说 |
|------|------|------------|
| 固定长度 | 实现简单，易断语义 | 仅作 baseline |
| 按标题/段落 | 贴合结构 | 制度、手册优先 |
| 递归切分 | 先结构后 token | LangChain 等常用 |
| 父子 chunk | 小 chunk 召回、父文档补全 | 兼顾精度与上下文 |

**chunk size**：过小丢上下文，过大检索变钝、费 token。**overlap**：适量防断裂，过多重复索引。  
**metadata**（来源、章节、页码、权限、更新时间）影响过滤、溯源和新鲜度加权。

### 3. Embedding 与索引

- 查询与文档**同一 Embedding 模型**；关注中英文、领域词、维度与成本。
- **向量检索**：语义相似，对错误码、型号、API 名可能弱。
- **BM25/关键词**：精确匹配强。
- **混合检索**：企业场景主流，召回后合并去重再 Rerank。

### 4. Query 改写与多轮

用户说「它怎么配置？」需结合历史改写成完整问句。常用：指代补全、多查询扩展、HyDE（先生成假想答案再检索——适合短问/措辞差异大，多一次 LLM 调用且有方向跑偏风险）。

### 5. Reranker

向量 top_k 追求召回，相似度≠可回答性。Cross-Encoder Rerank 精度高、延迟高；可结合标题匹配、时间、点击等业务信号。

### 6. 上下文组装与防幻觉

- 控制 top_k 与 token 预算；同文档去重。
- Prompt 明确要求：**仅基于上下文**；无法判断则拒答。
- 输出**引用**（片段 ID、标题、页码），便于核验。

```text
你只能根据【参考资料】回答。资料不足时明确说「知识库暂无足够信息」，禁止编造。
回答末尾列出引用：[1] 文档名 - 章节
```

### 7. 评估指标（必背）

**检索**：Recall@K、Precision@K、MRR、NDCG。  
**生成**：Faithfulness（是否忠于上下文）、Answer Relevance、Citation Accuracy。  
**工程**：延迟、单次成本、无答案率、幻觉率、采纳率/转人工率。

### 8. 权限与增量更新

- 权限：**检索阶段**按 metadata 过滤，不能先召回再让模型「别说」。
- 增量：新增/改文档删旧 chunk 再写新 chunk；维护 doc_id、chunk_id、version。

### 9. 常见问题定位表

| 现象 | 优先怀疑 | 手段 |
|------|----------|------|
| 答非所问 | 召回偏了 | 混合检索、改写、Rerank |
| 找不到 | 切分/索引缺数据 | 调 chunk、补库、提 recall |
| 幻觉 | 上下文不足或约束弱 | 拒答策略、引用、faithfulness 评测 |
| 延迟高 | 链路长 | 并行召回、减候选、缓存检索结果 |

## 高频面试问题与标准答案

### 1. 什么是 RAG？解决什么问题？

RAG 就是检索增强生成：先从知识库捞出相关片段，再让模型带着这些片段回答。我一般会强调三点——**更新企业知识不用重训模型**、**用引用约束幻觉**、**私有数据不必进模型权重**。它适合事实性强、会变、要溯源的场景；改语气、改输出格式更适合微调，两者常一起用。

### 2. RAG 和微调怎么选？

我的判断标准是：**事实会不会频繁变、要不要引用来源**。制度、工单、产品手册这类用 RAG；固定 JSON 抽取格式、客服话术风格这类用微调。事实知识硬塞进微调，更新成本高，还容易和旧知识冲突。

### 3. 怎么设计企业知识库 RAG？

我会分两条线讲。离线把文档治理好：清洗、按结构切分、打权限元数据、建混合索引。在线先鉴权和 Query 改写，检索带租户/角色过滤，Rerank 后按 token 预算拼上下文，生成要带引用。工程上还会提评估集、增量更新、监控 recall 和幻觉率——否则上线后很难证明优化有效。

### 4. chunk size 怎么定？

没有万能数字，我会用评估集扫几档：看 Recall@K 和最终答案正确率。结构化文档优先按标题切；需要跨段信息时加 overlap 或父子 chunk。面试里我会补一句：**别只调 chunk 不看检索指标**。

### 5. 为什么常用混合检索？

因为真实问题里既有「忘记密码怎么办」这种语义改写，也有「错误码 E1024」「API `/v1/orders`」这种必须字面命中的。单靠向量容易漏专有名词，单靠 BM25 又对口语问法不友好，所以生产里多数是向量 + 关键词，融合后再 Rerank。

### 6. Reranker 干什么？为什么不直接取向量 top_k？

向量检索为了速度会用 ANN，Embedding 相似不等于「能回答问题」。Rerank 用 query-document 精细打分，把真正能支撑答案的段落排到前面。代价是延迟和算力，所以常先多召回、再 Rerank 少量候选。

### 7. 怎么降低 RAG 幻觉？

我会从系统角度讲：先把**正确片段召回来**；Prompt 写死「仅依据上下文、不足则拒答」；答案带引用；对高风险场景做 faithfulness 抽检。只改模型不换检索，幻觉往往降不下来。

### 8. 知识库没有答案时怎么办？

要明确拒答，而不是硬编。实现上我会组合：检索分数/Rerank 分数阈值、上下文是否覆盖关键实体，必要时 LLM 自检但**不能单靠自检**。线上把高频无答案问题回流补文档。

### 9. 怎么评估 RAG？

分层评：检索看 Recall@K、MRR；生成看正确性、忠实度、引用是否对得上；业务看解决率、满意度、转人工；工程看延迟和成本。每次改切分、Embedding、top_k、Prompt 都在同一套标注集上回归。

### 10. RAG 权限怎么做？

chunk 写入时带 tenant、部门、角色等 metadata；查询时按当前用户身份过滤。**过滤发生在召回前**。先召回敏感内容再让模型保密，上下文已经泄露了。

### 11. 多轮对话怎么处理？

先把当前轮结合历史**改写成独立问题**再检索；生成阶段可保留最近几轮。我会区分「给检索用的历史」和「给生成用的历史」，避免整段聊天记录塞进索引。

### 12. 答案质量差怎么排查？

按链路排：数据是否全、切分是否断语义、top_k 里有没有金标准片段、Rerank 是否把对的挤到前面、上下文是否被截断、Prompt 是否要求 grounded。先判断是检索问题还是生成问题，别一上来只调 temperature。

### 13. 怎么优化延迟和成本？

缓存高频 query 的检索结果或最终答案；多路召回并行；Rerank 前粗筛；压缩上下文；简单问用小模型做改写。优化后用 P95 延迟和单次 token 验证，别牺牲权限和引用准确性。
