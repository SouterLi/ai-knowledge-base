## 一、核心概念

AI Agent 不是“让大模型自由聊天”，而是让模型在受控流程中理解目标、选择工具、读取结果并继续决策。面试常考：工具边界、调用可靠性、失败恢复和权限控制。

### 1. Agent 的基本组成

- LLM：负责理解任务、生成计划和选择动作。
- 工具：搜索、数据库查询、发邮件、业务 API 等外部能力。
- 工具协议：描述名称、参数、返回值和错误格式。
- 控制循环：选择工具、执行、观察结果、继续或结束。

### 2. Function Calling 与 Tool Calling

Function calling 强调模型输出结构化函数参数，由程序执行函数；tool calling 范围更广，工具可以是 HTTP API、数据库、浏览器、代码解释器或工作流。

关键点：模型只负责“决定调用什么以及传什么参数”，真实执行由后端控制。不能让模型直接拼接 SQL、执行 Shell 或绕过权限。

## 二、关键设计步骤

1. 明确任务边界：判断 Agent 是只读问答、自动执行，还是需要人工确认。
2. 设计工具集合：工具数量不要过多，名称要清晰，避免能力重叠。
3. 定义参数 Schema：使用 JSON Schema 或类型系统约束必填字段、枚举值、数值范围。
4. 参数校验：执行前再次校验模型输出，不信任模型参数。
5. 执行工具：加入超时、重试、幂等键、审计日志和权限检查。
6. 处理观察结果：把工具返回压缩成结构化内容，避免塞入过长原始数据。
7. 设置停止条件：限制最大轮数、最大成本、失败次数和高风险动作。

示例工具定义：

```python
tool = {
    "name": "search_orders",
    # 限制查询范围，避免模型发起无限制检索
    "days": {"type": "integer", "minimum": 1, "maximum": 90}
}
```

## 三、常见问题与面试追问

### 1. 为什么不能把所有 API 都暴露给 Agent？

工具越多，模型越容易选错，也更难控制权限和成本。转账、删除数据、发邮件等高风险 API，应增加人工确认、权限校验和审计。

### 2. 如何提升工具调用准确率？

使用清晰命名、短描述、强 Schema、少量高质量示例和明确系统提示。复杂任务可先做意图分类，再只开放相关工具子集。

### 3. 工具调用失败怎么办？

区分参数错误、权限错误、网络错误、业务错误。参数错误可让模型修正；网络错误可重试；权限错误应直接拒绝。

### 4. Agent 和普通工作流有什么区别？

工作流适合步骤固定、规则明确的任务；Agent 适合路径不确定、需要动态选择工具的任务。生产系统常采用“工作流骨架 + 局部 Agent 决策”。

### 5. 如何防止 Prompt Injection？

外部内容只能作为数据，不应覆盖系统指令。网页、邮件、文档中的“忽略之前指令”等内容，应视为不可信文本。

## 四、实践建议

- 先从只读工具做起，再逐步开放写操作。
- 高风险动作必须有人类确认或强业务规则兜底。
- 给 Agent 设预算：轮数、token、API 次数和总耗时。
- 用回放日志复盘失败案例，重点看是否选错工具、参数错误或缺少停止条件。

## 五、一分钟总结

Agent 工具调用的核心不是让模型拥有更多能力，而是把外部能力安全、结构化、可审计地交给模型使用。面试回答时要围绕工具 Schema、控制循环、参数校验、权限边界、失败恢复和人工确认展开，体现你理解 Agent 是工程系统，而不是单次 Prompt。
