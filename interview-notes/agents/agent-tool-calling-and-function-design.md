# AI Agent 工具调用与函数调用设计

## 主题选择记录

- **主题**：AI Agent 工具调用与 Function/Tool Calling 设计
- **分类**：AI 应用开发 / Agents
- **仓库去重**：`interview-guides` 中 Agent 主题偏编排与可靠性；本文件聚焦**工具协议与调用链**
- **适用岗位**：AI 应用开发、Agent 工程师

## 核心概念

Agent 让模型在**受控循环**里：理解目标 → 选工具 → 后端执行 → 读结果 → 继续或结束。模型只产出「调用意图和参数」；**真实执行权在后端**——不能信任模型拼 SQL、跑 Shell 或绕过权限。

Function Calling 强调结构化函数参数；Tool Calling 范围更广（HTTP、DB、浏览器、代码沙箱）。面试核心：**工具边界、参数校验、失败恢复、权限与预算**。

## 核心知识点

### 1. Agent 最小闭环

```
用户目标 → LLM(可选工具列表) → tool_call → 校验/鉴权 → 执行 → observation → LLM → … → 最终回复
```

### 2. 工具定义规范（高频）

- **名称**：动词+对象，如 `search_orders`，避免重叠。
- **描述**：何时用、何时禁用。
- **参数 Schema**：JSON Schema，枚举、范围、必填。
- **权限标签**：readonly / write / high_risk。
- **返回结构**：JSON 字段，便于下一步推理；过长结果要摘要。

```python
SEARCH_ORDERS = {
    "type": "function",
    "function": {
        "name": "search_orders",
        "description": "按用户 ID 查询近期订单，只读。",
        "parameters": {
            "type": "object",
            "properties": {
                "user_id": {"type": "string"},
                "days": {"type": "integer", "minimum": 1, "maximum": 90},
            },
            "required": ["user_id"],
        },
    },
}
```

### 3. 执行前校验（必答）

模型输出 → JSON 解析 → Schema 校验 → **业务规则**（用户是否拥有该 order）→ 预算检查 → 执行。高风险写操作：**人工确认或两阶段 preview/submit**。

### 4. 工具集规模

工具过多 → 选错率上升。做法：意图分类后只开放子集；合并相似工具；写操作单独分组。

### 5. 错误分类与恢复

| 类型 | 处理 |
|------|------|
| 参数错误 | 结构化错误回传，允许模型修正（限次） |
| 权限错误 | 终止，不交给模型「再试一次」绕过 |
| 网络/5xx | 有限重试 + 退避 |
| 业务错误 | 明确 message，引导用户或转人工 |

### 6. 停止条件与防循环

`max_steps`、`max_tool_calls`、token/费用预算；同一工具+相同参数重复调用则中断；无进展 N 轮则退出。

### 7. Agent vs 工作流

步骤固定、高风险 → **工作流骨架 + LLM 填节点**；路径不确定、只读探索 → Agent 循环。生产常见混合。

### 8. Prompt Injection 与工具

网页/邮件/检索内容视为**数据**，不能覆盖 system；外部文本不能定义新工具或提权。

## 高频面试问题与标准答案

### 1. Function Calling 的价值是什么？

把「调用哪个 API、传什么参」从自然语言里拆成结构化 JSON，后端能可靠解析。比正则抠意图稳，也方便统一做校验、审计和限流。

### 2. 为什么不能让模型直接执行工具？

模型会幻觉参数、误解权限，还可能被注入诱导调危险接口。我会强调：**模型建议，代码决定**——注册表、白名单、校验、日志都在应用层。

### 3. 怎么设计一个好的工具 Schema？

单一职责、描述里写清适用/禁用场景、参数尽量枚举化、返回值结构化。退款、删数据这类标 `high_risk`，走确认流，别和查询工具混在一个模糊的大工具里。

### 4. 工具太多怎么办？

先做意图路由，每次只暴露 3～5 个相关工具；合并重复能力；非必要不写操作不进默认列表。我们宁可多一轮分类，也不要一次塞 30 个工具让模型选。

### 5. 工具调用失败怎么处理？

把错误类型结构化返回给模型——比如 `INVALID_PARAM: days must be 1-90`。权限失败不要让它重试猜参数，直接失败并提示用户。网络错误可重试 1～2 次。

### 6. 如何防止无限循环？

硬上限步数 + 检测重复调用 + 要求连续失败时总结并 `finish`。编排层还可以看状态机有没有前进，没前进就转人工。

### 7. Agent 和普通 Chatbot 区别？

Chatbot 通常一轮生成；Agent 多轮调外部系统，有状态、有副作用。所以 Agent 面试一定会追问权限、幂等、审计，而不只是 Prompt 写得好不好。

### 8. 如何防 Prompt Injection 导致乱调工具？

system 与不可信内容隔离；工具层权限不依赖模型；写操作二次确认；对工具参数做白名单校验（例如 order_id 必须属于当前用户）。

### 9. 工具返回很长怎么办？

在 observation 里做摘要或只保留关键字段，完整结果存 session/对象存储，给模型一个 `result_id` 如需再取。否则几步之后上下文就爆掉。

### 10. 你会如何落地第一个 Agent？

从只读工具开始：查订单、查知识库。跑通校验、日志、步数上限后，再开放写操作，且写操作带确认和幂等键。评估看工具选择准确率、参数准确率、任务成功率。
