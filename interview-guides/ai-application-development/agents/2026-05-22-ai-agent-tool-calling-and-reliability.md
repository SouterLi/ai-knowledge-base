# AI 应用开发面试主题：AI Agent 应用开发：工具调用、规划执行与可靠性治理

## 本次主题回顾与去重

- 已有历史主题：RAG 应用开发：检索增强生成系统的设计、优化与评估
- 本次新主题：AI Agent 应用开发：工具调用、规划执行与可靠性治理
- 去重说明：RAG 重点解决“如何把外部知识检索后交给模型回答”；AI Agent 重点解决“如何让模型调用工具、拆解任务、执行动作并在真实系统中可控运行”。

## 主题定位

AI Agent 是以大模型为推理核心，通过工具调用、任务规划、状态管理和执行反馈完成复杂目标的 AI 应用形态。面试中常考察候选人是否理解 Agent 与普通 Chatbot 的区别、如何设计工具协议、如何控制幻觉和越权调用、如何评估 Agent 的成功率与线上可靠性。

## 核心知识点

### 1. Agent 与普通 LLM 应用的区别

普通 LLM 应用通常是“一次输入，一次生成”，主要关注提示词、上下文拼接和响应质量。Agent 应用会引入循环式执行流程：理解目标、规划步骤、选择工具、调用外部系统、读取结果、修正计划、输出最终答案。

常见 Agent 能力包括：

- 工具调用：调用搜索、数据库、代码执行器、业务 API、工单系统等外部能力。
- 任务规划：把复杂目标拆成多个可执行步骤。
- 记忆与状态：维护用户偏好、任务进度、中间结果和长期知识。
- 自我校验：根据工具结果或规则检查输出是否满足目标。
- 权限治理：限制敏感工具、危险操作和高风险数据访问。

### 2. 工具调用与 Function Calling

工具调用的本质是把模型输出约束成可解析的结构化调用请求，再由应用层负责真实执行。

一个可靠的工具定义通常包含：

- 工具名称：语义清晰，避免多个工具职责重叠。
- 工具描述：告诉模型什么时候应该调用，什么时候不应该调用。
- 参数 Schema：使用 JSON Schema 或等价结构约束字段类型、枚举值、必填项。
- 执行权限：标记只读、可写、高风险、需要人工确认等级。
- 返回结构：尽量结构化，便于模型继续推理。
- 错误协议：区分参数错误、权限错误、业务错误、系统错误和可重试错误。

工具调用链路通常是：

1. 用户提出目标。
2. 模型根据工具描述生成工具调用请求。
3. 应用层校验参数、权限和调用次数。
4. 应用层执行工具并返回结果。
5. 模型基于工具结果决定继续调用、修正参数或生成最终答案。

### 3. ReAct、Plan-and-Execute 与工作流编排

常见 Agent 模式：

- ReAct：模型交替进行推理和行动，适合探索式任务，但容易出现循环、成本不可控和步骤漂移。
- Plan-and-Execute：先生成整体计划，再逐步执行，适合流程明确的复杂任务，但计划可能需要动态修正。
- Workflow Agent：把关键路径固化为业务工作流，模型只在特定节点做判断或生成，可靠性更高，适合生产系统。
- Multi-Agent：多个角色协作，例如规划者、执行者、审查者，但会增加调试、成本和一致性复杂度。

生产环境通常不建议完全依赖开放式 Agent 循环。更稳妥的方案是把业务主流程固定下来，在低风险、语义判断强的节点引入 LLM。

### 4. 记忆、状态与上下文管理

Agent 的状态可以分为：

- 会话状态：当前对话、当前任务进度、中间工具结果。
- 短期记忆：本轮任务需要复用的临时事实。
- 长期记忆：用户偏好、历史行为、可持久化知识。
- 外部系统状态：数据库、工单、订单、知识库等真实业务数据。

设计时要注意：

- 不要把所有历史对话无差别塞进上下文。
- 长期记忆写入前要有明确规则，避免把错误信息永久保存。
- 敏感信息要脱敏、分级和最小化传递。
- 工具结果应保留原始结构，方便审计和复现。

### 5. 可靠性治理

Agent 的风险比普通问答应用更高，因为它可能执行真实动作。常见治理手段包括：

- 工具白名单：只允许模型调用被注册和授权的工具。
- 参数校验：所有模型生成的参数都必须由应用层校验。
- 权限分层：只读工具、低风险写操作、高风险写操作分级处理。
- 人工确认：涉及付款、删除、发送外部消息、修改生产数据时必须二次确认。
- 调用预算：限制最大步骤数、最大 token、最大工具调用次数和最大耗时。
- 幂等设计：写操作提供幂等键，避免重复执行。
- 可观测性：记录输入、计划、工具调用、结果、错误、延迟和最终输出。
- 回滚机制：高风险业务操作要有补偿或撤销方案。

### 6. 评估指标

Agent 评估不能只看最终文本质量，还要评估执行过程。

常见指标：

- 任务成功率：最终是否完成用户目标。
- 工具选择准确率：是否选择了正确工具。
- 参数准确率：工具参数是否完整、合法、符合用户意图。
- 步骤效率：完成任务所需的工具调用次数和 token 成本。
- 错误恢复率：工具失败或信息不足时能否修正。
- 安全违规率：是否发生越权调用、敏感信息泄漏或危险操作。
- 用户确认命中率：需要确认的操作是否正确触发确认。
- 可复现率：同一任务在固定环境下是否稳定完成。

## 高频面试题及参考答案

### 1. 什么是 AI Agent？它和普通 Chatbot 有什么区别？

AI Agent 是能够围绕目标进行规划、调用工具、读取反馈并迭代执行的 LLM 应用。普通 Chatbot 通常只基于上下文生成回复，而 Agent 会连接外部系统并执行动作。核心区别在于 Agent 具备“行动能力”和“状态驱动的多步执行能力”，因此也更需要权限、安全和可观测性治理。

### 2. Function Calling 的核心价值是什么？

Function Calling 的价值是把模型的自然语言输出约束为结构化工具调用，让应用层可以可靠解析、校验并执行外部操作。它降低了正则解析自然语言的脆弱性，也让工具参数、返回值和错误处理可以工程化管理。

### 3. 工具调用为什么不能让模型直接执行？

模型输出不可信，可能产生错误参数、越权意图或幻觉工具。生产系统中必须由应用层做工具注册、参数校验、权限检查、调用预算和审计记录。模型只负责“建议调用什么”，真实执行权应掌握在受控的业务代码中。

### 4. 如何设计一个好的工具 Schema？

工具 Schema 要职责单一、命名清晰、参数类型明确、枚举值收敛、必填项合理，并在描述中说明适用场景和禁用场景。返回值也应结构化，避免只返回长文本。对高风险工具，还应加入权限等级、确认要求和幂等键。

### 5. ReAct 模式有什么优缺点？

ReAct 通过“思考、行动、观察”的循环，让模型可以根据工具结果逐步推进任务。优点是灵活，适合开放式探索；缺点是容易循环、步骤漂移、成本不可控，并且中间推理不一定稳定。生产中通常要配合最大步数、工具白名单和失败退出策略。

### 6. Plan-and-Execute 适合什么场景？

Plan-and-Execute 适合目标明确但步骤较多的任务，例如生成报告、处理数据、完成多系统查询。它先规划再执行，便于审计和控制。但计划不一定一次正确，所以需要在执行过程中根据工具结果动态修正。

### 7. 什么时候应该选择 Workflow，而不是开放式 Agent？

当业务流程稳定、风险较高或需要强一致性时，应优先选择 Workflow。比如审批、支付、订单修改、客服工单流转等场景，关键路径应由代码控制，LLM 只在意图识别、摘要生成、字段补全等节点发挥作用。开放式 Agent 更适合低风险探索任务。

### 8. 如何避免 Agent 无限循环调用工具？

可以设置最大步骤数、最大工具调用次数、最大耗时和最大 token 预算；对重复调用同一工具同一参数进行去重；要求模型在连续失败后总结原因并退出；在编排层检测状态是否有实质进展，没有进展就中止或转人工。

### 9. Agent 调错工具怎么办？

首先要通过工具描述和 Schema 降低混淆，其次在应用层做参数和业务前置校验。如果调用失败，应把结构化错误返回给模型，让它有机会修正。对于高风险工具，不能只依赖模型自我纠正，必须加入权限和人工确认。

### 10. 如何处理工具调用失败？

工具错误要分类处理：参数错误可以提示模型修正；权限错误应终止或请求授权；临时系统错误可以有限重试；业务错误要返回明确原因；不可恢复错误应给用户透明说明并提供替代方案。错误返回格式应结构化，避免模型误判。

### 11. Agent 的记忆应该怎么设计？

记忆要分层设计。会话状态保存当前任务进度，短期记忆保存本轮任务事实，长期记忆保存经过确认的稳定偏好或知识。长期记忆不能自动写入所有内容，最好有写入规则、用户可见性、删除机制和敏感信息过滤。

### 12. 如何评估 Agent 是否可上线？

需要构建任务集和回放环境，评估任务成功率、工具选择准确率、参数准确率、错误恢复率、安全违规率、平均成本和延迟。同时要做红队测试，覆盖越权请求、提示注入、恶意工具参数、敏感信息访问和重复写操作等场景。

### 13. Prompt Injection 对 Agent 为什么更危险？

普通问答中的 Prompt Injection 主要影响回答内容；Agent 场景下，它可能诱导模型调用工具、泄露数据或执行危险动作。防护方式包括不信任外部内容、隔离工具结果和系统指令、限制工具权限、对敏感操作二次确认，并在应用层执行策略校验。

### 14. 如何设计需要人工确认的工具调用？

可以把工具分为预览和提交两阶段。模型先调用预览工具生成将要执行的操作摘要，用户确认后应用层再调用提交工具。确认内容应包含对象、动作、影响范围、不可逆风险和关键参数，不能只问“是否继续”。

### 15. Multi-Agent 一定比 Single-Agent 好吗？

不一定。Multi-Agent 可以通过角色分工提升复杂任务的组织性，例如规划者、执行者、审查者协作。但它也会增加通信成本、延迟、状态一致性和调试难度。生产中应先验证单 Agent 或 Workflow 是否足够，只有在角色分工确实带来收益时再引入 Multi-Agent。

### 16. Agent 系统的可观测性应该记录什么？

至少记录用户输入、系统提示版本、模型版本、工具候选列表、工具调用参数、工具返回结果、错误类型、执行耗时、token 成本、最终输出和用户反馈。对写操作还要记录操作者、确认记录、幂等键和影响对象，便于审计与回放。

### 17. 如何降低 Agent 的线上成本？

可以减少开放式循环、限制最大步骤数、使用小模型处理低复杂度节点、缓存工具结果、压缩上下文、只把必要字段传给模型、把稳定流程代码化，并对高频任务设计专用工具或工作流。

### 18. 如果让你设计一个“自动处理客户退款咨询”的 Agent，你会怎么做？

我会采用 Workflow Agent。流程包括：识别用户意图、查询订单和退款规则、判断是否满足条件、生成解释或退款方案、对真实退款操作进行人工或用户确认、调用退款 API、记录审计日志。LLM 负责意图识别、解释生成和异常摘要，订单查询、规则判断、退款执行由确定性服务完成。

## 面试表达模板

回答 Agent 设计题时可以按下面结构组织：

1. 明确目标和风险等级。
2. 判断使用开放式 Agent、Plan-and-Execute 还是 Workflow Agent。
3. 定义工具列表、Schema、权限和错误协议。
4. 设计状态管理和上下文策略。
5. 说明安全边界：白名单、参数校验、人工确认、预算限制。
6. 说明评估指标和上线监控。
7. 补充成本优化和失败降级方案。

## 一句话总结

AI Agent 应用开发的核心不是“让模型自由行动”，而是用工程化的工具协议、编排流程、权限控制和评估体系，让模型在可控边界内完成复杂任务。
