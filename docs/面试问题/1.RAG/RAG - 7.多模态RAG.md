## 一个RAG系统，做pdf解析的时候，遇到有文字有图片的情况，如何保证图片可以和它周围的文字信息绑定起来？

有两种常见的方案。

**方案一：布局感知绑定文字和图片**
第一种是使用可以感知布局的解析工具，比如PyMuPDF，它可以识别出页面上的每个元素，这是一个标题，这是一段文字，这是一个图片，每个元素都有自己的位置和边界。

我们首先将文字按照段落进行切分，然后根据空间位置或者基于规则，确定图片和某段文字有关系，为图片打上元数据belongs-to-chunk-id=chunk123，为文本块加上元数据image-id=image123，这样就将文字和图片绑定起来了。

将文字及其元数据向量化存入向量数据库，图片也进行向量化存入向量数据库，检索的时候如果命中了文本块，可以根据image-id调取图片。

**方案二：多模态向量化**
利用多模态模型，将文字和图片映射到同一向量空间。不需要特殊对文字和图片进行绑定，由于图片和它附近的文字基本上描述的就是同一事物，所以它们在向量空间的位置本身就会很接近。

检索的时候用户提问的问题，就会将文字和图片一起检索出来。

但是如果图片和它附近的文字从语义上关系不大，这种方式就无法生效了。

### 如果用户输入只有一张图，没有文字，你的检索Query如何构造？

首先，我们不会直接将图片转换成文字去提问，因为这样容易丢失图片中的信息。
我们的处理是用CLIP模型将图片转成向量，直接在库中对图像向量做ANN检索，召回相似的图片。
然后用图像理解模型生成图片的简短描述，再用这个描述做文本向量检索。
最后将这两条路的结果做合并。

### 请描述你们这个多模态RAG系统数据的写入流程

1.用户上传多模态文档；
2.路由解析：针对PDF，使用对应的解析库进行文本解析，使用OCR解析图片中的文字；针对纯图片，直接进入图片处理器；
3.多模态切片，文本使用对应的逻辑进行文本切片，并保留元数据；图片单独切片，使用CLIP生成图像向量，并生成简短的图片描述作为辅助字段，注意pdf中图片和它所在的文本块使用同一个chunk_id，保持关联；
4.向量化与存储，将文本块和图片分别生成向量，存入对应的向量数据库；
5.返回入库成功。

### 请简述一下你们这个多模态RAG系统的查询流程

1.查询解析，识别到输入有图片；
2.检索，提取图片的CLIP向量，去数据库做相似度检索，召回最相似的图像，并生成图片简短描述，同样去数据库做文本检索，合并两个通路返回的文本块；
3.根据文本块的chunk_id拉取图片对应的文本切片；
4.将问题，召回的图片，文本块，一起传递给大模型；
5.大模型输出答案，并附上来源引用。

### 你有一个包含10万份PDF文档的知识库，每份文档里都有表格、图表、照片和文字。你会采用什么样的文档解析与chunking策略，以保证后续跨模态检索的召回率？

**文档解析**
使用Unstructured或者layoutLMv3解析器，对pdf进行解析，并对内容分类，文本，表格，图片；
针对表格，转化为markdown格式，同时存一份自然语言描述；
针对图片，不进行OCR识别，而是直接存储CLIP向量+简短描述。

**Chunking策略**
有段落分割的文本块，按照段落，标题切分文本，保证每个块不超过500字符；
对于长文本，采用固定500字符进行分割，并设置100字符的重叠；
表格单独分割为一个chunk；
图片与其紧邻的上文图注或者段落合成一个chunk；
当文本与图片相关时，在文本的元数据中加入一个linked_chunk_id，保存对应图片的向量id；
为每个块附上元数据。

### 如果某张图表没有周围文字说明（比如独立的数据图），你如何建立它的文本索引？

首先，我们可以用一个模型给图片或图表生成一个整体描述，提取其中的关键数据或趋势，将这段描述向量化，存入向量库；
对于类似柱状图折线图这类的图标，可以使用专门的解析模型，直接解析成原始数据表，存入向量库；
图片的CLIP向量依然会保存到向量库中，但是文本向量可以存入一个链接字段元数据，指向图片的chunk_id。

### 多模态RAG中，我们通常需要同时索引图像和文本。你会选择**单一向量集合**（存储两种模态）还是**分离集合**？为什么？检索时如何实现跨模态搜索？

我们采用分离集合，原因如下：
1.文本和图像的向量维度不同，混在一起需要统一维度，牺牲各自最优表示，比如我们文本embedding使用的是BGE1536维，图片使用的是512维的CLIP；
2.文本更新可能需要频繁的重切分或更新元数据，而图片不经常变动，分离后可以单独重建文本索引而不影响图像检索；
3.多路召回可以分别设置不同的召回数量，权重，比单一集合更加灵活。

跨模态检索 
图像提取CLIP向量，存入图像向量库；
文本块也使用CLIP编码生成一组跨模态对齐向量，存入跨模态向量库；
检索阶段，如果用户输入一个图片，去图像向量库进行召回，同时去跨模态向量库检索文本；
如果用户输入文本查询图片，就用CLIP编码去图像向量库检索，如果用户输入文本查询文本，就使用BGE编码去文本向量库检索。

### 如何处理**图表（如折线图、流程图）**？你是直接存储原图，还是先调用图理解模型（如DePlot、MatCha）将其转为结构化文本再索引？对比两种方案的优劣。

**直接将原图CLIP向量化存储**
优点是可以保留图片的所有信息，进行图片相似度检索，速度快，适合用户使用图片提问的场景；
缺点是纯文本提问无法命中，无法支持精确数值查询；

**转化为结构化文本再索引**
优点：用户可以使用自然语言进行检索；支持精确数值检索；
缺点：丢失视觉风格信息，提取文本有错误率，需要额外的开销；

我们一般采用混合策略，既存储原图，也会将其转化为文本存储。正好弥补了各自的劣势。

### 用户输入包含文本和一张图片。你会用一个多模态encoder直接编码图文对还是分别检索后合并分数？各有什么适用场景？
- *考察点*：多模态查询的检索策略。  
  - 早期融合（如Flamingo、GIT）：效果好，但每个查询需要实时编码图像，延迟高。适合查询频率低、对精度要求高的场景。  
  - 晚期融合（CLIP分别编码，加权求和）：速度快，可缓存图像特征。适合实时交互场景。  
- *追问*：“如果用户上传的图片非常模糊，你会如何处理？是否先做图像超分或转文本描述？”

### 多模态检索中，有时CLIP特征在特定领域（如医疗影像、工业图纸）对齐效果差。你会采取哪些方法提升检索召回率？

1.模型领域微调
收集少量该领域内的图文对比数据，利用这些数据微调CLIP编码器。
2.替换专用编码器
采用对应领域专用的编码器，或者专用编码器与CLIP融合。
3.Query改写
使用多模态大模型，将用户输入的图片生成详细的文本描述，然后使用纯文本检索。
4.混合检索
同时使用CLIP视觉检索，OCR文本检索，元数据过滤混合检索

### 假设知识库有500万张图片+对应描述，在线检索延迟要求<100ms。你会如何设计索引和检索流水线？

**采用多级级联检索**
1.第一层，全局近似检索，对图片使用CLIP向量，采用IVFPQ索引，召回top2000
2.第二层，如果问题中有文本信息，就对召回的top2000提取文本描述向量，然后与问题进行文本相似度匹配，如果问题没有文本，跳过这一层；
3.第三层，使用一个轻量的跨模态编码器，计算更精确的图文匹配分数，最终取top10

其他优化
缓存，缓存最近的检索结果，相似或相同问题直接返回；
离线对图片进行文本描述向量化，可以加速第二层的速度；
索引分片，并行检索，合并结果；

## 初步检索返回了top-20的图文片段，但其中有些与问题不相关。你会用什么方法进行重排序（Re-ranking）**？**  
- *考察点*：精细排序能力。  
  - 跨模态cross-encoder：如CLIP Score、BLIP-2的ITM头、或者小型BERT（将query和图文拼接）。  
  - 利用LLM做rerank：将每个候选片段与问题拼接，让LLM输出相关性分数（成本高）。  
  - 工程常用方案：双塔召回 + cross-encoder重排。  
- *追问*：“如果重排序模型很大，推理慢，你有什么近似优化？”

**Q10：检索到的片段包含图片、纯文本、图文混合。在送入生成模型之前，你如何将这些异构信息组织成一个**有效的上下文**？**  
- *考察点*：上下文格式化。  
  - 如果生成模型支持多模态（如GPT-4V）：将图片以`<image>`占位符插入文本，并传递实际图像。  
  - 如果生成模型仅文本：将图片转为详细的文本描述（通过BLIP或LLaVA生成caption），然后纯文本拼接。  
  - 注意顺序：相关性高的片段放前面，并标注来源（如`[图1]`）。  

**Q11：你会选择哪种生成模型作为多模态RAG的reader？请从**成本、延迟、私有化**三个维度对比GPT-4V、LLaVA-NeXT、Qwen-VL。**  
- *考察点*：模型选型的工程权衡。  
  - GPT-4V：效果最好，但闭源、昂贵、延迟高，适合POC。  
  - LLaVA-NeXT：开源，可私有部署，效果接近GPT-4V，但需要GPU资源。  
  - Qwen-VL：中文优化，推理速度快，性价比高。  

**Q12：如果生成模型只能接收文本输入，你如何将检索到的图片信息传递给LLM？**  
- *考察点*：绕过多模态限制的工程技巧。  
  - 图像描述生成（Captioning）：BLIP-2、CoCa。  
  - 目标检测 + 标签序列：如“狗, 草坪, 飞盘”。  
  - OCR提取图中文字。  
  - 缺点：会丢失空间关系、颜色等细粒度信息。  
- *追问*：“你会优先选择哪种转换方式？为什么？”

**Q13：你如何确保生成的答案是基于检索到的多模态内容，而不是模型自身的幻觉？请给出具体的**溯源和引用**方案。**  
- *考察点*：可信RAG设计。  
  - Prompt约束：“你必须引用检索到的片段，格式如`[图3]`或`[第2页]`”。  
  - 后处理校验：提取答案中的引用标记，检查对应片段是否确实包含该信息。  
  - 生成时使用**工具调用**（如LLM写出检索到的图片ID）。  
  - 前端展示：高亮答案中引用的原图或原文。  

**Q14：你会如何评估一个多模态RAG系统？请给出至少3个维度的指标，并说明如何自动化计算。**  
- *考察点*：评估体系设计。  
  - **检索质量**：Recall@K（人工标注相关片段）、MRR。  
  - **生成质量**：  
    - 使用GPT-4作为裁判，对答案的正确性、相关性、引用正确性打分。  
    - 多模态指标：如**图文一致性**（答案描述的内容是否真的出现在检索到的图中）。  
  - **端到端任务成功率**：例如VQA准确率（使用标准数据集如MMMU、ScienceQA）。  
  - **系统性能**：p99延迟、QPS、GPU利用率。  

**Q15：用户反馈：上传一张包含复杂表格的图片，问“第三列平均值是多少？”，系统回答完全错误。你会如何系统性debug？**  
- *考察点*：故障排查流程。  
  1. 检查检索结果：是否召回了正确的表格图片？如果没有，原因可能是embedding失效或chunking切断了图片与周围文本的关联。  
  2. 检查上下文构造：图片是否成功转化为模型可理解的格式（如转为Markdown表格）？  
  3. 检查生成模型：直接询问模型“这张表格里第三列的平均值”，看是否理解表格。  
  4. 数据源头：PDF解析时表格结构是否被破坏？  
  - *建议日志打点*：记录每个环节的输入输出。  

**Q16：多模态embedding的维度通常比纯文本高（CLIP 512/768维），这会增加存储和计算成本。你有何优化手段？**  
- *考察点*：成本意识与向量优化。  
  - 降维：PCA到256维（通常精度损失<5%）。  
  - 量化：乘积量化（PQ）将内存压缩到1/8。  
  - 使用更轻量的模型：MobileCLIP、TinyCLIP。  
  - 冷热分离：热数据用全精度，冷数据用量化+压缩。  

**Q17：你的多模态RAG需要支持**实时增量更新**（每分钟新增100张图片和对应文本）。如何设计索引更新策略？**  
- *考察点*：动态索引能力。  
  - 向量数据库选型：Milvus、Qdrant、Weaviate都支持增量insert/update。  
  - 避免重建：使用**分段索引**（segment-based），新数据写入小段，定期合并大段。  
  - 一致性：保证图片和文本的embedding同时更新，避免检索到孤儿向量。  

**Q18：在云上部署多模态RAG，如何预估并优化月度成本？主要开销来自哪些部分？**  
- *考察点*：成本分析能力。  
  - 主要开销：  
    1. **图片embedding推理**（GPU实例昂贵，可考虑离线批量编码）。  
    2. **LLM生成**（按token计费，尤其是GPT-4V）。  
    3. **向量存储**（内存密集型）。  
  - 优化策略：  
    - 缓存常见图文对的embedding。  
    - 对低频访问的知识库使用更小的embedding模型。  
    - 使用开源LLM（如LLaVA）部署在Spot实例上。   

**Q20：如何防止多模态RAG从知识库中检索到敏感内容（如隐私图片）并生成回答？请给出安全设计。**  
- *考察点*：内容安全工程。  
  - 预处理阶段：所有入库图片经过NSFW检测、人脸模糊化。  
  - 检索阶段：敏感内容标记后，在检索时过滤（如设置deny list）。  
  - 生成阶段：增加安全引导词（如“如果内容涉及隐私，请回答无法提供”），并使用输出审核模型。  
## 作为面试官的额外建议

- **准备一个完整的项目经验**：比如“电商商品图文问答系统”或“企业内部故障手册多模态RAG”。重点说明：数据量、选型原因、遇到的坑（如图文不对齐、召回率低）、优化效果（召回率从60%提升到85%）。  
- **动手实操**：面试官很可能追问“你用的什么向量数据库？索引参数怎么调的？”如果只是纸上谈兵，很容易露馅。    
- **关注新兴模型**：比如ColPali（视觉检索模型）、MM-Embed（多模态embedding统一模型），了解它们和传统CLIP+LLaVA方案的差异。
