## 如何使用LangGraph设计一个多Agent系统？

使用监督者模式，有一个主管Agent负责接收用户的问题，并委派给合适的子Agent去执行。
子Agent执行完成后，返回给主管Agent，判断是否已经完成用户要求，如果没有完成，判断分派给另一个Agent，让这个子Agent继续执行，直到主管认为可以结束，将最终结果返回给用户。

监督者可以设置一个多层过滤的模式，首先设计若干个简单规则，如果用户请求命中，就直接分派给目标Agent；没有命中的问题，先进入一个轻量的意图分类器，判断应该分给哪个子Agent；如果还是无法判断的复杂问题，就使用大模型进行判断。
## 你们是怎么做多Agent路由的？  

我们采取了多层过滤的方式进行路由。
首先针对那些分类明显，比较容易判断的问题，我们**设计了若干个规则**，对元数据，特定关键词进行匹配；
针对规则无法快速匹配的问题，我们采用**基于向量相似度的轻量级意图分类器**进行筛选。具体做法是为每个Agent构建一组代表性的问题，将这些问题转换成向量，存储在向量库中，将用户问题转成向量，检索相似度最高的示例问题，决定调用哪个Agent。
针对更复杂的问题，就要使用**LLM+Function Calling**的能力，将Agent作为Function，LLM进行判断应该调用哪个Function。
针对**跨领域的问题**，单独一个Agent可能无法解决，我们采用监督者模式，由一个主管Agent判单是否需要多个子agent共同完成，并协调多个agent。
如果置信度较低，默认路由到通用Agent，没有特定功能，主要负责日常对话，引导用户明确问题。 

## 什么情况下你会考虑使用多Agent系统，而不是一个超级Agent？

1.有多个领域的问题，不同领域之间差异较大。
2.任务需要多个角色分工处理，比如一个负责规划，一个负责执行，一个负责校验结果。
3.需要并行处理，单个agent是串行的，如果你需要同时执行多个子任务，多agent更适合。
4.安全与权限隔离。对于数据，权限比较敏感的场景，单独设置agent来处理更加安全。

什么时候适合使用单个agent？
任务复杂度可控，步骤5步以内，不需要严格分工，使用单个agent更简单。多个agent增加了通信开销，一致性问题。

## 在多Agent协作中，如何解决Agent之间的“对话死锁”或“重复劳动”问题？

对话死锁
1.引入协调器agent，所有请求都通过这个agent进行路由，避免循环依赖。
2.超时与熔断，设置一个超时时间，超时后标记为失败，触发补偿逻辑。
3.有向无环图，明确agent之间的调用关系，按照顺序调用，设定不要出现相互引用的逻辑。

重复劳动 - 多个agent做同样的事情
任务去重， 每个任务生成唯一ID，新任务到达后先检查是由有相同ID任务在执行中，如果有就直接返回结果，不重复调用。
结果缓存，同一个任务缓存结果，后续类似的任务都直接从缓存读取结果。

## 请描述一下 AutoGen、LangGraph 这类框架的工作机制？它们解决了单Agent无法解决的什么问题？

AutoGen是对话式的多agent，多个agent都有自己的角色，它们会相互对话，最终完成任务。
LangGraph是基于有向图状态机。把任务拆分成多个节点和边，

解决了单agent的哪些问题？
1.长流程的状态管理。单agent在多步任务中容易遗忘中间状态，导致错误累积。LangGraph通过状态图持久化每个节点的输出，支持暂停，恢复，分支，循环。
2.多角色的协同与分工。单agent支持多角色，但是prompt会膨胀，且容易产生角色冲突，AutoGen可以定义多个角色，通过对话进行协同分工，质量明显提升。
3.容错与恢复。单agent的流程，中间有一步挂掉了，整个任务就失败了。Langgraph通过状态持久化，允许从失败节点重试或者领外走备用路线，容错性更高。
4.并行。多agent可以并行执行多个任务。

## 主子模式的多Agent架构下，如果一个子Agent出现幻觉怎么办？

首先我们可以通过多种方式降低Agent出现幻觉的概率。

如果真的出现幻觉，我们可以用这几种方式来检测和处理。

1.可以用两个Agent同时执行同一个任务，然后对比结果，如果相似度较高说明没有幻觉，如果相似度较低，就使用主Agent来裁判只保留真实答案；但这种方法意味着要调用两个Agent，成本较高，只在关键场景使用；

2.对于普通场景，我们使用规则+工具验证，如果子Agent的结果没有通过验证，就将具体错误反馈给Agent，让Agent再重新生成一次；

3.置信度阈值，让Agent对自己的结果打一个分数，如果分数较低，说明低分原因，将原因告诉Agent重新生成；
