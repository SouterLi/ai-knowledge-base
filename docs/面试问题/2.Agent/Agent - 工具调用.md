## Agent 如何处理大量工具的情况？

1.渐进式披露，先只将工具描述加载到大模型中，大模型先根据用户问题判断需要调用的工具，我们拿到工具名，由于缺乏参数，这里可能会返回几个相似的工具，查找到对应的完整工具schema，发给大模型，再进行后续流程；

2.将工具定义schema全部存入向量数据库，拿到用户问题，先做一次召回，将相关的K个工具放入prompt；

3.分层路由，将工具按照功能和场景进行分组，拿到用户问题，先使用规则或者小模型进行意图分析，只将匹配到的一组工具加载到prompt中。

## 请设计一个工具描述的最佳实践

首先工具本身功能的描述要清晰，没有歧义，与已有的相似工具要有明显的场景区分；

只将核心参数标记为required，可选参数设置默认值；

参数有明确可选值时使用枚举，比string更稳定；

固定格式的参数使用正则进行限制，减少无效请求。

## 工具调用的容错机制如何设计？

我设计了三层容错机制：调用层+执行层+系统层

**第一个是工具的调用层**。
大模型理解用户意图后，需要调用工具，它会给我们返回工具名称和参数，但是大模型返回的信息不一定是可靠的，我们需要对大模型返回的信息进行校验。
**工具名列表白名单校验**，防止大模型返回不存在的工具名，调用后才返回404；
**参数补全与默认值**，对缺失的非必填字段自动填充默认值；
**数据类型转换**，比如大模型返回字符串123，我们转换成工具需要的整数类型；
**Schema校验**，设计一个通用的schema校验工具，校验大模型返回的工具名和参数是否完全与工具描述相匹配，校验失败，引导Agent进行修正；

**第二个是工具的执行层**，就是工具内部的容错处理。
**幂等性设计**，保证工具重复调用不会有问题；
**超时控制**，超过时间直接返回失败；
**重试策略**，对于可重试异常进行指数退避重试，并保证幂等性；
**异常捕获**，对于所有的异常进行捕获，返回结构化错误和友好提示，方便Agent理解；
降级，对于非核心工具，工具出现问题，允许进行降级，直接返回降级结果；

第三个是系统层面。
负责整个系统的工具调用的熔断，限流，降级，状态恢复，兜底策略。

## 在代码层面，你是如何实现让大模型调用外部工具的？比如 Function Calling的具体流程是怎样的？

首先定义工具，使用@tool注解，在方法描述中清晰定义工具的描述。
初始化大模型的时候将工具注册进去。
接受到用户的任务，大模型会分析问题，找到最符合的工具，返回工具的方法名和参数。
调用该工具，返回结果。
再次调用大模型，将问题和工具结果都传进去，大模型整合信息，组装出一个易懂的回答给用户。

## Function Calling的安全性问题，如何防止恶意操作或越权？

1.**问题预处理**。配置恶意关键词，匹配拒绝。

2.**Function权限控制**。每个请求进来的时候，都会带上用户的相关信息，调用api之前，会先对权限进行校验，如果没有权限，就直接返回。

3.**敏感操作特殊处理**。针对全量操作，或者密码相关的敏感操作，即使用户有权限，我们也会在操作逻辑上做特殊处理，比如生成一条审批链，或者只是打开修改密码的页面。

4.**日志监控**。对用户的所有操作，我们都会有相应的日志记录，保证所有操作事后都可以追溯。

## 如何保证工具调用的准确性？

**1.工具描述的清晰化**。工具的描述包含功能边界，适用场景，注意事项，与其他工具有明显区分。
**2.参数的明确约束**。比如枚举值的参数在参数描述中给出所有可选的值，参数校验不通过直接返回；
**3.few-shot示例**。在system Prompt中嵌入几个典型例子和负面例子
**4.思维链与自我校验**。在Prompt中要求模型先思考再行动；还引入了质疑步骤，在模型决定调用某个工具后，我们会让它反问自己一次，这个决定合理吗，有没有更适合的工具？
**5.多轮澄清和追问机制**。我们会让模型给自己的结果打分，如果低于80分，就进入澄清流程，大模型会反问用户，澄清不明确的信息。
**6.持续优化，基于反馈的闭环**。我们建立了错误案例的收集机制，定期复盘这些案例，分析错误原因，并针对调整，调整后，做线上的小规模的A/B测试，确认调整后有提升，再上线。
**7.兜底方案**。人工审核，针对高价值，高风险的场景，我们设置了人工审核流程，Agent生成的调用请求会生成相应的审批链，人工审批后再执行。

## 你们是如何评估调用工具的质量？

#### 评估维度
我们分为三个维度来衡量工具调用的质量
**准确性**。工具选择的正确率，生成参数的正确率。
**健壮性**。异常恢复率，无效调用率。
**效率**。完成一个任务需要调用几次工具。是否会出现重复调用同一个工具的情况。

#### 评估方法
**离线测试集**，我们维护了200条左右真实用户请求，人工标注了期望的工具和参数，生成准确率报告。
**线上监控**。记录每次调用的结果，统计失败率，平均耗时，重试次数。
**用户反馈**。记录用户点赞点踩，针对badcase进行复盘。

## 简历中提到了一个工具 - 脱敏，你们具体是怎么做的？

在我们公司对于文档脱敏有一个标准的流程。我们有一个规则库，针对某种字段进行固定格式的脱敏，比如身份证保留前后4位，手机号保留前后3位之类的。
当大模型判断用户要调用这个工具时，会将文档中需要脱敏的元数据组装成一个list，和文档一起传入方法，脱敏方法就去文档中找到这些数据，进行相应的处理后替换，最终返回脱敏后的文档。
