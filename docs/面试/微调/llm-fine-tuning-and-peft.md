# AI 应用开发面试主题：LLM 微调与 PEFT 落地

## 主题选择记录

- 本次主题：LLM 微调与 PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）落地
- 所属分类：AI 应用开发 / 模型适配与微调
- 已回顾历史主题：RAG、Agent、Prompt 工程、评估观测、安全防护、上下文工程、流式异步、多模态、成本缓存限流、模型网关、工作流编排与 Human-in-the-loop
- 不重复原因：已有主题主要关注应用编排、检索、治理和生产运行；本主题聚焦“什么时候需要训练模型、如何准备数据、如何用 LoRA/QLoRA 做低成本适配、如何评估和上线微调模型”
- 适用岗位：AI 应用开发工程师、LLM 应用工程师、模型应用工程师、AI 平台工程师

## 一、为什么这是高频考点

很多候选人会把大模型应用理解成“Prompt + RAG + API 调用”。真实业务中，如果模型需要稳定学习某类输出格式、行业术语、业务风格、工具调用习惯或特定任务边界，仅靠 Prompt 往往会遇到上下文成本高、输出不稳定、延迟变长和维护困难的问题。

面试官问微调，通常不是只问“LoRA 怎么配参数”，而是考察你是否能判断：

- 什么时候该用 Prompt、RAG、规则、微调或继续预训练。
- 如何把业务样本整理成可训练、可评估、可追溯的数据集。
- 如何用 PEFT 降低训练成本和上线风险。
- 如何验证微调模型真的提升了业务指标，而不是只记住训练集。
- 如何把微调模型纳入模型网关、评估、灰度和回滚体系。

一句话总结：微调不是“让模型知道更多知识”，而是让模型在特定任务上更稳定地按期望行为工作。

## 二、核心概念

### 1. 微调、继续预训练与 RAG 的区别

| 方案 | 主要解决什么 | 典型数据 | 适合场景 | 不适合场景 |
| --- | --- | --- | --- | --- |
| Prompt 工程 | 指令表达、输出约束、少量示例 | Prompt、few-shot 示例 | 需求变化快、样本少、任务简单 | 长期高频任务、格式极其稳定 |
| RAG | 外部知识注入、引用溯源 | 文档、知识库、搜索结果 | 知识频繁变化、需要可追溯答案 | 学习稳定表达风格或复杂决策边界 |
| SFT | 学习任务格式、风格和行为模式 | 指令-回答样本 | 结构化抽取、客服话术、工具调用格式 | 需要实时知识、样本质量低 |
| PEFT | 低成本做任务适配 | 少量高质量训练样本 | 中小团队、垂直任务、快速试验 | 需要大幅改变模型基础能力 |
| 继续预训练 | 注入领域语言分布和术语 | 大规模无标注语料 | 医疗、法律、代码、金融等领域底座适配 | 小样本任务对齐、业务格式控制 |

面试中要避免说“模型不知道知识就微调”。如果知识频繁更新且需要引用，优先考虑 RAG；如果要改变模型的稳定行为和输出分布，才考虑微调。

### 2. SFT

SFT（Supervised Fine-Tuning，监督微调）使用成对的输入输出样本训练模型，让模型学习在特定指令下生成期望答案。常见样本形式包括：

- 单轮问答：适合分类、抽取、改写、摘要。
- 多轮对话：适合客服、助手、任务型对话。
- 工具调用轨迹：适合让模型稳定生成函数调用参数。
- 拒答样本：适合安全边界和合规场景。

关键点不是样本数量越多越好，而是样本要覆盖真实分布、边界情况和失败模式。

### 3. PEFT

PEFT 是一类只训练少量参数的微调方法。它通常冻结大模型主体参数，只训练新增的 adapter、低秩矩阵或少量可训练参数。

常见价值：

- 训练成本低：显存、时间和算力压力小。
- 版本管理轻：每个业务可以保存一份小 adapter。
- 上线灵活：同一个 base model 可以挂载不同任务 adapter。
- 回滚简单：回退 adapter 通常比替换完整模型更快。

### 4. LoRA

LoRA（Low-Rank Adaptation）的核心思想是：不直接更新原始权重矩阵，而是在部分线性层旁边增加两个低秩矩阵，让模型学习一个低秩增量。

简化理解：

```text
原始输出：y = W x
LoRA 输出：y = W x + B A x

W：冻结的原始权重
A、B：可训练的低秩矩阵
```

面试中要说清楚：LoRA 的 rank 越高，表达能力越强，但训练参数、显存和过拟合风险也会上升。

### 5. QLoRA

QLoRA 通常把 base model 量化到 4-bit，再训练 LoRA adapter，用更低显存完成微调。它适合资源有限但希望微调较大模型的场景。

需要注意：

- 量化主要降低显存占用，不等于没有质量损失。
- 训练稳定性依赖量化配置、学习率、batch size 和数据质量。
- 上线时要评估量化推理的延迟、吞吐和模型质量。

### 6. DPO、RLHF 与偏好对齐

SFT 让模型学习“标准答案长什么样”，偏好对齐让模型学习“多个答案里哪个更好”。

- RLHF：通过奖励模型和强化学习优化模型行为，工程复杂度高。
- DPO：直接使用偏好数据训练模型偏向更优回答，流程通常比 RLHF 简洁。
- RLAIF：用 AI 生成或辅助标注偏好数据，但要控制评审偏差。

应用开发面试中不一定要求你推导公式，但要知道：如果业务已经有大量“好答案 vs 差答案”的偏好数据，DPO 往往比继续堆 SFT 样本更合适。

## 三、核心知识点

### 1. 什么时候应该微调

适合微调的信号：

1. 输出格式长期稳定，Prompt 约束仍频繁失败。
2. 同类任务调用量大，长 Prompt 成本和延迟明显。
3. 业务语言、话术或决策边界需要长期一致。
4. 有足够多的高质量标注样本和评估集。
5. 线上失败样本可持续回流，能形成训练闭环。

不适合微调的信号：

1. 问题主要来自知识缺失，且知识频繁变化。
2. 样本少、噪声大、标准答案不一致。
3. 需求还在快速变化，训练后很快过期。
4. 只是想绕过安全限制或让模型输出不可靠内容。
5. 没有独立评估集，无法证明提升。

面试回答可以用一句话收束：先用 Prompt/RAG 建立基线，再用评估数据判断微调是否值得投入。

### 2. 数据集设计

微调成败高度依赖数据。一个可落地的数据集通常包括：

- 任务说明：明确输入、输出、边界和禁止行为。
- 正样本：高质量标准答案。
- 难例样本：容易混淆、容易误判、业务边界模糊的输入。
- 负样本或拒答样本：模型不该回答、不该调用工具或应该升级人工的场景。
- 多样化表达：覆盖用户真实问法，而不是只覆盖标注员模板。
- 元数据：来源、标注人、版本、业务线、时间、质量等级。

常见 JSONL 样本：

```json
{"messages":[{"role":"system","content":"你是企业报销审核助手，只输出 JSON。"},{"role":"user","content":"员工申请报销 2300 元打车费，没有发票，备注为客户拜访。"},{"role":"assistant","content":"{\"decision\":\"reject\",\"reason\":\"缺少有效发票\",\"need_human_review\":false}"}],"meta":{"source":"expense_review","label_version":"v1"}}
```

多轮工具调用样本：

```json
{"messages":[{"role":"user","content":"帮我查一下订单 A1001 能不能退款"},{"role":"assistant","tool_calls":[{"name":"get_order","arguments":{"order_id":"A1001"}}]},{"role":"tool","name":"get_order","content":"{\"status\":\"delivered\",\"days_since_delivery\":9,\"category\":\"standard\"}"},{"role":"assistant","content":"订单 A1001 已签收 9 天，标准品在 7 天后不支持自动退款，建议转人工复核。"}]}
```

注意：训练数据中的工具参数、拒答边界和最终回复要一致，否则模型会学到冲突行为。

### 3. 数据清洗与质量控制

常见清洗步骤：

1. 去重：避免同一答案重复出现导致模型过拟合固定表述。
2. 去泄漏：训练集不能包含测试集、线上评测题或敏感数据。
3. 统一格式：字段名、枚举值、JSON 结构必须一致。
4. 审核答案：移除事实错误、幻觉、过时规则和低质量解释。
5. 长度控制：过长样本会增加训练成本，也可能让模型学习无关噪声。
6. 分层抽样：按业务类型、难度、渠道和时间切分训练/验证/测试集。

高质量样本的价值通常大于大量低质量样本。面试中可以强调：“微调不是数据垃圾桶，线上坏 case 要先归因再入库。”

### 4. 训练流程

典型流程：

1. 建立基线：先记录原始模型在评估集上的指标。
2. 准备数据：清洗、去重、脱敏、切分 train/valid/test。
3. 选择 base model：根据质量、成本、许可证、部署方式选择。
4. 选择微调方法：SFT、LoRA、QLoRA、DPO。
5. 配置训练参数：学习率、rank、batch size、epoch、warmup、max length。
6. 训练和验证：关注训练 loss、验证 loss、任务指标和过拟合迹象。
7. 离线评估：对比 base model、Prompt baseline 和微调模型。
8. 灰度上线：小流量、可回滚、持续观测。
9. 失败回流：把新坏 case 标注后进入下一轮数据迭代。

一个简化的 LoRA 配置示例：

```python
from peft import LoraConfig

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj", "v_proj"],
    task_type="CAUSAL_LM",
)

training_args = {
    "learning_rate": 2e-4,
    "num_train_epochs": 3,
    "per_device_train_batch_size": 4,
    "gradient_accumulation_steps": 8,
    "warmup_ratio": 0.03,
    "max_seq_length": 2048,
}
```

这段代码在面试中不用背 API，但要能解释每个关键参数的影响。

### 5. 关键参数怎么解释

| 参数 | 作用 | 面试回答要点 |
| --- | --- | --- |
| learning rate | 控制参数更新幅度 | 太大容易发散或遗忘，太小收敛慢 |
| epoch | 数据被训练的轮数 | 小数据集 epoch 过多容易过拟合 |
| batch size | 每步训练样本数 | 影响稳定性和显存，可用梯度累积折中 |
| max sequence length | 最大训练上下文长度 | 要覆盖真实输入长度，过大浪费显存 |
| LoRA rank | 低秩矩阵维度 | rank 高表达强但更易过拟合 |
| target modules | 插入 LoRA 的模块 | 常见是 attention 的 q/v/o 或 MLP 层 |
| dropout | 训练正则化 | 小数据集可适当增加，降低过拟合 |

### 6. 微调评估

微调评估不能只看 loss。应用开发中更重要的是任务指标和线上表现。

常见指标：

- 分类：准确率、召回率、F1、混淆矩阵。
- 抽取：字段级准确率、JSON 可解析率、必填字段缺失率。
- 客服：解决率、转人工率、投诉率、违规话术率。
- 工具调用：工具选择准确率、参数准确率、无效调用率、越权调用率。
- 生成质量：人工偏好胜率、事实一致性、简洁度、风格一致性。
- 工程指标：延迟、吞吐、显存、成本、失败率。

推荐评估矩阵：

```text
模型版本       任务指标   JSON 可解析率   安全违规率   P95 延迟   单次成本
base+prompt    82.1%     91.4%          0.8%         1.2s      1.00x
lora-v1        88.7%     98.9%          0.6%         0.9s      0.74x
lora-v2        89.2%     98.5%          1.4%         0.9s      0.74x
```

如果 `lora-v2` 任务指标略高但安全违规率上升，就不一定应该上线。面试中要体现多目标权衡。

### 7. 过拟合、灾难性遗忘与数据泄漏

常见问题：

- 过拟合：训练集表现好，测试集下降，输出变得模板化。
- 灾难性遗忘：模型在目标任务上变好，但通用能力和安全行为下降。
- 数据泄漏：测试题进入训练集，离线指标虚高。
- 标注偏差：模型学习了某个标注员的偏好，而不是业务标准。
- 格式污染：训练样本中 JSON、工具调用和自然语言混杂不一致。

应对方式：

1. 使用独立测试集和时间切分测试集。
2. 保留通用能力和安全评估集。
3. 控制 epoch、rank 和学习率。
4. 做数据去重和近重复检测。
5. 对线上真实样本做灰度 A/B。

### 8. 上线与推理部署

微调模型上线要考虑两种形式：

1. 合并权重：把 LoRA adapter 合并进 base model，推理时更简单。
2. 动态挂载 adapter：一个 base model 根据任务加载不同 adapter。

动态挂载适合多业务共享底座，但要处理 adapter 缓存、热切换延迟和版本隔离。合并权重适合单一稳定任务，但存储和版本数量会增加。

推荐上线链路：

```text
业务请求
  -> 模型网关选择 model_alias
  -> 路由到 base model + adapter version
  -> 推理服务生成结果
  -> 结构化校验 / 安全检查
  -> 指标记录 / 样本回流
```

上线前检查：

- 模型卡：记录 base model、adapter、训练数据版本、评估结果。
- 版本别名：业务只依赖稳定别名，不直接依赖训练产物路径。
- 灰度策略：按租户、用户、流量比例逐步放量。
- 回滚策略：可快速回到上一个 adapter 或 base+prompt。
- 监控指标：质量、延迟、成本、安全和异常分布。

### 9. 微调与 RAG 的组合

微调和 RAG 不是互斥关系。常见组合：

- RAG 提供事实材料，微调模型学习如何引用和组织答案。
- 微调模型学习稳定的工具调用格式，工具再执行检索。
- 微调模型学习行业话术，RAG 负责最新政策和产品信息。
- 微调模型做 query rewrite 或检索意图分类，提高 RAG 召回质量。

面试中可以说：RAG 管“知识从哪里来”，微调管“模型如何稳定执行任务”。

## 四、面试高频问题与参考答案

### 1. 什么情况下你会选择微调，而不是继续优化 Prompt？

**参考答案：**

当任务长期稳定、调用量大、输出格式或行为边界需要高度一致，并且已有高质量训练和评估数据时，我会考虑微调。比如 JSON 抽取、固定业务审核、工具调用参数生成、客服话术统一。反过来，如果需求还在变化、样本少，或者问题主要是知识更新，我会优先用 Prompt、RAG 或规则解决。微调前必须先建立 base+prompt 的评估基线，证明微调有收益。

### 2. 微调能不能解决模型不知道公司内部知识的问题？

**参考答案：**

不应该默认用微调解决。内部知识如果频繁变化、需要引用来源或权限控制，优先用 RAG。微调更适合学习表达风格、任务格式和稳定行为。可以组合使用：RAG 检索内部知识，微调让模型更稳定地按公司要求组织答案、引用材料和处理无答案场景。

### 3. LoRA 的核心原理是什么？

**参考答案：**

LoRA 冻结原始模型权重，只在部分线性层旁边训练低秩增量矩阵。原始权重不变，训练参数量显著减少。它的好处是训练成本低、版本轻、回滚方便；代价是表达能力受 rank 和插入模块影响。如果任务需要大幅改变模型能力，单纯 LoRA 可能不够。

### 4. LoRA 的 rank 应该怎么选？

**参考答案：**

rank 决定 adapter 的表达能力。rank 太低可能学不动复杂任务，rank 太高会增加显存、训练时间和过拟合风险。实际会从较小值开始，例如 8 或 16，结合验证集指标、格式稳定性和过拟合情况调参。不能只看训练 loss，要看独立测试集和线上灰度指标。

### 5. QLoRA 和 LoRA 有什么区别？

**参考答案：**

LoRA 是低秩 adapter 微调方法，QLoRA 通常是在量化后的 base model 上训练 LoRA adapter，以降低显存占用。QLoRA 适合资源有限时微调更大模型，但量化会引入额外质量和推理性能评估问题。上线时需要验证量化模型在目标任务、延迟和吞吐上的表现。

### 6. 微调数据集应该如何构建？

**参考答案：**

先定义任务边界和输出规范，再从真实业务样本中抽取覆盖常见场景、边界场景和失败场景的数据。样本要清洗、去重、脱敏，并保留来源和版本。训练集、验证集、测试集要隔离，最好用时间切分保留最近线上样本做测试。对结构化任务，还要检查字段名、枚举值和 JSON 格式一致性。

### 7. 如何判断微调模型是否过拟合？

**参考答案：**

如果训练 loss 下降但验证集或测试集指标不提升，或者模型输出变得模板化、对同义表达泛化差，就可能过拟合。还要检查是否有训练/测试数据泄漏。处理方式包括减少 epoch、降低 rank 或学习率、增加 dropout、清洗重复样本、补充更多真实分布样本，并保留独立测试集验证。

### 8. 微调模型上线前你会做哪些评估？

**参考答案：**

我会至少做四类评估：第一，任务指标，例如抽取准确率、工具调用准确率、客服解决率；第二，格式和稳定性，例如 JSON 可解析率、必填字段缺失率；第三，安全和合规，例如越权调用、敏感信息泄露、拒答边界；第四，工程指标，例如延迟、吞吐、成本和失败率。还要和 base+prompt 基线对比，并通过灰度观察真实流量表现。

### 9. 微调后模型安全能力下降怎么办？

**参考答案：**

先用安全评估集定位是哪些场景下降，例如越权、敏感信息、危险建议或拒答失败。然后从数据上补充拒答样本和边界样本，从训练上控制学习率、epoch 和 rank，从应用层保留安全检查和权限校验。不能把安全完全交给微调模型，生产系统仍要有内容安全、工具权限和审计机制。

### 10. 微调模型和模型网关如何结合？

**参考答案：**

业务不应该直接依赖具体微调产物，而应该通过模型网关使用稳定别名。网关负责把别名路由到 base model、adapter version 或合并后的模型版本，并记录请求、评估、成本和异常。这样可以做灰度、A/B、回滚和多租户隔离。微调模型本质上是模型治理体系中的一个可版本化能力。

### 11. DPO 适合解决什么问题？

**参考答案：**

DPO 适合已有偏好数据的场景，也就是同一个输入下有“更好回答”和“更差回答”。如果 SFT 后模型已经会回答，但回答风格、帮助性、安全性或业务偏好还不稳定，可以用 DPO 进一步对齐。它通常比 RLHF 工程简单，但仍然依赖高质量偏好数据。

### 12. 为什么说微调不是一次性项目？

**参考答案：**

因为业务规则、用户问法、模型底座和线上分布都会变化。微调上线后还要持续收集坏 case、做归因、重新标注、更新评估集并定期训练。成熟流程应该包含数据版本、模型版本、评估报告、灰度发布和回滚机制。否则第一次指标好，不代表长期稳定。

## 五、常见追问与回答框架

### 1. 如果只有 200 条样本，能不能微调？

可以试验，但要谨慎。200 条高质量、边界清晰、分布集中的样本，可能足够让模型学习格式或简单分类；但不适合期望模型学习复杂业务能力。更稳妥的做法是先用 Prompt few-shot 建基线，再用 LoRA 小步实验，并保留严格测试集。如果评估没有明显提升，就不要为了微调而微调。

### 2. 微调会不会比 RAG 更省钱？

可能会，但不是必然。微调可以缩短 Prompt、减少 few-shot 示例和上下文长度，从而降低单次推理成本；但训练、评估、部署和运维也有成本。如果知识仍需要 RAG，微调不能替代检索成本。应该用总成本评估：训练成本 + 推理成本 + 维护成本 + 错误成本。

### 3. 如何处理微调数据中的敏感信息？

训练前要脱敏或匿名化，移除不必要的个人身份信息、密钥、合同敏感条款等。保留业务判断所需字段，不保留可识别个体的原文。还要控制训练数据访问权限、记录数据来源和处理流程。对合规要求高的场景，需要数据审批和可删除机制。

### 4. 如何解释“模型微调后仍然需要应用层校验”？

微调提高的是概率行为，不是强约束。模型仍可能输出非法 JSON、调用错误工具或越权回答。因此结构化输出要做 schema 校验，工具调用要做权限校验，敏感场景要做人审或规则兜底。生产系统不能把微调模型当成唯一可信边界。

## 六、面试答题模板

回答微调方案设计题时，可以按这个顺序：

1. 明确目标：要提升什么任务指标，而不是泛泛说“效果更好”。
2. 判断方案：先说明为什么 Prompt/RAG/规则不够，微调解决什么行为问题。
3. 数据设计：样本来源、清洗、脱敏、格式、难例和切分方式。
4. 训练方法：base model、SFT/LoRA/QLoRA/DPO、关键参数和版本管理。
5. 评估体系：离线指标、人工评审、安全评估、工程指标、A/B 对照。
6. 上线治理：模型网关、灰度、监控、回滚、坏 case 回流。
7. 风险控制：过拟合、遗忘、数据泄漏、敏感信息和安全边界。

一个简洁回答示例：

> 我不会直接说“做微调”。我会先用现有 Prompt/RAG 建一个评估基线，确认问题是输出格式和业务判断不稳定，而不是知识缺失。然后收集真实线上样本，清洗脱敏后构建 train/valid/test，并补充边界样本和拒答样本。训练上优先用 LoRA 或 QLoRA 做小步实验，记录 base model、adapter 和数据版本。评估时同时看任务准确率、JSON 可解析率、安全违规率、延迟和成本。上线通过模型网关挂版本别名，小流量灰度，保留回滚和坏 case 回流机制。

## 七、复习重点

- 微调解决的是稳定行为和输出分布，不是实时知识库。
- RAG、Prompt、规则和微调要按问题类型组合使用。
- 数据质量、评估集隔离和坏 case 归因比调参更关键。
- LoRA/QLoRA 的优势是低成本、轻量版本和易回滚。
- 微调模型上线后仍需要 schema 校验、权限校验、安全检查和观测。
- 面试回答要覆盖“数据、训练、评估、上线、回滚”，不要只讲训练参数。
