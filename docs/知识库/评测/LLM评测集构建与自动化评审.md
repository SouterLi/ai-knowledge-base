## 核心概念

### 1. 评测集不是线上日志的简单抽样

LLM 应用评测集是一组可版本化、可复现、可评分的样本资产，用来判断一次 Prompt、模型、RAG、工具或安全策略改动是否真的变好。

线上日志通常是原始事实，评测集必须进一步加工：

| 环节 | 目的 | 面试要点 |
| --- | --- | --- |
| 筛选 | 选择高频、高风险、长尾、坏 Case | 覆盖业务风险，不追求随机堆量 |
| 脱敏 | 移除 PII、商业敏感信息 | 评测数据也要合规 |
| 标注 | 给出参考答案、事实点、禁止项、标签 | 让结果可判定 |
| 版本化 | 记录样本、评分规则、来源、适用范围 | 支持回归和对比 |

面试里要避免说「把用户问题导出来让模型跑一遍」。这只能得到一批输入，不能形成可信评测集。

### 2. 黄金样例、回归集、探索集

| 类型 | 作用 | 特点 |
| --- | --- | --- |
| 黄金样例 | 发布前把关核心场景 | 数量不一定大，但人工确认质量高 |
| 回归集 | 防止历史问题再次出现 | 由坏 Case、边界场景沉淀 |
| 探索集 | 发现新问题、比较策略 | 可包含线上采样、长尾和灰度样本 |

好的评测体系不是一个大文件跑到底，而是按风险和成本分层：小集合快速阻断明显回退，大集合用于夜间回归或版本评估。

### 3. 标准答案不一定是唯一答案

自然语言任务不能只做全文匹配。更常见的标注方式是：

- **事实点**：必须覆盖哪些关键信息。
- **禁止项**：不能出现哪些错误、越权或误导内容。
- **证据要求**：RAG 场景是否引用正确文档、页码、段落。
- **格式契约**：JSON 字段、枚举、单位、时间格式是否合规。
- **业务结果**：是否解决问题、是否需要转人工。

因此，评测集更像「输入 + 评分规则」，而不只是「输入 + 标准答案」。

### 4. LLM-as-Judge 是裁判，不是最终真理

LLM-as-Judge 适合规模化评审语义质量、完整性、表达风格和复杂开放题，但它有偏差：

- 偏好更长、更流畅的答案。
- 可能被候选答案里的错误事实带偏。
- 对专业领域和合规边界不如规则与人工稳定。
- 同一裁判模型升级后，历史分数可能不可比。

工程上通常采用：

```text
规则校验（格式/禁用项/引用） → LLM-as-Judge（语义评分） → 人工抽检/仲裁（高风险样本）
```

面试表达重点：**Judge 可以提高效率，但必须被校准、抽检和版本化**。

## 核心知识点

### 1. 评测集构建流程

推荐流程：

```text
定义任务与指标 → 收集候选样本 → 分层筛选 → 脱敏去重
→ 设计标签与评分规则 → 人工标注/复核 → 小规模试跑
→ 固化版本 → 接入 CI/CD 与发布门禁
```

每一步都要服务于「可复现、可比较、可定位」。如果只看总分，而不知道是检索、Prompt、工具还是安全策略导致失败，评测集的价值会大幅下降。

### 2. 样本来源与覆盖策略

| 来源 | 适合覆盖 | 注意事项 |
| --- | --- | --- |
| 高频线上问题 | 主路径体验 | 避免被头部问题垄断 |
| 历史坏 Case | 防回退 | 必须先归因和脱敏 |
| 专家构造样本 | 高风险、边界、合规 | 数量少但价值高 |
| 对抗样本 | Prompt 注入、越权、恶意格式 | 定期更新攻击方式 |
| 合成样本 | 长尾补齐、格式多样化 | 需人工抽检，不能完全信任 |

覆盖维度可以这样设计：

```yaml
coverage:
  intent: ["查询政策", "办理流程", "异常申诉", "闲聊拒答"]
  risk: ["低风险", "高金额", "隐私", "合规"]
  input_form: ["短问句", "多轮上下文", "错别字", "中英混合"]
  expected_behavior: ["直接回答", "引用证据", "拒答", "转人工"]
```

面试中可以强调：评测集不是越大越好，而是要覆盖 **高频、关键链路、边界、历史事故和安全风险**。

### 3. 样本 Schema 设计

一个可落地的评测样本至少要包含输入、期望、标签和评分配置。

```python
from dataclasses import dataclass, field

@dataclass
class EvalCase:
    case_id: str
    user_input: str
    expected_facts: list[str]
    forbidden_claims: list[str]
    tags: list[str]
    source: str
    risk_level: str
    reference_doc_ids: list[str] = field(default_factory=list)


case = EvalCase(
    case_id="refund_001",
    user_input="会员自动续费后能退款吗？",
    expected_facts=["符合条件可申请退款", "需在订单页提交申请", "退款到账时间以支付渠道为准"],
    forbidden_claims=["一定全额退款", "直接联系数据库管理员"],
    tags=["客服", "退款", "高频"],
    source="线上高频问题",
    risk_level="medium",
    reference_doc_ids=["policy_refund_v3"],
)
```

关键字段的面试解释：

- `case_id`：用于回归追踪，不能每次重跑都变。
- `expected_facts`：避免全文匹配，关注事实覆盖。
- `forbidden_claims`：控制幻觉、越权和错误承诺。
- `tags`：支持分层报告，而不是只看总分。
- `source`：便于判断样本代表性和合规来源。
- `reference_doc_ids`：RAG 场景验证引用和证据归因。

### 4. 评分方式：规则、语义、人工三层

不同任务使用不同评分方式：

| 任务 | 优先评分方式 | 示例 |
| --- | --- | --- |
| JSON 抽取 | Schema + 类型规则 | 字段存在、枚举合法、日期格式 |
| RAG 问答 | 事实点 + 引用校验 + Judge | 答案是否被证据支持 |
| Agent 工具调用 | 工具名/参数/顺序断言 | 是否调用正确工具，参数是否越权 |
| 安全拒答 | 规则 + 对抗样本 + 人工抽检 | 是否拒绝泄露隐私 |
| 开放总结 | Judge + 人工校准 | 完整性、相关性、冗余度 |

一个简化评分函数：

```python
def rule_score(answer: str, case: EvalCase) -> dict:
    # 中文注释：规则评分先检查必须事实和禁止表述，适合作为上线硬门禁
    hit_facts = [fact for fact in case.expected_facts if fact in answer]
    violations = [claim for claim in case.forbidden_claims if claim in answer]

    return {
        "fact_recall": len(hit_facts) / max(len(case.expected_facts), 1),
        "has_forbidden_claim": bool(violations),
        "violations": violations,
        "passed": len(violations) == 0 and len(hit_facts) == len(case.expected_facts),
    }
```

规则评分稳定但覆盖不了所有语义；Judge 覆盖面更广但有偏差；人工最可靠但成本高。成熟做法是把它们组合，而不是押注单一方式。

### 5. LLM-as-Judge 提示词设计

Judge 提示词要把评分标准写清楚，避免只让模型回答「好不好」。

```python
def build_judge_prompt(question: str, answer: str, expected_facts: list[str]) -> str:
    # 中文注释：裁判只依据给定标准评分，减少被候选答案带偏
    facts = "\n".join(f"- {fact}" for fact in expected_facts)
    return f"""
你是企业 AI 应用评测裁判。请只根据评分标准判断候选答案。

用户问题：
{question}

候选答案：
{answer}

必须覆盖的事实点：
{facts}

请输出 JSON：
{{
  "score": 0 到 5 的整数,
  "missing_facts": ["缺失的事实点"],
  "unsupported_claims": ["无依据或错误承诺"],
  "reason": "一句话说明主要原因"
}}
"""
```

Judge 输出也要做结构化校验。如果裁判结果不是合法 JSON，或理由与分数矛盾，要重试或进入人工抽检。

### 6. Judge 校准与一致性

面试高频追问：「怎么知道 Judge 靠谱？」

可以这样回答：

1. 抽一批样本做人工金标。
2. 用 Judge 跑同一批样本。
3. 比较 Judge 与人工的一致率、误杀率、漏判率。
4. 对分歧样本分析原因，调整 rubric 或裁判模型。
5. 固定 Judge 模型版本、temperature、提示词版本。
6. 定期抽检线上新增样本，避免评分漂移。

常见指标：

| 指标 | 含义 |
| --- | --- |
| Agreement Rate | Judge 与人工结论一致比例 |
| False Pass | 人工判失败但 Judge 放过 |
| False Fail | 人工判通过但 Judge 拦截 |
| Score Drift | 裁判模型或提示词变化导致分数漂移 |

高风险场景宁可控制 False Pass，因为放过错误答案比多拦一些样本更危险。

### 7. 分层报告比总分更重要

只说「准确率 88%」面试上不够。应该按场景、风险、标签、失败类型拆开：

```text
总通过率：88%
高风险样本通过率：72%
退款类通过率：91%
隐私类拒答准确率：98%
RAG 引用准确率：83%
工具参数准确率：79%
```

这样才能指导修复：

- 高风险低：收紧拒答和人工复核。
- 引用低：查证据组装和引用校验。
- 工具参数低：优化 tool schema、参数校验和少样本示例。
- 某业务线低：补知识库或调整领域 Prompt。

### 8. 接入发布门禁

评测集要进入变更流程，而不是上线后再看。

```text
开发改动 → 冒烟评测集 → 全量回归集 → 分层报告 → 门禁判断 → 灰度 → 线上监控
```

门禁示例：

```yaml
release_gate:
  overall_pass_rate: ">= 0.90"
  high_risk_pass_rate: ">= 0.98"
  forbidden_claim_count: "== 0"
  json_valid_rate: ">= 0.99"
  p95_latency_growth: "<= 0.20"
```

注意不要只用总分作为门禁。比如整体提升 2%，但隐私拒答从 99% 掉到 90%，这次发布仍应阻断。

### 9. 评测集维护：新增、淘汰与防泄漏

评测集不是只增不删：

- **新增**：高频新问题、线上坏 Case、新功能、新安全风险。
- **淘汰**：业务规则过期、重复样本、不可复现样本、标注争议长期无法解决。
- **拆分**：训练集、调参集、最终评测集必须隔离，避免过拟合。
- **防泄漏**：不要把最终评测集样本直接塞进 Prompt 示例或微调训练集。

面试中可以说：评测集需要像代码一样管理版本、评审和变更记录。

### 10. 常见误区

| 误区 | 问题 | 正确做法 |
| --- | --- | --- |
| 只看相似度 | 语义相似不代表事实正确 | 事实点、禁用项、证据校验 |
| 只用线上点赞踩 | 用户反馈噪声大 | 反馈只是候选信号，需标注 |
| Judge 全自动决定上线 | 裁判有偏差 | 规则硬门禁 + 人工抽检 |
| 评测集越大越好 | 成本高且可能重复 | 分层覆盖和定期清理 |
| 改 Prompt 后只测几个例子 | 无法发现回退 | 固定回归集 + 分层报告 |

## 高频面试问题与标准答案

**Q1：你会怎么从 0 到 1 建一个 LLM 应用评测集？**  
我会先明确任务和指标，比如客服问答要看事实正确、引用准确、拒答质量和格式合规。然后从高频线上问题、历史坏 Case、专家构造的高风险样本和对抗样本里筛选候选，做脱敏、去重和分层标签。标注时不只写标准答案，还会写必须事实点、禁止项、参考证据和适用场景。最后先小规模试跑，看样本是否能区分好坏，再固化版本，接入发布前回归和灰度监控。

**Q2：评测集和线上日志有什么区别？**  
线上日志只是原始数据，里面有噪声、隐私信息，也不一定有标准答案。评测集是加工后的数据资产，要经过筛选、脱敏、标注和版本化，能稳定回答「这次改动有没有回退」。所以我不会直接把日志导出来当评测集，而是把日志作为样本来源之一。

**Q3：自然语言答案不唯一，怎么评分？**  
我不会做全文匹配，而是拆成事实点、禁止项、引用证据和格式契约。比如客服答案必须提到申请入口、处理时效和限制条件，不能承诺一定退款。开放表达可以交给 LLM-as-Judge 做语义评分，但关键事实和安全边界要用规则或人工复核兜住。

**Q4：LLM-as-Judge 能不能直接作为上线依据？**  
不能直接单独用。Judge 适合规模化初筛，但它会受提示词、模型偏好和候选答案表达影响。我会先用人工金标样本校准 Judge，看一致率、误杀率和漏判率；线上发布门禁里，格式、禁用项、引用这类确定性问题用规则硬校验，高风险分歧样本进入人工抽检。Judge 是提效工具，不是最终责任人。

**Q5：如何判断 Judge 是否稳定？**  
我会固定裁判模型版本、temperature、Judge Prompt 和输出 Schema，然后用一批人工标注样本定期回归，观察与人工的一致率以及分数漂移。如果换了裁判模型或提示词，要重新跑基准集，不能把新旧分数直接混在一起比较。对高风险场景，我更关注 False Pass，也就是错误答案被放过的比例。

**Q6：评测集样本怎么分层？**  
至少按业务意图、风险等级、输入形态和期望行为分层。比如高频 FAQ、隐私问题、多轮上下文、无答案拒答、工具调用、RAG 引用都应该有独立标签。报告也要按标签看，不只看总分，因为总分可能掩盖高风险样本的回退。

**Q7：坏 Case 都要放进评测集吗？**  
不是。坏 Case 要先脱敏、去重、确认可复现，并完成归因。比如知识库缺失的样本，应该先修知识；如果业务规则即将变更，也不适合马上放进稳定回归集。真正适合进入回归集的是高风险、可复现、修复后需要长期防回退的样本。

**Q8：合成数据能不能用于评测集？**  
可以作为补充，尤其是长尾、边界输入、格式扰动和对抗样本，但不能完全依赖。合成样本可能分布不真实，也可能把生成模型的偏见带进评测集。我会对合成样本做人工抽检，并在报告里区分真实线上样本和合成样本的表现。

**Q9：如何把评测集接入 CI/CD？**  
我会做分层门禁：提交或合并前跑小规模冒烟集，发布前跑全量回归集，灰度阶段看线上同口径指标。门禁不仅看总体通过率，还要看高风险通过率、禁用项违规数、JSON 合规率、引用准确率和延迟成本变化。任何高风险硬指标回退都阻断发布。

**Q10：模型升级时怎么用评测集判断能不能切换？**  
我会用同一版本评测集同时跑旧模型和新模型，按场景标签比较质量、成本、延迟和安全指标。不能只看平均分，要看高风险样本、工具调用、结构化输出和拒答质量有没有下降。通过离线评测后再小流量灰度，并记录模型版本和配置，方便出现问题时回滚。

**Q11：如果离线评测很好，线上效果还是差，可能是什么原因？**  
通常是评测集覆盖不足或分布漂移。比如线上有更多口语化、多轮、省略表达，或者新业务规则没有进入评测集。也可能是离线环境固定了检索结果和工具状态，线上真实链路存在权限、延迟、超时和知识更新问题。解决方式是做线上分层采样，把新问题回流到评测集，并保证离线评测尽量复现真实链路。

**Q12：面试中一句话怎么总结这个主题？**  
我会说：LLM 评测集的核心不是攒一堆问答，而是把业务风险转成可复现、可标注、可评分、可回归的数据资产；规则校验、LLM-as-Judge 和人工抽检组合使用，最后接入发布门禁，才能真正支撑 Prompt、模型、RAG 和 Agent 的持续迭代。
