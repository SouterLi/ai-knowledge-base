## 核心概念

### 1. 什么是 Agentic RAG

Agentic RAG 是把 Agent 的规划、工具调用和多步推理能力引入 RAG 链路，让系统不再固定执行“一次 query → 一次检索 → 一次生成”，而是根据问题复杂度动态决定：

- 是否需要拆解问题；
- 要调用哪些检索工具或业务工具；
- 是否需要多轮检索、交叉验证或补充证据；
- 证据不足时是追问用户、扩大检索还是拒答；
- 如何把多源证据压缩成可生成答案的上下文。

普通 RAG 更像一条固定流水线：

```text
用户问题
  → 查询改写
  → 检索 top_k
  → rerank
  → 拼上下文
  → 生成答案
```

Agentic RAG 更像一个带策略的检索执行器：

```text
用户问题
  → 判断问题类型和复杂度
  → 规划检索步骤
  → 调用向量检索 / BM25 / SQL / 图谱 / Web / 业务 API
  → 汇总证据并检查是否足够
  → 必要时继续检索或澄清
  → 生成带引用、边界和置信度的答案
```

一句面试表达：**普通 RAG 解决“给定问题找相关上下文”，Agentic RAG 解决“复杂问题下如何主动规划检索路径、组合工具并验证证据是否足够”。**

### 2. Agentic RAG 适合解决什么问题

Agentic RAG 不适合所有问答场景。简单 FAQ、规则明确的单跳问题，用固定 RAG 流水线通常更快、更稳、更便宜。它更适合以下复杂场景：

| 场景 | 普通 RAG 的问题 | Agentic RAG 的价值 |
| --- | --- | --- |
| 多跳问题 | 一次检索只能命中部分证据 | 拆成子问题，分步检索和合并证据 |
| 跨数据源问题 | 文档、数据库、工单、日志分散 | 按需调用不同工具和索引 |
| 对比分析 | 需要同时找多个对象的材料 | 分别检索、结构化对齐、再总结差异 |
| 诊断排查 | 需要按假设逐步查证 | 根据中间结果决定下一步工具 |
| 证据不足 | 固定流程容易硬答 | 触发补充检索、追问或拒答 |
| 时效性问题 | 离线索引可能过期 | 结合实时查询、业务 API 或在线搜索 |

面试中要强调：**Agentic RAG 的目标不是让链路更炫，而是在问题复杂度超过固定检索链路能力时，提高证据覆盖率和答案可靠性。**

### 3. Agentic RAG 的核心组件

一个工程化的 Agentic RAG 通常包含以下组件：

```text
意图与复杂度判断器
  判断问题是否需要 Agentic 流程

检索规划器
  将复杂问题拆成子任务，决定工具、顺序和停止条件

工具注册表
  描述每个检索工具的数据范围、成本、延迟、权限和输入输出

执行器
  负责调用工具、重试、超时、并发、限流和执行日志

证据聚合器
  去重、归一、按子问题归档证据，并保留引用来源

证据校验器
  判断证据是否足够、是否冲突、是否越权、是否需要继续检索

答案生成器
  基于结构化证据生成答案，明确引用、假设和不确定性
```

其中最容易被面试追问的是 **规划器、工具边界、停止条件和证据校验**。如果回答只停留在“让 Agent 多调用几次搜索”，会显得没有生产落地经验。

### 4. Agentic RAG 与 Query Router 的区别

Query Router 通常是一次性决策：根据问题类型选择某个检索路径，例如走向量库、关键词检索、SQL 或客服 FAQ。

Agentic RAG 是多步决策：它可以先走向量检索，发现证据缺少价格字段后再查 SQL，发现政策版本不确定后再查文档元数据，最后把多源证据合并。

```text
Query Router：选择一条路
Agentic RAG：规划一组步骤，并根据中间结果动态调整
```

面试里可以这样表达：**Query Router 适合入口分流，Agentic RAG 适合复杂任务执行；前者解决“该走哪条链路”，后者解决“走到一半发现不够时下一步怎么办”。**

## 核心知识点

### 1. 先判断是否值得进入 Agentic 流程

Agentic RAG 会增加延迟、成本和不确定性，因此生产系统通常需要一个轻量判断器，而不是所有问题都走 Agent。

常见判断维度：

| 判断维度 | 进入 Agentic RAG 的信号 | 继续走普通 RAG 的信号 |
| --- | --- | --- |
| 问题复杂度 | 多条件、多实体、多跳推理、对比分析 | 单一事实、FAQ、定义解释 |
| 数据源数量 | 需要文档 + 数据库 + 业务 API | 单一知识库即可回答 |
| 时效性 | 需要实时库存、订单、日志、公告 | 离线知识库内容足够 |
| 风险等级 | 答错影响决策，需要证据校验 | 低风险泛知识问答 |
| 检索反馈 | 首轮召回低分、证据冲突、引用不足 | 首轮检索命中高且一致 |

一个常见入口策略是：

```python
def should_use_agentic_rag(question, first_pass_result):
    """判断是否升级到 Agentic RAG。"""
    if first_pass_result["top_score"] < 0.45:
        return True
    if first_pass_result["has_conflict"]:
        return True
    if contains_multi_hop_signal(question):
        return True
    if needs_live_business_data(question):
        return True
    return False
```

面试重点：**先用低成本路径解决大部分简单问题，只把复杂、低置信、跨源或高风险问题升级到 Agentic RAG。**

### 2. 工具不是越多越好，要有工具契约

Agentic RAG 的工具通常包括：

- `vector_search`：语义召回非结构化文档；
- `keyword_search`：处理专有名词、编号、错误码；
- `sql_query`：查询结构化业务数据；
- `graph_search`：查实体关系和路径；
- `web_search`：获取外部实时信息；
- `log_search`：排查线上日志和 trace；
- `policy_lookup`：查强约束政策、权限或规则。

每个工具都应该有清晰契约：

```yaml
name: sql_query
purpose: 查询订单、库存、账单等结构化业务数据
input_schema:
  sql: string
permissions:
  required_roles: ["support_analyst"]
constraints:
  readonly: true
  max_rows: 100
  timeout_ms: 1500
  allow_tables: ["orders", "refunds", "inventory"]
  require_tenant_filter: true
  parameterized_only: true
cost:
  latency_level: medium
  token_cost: low
output:
  rows: array
  source: database
  freshness: realtime
```

工具契约要解决四个问题：

1. **能不能调**：权限、租户、数据范围是否允许。
2. **怎么调**：输入输出 schema 是否稳定。
3. **调多久**：超时、重试、并发和限流策略。
4. **结果怎么算可信**：是否带来源、时间、版本和置信度。

面试中可以补一句：**工具描述不是只给模型看的文案，它也是系统执行权限、审计、限流和测试的契约。**

### 3. 检索规划要显式化，而不是只靠模型自由发挥

生产系统里不建议让模型无限制地“想调什么就调什么”。更稳的做法是让模型生成结构化计划，再由执行器校验。

示例：

```json
{
  "goal": "比较 A 产品和 B 产品在企业版中的权限差异",
  "steps": [
    {
      "id": "s1",
      "question": "检索 A 产品企业版权限说明",
      "tool": "vector_search",
      "query": "A 产品 企业版 权限 功能列表"
    },
    {
      "id": "s2",
      "question": "检索 B 产品企业版权限说明",
      "tool": "vector_search",
      "query": "B 产品 企业版 权限 功能列表"
    },
    {
      "id": "s3",
      "question": "按权限项对齐差异",
      "tool": "evidence_compare",
      "depends_on": ["s1", "s2"]
    }
  ],
  "stop_condition": "两个产品都找到最新企业版文档，且差异表有引用来源"
}
```

执行器需要校验：

- 工具是否在白名单内；
- 参数是否符合 schema；
- 查询是否包含越权字段；
- 步骤数量是否超过上限；
- 是否存在循环依赖；
- 停止条件是否可检查。

面试回答要突出：**规划可以由模型生成，但执行边界必须由代码控制。**

### 4. 多步检索要有停止条件

Agentic RAG 最常见的问题是停不下来：模型觉得证据不够就继续搜，导致延迟、成本和不确定性上升。

常见停止条件：

| 停止条件 | 示例 |
| --- | --- |
| 证据足够 | 每个子问题至少有一个高相关引用 |
| 分数达标 | rerank 分数或引用覆盖率超过阈值 |
| 预算耗尽 | 最多 3 轮、最多 6 次工具调用、最多 5 秒 |
| 无新增信息 | 新一轮检索与已有证据高度重复 |
| 风险升级 | 发现证据冲突、权限不足或需要用户澄清 |
| 明确不可答 | 合法检索范围内没有足够证据 |

示例执行循环：

```python
def run_agentic_rag(plan, budget):
    evidence = []

    for step in plan.steps:
        if budget.tool_calls_left <= 0:
            break

        # 执行前做权限、schema 和预算校验
        validate_step(step)
        result = call_tool(step.tool, step.arguments)
        evidence.extend(normalize_evidence(result))
        budget.tool_calls_left -= 1

        # 如果证据已经足够，就提前结束，避免无意义检索
        if evidence_is_sufficient(evidence, plan.stop_condition):
            break

    return build_answer_context(evidence)
```

面试中不要只说“设置 max iteration”，更好的表达是：**最大轮数是兜底，真正的停止条件应该来自证据覆盖、冲突检测、新信息增益和业务风险。**

### 5. 证据聚合要保留结构，而不是直接拼文本

多工具检索会产生不同格式的结果，如果直接拼成一大段上下文，模型很容易混淆来源、版本和适用范围。

更稳的做法是把证据结构化：

```json
{
  "sub_question": "企业版是否支持 SSO",
  "evidence": [
    {
      "source_type": "policy_doc",
      "title": "企业版权限说明",
      "version": "2026-05",
      "quote": "企业版支持 SAML SSO 和 SCIM 用户同步。",
      "confidence": 0.91
    },
    {
      "source_type": "pricing_db",
      "title": "套餐能力表",
      "version": "realtime",
      "quote": "enterprise.sso_enabled = true",
      "confidence": 0.98
    }
  ],
  "status": "supported"
}
```

结构化证据的好处：

- 方便检查每个子问题是否有证据；
- 可以把冲突证据显式交给模型处理；
- 能在答案里生成准确引用；
- 便于 trace、评测和坏 Case 归因；
- 可以按来源可信度、时效性、权限范围排序。

面试重点：**Agentic RAG 的上下文不是越多越好，而是要把“问题 - 证据 - 来源 - 结论”组织清楚。**

### 6. 证据冲突时不要让模型自由裁判

多源检索很容易出现冲突：

- 文档说支持某功能，数据库套餐表显示未开通；
- 旧版本政策和新版本政策都被召回；
- FAQ 与法律条款描述不一致；
- 外部网页和内部系统口径不同。

工程上可以定义优先级规则：

```text
实时业务系统 > 已发布政策文档 > 审核 FAQ > 历史工单 > 外部网页
新版本 > 旧版本
当前租户配置 > 通用产品说明
强规则 > 经验总结
```

如果冲突无法自动解决，应该：

1. 在答案中说明存在冲突；
2. 给出可确认的证据来源；
3. 请求用户补充范围或转人工；
4. 将冲突样本进入知识库治理或数据闭环。

面试表达：**模型可以辅助总结冲突，但不能凭语言流畅度决定哪个证据是真的；证据优先级、版本和数据源可信度要在系统层定义。**

### 7. Agentic RAG 的评估要覆盖过程和结果

普通 RAG 常评估召回率、MRR、NDCG、答案准确率和引用命中率。Agentic RAG 还要评估过程质量：

| 评估维度 | 关注问题 | 常见指标 |
| --- | --- | --- |
| 规划质量 | 是否拆对问题，工具选择是否合理 | plan accuracy、tool selection accuracy |
| 工具执行 | 是否越权、超时、重复调用 | tool success rate、timeout rate、denied rate |
| 证据覆盖 | 子问题是否都有证据 | sub-question coverage、citation coverage |
| 证据忠实 | 答案是否被证据支持 | groundedness、faithfulness |
| 成本延迟 | 是否超过预算 | p95 latency、avg tool calls、token cost |
| 稳定性 | 同类问题计划是否一致 | plan variance、answer consistency |

离线评测可以准备复杂多跳问题集，并标注期望工具路径和标准证据；线上评测则结合 trace 看每一步为什么被调用、是否产生新增信息。

面试重点：**Agentic RAG 不是只看最终答案对不对，还要看它有没有用合理、可控、可复现的路径得到答案。**

### 8. 生产落地要重点控制权限、成本和可观测性

Agentic RAG 一旦能调用多个工具，就必须考虑生产约束：

- **权限**：每次工具调用都要带用户身份、租户和数据范围，不能只在最终答案过滤。
- **成本**：规划、工具调用、rerank、答案生成都要有预算；复杂问题可以异步执行或分阶段返回。
- **延迟**：支持并行检索、缓存中间结果、提前停止和低置信降级。
- **安全**：防止提示注入诱导 Agent 调用越权工具或泄露检索结果。
- **可观测性**：记录 plan、tool call、query、证据、引用、预算消耗和最终答案。
- **可回放**：坏 Case 要能复现当时的工具版本、索引版本、Prompt 版本和证据集。

一个简化 trace 结构如下：

```json
{
  "run_id": "rag_run_20260627_001",
  "user_id": "u_123",
  "question": "A 套餐和 B 套餐在权限上有什么差异？",
  "plan": ["search_a_plan", "search_b_plan", "compare_permissions"],
  "tool_calls": [
    {"tool": "vector_search", "latency_ms": 180, "hits": 8},
    {"tool": "pricing_db", "latency_ms": 96, "rows": 2}
  ],
  "budget": {"max_tool_calls": 5, "used_tool_calls": 2},
  "answer_status": "supported"
}
```

面试里可以总结为：**Agentic RAG 的生产难点不是“让模型会调用工具”，而是让多步检索在权限、预算、延迟、证据和可观测性边界内稳定运行。**

## 高频面试问题与标准答案

### 1. 什么是 Agentic RAG？它和普通 RAG 有什么区别？

**标准答案：**

普通 RAG 通常是固定链路：用户问题进来后做查询改写、召回、重排、拼上下文，然后生成答案。Agentic RAG 则会引入 Agent 的规划和工具调用能力，让系统根据问题复杂度动态决定要不要拆解问题、调哪些检索工具、是否需要多轮检索，以及证据是否足够。

我会这样区分：普通 RAG 更适合单跳、明确、低风险的问题；Agentic RAG 更适合多跳、跨数据源、需要实时数据或需要证据校验的问题。它的核心价值不是“多调几次工具”，而是能主动规划检索路径，并根据中间结果调整下一步。

### 2. 什么场景下你会引入 Agentic RAG？

**标准答案：**

我不会默认所有问题都走 Agentic RAG，因为它会增加延迟、成本和不确定性。通常在几类场景引入：第一，多跳问题，比如需要先找政策再查用户状态；第二，跨数据源问题，比如文档、数据库和日志都要查；第三，对比分析问题，需要分别收集多个对象的证据；第四，首轮 RAG 低置信或证据冲突，需要继续检索或校验。

生产上我会先用普通 RAG 处理高频简单问题，只有当首轮召回分低、引用不足、存在冲突或识别出复杂意图时，才升级到 Agentic RAG。

### 3. Agentic RAG 的系统架构一般怎么设计？

**标准答案：**

我会拆成几个模块：入口先做意图和复杂度判断，决定是否进入 Agentic 流程；进入后由规划器生成结构化检索计划；工具注册表描述每个工具的数据范围、权限、成本和输入输出；执行器负责工具调用、超时、重试、并发和审计；证据聚合器把多源结果按子问题组织；证据校验器判断证据是否足够、是否冲突；最后答案生成器基于结构化证据生成带引用的回答。

这里面最关键的是边界控制：模型可以生成计划，但工具白名单、参数校验、权限、预算和停止条件要由系统代码控制，不能让模型无限制自由调用。

### 4. 如何避免 Agentic RAG 失控或者一直检索下去？

**标准答案：**

我会从两层控制。第一层是硬预算，比如最多几轮、最多几次工具调用、总超时时间、token 上限和并发上限。第二层是业务停止条件，比如每个子问题是否都有高质量引用、有没有新增信息、证据是否冲突、是否已经达到置信度阈值。

只设置 max iteration 还不够，因为它只是兜底。更好的做法是让系统判断“继续检索是否还能带来新证据”。如果多轮结果重复、证据冲突无法解决、权限不足或问题本身不明确，就应该停止，转为澄清、拒答或人工处理。

### 5. Agentic RAG 里工具应该怎么设计？

**标准答案：**

工具要有明确契约，而不是只写一段自然语言描述。每个工具至少要说明用途、输入输出 schema、数据范围、权限要求、超时时间、限流策略、是否只读、结果是否带来源和时间。

比如 SQL 工具必须限制只读、白名单表、最大返回行数和租户过滤；文档检索工具要返回 doc_id、版本、chunk、分数和引用位置；外部搜索工具要标记可信度和时效性。这样做的目的是让 Agent 能选工具，也让执行层能校验工具调用是否合法、可审计、可测试。

### 6. 多个工具返回的证据不一致怎么办？

**标准答案：**

我不会让模型仅凭语言感觉自由判断哪个证据正确。工程上要先定义证据优先级，比如实时业务系统优先于静态文档，新版本优先于旧版本，当前租户配置优先于通用说明，强规则优先于经验总结。

如果冲突能按规则解决，就在答案中引用更高优先级证据；如果不能解决，就要明确告诉用户存在冲突，展示关键来源，并触发澄清、转人工或知识库治理流程。这个问题本质上是证据治理，不是单纯 Prompt 优化。

### 7. Agentic RAG 如何做评估？

**标准答案：**

除了评估最终答案准确率、引用命中率和幻觉率，我还会评估过程。比如问题是否拆解正确、工具选择是否合理、每个子问题是否找到证据、是否调用了不该调用的工具、是否超时或超预算、同类问题的计划是否稳定。

离线可以构造一批多跳和跨源问题，标注标准答案、标准证据和期望工具路径；线上则看 trace，分析每一步工具调用是否带来新增信息。Agentic RAG 的评估重点是“答案对不对”和“得到答案的路径是否合理、可控、可复现”。

### 8. Agentic RAG 和多 Agent 有什么关系？

**标准答案：**

Agentic RAG 不一定等于多 Agent。很多场景一个 Agent 加多个工具就够了，比如一个规划器负责拆问题，再调用不同检索工具。多 Agent 是更复杂的组织方式，比如让检索 Agent、SQL Agent、验证 Agent、写作 Agent 分工协作。

我通常会先从单 Agent + 工具编排开始，因为可控性和调试成本更好。只有当任务天然需要不同角色、不同权限或不同评估标准时，才考虑多 Agent。面试里我会强调，不要为了架构复杂而引入多 Agent，先把工具契约、证据结构和停止条件做好。

### 9. Agentic RAG 如何控制延迟和成本？

**标准答案：**

首先要做分层路由，简单问题走普通 RAG，复杂或低置信问题才升级。其次要给每次运行设置预算，比如最大工具调用次数、总超时、token 上限和 rerank 候选上限。第三，可以并行执行互不依赖的检索步骤，缓存稳定结果，并在证据足够时提前停止。

如果问题非常复杂，也可以把它做成异步任务，先返回“正在分析”，后续给结构化结果。核心思路是：Agentic RAG 的能力要按需使用，不能让所有流量都承担最复杂链路的成本。

### 10. 面试官问“Agentic RAG 是否一定比普通 RAG 好”，你怎么回答？

**标准答案：**

不一定。Agentic RAG 在复杂问题、跨数据源、多跳推理和证据校验上更有优势，但它也带来更高延迟、更高成本和更难调试的不确定性。对于简单 FAQ 或单一知识库问答，普通 RAG 往往更稳定、更便宜。

我的选择标准是看业务问题复杂度和风险。如果大部分问题是单跳问答，我会优先优化普通 RAG；如果线上坏 Case 大量来自证据不全、跨源查询、版本冲突或需要实时数据，再引入 Agentic RAG，并且通过路由、预算、工具契约和 trace 把它控制住。
