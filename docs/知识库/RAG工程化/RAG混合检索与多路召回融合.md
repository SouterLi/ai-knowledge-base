## 核心概念

### 1. 什么是混合检索

混合检索是指在 RAG 检索阶段同时使用多种召回方式，把不同信号召回的候选文档融合后，再交给重排序、上下文压缩和答案生成。

常见组合是：

```text
用户问题
  → 查询理解：意图、关键词、实体、时间、权限、改写 query
  → 多路召回：
      - 关键词检索：BM25 / Elasticsearch
      - 向量检索：Embedding / ANN
      - 元数据过滤：时间、部门、产品线、权限、文档类型
      - 结构化召回：FAQ、知识图谱、SQL、业务 ID
  → 候选融合：去重、归一化、RRF、加权打分
  → Rerank：交叉编码器或 LLM rerank
  → 构造上下文并生成答案
```

一句面试表达：**向量检索擅长语义相似，关键词检索擅长精确匹配，元数据过滤保证业务边界；混合检索的目标是用多种互补信号提高召回率，同时用融合和重排控制噪声。**

### 2. 为什么不能只依赖向量检索

只做向量检索在 Demo 阶段很快，但真实业务里会遇到很多问题：

| 问题 | 典型表现 | 混合检索补充手段 |
| --- | --- | --- |
| 专有名词召回差 | 型号、条款号、错误码、订单号被语义化后丢失 | BM25、字段检索、实体识别 |
| 数字和时间敏感 | “2025 版”“7 天内”“P1 故障”被相似语义干扰 | 元数据过滤、结构化条件 |
| 短 query 信息少 | “报销标准”“怎么退款”无法精确定位范围 | 查询扩展、FAQ 召回、热门问题召回 |
| 长 query 噪声多 | 用户带了很多背景，Embedding 被无关内容稀释 | 查询改写、关键词抽取、多 query 召回 |
| 多租户和权限 | 语义相似但用户无权访问 | ACL 过滤、租户隔离、文档可见性校验 |

面试中要强调：**Embedding 不是万能匹配器。企业知识库里有大量编号、实体、权限、版本和业务字段，这些信号需要和语义信号一起工作。**

### 3. 多路召回和重排序的关系

多路召回负责“尽量别漏”，重排序负责“把最相关的排到前面”。

```text
召回阶段：宁可多拿一些可能相关的候选，但要控制上限
融合阶段：把不同召回源的候选统一到一个候选池
重排阶段：用更贵但更准的模型判断 query 与 chunk 的相关性
生成阶段：只把最可信、最互补、最符合权限的内容放进上下文
```

如果召回阶段漏掉了正确 chunk，后面的 rerank 和大模型通常救不回来；如果召回阶段候选太多且噪声太大，rerank 成本、延迟和误召回风险都会上升。

### 4. 混合检索的核心矛盾

混合检索的核心矛盾是 **召回率、精度、延迟、成本、可解释性** 之间的平衡：

- 召回路数越多，正确答案进入候选池的概率越高，但噪声和延迟也会上升。
- top_k 越大，召回率可能更高，但 rerank、上下文压缩和 token 成本更高。
- BM25 更可解释，但对语义改写不敏感。
- 向量检索能处理同义表达，但容易漏掉精确编号和业务实体。
- 权重调得过死，跨场景泛化差；完全动态又难排查线上问题。

所以一个成熟方案不会说“向量 + BM25 就完了”，而会说明 **召回源设计、融合策略、评测指标、延迟预算和线上调参闭环**。

## 核心知识点

### 1. 召回源要按业务问题设计

多路召回不是把所有检索方式堆起来，而是针对业务里常见的失败类型补信号。

| 召回源 | 适合解决的问题 | 面试关注点 |
| --- | --- | --- |
| BM25 / 关键词检索 | 专有名词、编号、法规条款、错误码、精确短语 | 分词、同义词、字段权重、停用词 |
| 向量检索 | 同义表达、口语问题、语义相近内容 | Embedding 模型、chunk 粒度、向量索引参数 |
| 元数据过滤 | 时间、权限、租户、产品线、文档类型 | 过滤必须前置还是后置、是否影响召回 |
| FAQ / 标准问召回 | 高频标准问题、客服知识库 | 问题改写、相似问、答案版本 |
| 结构化数据召回 | 订单、工单、指标、配置 | Text-to-SQL、API 查询、字段映射 |
| 图谱召回 | 实体关系、上下游依赖、复杂关联 | 实体链接、关系扩展、路径约束 |

面试表达：**我会先分析 bad case，是漏关键词、漏实体、漏语义，还是权限和时间过滤不对，再决定加哪一路召回，而不是盲目增加召回源。**

### 2. 典型混合检索架构

一个可落地的 RAG 混合检索链路通常长这样：

```text
1. Query 分析
   - 识别意图、实体、关键词、时间范围、用户权限
   - 生成原始 query、关键词 query、改写 query

2. 并行召回
   - BM25 top 50
   - 向量检索 top 50
   - FAQ 相似问 top 20
   - 元数据/权限过滤贯穿召回链路

3. 候选融合
   - doc_id/chunk_id 去重
   - 分数归一化或按排名融合
   - 保留召回来源、原始分数、命中字段

4. 重排序
   - 先轻量规则过滤明显无关内容
   - 再用 rerank 模型取 top 5～10

5. 上下文构造
   - 合并相邻 chunk
   - 去掉重复内容
   - 保留引用和来源
```

并行召回时要注意超时控制：某一路慢了不能拖垮整体，可以设置单路 timeout、fallback 和最大候选数。

### 3. 融合策略：从简单到复杂

候选融合常见有三类做法。

**第一类：拼接去重。**

把各路 top_k 合并后按简单规则排序，例如优先关键词命中、再按向量分数排序。实现简单，适合早期验证，但不同召回源的分数不可比。

**第二类：加权归一。**

把 BM25 分数、向量相似度、字段命中分、时间新鲜度归一化后加权：

```text
final_score = 0.45 * vector_score
            + 0.35 * bm25_score
            + 0.10 * metadata_boost
            + 0.10 * freshness_score
```

优点是可控，缺点是归一化和权重依赖评测集，换业务场景后需要重新调参。

**第三类：RRF 排名融合。**

RRF（Reciprocal Rank Fusion）不直接比较原始分数，而是按各路召回排名融合：

```python
def reciprocal_rank_fusion(rankings, k=60):
    scores = {}
    for source_name, docs in rankings.items():
        for rank, doc_id in enumerate(docs, start=1):
            # 中文注释：排名越靠前贡献越大，k 用来降低单一路召回的极端影响
            scores.setdefault(doc_id, 0.0)
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)

rankings = {
    "bm25": ["doc_1", "doc_8", "doc_3"],
    "vector": ["doc_8", "doc_2", "doc_1"],
    "faq": ["doc_5", "doc_1"]
}

print(reciprocal_rank_fusion(rankings)[:3])
```

RRF 在面试里很好讲：**它适合不同召回源分数尺度不一致的情况，用排名而不是原始分数融合，工程上稳定、可解释、容易上线。**

### 4. 分数归一和去重是面试高频点

不同召回源的分数不能直接比较：

- BM25 分数和语料长度、词频有关。
- 向量相似度可能是 cosine，也可能是 inner product 或 distance。
- FAQ 召回可能返回匹配置信度。
- 图谱召回可能是路径长度或关系权重。

因此融合前要做归一化或排名融合。常见归一方式有：

```text
min-max：适合单次候选集合内做相对比较，但受异常值影响
z-score：适合分布稳定的分数，但需要统计均值方差
rank-based：只看排名，稳定但丢失分数差距
bucket：把分数映射为强相关、相关、弱相关几档，便于规则解释
```

去重也不能只按文本完全一致，常见 key 包括：

```text
chunk_id：同一切片去重
doc_id + paragraph_id：同一段落去重
content_hash：文本重复去重
canonical_question_id：FAQ 相似问归并
source_uri + version：网页、文档版本去重
```

面试表达：**融合阶段我会保留每个候选的召回来源和原始分数，最终分数只用于排序，排查时能看到它为什么被召回。**

### 5. 元数据和权限过滤的位置很关键

元数据过滤包括租户、部门、角色、时间、文档类型、语言、产品线、版本等。它既影响正确性，也影响性能。

常见策略：

| 策略 | 做法 | 适用场景 |
| --- | --- | --- |
| 前置过滤 | 检索前带上 tenant、ACL、doc_type 等过滤条件 | 权限、租户、强业务边界 |
| 后置过滤 | 先召回更多候选，再过滤不满足条件的结果 | 过滤条件会导致召回过少的弱约束场景 |
| 前后结合 | 强约束前置，弱约束后置或加权 | 企业 RAG 最常见 |

权限过滤一般必须前置或至少在最终放入上下文前强校验，不能只靠 Prompt 要求模型“不回答无权内容”。

示例配置：

```json
{
  "retrieval_policy": {
    "hard_filters": ["tenant_id", "acl_scope", "doc_status"],
    "soft_filters": ["doc_type", "freshness", "language"],
    "recall": {
      "bm25_top_k": 40,
      "vector_top_k": 60,
      "faq_top_k": 10
    },
    "fusion": {
      "method": "rrf",
      "rrf_k": 60,
      "max_candidates": 80
    },
    "rerank_top_k": 8
  }
}
```

### 6. top_k 不是拍脑袋，要用评测集调

top_k 决定召回质量、延迟和成本。常见调参思路：

1. 先构建覆盖真实问题的评测集，包括 FAQ、长尾问题、编号问题、多跳问题、权限问题。
2. 对每一路召回单独评估 recall@k，找出各自擅长和失败的场景。
3. 评估融合后的 recall@k、MRR、nDCG，看正确 chunk 是否进入候选池并排在前面。
4. 加入 rerank 后评估 answer accuracy、citation accuracy 和 hallucination rate。
5. 在满足效果指标的前提下压缩 top_k 和 timeout，控制 P95 延迟。

常用指标：

| 指标 | 含义 | 面试解释 |
| --- | --- | --- |
| recall@k | 正确 chunk 是否在前 k 个候选中 | 召回阶段最核心 |
| precision@k | 前 k 个候选有多少是相关的 | 防止噪声过多 |
| MRR | 第一个正确结果排名的倒数均值 | 关注首个正确结果位置 |
| nDCG | 考虑多级相关性和排序位置 | 适合多个相关 chunk |
| answer faithfulness | 答案是否被上下文支持 | 检索质量最终要体现在答案上 |

面试重点：**不要只看最终回答感觉好不好，要把召回、融合、重排、生成分段评测，否则定位不了问题。**

### 7. 混合检索的性能优化

混合检索会增加链路复杂度，所以要有性能预算：

- **并行召回**：BM25、向量、FAQ 并行执行，整体耗时取最慢一路，而不是串行相加。
- **超时降级**：某一路超过阈值则放弃该路候选，记录 degraded source。
- **分层召回**：先用便宜召回拿较多候选，再用较贵 rerank 精排少量候选。
- **缓存 query 分析**：高频问题的关键词、实体、改写结果可以缓存。
- **限制最大候选数**：融合后统一截断，避免 rerank 被候选池拖垮。
- **按场景开关召回源**：编号类问题提高 BM25 权重，口语问答提高向量权重，实时数据走结构化 API。

一个实际面试回答可以这样说：**我会给每一路召回设置 top_k、timeout 和熔断策略，并把 retrieval latency、source hit rate、rerank latency、最终答案准确率一起监控。**

### 8. 常见 bad case 和排查方法

| Bad Case | 可能原因 | 排查方向 |
| --- | --- | --- |
| 用户输入订单号却召回语义相似文档 | 只走向量检索，编号信息丢失 | 加 BM25、字段检索、正则识别业务 ID |
| 正确文档被召回但排在很后面 | 融合权重不合理或 rerank 不适配 | 看各路 rank、原始分数、rerank 分数 |
| 召回很多同一文档重复 chunk | 切片重叠大、去重 key 不合理 | 按 doc_id/paragraph_id 合并，控制多样性 |
| 新文档搜不到 | 索引未更新或 metadata 过滤过严 | 查索引版本、增量任务、过滤条件 |
| 用户无权内容进入上下文 | ACL 未前置或后置校验缺失 | 检查权限过滤链路和引用可见性 |
| 延迟明显升高 | 召回路数过多、top_k 太大、rerank 候选过多 | 并行、超时、截断、分层 rerank |

面试中可以按“query 分析结果 → 各路召回结果 → 融合分数 → rerank 分数 → 最终上下文 → 答案引用”逐段排查。

## 高频面试问题与标准答案

### 1. 为什么 RAG 里常用混合检索，而不是只用向量检索？

标准答案：我理解向量检索解决的是语义相似，但企业知识库里很多问题不是纯语义匹配，比如型号、错误码、合同条款号、版本号、时间范围和权限范围。只用向量检索容易漏掉精确关键词，也可能把语义相近但业务边界不同的内容召回来。所以我一般会用 BM25 处理关键词和编号，用向量检索处理同义表达和口语问题，再用元数据和 ACL 控制业务边界。最后通过融合和 rerank 把候选排好，而不是简单把几路结果拼起来。

### 2. BM25 和向量检索各自适合什么场景？

标准答案：BM25 适合精确匹配，尤其是专有名词、编号、条款、错误码、产品型号这类不能被语义稀释的信息；它也比较可解释，能看到命中了哪些词。向量检索适合表达方式不一致但语义相近的问题，比如用户用口语问政策、问流程、问概念。实际项目里我不会二选一，而是让两者互补：关键词强的 query 提高 BM25 权重，语义化问题提高向量权重，融合后再交给 rerank。

### 3. 多路召回的结果怎么融合？

标准答案：我会先做去重，保留每个候选来自哪一路召回、原始分数和排名。融合上有几种选择：早期可以拼接去重加简单权重；如果各路分数比较稳定，可以做分数归一后加权；如果 BM25、向量和 FAQ 的分数尺度差异很大，我更倾向用 RRF 这种排名融合。RRF 不直接比较原始分数，而是看每个候选在各路里的排名，工程上比较稳定，也方便解释为什么某个文档靠前。

### 4. top_k 应该怎么设置？

标准答案：top_k 不能拍脑袋。我会先用评测集分别测单路召回的 recall@k，再测融合后的 recall@k、MRR 和 nDCG，看正确 chunk 能不能进入候选池以及排名是否靠前。然后再加入 rerank 和生成，观察答案准确率、引用准确率、幻觉率和 P95 延迟。一般做法是召回阶段稍微多拿一些候选，融合后截断，再让 rerank 处理一个可控数量，比如几十个候选里选出 5 到 10 个进上下文。最终取值要在效果和延迟预算之间平衡。

### 5. 混合检索召回很多噪声怎么办？

标准答案：我会先判断噪声来自哪一路召回，是 query 改写太宽、BM25 分词问题、向量模型不适配，还是 metadata 过滤不够。处理方式包括收紧召回条件、调整权重、限制每一路最大候选数、用 RRF 降低单一路异常高分的影响，以及在 rerank 前做轻量规则过滤。更重要的是把 bad case 固化到评测集里，避免只凭一次线上现象调参数。

### 6. 元数据过滤应该在召回前做还是召回后做？

标准答案：强约束要尽量前置，比如 tenant、ACL、文档状态、业务域，这些不应该等模型看到之后再处理；否则会有越权和上下文污染风险。弱约束可以后置或作为加权信号，比如文档类型、时间新鲜度、语言偏好等，因为前置太严可能导致召回不足。企业 RAG 里常见是前后结合：权限和租户强过滤，时间和类型作为软过滤或 boost，最终进入上下文前再做一次可见性校验。

### 7. 如果正确文档被召回了，但最终答案还是错，怎么排查？

标准答案：我会分段排查。第一看正确 chunk 在各路召回中的排名和分数，确认召回没问题；第二看融合后有没有被去重或截断掉；第三看 rerank 是否把它排到了前面；第四看上下文构造时有没有被压缩、合并或裁剪掉；最后看生成时是否没有正确引用上下文。RAG 的问题不能只看最终答案，要把 query 分析、召回、融合、重排、上下文和生成链路都打 trace。

### 8. RRF 相比加权分数融合有什么优点？

标准答案：RRF 的优点是不用强行比较不同召回源的原始分数。BM25 分数、向量相似度、FAQ 置信度的尺度不一样，直接加权很容易不稳定；RRF 用排名融合，只要一个候选在多路里都排得比较靠前，它的综合分就会上来。它实现简单、可解释、对分数分布变化不那么敏感，适合作为混合检索早期上线的稳健方案。缺点是它会丢掉原始分数差距，所以后面通常还要接 rerank。

### 9. 混合检索如何控制延迟？

标准答案：我会把召回做成并行，而不是 BM25 查完再查向量；每一路设置 top_k、timeout 和最大候选数。某一路超时可以降级，不让它拖垮整体链路。融合后要统一截断，避免 rerank 处理过多候选。对于高频 query，可以缓存 query 分析、Embedding 和部分检索结果。线上监控要拆开看 BM25 latency、vector latency、fusion latency、rerank latency 和总体 P95，这样才能知道瓶颈在哪。

### 10. 你怎么评估混合检索有没有提升？

标准答案：我会同时看离线评测和线上指标。离线先构建带标准答案或相关 chunk 标注的评测集，看 recall@k、precision@k、MRR、nDCG，以及加入 rerank 后的答案准确率和引用准确率。线上看用户点击、追问率、人工反馈、无答案率、延迟和成本。重点是和单向量检索、单 BM25 做对照实验，证明混合检索在目标场景确实提升，而不是只增加了复杂度。
