## 核心概念

### 1. 什么是 RAG 增量索引

RAG 增量索引是指知识库发生新增、修改、删除时，只处理变化的数据，并把变更同步到检索索引、元数据表、权限索引和缓存体系中，而不是每次都重建全量索引。

一句面试表达：**全量索引解决“从零构建”，增量索引解决“线上知识持续变化时如何低成本、可恢复、可追溯地保持检索结果正确”。**

### 2. 增量索引不只是新增向量

很多候选人会把增量索引理解成“新增文档就向量化后 upsert 到向量库”，这只覆盖了最简单场景。真实系统至少有四类变更：

| 变更类型 | 处理动作 | 面试关注点 |
| --- | --- | --- |
| 新增文档 | 解析、切分、Embedding、写索引 | 幂等、批量吞吐、可见性延迟 |
| 修改文档 | 找到旧 chunk，生成新 chunk，替换或新版本覆盖 | chunk_id 稳定性、引用失效、缓存失效 |
| 删除文档 | 标记删除或物理删除向量与元数据 | 防止旧向量被召回、审计可追溯 |
| 权限变化 | 更新 ACL / permission_version | 避免越权召回和缓存越权 |

面试中要强调：**删除和权限变化比新增更容易出事故，因为它们关系到旧数据是否还能被检索出来。**

### 3. 数据一致性的边界

RAG 索引通常不是强一致系统。文档库、对象存储、解析任务、向量库、关键词索引、缓存和权限服务之间存在异步链路，所以工程目标一般是：

- 对用户可解释的**最终一致性**：允许短暂延迟，但要有状态、版本和可观测指标。
- 对安全边界的**强校验**：检索命中后仍要按 tenant、ACL、permission_version 做服务端过滤。
- 对线上发布的**可回滚性**：新索引异常时能切回旧索引或旧别名。

一句话总结：**内容新鲜度可以有延迟，权限和删除不能靠“等索引慢慢同步”来兜底。**

### 4. 索引版本

索引版本是增量索引治理的核心字段。常见维度包括：

- `doc_version`：文档内容版本。
- `chunk_version`：切分策略或 chunk 内容版本。
- `embedding_version`：Embedding 模型与参数版本。
- `index_version`：当前线上索引批次或别名版本。
- `permission_version`：权限规则版本。

检索时把版本写入 trace，回答引用中也保留 chunk_id 与版本，后续才能复现“当时为什么召回这段内容”。

## 核心知识点

### 1. 推荐架构

```text
文档源 / CMS / 工单系统
  → 变更捕获 CDC / Webhook / 定时扫描
  → 变更事件队列
  → 解析与切分 Worker
  → Embedding Worker
  → 向量索引 + 关键词索引 + 元数据表
  → 索引别名切换 / 灰度发布
  → RAG 检索服务
```

关键设计点：变更事件要有 `event_id`、`doc_id`、`doc_version`、`operation`、`tenant_id` 和时间戳，Worker 根据这些字段做幂等处理和失败重放。

### 2. 变更捕获方式

| 方式 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 定时扫描 | 实现简单 | 延迟高，容易漏边界状态 | 小型知识库、低频更新 |
| Webhook | 实时性较好 | 依赖源系统可靠投递 | CMS、协同文档 |
| CDC / Binlog | 可追溯、适合高频更新 | 实现复杂，需要事件治理 | 企业知识库、业务数据库 |
| 手工触发重建 | 可控 | 依赖运营流程 | 重要文档批量发布 |

面试表达：**我不会只说“定时跑脚本”，而是会根据更新频率、实时性要求和源系统能力选择变更捕获方式，并用事件队列承接削峰和重试。**

### 3. 幂等写入

增量索引链路一定要支持重复消费，因为队列重试、Worker 崩溃和网络超时都可能导致同一事件处理多次。

```python
def build_chunk_id(doc_id: str, doc_version: int, chunk_no: int) -> str:
    # 中文注释：chunk_id 包含文档版本，避免新旧内容互相覆盖
    return f"{doc_id}:v{doc_version}:c{chunk_no}"

def handle_index_event(event: dict, metadata_store, vector_store):
    existing = metadata_store.get_event_status(event["event_id"])
    if existing == "indexed":
        return "skip"

    chunks = split_document(event["content"])
    for chunk_no, chunk_text in enumerate(chunks):
        chunk_id = build_chunk_id(event["doc_id"], event["doc_version"], chunk_no)
        vector = embed(chunk_text)
        # 中文注释：upsert 保证同一个 chunk_id 重复写入结果一致
        vector_store.upsert(
            id=chunk_id,
            vector=vector,
            metadata={
                "doc_id": event["doc_id"],
                "doc_version": event["doc_version"],
                "tenant_id": event["tenant_id"],
                "deleted": False,
            },
        )

    metadata_store.mark_event_status(event["event_id"], "indexed")
    return "indexed"
```

面试重点：**幂等键通常不是用户问题，而是 event_id、doc_id、doc_version、chunk_no 这类确定性字段。**

### 4. 修改文档的处理

文档修改后有两种常见策略：

| 策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 原地覆盖 | 旧 chunk_id 被新向量覆盖 | 索引体积小 | 难复现旧答案，引用可能漂移 |
| 新版本写入 + 旧版本下线 | 新 chunk 使用新版本 ID，旧版本标记不可见 | 可回滚、可审计 | 需要清理旧版本和版本过滤 |

生产系统更推荐 **新版本写入 + 原子切换可见性**。先把新版本索引构建好，通过验证后更新 `active_doc_version` 或索引别名，再让检索流量看到新版本。

### 5. 删除文档的处理

删除要同时处理三件事：

1. 元数据表标记 `deleted=true`，检索服务强制过滤。
2. 向量库和关键词索引异步物理删除。
3. 语义缓存、检索缓存和引用缓存按 doc_id / index_version 失效。

```python
def filter_retrieval_hits(hits: list[dict], active_docs: dict[str, int]) -> list[dict]:
    visible_hits = []
    for hit in hits:
        doc_id = hit["metadata"]["doc_id"]
        doc_version = hit["metadata"]["doc_version"]
        if active_docs.get(doc_id) != doc_version:
            continue
        if hit["metadata"].get("deleted"):
            continue
        visible_hits.append(hit)
    return visible_hits
```

面试里要说清楚：**即使向量库删除是异步的，检索服务也必须用元数据过滤兜住，不允许已删除文档继续出现在答案里。**

### 6. 索引别名与蓝绿切换

大规模重建索引或更换 Embedding 模型时，不建议边写边让线上直接读新索引。更稳妥的方式是：

1. 线上读 `rag_index_current`。
2. 后台构建 `rag_index_20260622_v2`。
3. 用评测集验证召回率、权限过滤、延迟和引用质量。
4. 小流量灰度读新索引。
5. 通过后把别名从旧索引切到新索引。
6. 保留旧索引一段时间用于回滚。

这个问题经常考察候选人是否理解：**索引发布也是一次线上发布，需要灰度、监控和回滚。**

### 7. 增量索引与缓存联动

RAG 常见缓存包括查询改写缓存、检索结果缓存、语义缓存和最终答案缓存。文档变更后要考虑：

- 新增文档：未必需要全量清缓存，但高频查询可能要预热。
- 修改文档：按 doc_id、知识域、index_version 失效相关缓存。
- 删除文档：必须清理包含该 doc_id / chunk_id 的检索结果和答案缓存。
- 权限变更：按 permission_version 或 ACL 版本隔离缓存 key。

缓存 key 示例：

```text
tenant_id:user_role:query_hash:index_version:permission_version:prompt_version
```

面试表达：**缓存命中前也要校验索引版本和权限版本，否则缓存可能绕过最新的删除或权限变更。**

### 8. 失败恢复与补偿

增量索引链路常见失败包括解析失败、Embedding 超时、向量库写入失败、部分 chunk 成功部分失败。成熟方案需要：

- 事件状态机：`pending → parsing → embedding → indexing → indexed / failed`。
- 失败重试：只对临时错误重试，参数错误和格式错误进入人工队列。
- 死信队列：超过重试次数后保留事件、错误原因和原始输入引用。
- 对账任务：定期比较文档源版本、元数据表版本和索引版本。
- 补偿重建：发现缺 chunk、旧版本残留、删除未生效时定向重放事件。

面试重点：**不能只依赖 Worker 成功日志，要有对账，因为索引不一致往往是静默发生的。**

### 9. 质量验证指标

增量索引上线后重点看：

| 指标 | 说明 |
| --- | --- |
| 索引延迟 | 文档变更到可检索的时间 |
| 事件积压 | 队列长度、最老事件等待时间 |
| 索引成功率 | 分解析、Embedding、写入阶段统计 |
| 删除生效时间 | 删除后不再可检索的时间 |
| 权限误召回率 | 无权限数据是否被召回 |
| 召回质量 | 新旧索引 Recall@K、MRR、人工评测 |
| 引用失效率 | 答案引用的 chunk 是否仍有效 |

面试中可以补一句：**对 RAG 来说，索引延迟是体验问题，权限误召回是安全事故，优先级不一样。**

## 高频面试问题与标准答案

### Q1：RAG 知识库每天都有新增和修改文档，你会怎么设计增量索引？

标准答案：我会把它设计成事件驱动链路。源系统通过 Webhook、CDC 或定时扫描产生变更事件，事件里带 doc_id、doc_version、operation、tenant_id 和 event_id。后面通过队列解耦解析、切分、Embedding 和索引写入。写入时用 doc_id、doc_version、chunk_no 生成稳定 chunk_id，保证重复消费是幂等的。修改文档我更倾向写新版本并切换 active_doc_version，而不是直接覆盖旧 chunk，这样方便回滚和复现。最后还要有索引延迟、失败率、事件积压和对账任务，确保不是只看 Worker 成功就认为索引一致。

### Q2：删除文档后，如何保证 RAG 不再召回旧内容？

标准答案：我不会只依赖向量库物理删除，因为删除可能是异步的，也可能失败。我的做法是先在元数据表把文档标记为 deleted 或更新 active_doc_version，检索服务在返回结果前必须做服务端过滤；同时异步删除向量库和关键词索引里的旧 chunk，并按 doc_id、chunk_id、index_version 清理检索缓存和答案缓存。对高风险场景，还要监控删除生效时间，并用对账任务检查是否还有旧 chunk 能被召回。面试里我会强调：删除和权限属于安全边界，不能只靠最终一致性。

### Q3：文档修改后，chunk_id 应该保持不变还是生成新版本？

标准答案：要看业务是否需要审计和回滚。Demo 可以覆盖原 chunk_id，但生产环境我更推荐生成带 doc_version 的新 chunk_id，然后通过 active_doc_version 或索引别名控制线上可见版本。这样旧答案引用可以复现，新版本质量有问题也能回滚。缺点是索引体积会变大，所以需要旧版本清理策略。这个问题本质是在索引体积和可追溯性之间取舍，企业知识库通常更看重可追溯和可回滚。

### Q4：增量索引如何做到幂等？

标准答案：核心是给每个变更事件和每个 chunk 都设计确定性 ID。事件层用 event_id 记录处理状态，防止同一事件重复执行产生脏数据；chunk 层用 doc_id、doc_version、chunk_no 生成 chunk_id，向量库使用 upsert。Worker 在每个阶段记录状态，比如 parsing、embedding、indexing、indexed，失败后可以从明确阶段重试。这样即使队列重复投递、Worker 中途崩溃或网络超时，也不会写出多份不可控的数据。

### Q5：更换 Embedding 模型时，RAG 索引怎么升级？

标准答案：我会把它当成一次索引发布，而不是在线上原地替换。先用新 Embedding 模型构建一套新索引，保留 embedding_version 和 index_version；然后用评测集比较新旧索引的 Recall@K、MRR、引用质量、权限过滤和延迟；通过后小流量灰度，再把线上索引别名切到新版本。旧索引会保留一段时间用于回滚。因为不同 Embedding 空间不可混用，新旧向量不能简单放在同一个索引里混查。

### Q6：如何处理增量索引中的失败和部分成功？

标准答案：我会用状态机和补偿机制处理。每个事件都有 pending、parsing、embedding、indexing、indexed、failed 等状态。临时错误比如模型超时、向量库 5xx 可以有限重试；文档格式损坏、解析不支持这类问题进入死信队列，并保留错误原因和原始文档引用。对于部分 chunk 成功的情况，要么整批按版本不可见直到全部成功，要么通过对账任务发现缺失 chunk 后补偿重放。关键是不要让半成品索引直接对线上可见。

### Q7：增量索引和 RAG 缓存有什么关系？

标准答案：关系很大。RAG 里可能缓存查询改写、检索结果、语义缓存和最终答案。文档修改或删除后，如果缓存 key 里没有 index_version、doc_version 或 permission_version，就可能返回旧引用甚至越权内容。我的做法是缓存 key 带上租户、角色、索引版本、权限版本和 prompt_version；删除文档时按 doc_id 或 chunk_id 反向清理相关缓存；缓存命中前也要做版本和权限校验。也就是说，缓存是性能优化，不能绕过索引一致性和权限边界。

### Q8：如果业务要求“文档更新后 1 分钟内可检索”，你会怎么保证？

标准答案：我会先把它拆成可观测的链路指标：变更捕获延迟、队列等待、解析耗时、Embedding 耗时、索引写入耗时和缓存失效耗时。架构上用事件队列和独立 Worker 池承接增量任务，对高优先级知识域设置优先级队列；Embedding 和索引写入要做批处理但不能无限等批。线上监控最老事件等待时间和 P95 索引延迟，超过阈值告警。如果索引延迟影响业务，还可以先展示“知识库正在更新”的状态，避免用户误以为系统已经使用了最新文档。

### Q9：如何做增量索引的数据对账？

标准答案：我会定期比较三类数据：源文档系统里的 doc_id 和 doc_version，索引元数据表里的 active_doc_version，以及向量库/关键词索引里的 chunk 数量和版本。对账结果分几类：源系统有但索引没有，说明漏建；索引有但源系统已删除，说明删除未生效；版本不一致，说明旧内容残留；chunk 数量异常，说明切分或写入部分失败。发现问题后不是人工猜，而是按 doc_id 定向重放变更事件或触发局部重建。

### Q10：面试官问“为什么不每天全量重建一次索引”，你怎么回答？

标准答案：全量重建简单，但不一定满足实时性和成本要求。文档量大时，全量解析、Embedding 和写索引成本很高，也会拉长知识更新可见时间。我的方案通常是日常走增量索引，保证新增、修改、删除能较快同步；同时保留周期性全量校验或低峰全量重建，用来消除长期漂移和历史脏数据。也就是说，不是完全不要全量，而是增量负责时效，全量负责校准和兜底。
