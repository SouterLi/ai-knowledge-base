## 核心概念

### 1. 澄清追问是什么

澄清追问是指 AI 应用在用户意图、约束、参数或风险边界不明确时，不急着生成最终答案或执行工具，而是通过一到两轮有目标的问题，把模糊需求转成可执行的结构化任务。

一句面试表达：**澄清追问不是闲聊，而是把不确定的自然语言输入补齐成可验证、可执行、可审计的任务参数。**

例如用户说：

```text
帮我把这个报表发给客户。
```

系统不能直接执行，因为至少缺少：

- 发给哪个客户；
- 使用哪个报表版本；
- 通过邮件、IM 还是 CRM；
- 是否需要脱敏；
- 发送前是否需要用户确认。

一个更合理的追问是：

```text
请确认要发送给哪位客户，以及是否使用当前最新报表版本？如果涉及客户隐私，我会先生成预览供你确认。
```

### 2. 模糊性的四种来源

| 类型 | 示例 | 风险 |
| --- | --- | --- |
| 意图模糊 | “帮我处理一下这个投诉” | 路由到错误流程 |
| 槽位缺失 | “订明天的会议室”但没说人数和时间 | 工具参数不完整 |
| 约束冲突 | “越详细越好，但控制在 100 字以内” | 输出不可满足 |
| 风险边界不清 | “把合同发出去”但没说收件人和脱敏要求 | 数据泄露或误操作 |

面试中不要只说“让模型再问一句”。成熟方案要先判断模糊属于哪一类，再决定追问、默认值、拒答、人工确认或降级处理。

### 3. 槽位与对话状态

槽位（Slot）是完成一个任务所需的关键字段。例如“创建会议”任务通常需要：

| 槽位 | 示例 | 是否必填 |
| --- | --- | --- |
| title | 项目周会 | 是 |
| start_time | 明天 10:00 | 是 |
| duration | 30 分钟 | 可默认 |
| participants | 张三、李四 | 是 |
| location | 3 号会议室 | 可选 |

对话状态不是简单保存聊天记录，而是保存当前任务的结构化进度：

```json
{
  "intent": "create_meeting",
  "slots": {
    "title": "项目周会",
    "start_time": null,
    "duration": "30m",
    "participants": ["张三", "李四"]
  },
  "missing_required_slots": ["start_time"],
  "risk_level": "low"
}
```

澄清问题应该围绕 `missing_required_slots` 或高风险字段生成，而不是重复问用户已经说过的信息。

### 4. 置信度与追问阈值

AI 应用通常会同时产生：

- **意图置信度**：系统是否知道用户想做什么；
- **槽位置信度**：提取出的字段是否可信；
- **执行风险等级**：是否涉及写操作、资金、权限、隐私；
- **上下文一致性**：多轮对话里的新输入是否覆盖旧输入。

追问阈值要按场景分级：

| 场景 | 策略 |
| --- | --- |
| 低风险问答 | 可直接回答，并说明假设 |
| 信息抽取 | 缺少关键字段时追问 |
| 只读工具 | 低置信时可追问或返回候选项 |
| 写操作工具 | 必填参数缺失必须追问，执行前通常要确认 |
| 高风险业务 | 即使字段齐全，也可能需要二次确认或人工审核 |

关键观点：**低置信不一定都追问，高风险也不一定因为高置信就直接执行。**

### 5. 澄清、确认与拒答的区别

| 动作 | 触发条件 | 示例 |
| --- | --- | --- |
| 澄清 | 信息不足或存在多个可能解释 | “你指的是退款申请还是查询退款进度？” |
| 确认 | 信息基本齐全，但执行有副作用或风险 | “我将向客户 A 发送脱敏版报表，是否确认？” |
| 拒答 | 请求违反权限、安全或合规要求 | “我不能帮你导出无权限客户的数据。” |

面试里常见坑是把三者混在一起。澄清解决的是“不知道该怎么做”；确认解决的是“知道怎么做，但执行前要让用户承担明确选择”；拒答解决的是“即使用户确认也不能做”。

## 核心知识点

### 1. 典型架构

一个可落地的澄清追问链路通常是：

```text
用户输入
  → 会话上下文读取
  → 意图识别与槽位抽取
  → 置信度与风险评估
  → 缺失槽位 / 冲突约束检测
  → 决策：直接回答 / 追问 / 确认 / 拒答 / 人工介入
  → 状态更新与 Trace 记录
```

重点是把“是否追问”做成一个明确的决策节点，而不是把所有事情都交给一个大 Prompt 自由发挥。这样才能评估、回放和调优。

### 2. 追问决策规则

可以用规则、模型或混合方式决策。面试中推荐讲“规则兜底 + 模型理解”的组合：

```python
from dataclasses import dataclass


@dataclass
class ClarificationDecision:
    action: str
    reason: str
    missing_slots: list[str]


def decide_next_action(intent_confidence: float, missing_slots: list[str], risk_level: str) -> ClarificationDecision:
    # 中文注释：意图不清时先问意图，不能用高风险确认替代意图澄清
    if intent_confidence < 0.7:
        return ClarificationDecision("clarify", "用户意图置信度不足", [])

    # 中文注释：高风险写操作不能因为模型置信度高就直接执行
    if risk_level == "critical":
        if missing_slots:
            return ClarificationDecision("clarify", "高风险任务缺少必填参数", missing_slots)
        return ClarificationDecision("confirm", "高风险任务执行前需要用户确认", [])

    if missing_slots:
        return ClarificationDecision("clarify", "缺少必填槽位", missing_slots)

    return ClarificationDecision("execute", "信息完整且风险可控", [])
```

这段代码表达的是工程原则：**先确认意图是否清楚，再按风险和槽位决定追问、确认或执行**。高风险不代表跳过意图澄清；信息完整也不代表可以绕过风险确认。

### 3. 槽位 Schema 要区分必填、可默认、需确认

任务槽位不应该只有字段名，还要包含提取方式、校验规则、默认值和确认策略。

```yaml
intent: send_report
slots:
  recipient:
    required: true
    confirm_before_execute: true
  report_version:
    required: false
    default: latest
    confirm_before_execute: true
  channel:
    required: false
    default: email
  pii_policy:
    required: true
    enum: [masked, original]
    confirm_before_execute: true
```

面试表达重点：

1. 必填字段缺失要追问；
2. 有默认值的字段可以使用默认值，但要在回复里显式说明；
3. 涉及隐私、资金、权限、外发动作的字段，即使已填也要确认；
4. Schema 变化要版本化，否则多轮对话状态可能和新逻辑不兼容。

### 4. 追问问题要一次解决关键不确定性

好的追问应该满足四点：

- **具体**：明确缺哪个字段；
- **低负担**：尽量给候选项，而不是开放式长问；
- **可执行**：用户回答后能直接更新槽位；
- **不重复**：不问已经确认过的信息。

对比：

```text
差：你能说得更清楚一点吗？
好：你想查询退款进度，还是发起退款申请？如果是发起退款，请补充订单号。
```

如果缺多个字段，通常不要一次性抛出长表单。可以按优先级分轮：

1. 先确认意图；
2. 再补必填槽位；
3. 最后确认高风险动作。

### 5. 多轮状态合并要处理覆盖与冲突

用户后续输入可能补充、修改或否定前面的信息：

```text
用户：明天上午安排和王总的会。
助手：请确认具体时间？
用户：10 点，地点改成线上。
```

这里“10 点”补充了 `start_time`，“地点改成线上”覆盖了旧的 `location`。状态合并不能只追加文本，而要做结构化更新：

```python
def merge_slots(current: dict, extracted: dict) -> dict:
    merged = current.copy()
    for key, value in extracted.items():
        if value is None:
            continue
        # 中文注释：用户新一轮明确给出的槽位优先级高于历史推断值
        merged[key] = {
            "value": value,
            "source": "latest_user_turn",
            "confirmed": False,
        }
    return merged
```

对高风险字段，覆盖后应重新确认。例如用户把“发给内部同事”改成“发给外部客户”，风险等级已经变化，不能沿用之前的确认结果。

### 6. 追问不要破坏用户体验

澄清追问能提升准确性，但过度追问会让用户觉得系统“很笨”。工程上要做几类控制：

| 控制点 | 做法 |
| --- | --- |
| 最大追问轮数 | 超过 2～3 轮后给出人工入口或候选方案 |
| 可默认字段 | 使用安全默认值，并在回复中说明 |
| 候选项 | 给 2～4 个可选项，减少用户输入成本 |
| 渐进式收集 | 先收最关键字段，不一次性问所有字段 |
| 低风险假设 | 可以边说明假设边回答 |

例如：

```text
我先按“内部分享、使用最新版本、脱敏数据”这三个默认假设生成预览；如果你要外发给客户，请再确认收件人。
```

这比连续追问三个问题更适合低风险预览场景。

### 7. 工具调用前的澄清和确认

Function Calling 或 Agent 工具调用中，澄清追问尤其重要。常见流程是：

```text
模型生成工具意图
  → 应用层校验工具权限
  → 校验必填参数和业务规则
  → 缺参数则追问
  → 高风险写操作则确认或审批
  → 执行工具
```

不要让模型自己决定“参数差不多就调用”。应用层要拒绝不完整或不安全的工具调用。

```python
def validate_tool_call(tool_name: str, args: dict, schema: dict) -> list[str]:
    errors = []
    for field, rule in schema["slots"].items():
        value = args.get(field)
        if rule.get("required") and value in (None, ""):
            # 中文注释：缺少必填字段时返回给追问生成器，而不是直接调用工具
            errors.append(f"missing:{field}")
            continue
        if value not in (None, "") and "enum" in rule and value not in rule["enum"]:
            errors.append(f"invalid_enum:{field}")
    return errors
```

面试中可以补一句：**模型负责提出调用意图，应用层负责参数校验、权限校验、风险确认和最终执行。**

### 8. 澄清问题也要可评估

澄清追问不是体验细节，而是可以量化的工程能力。常见指标包括：

| 指标 | 含义 |
| --- | --- |
| clarification_rate | 进入追问的请求占比 |
| clarification_success_rate | 追问后成功完成任务的比例 |
| unnecessary_clarification_rate | 本可直接处理却追问的比例 |
| missing_slot_after_clarification | 追问后仍缺字段的比例 |
| user_abandon_rate | 追问后用户放弃的比例 |
| tool_param_error_rate | 工具参数错误率 |
| risky_action_without_confirm | 高风险动作未确认比例 |

面试里如果能说出“追问率不是越高越好”，会比单纯说“加一个澄清 Prompt”更有工程深度。追问的目标是降低错误执行和返工，而不是把责任都推回给用户。

### 9. Prompt 设计要约束追问输出格式

如果用 LLM 生成追问，建议输出结构化结果，便于前端渲染和状态更新。

```json
{
  "action": "clarify",
  "question": "你想查询退款进度，还是发起退款申请？",
  "options": [
    {"label": "查询退款进度", "fills": {"intent": "query_refund_status"}},
    {"label": "发起退款申请", "fills": {"intent": "create_refund"}}
  ],
  "required_slots": ["intent"]
}
```

这样前端可以展示按钮，用户点击后直接填槽位；服务端也能记录本次追问解决了哪个不确定性。

### 10. 常见设计误区

| 误区 | 问题 | 更好的做法 |
| --- | --- | --- |
| 一律追问 | 用户体验差，完成率下降 | 按风险和缺失字段决定 |
| 一律猜测 | 容易误执行和幻觉 | 低风险可说明假设，高风险必须确认 |
| 只靠 Prompt | 不可控、不可评估 | 应用层维护状态和策略 |
| 追问太泛 | 用户不知道怎么回答 | 问具体字段，给候选项 |
| 不记录状态 | 多轮重复问、无法回放 | 保存槽位、版本、决策原因 |
| 不做评估 | 无法判断追问策略好坏 | 建立指标和样本回归 |

## 高频面试问题与标准答案

### Q1：用户问题不完整时，你的 AI 应用会怎么处理？

标准答案：我不会直接把问题丢给大模型自由发挥，而是先做意图识别和槽位抽取，判断缺的是意图、必填参数还是风险确认。如果是低风险问答，可以说明假设后先回答；如果是工具调用或写操作，缺少必填参数就追问，高风险动作还要二次确认。追问问题会尽量具体，比如给用户两个候选意图或要求补一个订单号，而不是泛泛地说“请描述清楚一点”。

### Q2：怎么判断应该追问还是直接回答？

标准答案：我会综合看三个因素：意图置信度、关键槽位是否完整、执行风险等级。低风险内容生成类任务，如果缺的是偏好信息，可以按默认假设回答并提示用户可调整；但如果是外发邮件、退款、改权限这类有副作用的任务，哪怕模型置信度高，也要校验参数和确认。简单说，低风险可以适度猜测，高风险必须收敛到明确参数和明确确认。

### Q3：澄清追问和意图识别是什么关系？

标准答案：意图识别是判断用户想做什么，澄清追问是在意图或参数不确定时把任务补齐。实际链路里一般先做意图识别，如果意图置信度低，就先追问意图，例如“你是要查询退款进度还是发起退款”；如果意图明确但槽位缺失，再追问参数，例如订单号、时间、收件人。不要在意图不清楚时直接追问细节，否则很容易问错方向。

### Q4：如果用户一句话里缺很多参数，要一次性全问吗？

标准答案：不建议一上来抛一个很长的表单式问题。我的做法是按优先级渐进收集：先确认意图，再补最关键的必填槽位，最后对高风险动作做确认。对于可以安全默认的字段，比如会议时长默认 30 分钟、报表版本默认最新版，可以在回复里说明默认值，不一定都追问。这样既能保证任务可执行，也能减少用户负担。

### Q5：如何避免 AI 一直追问，导致体验很差？

标准答案：要给追问策略加边界。比如限制最大追问轮数，超过后给候选方案、生成预览或转人工；对低风险字段使用安全默认值；尽量用选择题替代开放式问题；并且监控 user_abandon_rate 和 unnecessary_clarification_rate。追问不是越多越安全，过度追问会降低完成率，所以要用数据看追问是否真的降低了错误执行和返工。

### Q6：多轮对话里，用户修改了之前的信息怎么办？

标准答案：不能只把新消息追加到 Prompt，要维护结构化对话状态。每轮都抽取新的槽位，并和历史槽位合并；用户明确说“改成”“不是”“换成”的内容，要覆盖历史推断值。对于高风险字段，比如收件人从内部同事改成外部客户，之前的确认要失效，重新进入确认流程。这样可以避免系统拿旧信息执行新任务。

### Q7：在 Function Calling 场景下，模型生成了工具调用但参数不完整怎么办？

标准答案：应用层要先做 Schema 和业务规则校验，不能让模型参数差不多就调用工具。缺少必填字段时，把缺失字段交给追问生成器，让用户补齐；枚举错误或权限不满足时，要拒绝或给出可选项；如果是写操作，还要生成幂等键并做确认。我的原则是模型负责提出工具意图，真正的参数校验、权限判断和执行决策必须在服务端。

### Q8：高风险操作为什么不能只靠用户一句“可以”就执行？

标准答案：因为高风险操作需要确认的是明确动作、明确对象和明确后果。比如“把报表发出去”这句话即使用户说可以，也可能没说明发给谁、是否脱敏、用哪个版本。更合理的确认是把关键参数复述出来：“我将向客户 A 发送脱敏版 6 月经营报表，是否确认？”必要时还要走审批或人工审核。确认不是形式上的 yes/no，而是让用户确认具体、可审计的执行计划。

### Q9：澄清问题怎么生成才算好？

标准答案：好的澄清问题要具体、低负担、能更新状态。比如意图不清时给两个候选项，参数缺失时只问缺的关键字段，并尽量用按钮或枚举让用户选择。问题本身最好结构化输出，包含 question、options、required_slots，这样前端能渲染，服务端也能知道本次追问解决了什么。差的追问是“请补充更多信息”，用户不知道该补什么，系统也没法稳定填槽位。

### Q10：如何评估澄清追问模块做得好不好？

标准答案：我会同时看质量和体验。质量上看追问后任务完成率、工具参数错误率、缺失槽位残留率、高风险动作未确认比例；体验上看追问率、无必要追问率、追问后的用户放弃率和平均追问轮数。还会把线上坏 Case 做成回归样本，比如本该追问却直接执行、本可回答却反复追问、用户修改信息但系统没覆盖。这样才能持续调阈值和策略。

### Q11：如果模型对用户意图置信度很高，还需要追问吗？

标准答案：要看风险和业务后果。高置信只能说明模型比较确定用户想做什么，不代表参数完整、权限满足或执行安全。比如模型很确定用户要退款，但订单号、金额、原因、是否符合政策仍然要校验；如果涉及真实退款，还需要确认或审批。所以我会把意图置信度作为一个输入，而不是唯一依据，最终决策还要结合槽位完整性、权限和风险等级。

### Q12：面试官问“为什么不让大模型自己决定追问”，你怎么答？

标准答案：可以让大模型参与生成追问，但不能完全让它决定策略。因为是否追问涉及业务风险、权限、必填字段、默认值和用户体验，这些需要可配置、可审计、可评估。我的设计是应用层先根据 Schema、置信度和风险等级决定 action，比如 execute、clarify、confirm、reject；如果 action 是 clarify，再让模型生成自然、简洁的问题。这样既利用了模型的表达能力，又保留了工程控制。
