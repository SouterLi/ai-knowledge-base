# LLM 工作流编排与 Human-in-the-loop

## 主题定位

这篇笔记讨论的不是「怎么把几个 Prompt 串起来」，而是：**当大模型要进入退款、合同审查、工单流转、内容发布这类真实业务流程时，如何用工作流把 LLM 嵌进一条可暂停、可恢复、可审计、必要时由人接管的业务链路里**。Human-in-the-loop（HITL，人在回路）在这里也不是「模型不行就找人兜底」这么简单，而是和权限、合规、副作用一起构成风险治理的一部分。

如果你已经读过同知识库下的 Agent 主题，可以这样区分边界：**Agent 文档侧重「模型如何在循环里选工具、改计划」；本文侧重「业务状态机如何编排节点、何时必须停下来等人、失败后如何从中间恢复」**。两者经常组合使用——外层是工作流状态机，某个步骤内部可以跑一段受预算限制的 Agent 子流程，但「能不能退款」「能不能发布」仍应由工作流策略和人工节点说了算。

---

## 一、核心概念：从「一次问答」到「一条可治理的流程」

很多团队第一次做 LLM 应用，形态是同步 API：用户提问，后端调模型，返回答案。这在 Demo 阶段足够，但一旦业务要求「先分类再检索再生成再合规检查再人工盖章再落库」，单次 API 调用就承载不了：**谁记录当前走到哪一步、某一步超时怎么办、人工审了两天之后从哪里继续、同一条请求重试会不会退两次款**。

工作流编排要解决的，正是这类**跨步骤、跨时间、跨服务**的问题。你可以把它理解成：为业务定义一张「允许发生的状态迁移图」，每个迁移由明确的节点触发——有的是规则，有的是 LLM，有的是外部工具，有的是人在审核台上点下「通过」或「驳回」。整条链路共享一份**流程上下文**（例如工单 ID、订单号、当前分类、模型草稿、审核意见），每个节点只读写自己契约内的字段，而不是把全部历史聊天记录无差别塞给下一个模型。

Human-in-the-loop 嵌在这条链路里，出现在「自动化不再安全或不再合理」的位置。典型触发包括：模型置信度低、涉及退款/发信/改权限等副作用、合规敏感领域、规则引擎与模型结论冲突、用户主动要求升级人工、或自动化已重试仍失败。进入人工节点时，流程进入类似 `waiting_for_review` 的等待态，**上下文必须落库**——否则服务重启、审核跨天、审核员换班都会导致「审完了但流程不知道往哪走」。

用一句话收束面试里常问的定位：**LLM 工作流 = 把模型能力放进业务状态机；HITL = 在状态机上为高风险迁移增加「必须经人确认」的边。**

## 二、核心知识点

### 1. 工作流的六要素：整条链路的「骨架」

要把知识点和主题串起来，最好先看清工作流在工程上到底由什么组成，后面讲的 HITL、重试、权限都挂在这六根柱子上。

**触发（Trigger）** 决定流程何时启动：用户一次提交、定时任务、或消息队列里的业务事件。触发时要带上幂等键（例如 `request_id`），避免网络重试或前端双击创建两条并行流程。

**步骤/节点（Step/Node）** 是流程里真正干活的单元。一个节点可能是「调用 LLM 做意图分类」，也可能是「调用退款 API」，或「打开人工审核台」。节点之间通过**有类型的输入输出**连接，而不是靠模型自由发挥串联。

**状态（State）** 描述「这一条流程实例此刻处在什么阶段」。除了粗粒度的 `running/succeeded/failed`，生产里几乎一定会有 `waiting_for_review` 这类**等人**的状态。状态存在数据库里，而不是只存在某台 Worker 内存里，这样进程重启、扩缩容都不会丢进度。

**迁移（Transition）** 是「满足什么条件，从哪个状态到哪个状态」。迁移条件可以是规则（金额大于 1 万走人工）、可以是上一步输出（分类为 `refund` 进入退款子流程）、也可以是外部事件（审核员提交 decision）。**LLM 可以参与判断迁移条件，但不应单独拥有绕过规则的迁移权。**

**上下文（Context）** 是跨节点共享的结构化数据：业务字段（订单号、用户 ID）、节点产出（分类结果、检索片段、模型草稿）、审核记录（谁、何时、何种 decision）。上下文要分层管理：业务层字段长期保留；模型 Prompt 和原始检索可归档追溯；临时变量可设置 TTL。每个节点应遵循**最小可见原则**——分类节点不需要看到完整合同正文，审核节点则需要看到模型建议和相关证据。

**策略（Policy）** 横跨所有节点：谁能触发这条 workflow、某节点允许调用哪些工具、单流程最大步数/token/耗时、失败重试几次、哪些错误必须进人工。策略是「主题里的 HITL」能和「编排」绑在一起的纽带：没有策略，人工节点就只是 UI 上的按钮，而不是治理体系的一部分。

这六要素串起来，回答「和主题的关系」：**编排解决的是节点与状态；HITL 解决的是在高风险迁移上由人行使最终决策权，且决策被写回 Context 驱动后续迁移。**

### 2. DAG、状态机与 Agent：三种「控制流」如何配合

面试里常问「用 DAG 还是状态机」。脱离业务谈选型没有意义，关键是**你的不确定性主要来自「步骤顺序」还是「业务生命周期」还是「开放探索」**。

**DAG（有向无环图）** 适合步骤依赖相对固定、分支有限的链路，例如：解析上传文件 → 切块 → 向量化 → 检索 → 生成摘要 → 规则校验。DAG 的优势是可视化清晰、并行好做（无依赖的节点可同时跑）、回放方便。劣势是**对「工单从打开到关闭」这类长生命周期业务**，纯 DAG 往往要画很多「绕回来」的边，反而别扭。

**状态机** 适合生命周期明确、状态名就是业务语言的场景：工单 `open → pending_review → approved → resolved`，或退款 `draft → risk_check → waiting_for_review → executed`。状态机的优势是**暂停/恢复天然匹配**——`waiting_for_review` 可以停几天；迁移条件可以和权限、审计强绑定。LLM 工作流 + HITL 在生产里最常见的外层形态就是状态机。

**Agent（开放式循环）** 适合目标清晰但路径不确定的探索任务，例如「帮我在三个系统里查清楚这笔订单为何异常」。Agent 灵活，但带来循环、成本漂移、难审计等问题。工程上常见做法是：**外层状态机定边界，某一状态内部运行「有步数上限、工具有白名单」的 Agent 子流程**，子流程结束只把结构化结果写回 Context，再由状态机决定下一步——而不是让 Agent 直接执行退款。

三者关系可以叙述为：**状态机管「业务走到哪」；DAG 管「这一步里面有哪些固定子步骤」；Agent 管「这一步里需要动态探索的那一小段」。** HITL 是状态机上的特殊迁移：从自动态进入等待人工，再人工触发迁出。

### 3. 节点契约：让 LLM 节点和普通节点「同一种语言」说话

工作流要可测、可恢复，每个节点必须有**契约**，而不是「调一下模型返回字符串」。契约至少包括：输入 Schema、输出 Schema、可能的状态枚举、错误分类、超时与资源预算、需要写入审计的字段。

从主题角度看，契约是把「LLM 的不确定性」关进业务能接受的范围。例如意图分类节点输出不仅是 `category: refund`，还应输出 `confidence` 和 `reason`；工作流引擎读 `confidence < 0.7` 时**强制迁移到人工**，而不是让下游退款节点继续自动执行。这样 HITL 的触发来自**显式策略**，而不是事后发现模型猜错了。

错误分类要和迁移策略对应。可重试错误（网络超时、429）适合退避后重试同一节点；不可重试错误（参数非法、权限不足）应进入 `failed` 或 `need_human`；已产生副作用的错误要走幂等查询 + 补偿，而不是简单重跑整个流程。

下面是一段示意代码，表达「节点返回的不是纯文本，而是驱动状态机的结构化结果」：

```python
from dataclasses import dataclass
from typing import Literal

@dataclass
class WorkflowStepResult:
    # 中文注释：status 直接参与工作流引擎的迁移判断
    status: Literal["ok", "retryable_error", "blocked", "need_human"]
    output: dict
    error_code: str | None = None
    reason: str | None = None

def classify_ticket(ticket: dict) -> WorkflowStepResult:
    # 省略：调用 LLM 或规则模型得到 category、confidence
    category, confidence = llm_classify(ticket["content"]), 0.62
    if ticket.get("vip") and category == "refund":
        return WorkflowStepResult(
            status="need_human",
            output={"category": category, "confidence": confidence},
            reason="VIP 退款需人工确认",
        )
    if confidence < 0.7:
        return WorkflowStepResult(
            status="need_human",
            output={"category": category, "confidence": confidence},
            reason="分类置信度不足",
        )
    return WorkflowStepResult(status="ok", output={"category": category, "confidence": confidence})
```

**和主题的关系：** 没有契约，HITL 只能事后补救；有契约，才能在「分类」这一环就把流程导进 `waiting_for_review`，把人工审核变成设计内的一环，而不是线上事故处理。

### 4. Human-in-the-loop：触发、审核台与决策如何写回流程

HITL 要设计清楚三件事：**什么时候停、人看到什么、人做决定后流程怎么走**。

**何时触发** 应写成可测试的策略，而不是运营口头约定。除了上文置信度与 VIP 规则，还包括：涉及资金变动、对外发送、权限变更；合规清单内的领域（医疗、法律、未成年人）；规则引擎与模型结论不一致；同一流程在自动重试后仍失败；用户点击「转人工」。多条规则可以叠加，命中任一条即进入等待人工状态。

**审核台展示什么** 决定人工决策质量。至少应包含：触发原因（为何不能自动往下走）、模型或系统的建议动作（不是裸结论，而是「建议退款 199 元，依据订单状态与规则 R3」）、可追溯证据（检索片段、工具返回摘要、规则命中记录）、当前业务对象的关键字段。审核员需要能在**不打开原始 Prompt 日志**的情况下做判断，但工程师事后必须能根据 `workflow_id` 回放完整链路。

**决策如何写回** 常见 decision 包括：`approve`（按建议执行）、`reject`（终止并通知用户）、`edit`（修改参数后执行，例如改退款金额）、`return`（打回上一自动节点或让用户补充材料）。每种 decision 应对应明确的状态迁移，并记录 `reviewer_id`、`decision_note`、时间戳。模型建议未被采纳时，应把「人工修正」作为高质量标注回流评测，而不是只存最终通过。

持久化方面，流程实例至少要有：`workflow_name`、`status`、`current_step`、`context_json`、`idempotency_key`、`updated_at`。恢复时根据 `current_step` 和上下文继续，**不要从第一步重跑**——否则可能重复调用已成功的副作用节点。这也是工作流与「Prompt 串联脚本」的本质区别之一。

### 5. 暂停、恢复、重试、补偿与幂等：副作用场景下的连贯叙事

这些概念单独列都会考，但在工作流主题里它们是一条链：**暂停是为了等人或等外部条件；恢复依赖持久化上下文；重试只适用于无副作用或已幂等的步骤；补偿用于已经产生了部分副作用但无法简单重试的情况。**

**暂停** 发生在进入 `waiting_for_review`、等待用户上传补充材料、或等待外部系统回调。暂停期间 Worker 可以释放，状态留在 DB。

**恢复** 由审核提交、回调到达或超时策略触发。恢复前要做权限校验：当前操作者是否有权对该 `workflow_id` 做 decision。

**重试** 针对临时故障。模型节点可以重试（注意 temperature 带来的非确定性，评测应用固定 seed 或缓存）。调用支付、退款、发邮件的节点，必须先实现**幂等**：同一 `request_id` 多次执行只产生一次副作用。伪代码逻辑是：先查是否已有成功记录，有则直接返回，无则创建并记录。

**补偿** 用于「已经执行了步骤 A，但步骤 B 失败且不能重放 A」的场景，例如已冻结金额但审批驳回，需要解冻。补偿步骤也应作为工作流中的显式节点，有审计记录，而不是运维手工改库。

把这些和 HITL 连起来：**人工驳回往往触发补偿或终态失败；人工批准则触发带幂等的执行节点。** 若只有重试没有幂等，面试里可以说清「为什么退款工作流绝不能只靠重试整个 DAG」。

---

### 6. 上下文、权限与审计：为什么「只存最终答案」不够

工作流排障时，最常见的问题是：用户说结果错了，但你只有最后一句话，不知道是分类错、检索偏、生成幻觉还是人工改错了。因此上下文必须保留**节点级输入输出摘要**（可脱敏），并记录模型版本、Prompt 版本、工具版本。

权限要分四层叙述：用户能否**启动**这条 workflow；某节点能否调用某工具（模型不能绕过）；审核员能否看到该业务对象的数据域；执行节点是否在应用层校验 `session.user_id` 与订单归属。HITL 不是万能挡箭牌——审核员也不能看到无权数据，否则合规仍失败。

审计要满足：谁、何时、在哪个 `step`、基于什么证据、做了什么 decision、下游执行结果如何。监管或客诉场景下，需要能回答「当时为什么让机器建议退款、谁批准的」。

### 7. 典型架构与防死循环：落地时如何不「编排成无限循环」

一条常见链路是：客户端 → Workflow Gateway（鉴权、幂等、限流）→ 流程存储 → 队列/调度器 → Worker/Orchestrator → LLM/检索/工具/规则引擎 → 人工审核台 → 指标与 Trace。Gateway 层挡重复创建；队列削峰；Worker 无状态，状态在 DB。

若在工作流里嵌入 Agent 子流程，必须单独设：**最大步数、最大工具调用次数、单流程 token 上限、单流程最长运行时间**。还要检测「连续两轮相同工具+相同参数」等无进展模式，触发熔断或转人工。否则外层状态机再严谨，内层 Agent 仍可能把成本打穿。

## 三、与相关主题的关系

同知识库中的 **Agent 工具调用与 Function Calling** 解决「模型如何提出结构化工具调用、应用层如何校验执行」。本文不关心 Tool Schema 细节，而关心**调用发生在流程的哪一态、失败后流程迁到哪里、是否允许自动调用高风险工具**（通常不允许，仅允许建议 + 人工批准后由后端节点执行）。

**LLM 流式响应与异步任务** 解决「用户如何少等待、长任务如何后台跑」。异步任务关注单次长作业；工作流关注多步与状态。实践中长流程往往用工作流编排，其中个别 LLM 步骤对用户流式输出。

**LLM 应用安全防护** 中的 Prompt Injection，在工作流里还多一层风险：诱导模型在某一节点做出错误分类，把流程导向危险迁移。防护仍依赖不可信数据隔离、工具白名单、高风险迁移必须 HITL。
