# LLM 工作流编排与 Human-in-the-loop · 面试问答

> 本篇为 [LLM工作流编排与Human-in-the-loop](./LLM工作流编排与Human-in-the-loop.md) 的配套材料。以下回答按**面试者现场作答**的口吻撰写，力求完整、可口述，不是提纲式「标准答案」。

---

## 问题 1：工作流编排和普通的异步任务，在你看来本质区别是什么？

我一般会先澄清面试官问的是哪一层。如果只是「接口很慢，用户不想干等」，那用消息队列加异步任务就够了，比如把报告生成丢到 Celery 里跑，前端轮询或 WebSocket 拿结果，这解决的是**时间和吞吐**问题。

但 LLM 工作流编排解决的是另一件事：**业务上有多步、有分支、有状态，而且中间可能要停下来等人**。比如客服退款，不是一次模型调用就结束，而是要先识别意图，再查订单，再做规则校验，模型生成解释，金额超过阈值或 VIP 用户就进人工，人工点了同意以后再调退款接口，最后通知用户并归档。这条链路里每一步的输入输出不一样，失败处理方式也不一样，有的步骤能重试，有的不能，有的必须幂等。异步任务通常只有一个「任务体」和一个「成功/失败」终态，很难表达「现在在等审核员张三，两天后再从这一步继续」。

所以我会总结：异步任务是**把一件长活放到后台**；工作流是**把一件业务拆成有契约的节点，用状态机管理走到哪了，并且支持人工介入和从中间恢复**。线上经常是两者结合——工作流引擎负责编排，某个节点内部用异步执行 LLM 或工具，但对外呈现的是流程实例 ID 和当前状态，而不是单一的 job id。

## 问题 2：什么情况下你会坚持上 Human-in-the-loop？是不是模型不准才需要人？

不完全是。模型不准可以是一种触发条件，比如分类置信度低于阈值就转人工，但我在设计时会把 HITL 理解成**风险治理**，而不是「模型兜底」。只要这一步如果错了或未经确认，会对用户资金、隐私、合规或品牌造成实质影响，我就倾向于默认不进全自动，或者自动只能到「建议」，执行必须有人或二次确认。

具体我会看几类信号：第一，有没有**不可逆或难逆的副作用**，比如退款、对外发邮件、改权限、写生产配置。第二，是不是**合规明确要求人工**的领域。第三，规则引擎和模型结论是否冲突——这种时候不能谁置信度高听谁的，而要停下来让人看证据。第四，用户是否主动要求人工。第五，自动化是否已经重试仍然失败，继续自动跑可能只是重复烧钱或重复骚扰用户。

实现上，人工节点不是弹个框让人随便填，而是流程进入 `waiting_for_review`，上下文落库，审核台展示「为什么停在这里、系统建议做什么、依据是什么」，人提交 decision 之后，工作流引擎根据 decision 迁移到下一状态，并记下审核人和备注。这样 HITL 和编排是绑死的，不是运营事后捞日志。

## 问题 3：如果流程执行到一半失败了，你会怎么排查和恢复？

我会先问清失败发生在哪个节点、当时流程状态是什么、有没有已经产生副作用。这三个信息决定恢复策略，不能一上来就「重跑整个流程」。

如果是网络超时、429 这类临时错误，节点契约应标成 `retryable_error`，工作流引擎在退避后重试**同一个节点**，并且对有副作用的节点必须先幂等——比如退款前先查 `request_id` 是否已经成功过，成功过就直接返回历史结果，避免重试退两次款。

如果是参数非法、权限不足、合规拦截，这类不应无限重试，应迁到 `failed` 或 `need_human`，把错误原因写进上下文，让人或用户知道下一步怎么办。

如果前面某步已经成功写了库或调了外部 API，后面步骤失败，就不能简单重放 DAG，而要嘛从**最近一个一致的状态**继续，要嘛走**补偿节点**，比如已冻结金额需要解冻。恢复依赖的是持久化的 `current_step` 和 `context_json`，而不是 Worker 内存。服务重启、扩缩容、审核跨天都应该能接着跑。

排查时我会看节点级输入输出和模型版本，而不是只看最终给用户的那句话。很多时候问题是分类错了导致进了错误分支，或者检索片段不对，而不是最后一遍生成不好。工作流的价值之一就是把这些步骤拆开，定位更快。

## 问题 4：为什么你说不能只用 Prompt 把几个步骤串起来？看起来也能跑通。

Demo 阶段确实可以：第一个 Prompt 分类，第二个 Prompt 根据分类写回复，第三个再总结，脚本里顺序调用就行。但上线后很快会遇到 Prompt 串联解决不了的问题。

第一，**没有显式状态**。脚本跑完就结束，中间停了、服务挂了、审核员第二天才来，你不知道「停在哪一步」，只能从头再调一遍模型，成本和副作用都不可控。

第二，**权限和审计**。Prompt 串联通常在应用代码里写死，很难表达「这个节点只有审核员角色能触发迁移」「这个工具只有后端在收到 confirm_token 后才能调」。工作流把策略放在引擎层，模型输出只是建议。

第三，**失败语义不清**。某次 HTTP 超时，你是重试第二步还是全部重来？退款已经成功了还能不能重试？没有节点契约和幂等键，团队只能拍脑袋。

第四，**成本和可观测性**。串联脚本很难统计「多少单卡在人工」「分类节点平均耗时」「哪一步 token 占比最高」。工作流实例 ID 加步骤日志，这些指标才自然。

所以我的观点是：Prompt 串联适合验证想法；**生产要用节点 + 状态 + 上下文 + 策略**，LLM 只是某一类节点的实现方式。HITL 更是必须嵌在状态迁移里，而不是脚本里 `input("是否继续")` 这种临时方案。

## 问题 5：DAG 和状态机你会怎么选？能结合吗？

我会看业务的不确定性长在哪里。如果步骤依赖基本固定，只是偶尔并行，比如文档解析、切块、索引、检索、生成、规则校验，这条链用 **DAG** 很清晰，节点之间是数据依赖，方便做并行和可视化。

如果业务语言本身就是生命周期，比如工单从打开到待审到已解决，或者退款从草稿到风控到待人工到已执行，我会用**状态机**，因为「等待人工」天然是一个可以停很久的状态，迁移条件也和业务角色绑定。

复杂系统里我常见的是**外层状态机、内层 DAG**：外层管「这单业务走到哪了、要不要人审」；进入某个状态后，内层跑一段固定的 DAG 完成文档处理或批量检查。如果某一步需要探索式查数，再在这个状态里嵌一个有步数上限的 Agent 子流程，子流程结束只把结构化结果写回上下文，由外层状态机决定下一跳。

选型的面试收束句可以是：**DAG 管步骤依赖，状态机管业务生命周期的暂停和恢复，Agent 只放在需要动态探索且边界被状态机包住的局部。**

## 问题 6：高风险操作，比如退款，你会让模型直接调工具吗？

不会让模型拥有最终执行权。模型最多做到两件事：一是根据上下文**建议**是否应该退款、退多少、依据哪些规则；二是在受控节点里输出结构化字段，供规则引擎或工作流判断。

真正调用退款 API 的应该是工作流里的**执行节点**，前面经过分类、风控、必要时人工 `approve`，并且带幂等键。应用层要校验订单归属、金额上限、用户权限，这些不能交给模型「自觉」。我在 Agent 相关主题里也会强调 Tool Calling 是建议，执行在应用层；在工作流主题里更进一步：**高风险迁移本身就是图上的一条边，这条边可以由人工触发，而不是由 tool_calls 直接触发。**

如果产品希望体验流畅，可以做「预览 + 确认」：自动节点生成退款预览和解释，人工或用户确认后，后端用 confirm_token 调 submit 节点。模型不应该能跳过确认直接进 submit。

## 问题 7：人工审核台你会让审核员看到什么？怎么避免人变成「点同意机器」？

我会刻意设计三类信息，让审核是「决策」而不是「橡皮图章」。

第一类是**为什么停**：低置信、VIP 规则、金额阈值、规则冲突，用业务语言写清楚，不要只显示一个 error code。

第二类是**系统建议做什么**：不是裸一句「建议退款」，而是「建议退款 199 元，依据订单状态已发货且符合规则 R3」，必要时附检索片段或工具返回摘要，让审核员能质疑依据。

第三类是**操作后果**：批准会触发什么 API、是否可逆、预计到账时间，驳回或打回会让用户看到什么。

决策上除了通过和拒绝，我会保留**修改后执行**和**打回补充材料**，并把人工修改记录进上下文和离线评测集——这些是模型对齐的宝贵数据。

同时，审核员自己的权限也要控，不能因为是人工就绕过数据域。HITL 解决的是「自动不可信」，不解决「人越权」。

## 问题 8：工作流里的上下文到底该存什么？和对话历史是一回事吗？

不是一回事。对话历史是给模型续写的；工作流上下文是给**引擎和节点**用的业务状态机快照。

我会分层存：业务层字段，比如订单号、用户 ID、当前分类、审核结论，这些后续节点必须读；节点级输入输出摘要，方便排障和评测；模型层材料，比如 Prompt 版本、检索证据 ID、模型草稿，用于追溯和合规；审计层，谁何时做了什么 decision。

不会把几万字原始日志都塞进每个节点的 Prompt。每个节点按契约读最小字段。敏感信息脱敏进审核台，完整链路留在受控审计存储。

如果只存最终答案，出问题时你只能重新问模型，无法复现当时检索到了什么、分类置信度多少，这在生产里是扛不住客诉和监管的。

## 问题 9：你会怎么测一条 LLM 工作流？

我会分四层，而且都和工作流主题相关，不是只测模型准不准。

第一层，**单节点单测**：契约是否满足，比如分类节点在 VIP 退款样例上是否返回 `need_human`，幂等节点重复 `request_id` 是否只写一次库。

第二层，**流程测**：给定初始上下文，跑完整条状态机，覆盖自动通过、转人工、人工驳回、人工修改后执行、临时错误重试成功、不可重试失败等路径。这里会用固定 seed 或 mock LLM，避免 flake。

第三层，**回归与评测集**：真实或合成的业务 case，看端到端指标，比如自动闭环率、人工介入率、平均处理时长、人工纠正率。

第四层，**混沌和运维**：Worker 重启、消息重复投递、审核延迟两天再恢复，验证持久化和幂等是否真的有效。

权限也要单测：无权限用户不能批准、不能触发执行节点。这些测的是编排和 HITL，不是 BLEU 分数。

## 问题 10：如果让你设计「用户申请退款」的工作流，你会怎么讲整体方案？

我会先画状态，再填节点，而不是先写 Prompt。

用户提交后，流程实例创建，带幂等键。第一步意图与材料校验，规则加轻量模型，把明显不符合的挡在外面。第二步拉订单与物流事实，工具节点只读，结果结构化进上下文。第三步规则引擎加模型生成「是否可退、退多少、依据」，输出置信度和解释。若命中高风险策略——大额、VIP、置信度低、规则冲突——进入 `waiting_for_review`，审核台展示建议、订单摘要、规则命中说明。审核员 approve 后，才进入执行退款节点，带 `request_id` 幂等调支付接口。成功则通知用户并归档；失败则根据错误类型重试或补偿解冻。全程有 `workflow_id` 可追溯，模型不直接调退款。

对内我会强调：外层状态机管业务和人工；LLM 节点负责理解和生成解释；执行权在后端；人工边是设计的一部分，不是故障处理。这套说法和本文主题——编排加 HITL——是一致的。
