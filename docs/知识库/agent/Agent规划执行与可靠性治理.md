# AI Agent 规划执行与可靠性治理

## 核心概念

AI Agent 是以大模型为推理核心，通过工具调用、任务规划、状态管理和执行反馈完成复杂目标的 AI 应用形态。与普通 Chatbot「一次输入、一次生成」不同，Agent 引入循环式执行模式：首先理解用户目标，然后进行任务规划，接着选择合适的工具，调用外部系统获取信息或执行操作，读取返回结果，根据反馈修正计划，最终输出答案。这种循环执行让 Agent 能够处理单轮对话无法完成的复杂任务。

与普通 LLM 应用相比，Agent 在多个维度上有显著区别。在执行模式上，普通 LLM 应用通常是单次生成，输入一次、输出一次；而 Agent 是多步循环，可能需要多次与外部系统交互才能完成目标。在外部能力上，普通应用要么没有外部能力，要么仅具备 RAG 检索能力；Agent 则可以调用各种工具、API，甚至执行代码。在状态管理上，普通应用主要依靠上下文拼接来维持对话历史；Agent 则拥有更复杂的会话状态、任务状态和长期记忆。在风险层面，普通应用主要关注内容质量；Agent 由于具备行动能力，还面临越权执行、产生真实副作用等风险。

规划执行模式方面，业界主要有几种典型方案。ReAct 模式将推理与行动交替进行，模型先思考下一步该做什么，然后执行动作，再根据结果继续思考。这种方式灵活性强，适合探索式任务，但容易产生循环、步骤可能漂移、成本难以预估。Plan-and-Execute 模式先进行整体计划，再逐步执行，适合步骤明确的复杂任务，但计划可能需要根据执行情况动态修正。Workflow Agent 将关键路径由代码或工作流固定，模型仅在特定节点做判断，这是生产环境的首选方案，因为它提供了更强的确定性和可控性。Multi-Agent 模式引入角色分工，比如规划者、执行者、审查者分别由不同 Agent 担任，这种方式可以提升复杂任务的组织性，但会增加通信成本和一致性难度。

可靠性治理的核心原则是：模型只负责建议调用什么，真实的执行权控制在受控的应用层；高风险动作必须经过人工确认；全流程要具备可观测性和可回放能力。这意味着即使模型给出了工具调用建议，应用层也需要进行参数校验、权限检查，确认无误后才真正执行。

一个带预算与终止条件的 Agent 循环骨架通常包含以下要素：设置最大执行步数限制，在循环中调用大模型获取响应，如果模型没有产生工具调用则直接返回答案，检测是否存在实质进展以避免空转，对于每个工具调用在应用层进行校验后执行，将执行结果反馈给模型，如果达到最大步数仍未完成则返回预算超限状态。

## 核心知识点

### 1. 记忆与状态分层

Agent 的记忆和状态需要分层管理，不同类型的信息有不同的生命周期和存储要求。

会话状态包含当前对话内容、任务执行进度、工具调用结果等。这类信息通常存储在上下文中，需要按照 token 预算进行裁剪，避免超出模型的上下文长度限制。当会话结束或超时时，会话状态可以被清理。

短期记忆存储本轮任务中的临时事实，比如中间计算结果、临时检索到的信息等。这类信息在任务结束后可以丢弃，不需要长期保留。

长期记忆存储用户偏好、稳定的领域知识等需要跨会话保留的信息。长期记忆的写入不能自动进行，需要设定明确的写入规则、可见性控制和删除机制，同时要防止记忆污染，确保写入内容的质量和安全性。

外部状态指存储在数据库、订单系统、工单系统等外部存储中的业务数据。Agent 应该以结构化字段引用这些外部状态，而不是将全量数据塞入上下文，这样既能节省 token，又能保证数据的实时性。

### 2. 可靠性治理手段

生产级 Agent 系统需要建立完善的可靠性治理体系。

工具白名单机制确保 Agent 只能调用经过授权的工具，防止模型调用未经验证或危险的功能。所有可用工具必须在系统中显式注册，未注册的工具即使模型建议调用也会被拒绝。

参数校验在多个层面进行：首先是 Schema 校验，确保参数类型、必填项等符合定义；其次是业务规则校验，比如验证订单号是否属于当前会话的用户，防止越权访问。

权限分层将操作分为只读、低风险写、高风险写三个级别。只读操作如查询信息，风险较低；低风险写如更新用户偏好；高风险写如付款、删除数据、发送外部消息、修改生产数据等，需要额外的确认步骤。

人工确认机制要求高风险动作在执行前必须获得用户明确确认，确认信息应该清晰展示将要执行的操作和可能的影响，避免用户误操作。

调用预算从多个维度限制 Agent 的执行成本：最大执行步数防止无限循环；最大 token 消耗控制计算成本；最大工具调用次数限制外部依赖；最大执行时间保证响应及时性。

幂等设计确保写操作即使被重复执行也不会产生副作用。通常通过幂等键来实现，相同的幂等键多次调用只执行一次实际修改。

可观测性要求记录全流程信息：用户输入、生成的计划、工具调用选择、调用参数、执行结果、遇到的错误、资源消耗等，为问题排查和系统优化提供数据支撑。

回滚和补偿机制为高风险操作提供撤销方案，当操作失败或需要取消时，能够将系统状态恢复到操作前的状态。

### 3. 防无限循环

Agent 执行过程中可能出现无限循环，需要设计多种终止条件来防范。

重复调用检测可以识别连续多轮使用相同工具且参数相同的情况，这通常意味着模型陷入了循环，应该终止执行并提示用户。

资源预算限制包括执行时间上限、工具调用次数上限、token 消耗上限等，任何一项达到阈值都应该终止执行。

进展检测通过分析连续多轮是否获得了新的事实或进展来判断是否陷入停滞，如果没有实质进展则应该终止或转人工处理。

### 4. 评估指标

评估 Agent 不能只看最终输出的文案质量，需要建立多维度的评估体系。

任务成功率衡量 Agent 是否真正完成了用户的目标，这是最核心的指标。

工具选择准确率评估模型在面对任务时是否选择了合适的工具，错误的选择会导致后续执行偏离目标。

参数准确率评估工具调用的参数是否合法且符合用户意图，参数错误可能导致调用失败或产生错误结果。

步骤效率评估完成任务的调用次数和 token 成本，效率低的 Agent 虽然可能完成任务，但成本过高不具实用性。

错误恢复率衡量 Agent 在遇到失败后能否正确诊断问题并修正策略，最终完成任务。

安全违规率监控越权访问、数据泄漏、危险操作等安全事件的发生频率。

可复现率评估在固定环境下多次执行相同任务的结果一致性，稳定性是生产环境的重要要求。

### 5. Prompt Injection 在 Agent 场景更危险

提示注入攻击在 Agent 场景比普通 Chatbot 更加危险。在普通场景中，注入攻击主要影响模型的回答内容；而在 Agent 场景中，攻击者可能诱导 Agent 调用工具、泄露敏感数据、执行危险操作。

防护措施包括：不信任任何外部输入内容，将系统指令与不可信数据进行隔离，工具权限最小化原则，敏感操作要求二次确认，在应用层进行策略校验等。

### 6. 预览加确认两阶段

对于高风险操作，应该采用预览加确认的两阶段模式。第一阶段生成操作预览，向用户展示将要执行的操作详情和可能影响；第二阶段只有在后端收到用户的确认令牌后才真正触发执行，这个确认过程不由模型自主控制，而是由应用层严格管理。

确认令牌需要与用户信息、操作对象绑定，防止重放攻击。写操作还需要携带幂等键，确保重复提交不会导致多次执行。

## 高频面试问题与标准答案

**Q1：什么是 AI Agent？与 Chatbot 区别？**

A：AI Agent 是以大模型为推理核心，能够围绕目标进行规划、调用外部工具、读取执行反馈并迭代执行的智能系统。与 Chatbot 最大的区别在于执行模式和能力边界。

Chatbot 通常是单次生成模式，用户输入一次，模型输出一次，主要依赖预训练知识和上下文中的检索信息。它的能力边界限于文本生成，没有与外部系统交互的能力。

Agent 引入了多步循环执行机制。它会分析用户目标，拆解成多个步骤，选择合适的工具调用外部 API 或执行代码，根据返回结果调整策略，循环往复直到完成目标。这种机制让 Agent 能够处理复杂任务，比如查询数据库、调用搜索引擎、执行计算、操作业务系统等。

正因为 Agent 具备行动能力，它面临的风险也更复杂。除了内容质量，还需要考虑权限控制、安全边界、可观测性等治理问题。模型可能建议调用敏感操作，应用层必须进行校验；模型可能陷入循环，系统需要设置终止条件；模型可能出错，需要记录完整日志便于排查。

**Q2：ReAct 模式的优缺点是什么？生产环境如何改进？**

A：ReAct 是 Reasoning 和 Acting 的缩写，代表推理与行动交替进行的模式。模型先思考当前情况并决定下一步行动，然后执行工具调用，再根据结果继续思考，形成循环。

优点是灵活性高，模型可以根据实时反馈动态调整策略，适合探索式、开放式的任务。比如信息收集类任务，模型可以先搜索获取初步信息，根据结果决定下一步搜索方向，这种自适应能力很强。

缺点也很明显。首先是容易陷入循环，模型可能在相似的思考路径中反复，无法推进任务。其次是步骤可能漂移，随着执行深入，模型可能偏离原始目标。第三是成本不可控，因为无法预估需要多少轮循环才能完成任务。

在生产环境中使用 ReAct 需要增加多重保障。设置最大步数上限，比如最多 8 步，防止无限循环。维护工具白名单，限制模型可调用的工具范围。监控执行过程，当检测到重复调用或无实质进展时主动终止。记录完整执行轨迹，便于事后分析和优化。对于关键业务，建议采用 Workflow 模式替代开放式 ReAct。

**Q3：何时应该选择 Workflow Agent 而非开放式 Agent？**

A：Workflow Agent 将关键执行路径由代码或工作流固定，模型仅在特定节点做判断，比如意图识别、字段提取、内容摘要等。选择 Workflow 还是开放式 Agent，主要取决于业务特性和风险要求。

当业务流程稳定、步骤明确时，适合使用 Workflow。比如审批流程、支付流程、工单流转，这些业务的步骤顺序是固定的，不需要模型动态规划。Workflow 提供了更强的确定性和可预测性，每次执行都遵循相同路径，便于测试和验证。

当业务风险较高、需要强一致性保障时，也应该选择 Workflow。关键路径由代码控制，可以避免模型的不确定性带来的风险。比如涉及资金的操作，转账金额、收款账户等关键信息必须由代码校验，不能依赖模型判断。

当业务需要满足合规审计要求时，Workflow 更容易实现完整的操作记录和回放。每个步骤的输入输出、决策依据都可以精确记录，满足审计要求。

开放式 Agent 更适合探索性任务，比如信息调研、创意生成、问题诊断等目标明确但路径不固定的场景。这类任务需要模型根据中间结果灵活调整策略，Workflow 的固定路径反而会成为限制。

**Q4：如何避免 Agent 陷入无限循环？**

A：防止无限循环需要从多个维度设置终止条件，形成立体防护。

预算类限制是最基础的防护。设置最大执行步数，比如单轮对话最多 8 步；设置最大工具调用次数，防止频繁调用外部服务；设置最大执行时间，确保响应及时性；设置最大 token 消耗，控制计算成本。任何一项达到阈值都应该终止执行。

重复检测可以识别循环模式。监控连续多轮的工具调用，如果发现使用相同工具且参数相同，说明模型可能在重复尝试，应该终止执行。也可以检测思考内容的相似度，如果多轮推理高度相似，同样应该触发终止。

进展检测判断任务是否在推进。分析每轮执行是否获得了新的事实、是否向目标靠近，如果连续多轮没有实质进展，说明可能陷入了僵局，应该终止或转人工处理。

失败处理也很重要。当工具调用连续失败时，不应该无限重试，而是要求模型总结当前情况并给出结论，或者转人工处理。

**Q5：工具调用失败时应该如何处理？**

A：工具调用失败的处理需要根据错误类型采取不同策略，核心是分类处理、优雅降级。

参数错误是最常见的情况，可能是模型生成的参数格式不对，或者缺少必填字段。这类错误应该将结构化错误信息回灌给模型，让模型理解错误原因并尝试修正参数后重新调用。

权限错误表示当前用户或会话没有执行该操作的权限，这类错误通常不应该重试，而是直接终止并告知用户权限不足，避免重复尝试浪费资源。

临时故障指网络超时、服务暂时不可用等可能自恢复的错误。对于这类错误可以实现有限重试，采用指数退避策略，第一次等待 1 秒，第二次等待 2 秒，最多重试 3 次。如果仍然失败则返回错误。

业务错误指工具执行成功但业务逻辑不通过，比如订单状态不允许退款、库存不足等。这类错误需要明确告知用户具体原因，让模型生成解释性的回复。

不可恢复错误指系统性故障或未知错误，应该向用户透明说明情况，提供降级方案或转人工处理。

**Q6：Agent 的记忆应该如何设计？**

A：Agent 的记忆设计需要分层管理，不同层次有不同的存储策略和生命周期。

会话状态层保存当前对话的上下文、任务执行进度、工具调用历史等。这层信息存储在内存或 Redis 中，按 token 预算进行裁剪，避免超出模型上下文长度。会话结束或超时时可以清理。

短期记忆层保存本轮任务的临时事实，比如中间计算结果、临时检索的信息等。这层信息在任务结束后可以丢弃，不需要持久化存储。

长期记忆层保存用户偏好、稳定的领域知识等需要跨会话保留的信息。这层信息写入前需要经过规则过滤和授权确认，不能自动写入全部内容。需要设计写入规则、可见性控制、删除机制，防止记忆污染。敏感信息不应该进入长期记忆。

外部状态层指存储在数据库、订单系统、工单系统等外部存储中的业务数据。Agent 应该以结构化字段引用这些外部状态，而不是将全量数据塞入上下文。这样既能节省 token，又能保证数据的实时性和一致性。

**Q7：如何评估 Agent 是否可以上线？**

A：Agent 上线前需要建立完整的评估体系，不能只看最终输出的文案质量。

首先要建立测试任务集，覆盖核心场景和边界情况。测试集应该包含简单任务、复杂任务、异常场景、安全测试用例等。

在固定环境中进行回放测试，确保结果可复现。评估指标包括：任务成功率，是否完成用户目标；工具选择准确率，是否选对工具；参数准确率，参数是否合法且符合意图；步骤效率，调用次数和 token 成本是否合理；错误恢复率，失败后能否修正；安全违规率，是否有越权、泄漏等风险。

除了自动化指标，还需要进行红队测试。模拟攻击者进行提示注入、参数篡改、权限越界等尝试，验证系统的安全防护是否有效。

性能测试也很重要，评估系统的响应延迟、并发处理能力、资源消耗等是否满足生产要求。

最后需要建立监控和告警机制，上线后持续观察各项指标，发现问题及时回滚或修复。

**Q8：Multi-Agent 架构一定比单 Agent 更好吗？**

A：不一定。Multi-Agent 架构通过角色分工来提升复杂任务的组织性，比如规划者负责拆解任务、执行者负责调用工具、审查者负责检查结果。但这种架构也有明显的代价。

通信成本是首要问题。多个 Agent 之间需要交换信息，增加了延迟和 token 消耗。一致性难度也很高，不同 Agent 可能对任务理解不一致，需要额外的协调机制。系统复杂度显著增加，调试和维护成本更高。

选择架构时应该根据任务特性决定。对于简单任务，单 Agent 或 Workflow 通常足够，引入 Multi-Agent 反而增加不必要的复杂度。对于复杂任务，如果单 Agent 确实难以处理，可以考虑 Multi-Agent，但要设计清晰的通信协议和协调机制。

建议先从单 Agent 或 Workflow 开始验证，只有当确实遇到瓶颈时再考虑引入 Multi-Agent。很多情况下，优化提示词、增加工具、改进工作流就能解决问题，不需要引入多 Agent 的复杂性。

**Q9：Agent 系统的可观测性应该记录什么？**

A：可观测性是生产级 Agent 系统的基础，需要记录全流程的详细信息。

用户输入侧要记录原始输入、预处理后的输入、用户身份和会话信息。

模型交互侧要记录使用的 Prompt、模型版本、生成的输出、工具调用建议、推理过程等。

工具执行侧要记录选中的工具、调用参数、执行结果、执行耗时、错误信息等。

资源消耗侧要记录 token 使用量、执行步数、工具调用次数、总耗时等成本指标。

输出侧要记录最终返回给用户的内容、输出格式、渲染方式等。

反馈侧要记录用户的显式反馈和隐式反馈，比如是否满意、是否追问、是否转人工等。

对于写操作，还需要记录操作者身份、确认记录、幂等键、执行前后的状态快照等审计信息。

这些数据应该结构化存储，便于查询、分析和可视化。同时要注意敏感信息的脱敏处理，避免数据泄漏。

**Q10：如何设计一个自动处理退款咨询的 Agent？**

A：退款咨询涉及资金安全，应该采用 Workflow 模式，将关键路径固定，LLM 负责语义理解，规则和执行由确定性服务完成。

流程设计如下：首先进行意图识别，判断用户是否在咨询退款、查询退款进度、或申请退款。然后查询订单信息和退款规则，获取订单状态、购买时间、退款政策等。接着判断是否满足退款条件，这一步由规则引擎完成，比如是否在购买后 7 天内、订单是否已发货等。如果满足条件，生成解释说明，告知用户退款金额、到账时间等。如果不满足，说明具体原因和可能的解决方案。

对于真正需要执行退款的场景，不能直接由 Agent 调用退款 API，而应该进入确认流程。向用户展示退款详情，包括退款金额、原路返回的账户、预计到账时间等，要求用户明确确认。只有在收到用户确认后，后端服务才调用退款 API，并记录完整的审计日志。

LLM 在整个流程中主要负责语义理解、信息抽取、解释生成等任务，不涉及资金操作的决策和执行。这样既发挥了 LLM 的语言理解能力，又保证了资金操作的安全性和可控性。

## 面试回答加分点

第一，先定风险等级再选模式。低风险探索场景可以用 ReAct 等开放式 Agent；高价值生产场景应该用 Workflow 加局部 LLM 的组合，确保可控性。

第二，强调模型建议、系统执行的原则。三条铁律要牢记：模型只负责决策建议，参数不可信必须经过校验，工具调用即契约必须严格管控。

第三，用具体数字体现专业性。比如最大步数设为 8 步、每轮工具选择控制在 5 到 15 个、关注 P95 延迟、设定单任务 token 上限等，这些具体参数能体现实际经验。

第四，清晰对比 RAG 和 Agent。RAG 解决的是外部知识怎么检索的问题；Agent 解决的是如何调用工具、拆解任务、可控执行的问题。两者可以结合使用，但解决的问题域不同。

第五，掌握设计题的七步模板。面对系统设计题，按这个框架回答：明确目标与风险、选择执行模式、设计工具和 Schema 及权限、规划状态与上下文、设定安全边界、确定评估指标、考虑成本与降级方案。

第六，用一句话收束观点。Agent 的核心不是让模型自由行动，而是用工具协议、编排逻辑、权限控制和评估体系，让模型在可控边界内可靠地完成任务。
