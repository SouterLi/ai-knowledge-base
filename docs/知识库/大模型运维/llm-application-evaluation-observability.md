# LLM 应用评估与可观测性

## 核心概念

### 1. 评估 vs 可观测性

- **评估（Evaluation）**：离线/在线判断效果是否达标——正确性、忠实度、格式、安全、成本。  
- **可观测性（Observability）**：线上记录「发生了什么」——日志、链路、指标、追踪。  

二者结合：评估定义「什么是好」，观测记录事实，数据驱动 Prompt/检索/模型/工具优化。模型、知识库、用户分布都会变，上线后质量不会自动稳定。

### 2. 为什么不能只靠体感

「感觉更好」无法回归；改动（Prompt、模型、索引）需用同一评测集证明收益或发现回退。

### 3. LLM-as-Judge 的定位

适合规模化初筛；受提示词、裁判模型偏好影响。关键业务需**规则校验 + 人工评审 + 业务指标**三角校验。

### 4. 幻觉排查逻辑

```text
上下文无正确答案 → 检索/数据问题
上下文有答案但编造 → Prompt/模型/拒答/输出校验问题
```

## 核心知识点

### 1. 质量指标

| 类别 | 指标 |
| --- | --- |
| 答案质量 | 正确性、忠实度、相关性、完整性 |
| 结构化 | JSON/字段合规率、必填缺失率 |
| Agent | 工具选择准确率、参数准确率、无效/越权调用率 |
| RAG | 召回命中率、引用命中率、答案 grounded 比例 |
| 安全 | 违规率、拒答准确率、敏感泄露 |

### 2. 工程与业务指标

首 token 延迟（TTFT）、端到端 P95、token 数、单次成本、错误率/重试/限流；采纳率、追问率、人工转接率、解决率。

### 3. 评测集建设

来源：高频问题、边界、安全、历史坏 Case、线上分层采样。  
每条 case 含：问题、参考答案或评分规则、必含事实点、禁用内容、场景标签。

```python
case = {
    "question": "如何重置企业账号密码？",
    "expected_facts": ["进入账号中心", "验证手机号", "设置新密码"],
    "forbidden": ["联系数据库管理员"],
    "tags": ["高频", "账号"],
}

def score_answer(output: str, case: dict) -> dict:
    # 中文注释：规则层检查必含事实与禁用表述
    hits = [f for f in case["expected_facts"] if f in output]
    violations = [f for f in case["forbidden"] if f in output]
    return {
        "fact_recall": len(hits) / max(len(case["expected_facts"]), 1),
        "safe": len(violations) == 0,
    }
```

### 4. 自动化回归流程

改 Prompt/模型/检索/工具 → 跑全量或分层评测集 → 对比基线 → 通过再灰度 → 线上监控同类指标。

### 5. 可观测性：日志与追踪

- 每次请求 **request_id** 串联：输入、检索结果、模型版本、工具调用、输出、token、延迟、错误。  
- 分布式追踪（OpenTelemetry 等）：span 覆盖 retrieve / llm / tool。  
- 敏感字段脱敏；采样策略平衡成本与覆盖。

```python
import time
import uuid

def traced_chat(user_msg: str, retrieve_fn, llm_fn):
    request_id = str(uuid.uuid4())
    t0 = time.time()
    docs = retrieve_fn(user_msg)  # 中文注释：记录召回文档 ID 便于复盘
    answer = llm_fn(user_msg, docs)
    log = {
        "request_id": request_id,
        "retrieve_doc_ids": [d["id"] for d in docs],
        "latency_ms": int((time.time() - t0) * 1000),
        "input_tokens": estimate_tokens(user_msg),
    }
    emit_observability(log)
    return answer
```

### 6. 线上监控与告警

按场景/租户/模型版本看：成功率、P95、成本分布、幻觉/格式失败率、安全拦截率。告警阈值基于基线而非固定 magic number。

### 7. 问题回流

差评、无答案、高成本、审核失败 → 归因 → 进入评测集或坏 Case 池 → 下次改动必回归。

### 8. 成本观测

监控输入/输出 token 分布；识别超长上下文、重复调用；简单任务路由小模型；缓存高频；限制工具重试。

## 高频面试问题与标准答案

**Q1：如何证明应用变好了？**  
建立版本化评测集与基线分数；每次改动跑回归；线上看采纳率、转人工率、安全与成本；A/B 或灰度对比。

**Q2：离线好、线上差？**  
评测集脱离真实表达、缺多轮/长尾/异常输入；需线上分层采样持续补充。

**Q3：能完全用 LLM 当裁判吗？**  
不能。用于初筛；关键场景加规则（事实点、禁用词）、人工与业务结果。

**Q4：如何排查幻觉？**  
先看检索是否包含正确答案；再查上下文拼接与 Prompt 约束；最后看模型能力与输出校验/拒答。

**Q5：RAG 应用评估什么？**  
检索（Recall@k、MRR）、生成（忠实度、引用命中）、端到端任务指标；分开看便于定位。

**Q6：Agent 评估什么？**  
工具选择、参数正确、计划是否合理、任务完成率、副作用（重复调用、越权）。

**Q7：日志记什么才够复盘？**  
request_id、版本号、检索明细、工具 IO 摘要、完整 prompt 哈希或模板 id、输出、成本延迟、用户反馈。

**Q8：如何控评估成本？**  
分层标签先跑冒烟集；全量夜间跑；LLM Judge 仅用于不确定样本。

**Q9：安全如何评估？**  
红队集、越狱、敏感泄露、越权工具；与安全策略版本绑定回归。

**Q10：观测与隐私平衡？**  
最小必要、脱敏、访问控制、保留周期；不把 PII 打进长期日志。

## 面试回答加分点

1. **先定义「好」再谈工具**：指标与业务场景绑定（客服解决率 vs 代码通过率）。  
2. **分层评估**：检索错还是生成错，分开指标。  
3. **改动必回归**：体现工程纪律，反对无评测上线。  
4. **三角校验**：规则 + 人工 + 模型裁判。  
5. **可观测驱动定位**：用 request_id 讲一次完整排障故事。  
6. **成本是一等公民**：token 与 P95 与质量并列。  
7. **与数据闭环衔接**：观测发现问题 → 坏 Case → 评测集 → 验证修复。  
8. **一分钟总结**：评测集 + 指标体系 + 自动回归 + 线上日志 + 回流——五要素背全即高分。
