## 核心概念

### 1. 评测集不是测试用例清单

LLM 评测集是一组带有场景标签、输入、期望行为、评分规则和数据血缘的样本资产。它不仅回答「这次改动有没有变好」，还要支持：

- Prompt、模型、RAG、工具链变更前后的回归对比。
- 线上坏 Case 的复现和修复验证。
- 多模型、多版本、多租户策略的横向比较。
- 人工评审、规则评分和 LLM-as-Judge 的一致性校准。

面试中要强调：**评测集的质量决定评估结论是否可信**。样本失真、标注含糊、版本混乱时，分数越精确越容易误导。

### 2. 样本、标签、Rubric

- **样本**：用户问题、上下文、检索证据、工具状态、历史轮次等输入。
- **标签**：场景、难度、风险等级、意图、租户、语言、渠道、是否长尾。
- **Rubric**：评分标准，例如事实正确性、忠实度、完整性、安全性、格式合规、工具路径正确。

Rubric 要比「标准答案」更重要，因为很多 LLM 输出不是逐字唯一答案。好的 Rubric 能告诉评审者：哪些点必须命中，哪些表达可接受，哪些内容一票否决。

### 3. 黄金集、回归集、挑战集

| 类型 | 作用 | 样本特点 |
| --- | --- | --- |
| 黄金集 | 作为核心质量基线 | 人工精标、覆盖高频业务 |
| 回归集 | 防止已修复问题再次出现 | 来自历史坏 Case、版本固定 |
| 挑战集 | 压测边界和安全 | 歧义、越权、注入、长上下文、多轮 |
| 探索集 | 快速发现趋势 | 可包含弱标注、合成样本 |

成熟团队不会只维护一个大而全的集合，而是按用途拆分，并明确哪些集合可以影响上线门禁，哪些只用于分析。

### 4. 标注一致性

同一个样本被不同标注者判出不同结论，评测结果就不稳定。常见手段：

1. 给出正例、反例和边界例。
2. 高风险样本双人标注，不一致时仲裁。
3. 计算一致率，例如 Cohen's Kappa 或简单一致率。
4. 定期回看争议样本，修订 Rubric。

面试表达重点：**不是靠更多标注人解决问题，而是靠更清晰的标准降低分歧**。

## 核心知识点

### 1. 评测集建设流程

```text
目标定义 → 样本采集 → 脱敏清洗 → 场景分层 → 标注规范 → 人工/规则/模型标注
       → 一致性校准 → 版本冻结 → 基线跑分 → 上线门禁 → 坏 Case 回流
```

每一步都要留下数据血缘：样本来源、采集时间、脱敏策略、标注人或裁判模型、Rubric 版本、适用业务范围。

### 2. 样本来源

| 来源 | 优点 | 风险 |
| --- | --- | --- |
| 线上真实请求 | 贴近用户表达 | 隐私、分布偏差、缺标准答案 |
| 历史坏 Case | 对回归最有价值 | 容易过拟合局部问题 |
| 产品需求/专家编写 | 覆盖关键流程 | 表达可能不真实 |
| 合成数据 | 快速补长尾和对抗 | 质量漂移、模式单一 |
| 竞品/公开基准 | 便于横向认知 | 与业务目标不一定一致 |

实际落地时，建议以真实请求和坏 Case 为骨架，用专家样本补关键路径，用合成数据补边界和安全场景。

### 3. 分层抽样

只按总体准确率看分数，很容易掩盖关键问题。评测集至少按这些维度分层：

- **场景**：知识问答、意图识别、工具调用、数据查询、总结改写。
- **风险**：普通咨询、账号权限、金融医疗、合规安全。
- **输入复杂度**：短问、长文档、多轮、口语化、错别字、混合语言。
- **链路模块**：Prompt-only、RAG、Agent、工作流、Human-in-the-loop。
- **数据分布**：高频、长尾、冷启动、新业务。

上线门禁不能只看平均分，要看关键分层是否退化。例如整体提升 2%，但高风险权限类下降 8%，仍然不能发布。

### 4. 标注 Schema 设计

```json
{
  "case_id": "refund_001",
  "input": "会员退款多久到账？",
  "context": ["退款审核通过后 3-5 个工作日原路退回"],
  "expected_facts": ["3-5 个工作日", "原路退回"],
  "forbidden": ["当天到账", "联系数据库管理员"],
  "tags": ["客服", "退款", "高频"],
  "risk_level": "low",
  "rubric_version": "v1.2"
}
```

如果是 RAG 样本，还应保留相关文档、金标准 chunk、引用页码；如果是 Agent 样本，还应保留期望工具名、参数、调用顺序和禁止调用的工具。

### 5. 规则评分示例

```python
def score_customer_answer(answer: str, case: dict) -> dict:
    # 中文注释：必含事实用于衡量完整性，禁用内容用于一票否决
    expected = case.get("expected_facts", [])
    forbidden = case.get("forbidden", [])

    hit_facts = [fact for fact in expected if fact in answer]
    violations = [item for item in forbidden if item in answer]

    return {
        "fact_recall": len(hit_facts) / max(len(expected), 1),
        "has_violation": len(violations) > 0,
        "pass": len(hit_facts) == len(expected) and not violations,
        "missing_facts": [fact for fact in expected if fact not in hit_facts],
    }
```

规则评分适合格式、字段、事实点、禁用项；语义相关性、表达质量、复杂推理可以引入 LLM-as-Judge，但要抽样人工校准。

### 6. LLM-as-Judge 的正确用法

LLM-as-Judge 适合做规模化初筛，但不能无约束地让模型「凭感觉打分」。推荐做法：

1. 固定裁判 Prompt、裁判模型和温度。
2. 输出结构化评分与理由。
3. Rubric 明确一票否决项。
4. 与人工标注做一致性抽检。
5. 记录裁判模型版本，模型升级后重跑基线。

```python
judge_prompt = """
你是企业客服答案评审员。请只根据给定标准评分。
评分维度：
1. 必含事实是否全部出现。
2. 是否出现禁用内容。
3. 是否忠实于证据。
输出 JSON：{"score": 0-5, "pass": true/false, "reason": "..."}
"""
```

面试中可以说：我会把 Judge 当成评审工具，而不是质量真相本身。

### 7. 合成数据怎么用

合成数据适合补这些场景：

- 长尾问法、口语化、错别字、多语言。
- Prompt Injection、越权请求、恶意格式。
- 新业务冷启动，真实样本还不够。
- 工具参数边界，例如缺参、非法枚举、时间范围异常。

但合成数据不能直接替代真实评测集。必须做：

1. 去重和多样性检查，避免模板味太重。
2. 专家抽检，确认业务事实正确。
3. 标记 `synthetic=true`，与真实样本分开看分。
4. 不用待测模型生成自己的考试题，避免自我偏置。

### 8. 数据泄漏与集合隔离

评测集、训练集、Prompt 示例、Few-shot 示例必须隔离。常见问题是把评测样本写进 Prompt 示例，或把回归集拿去微调，导致离线分数虚高。

隔离原则：

- 训练集、验证集、测试集按 `case_id` 和相似问题去重。
- 评测集只读使用，禁止作为 Prompt 示例池自动召回。
- 样本进入微调前检查是否来自上线门禁集。
- 报告里区分 seen / unseen、真实 / 合成、高频 / 长尾。

### 9. 版本治理

评测集应像代码一样版本化：

- `dataset_version`：样本集合版本。
- `rubric_version`：评分标准版本。
- `judge_version`：裁判模型和 Prompt 版本。
- `baseline_version`：当前线上策略跑分。

一旦样本或 Rubric 变了，历史分数不能简单横向比较。正确做法是用同一版本集合重跑候选方案和基线。

### 10. 上线门禁设计

不要只设置一个总分阈值。更合理的是：

- 总体通过率不低于基线。
- 高风险场景零严重违规。
- 核心分层不允许显著下降。
- P95 延迟、成本、错误率不超过预算。
- 新增坏 Case 必须在回归集中通过。

评测报告最好同时展示「提升项、退化项、失败样本列表和归因建议」，这样工程团队才能决定是否发布、回滚或继续修复。

## 高频面试问题与标准答案

### Q1：你会怎么从零建设一个 LLM 应用评测集？

**标准答案：**  
我会先明确评测目标，是评 Prompt、RAG、工具调用还是端到端业务效果。然后从线上高频请求、历史坏 Case、产品关键路径和安全边界采样，先做脱敏和去重，再按场景、风险等级、输入复杂度分层。每条样本不只存问题和标准答案，还会存期望事实点、禁用项、相关证据、标签和 Rubric 版本。标注阶段先小规模试标，校准标准，再做双人标注和争议仲裁。最后冻结一个版本作为基线，每次 Prompt、模型、索引或工具变更都用同一版本回归，避免凭感觉上线。

### Q2：LLM 输出不唯一，怎么定义“标准答案”？

**标准答案：**  
我不会要求逐字匹配，而是把标准答案拆成 Rubric。比如客服问答要看必含事实、禁止误导、是否引用正确证据、语气是否合规；结构化任务看字段完整、类型合法、枚举正确；Agent 任务看工具选择、参数和调用顺序。这样不同表达只要满足关键事实和约束就算通过，既不会误杀合理答案，也能抓住真正有风险的问题。

### Q3：线上差评或点踩能不能直接进评测集？

**标准答案：**  
不能直接进。点踩只是一个信号，不等于模型一定错。我要先结合日志、检索结果、工具调用和用户上下文做归因，判断是知识缺失、检索失败、Prompt 问题、工具错误还是用户预期不匹配。确认有复现价值后再脱敏、补标准答案或评分规则，加入对应分层的回归集。如果只是情绪反馈或业务数据本身错误，直接放进评测集会污染评估结论。

### Q4：合成数据在评测集中有什么价值和风险？

**标准答案：**  
合成数据的价值是补长尾和边界，比如新业务冷启动、恶意注入、缺参、多语言、错别字这些真实样本少但面试和生产都很关键的场景。风险是模型生成的问题可能模式单一、事实不准，甚至和待测模型有相同偏置。所以我会把合成样本单独打标，专家抽检，和真实样本分开统计；核心上线门禁仍以真实样本和人工精标样本为主。

### Q5：如何保证标注质量？

**标准答案：**  
我会先写清楚标注规范，不只写定义，还要给正例、反例和边界例。标注前先做一轮试标，看标注者分歧最大的地方，然后修 Rubric。正式标注时，高风险样本双人标注，不一致的进入仲裁；低风险样本可以抽检。之后定期计算一致率，回看争议样本。如果一致率低，我优先怀疑标准不清，而不是简单要求标注者更认真。

### Q6：怎么防止评测集泄漏到训练集或 Prompt 示例里？

**标准答案：**  
我会把评测集作为只读资产管理，和训练集、Few-shot 示例池隔离。样本有唯一 `case_id`、来源和集合标签，进入微调或示例池前要做 ID 和语义相似去重。Prompt 示例不能自动从上线门禁集里抽，回归集也不能拿去训练。报告里区分 seen 和 unseen，如果发现某个版本对 seen 样本提升很大但 unseen 不提升，就要警惕过拟合或泄漏。

### Q7：LLM-as-Judge 能不能替代人工评审？

**标准答案：**  
不能完全替代。LLM-as-Judge 很适合做规模化初筛和语义评分，但它也有模型偏好、提示词敏感和版本漂移问题。我的做法是把 Judge 的 Prompt、模型、温度固定，输出结构化分数和理由，并用人工抽样校准一致性。高风险场景还要加规则校验和人工复核。面试里我会强调：Judge 是评审工具，不是绝对真相。

### Q8：如果评测集越来越大，回归成本太高怎么办？

**标准答案：**  
我会分层管理。核心黄金集和安全集每次都跑，历史回归集按影响模块选择性跑，大规模探索集可以夜间或发布前跑。也可以做 smoke eval，先用小集合快速拦截明显退化，再跑完整集合。关键是抽样要稳定，不能每次随机导致分数不可比；同时保留失败样本列表和分层指标，而不是只看总体平均分。

### Q9：评测结果显示总体提升，但某些分层下降，你怎么判断能不能上线？

**标准答案：**  
我会先看下降分层的业务风险。如果是高风险权限、支付、合规、安全类，即使总体提升也不能直接上线；如果是低风险长尾表达下降，要看幅度、样本数量和线上影响面。决策上我会对比基线，分析失败样本，必要时做定向修复或灰度限制。上线门禁应该提前定义，比如核心分层不允许显著下降，严重安全违规必须为零。

### Q10：面试官问“你们评测集多少条才够”，怎么回答？

**标准答案：**  
我不会只报一个固定数字。够不够取决于业务复杂度、场景分层和上线风险。早期可以用几十到几百条覆盖核心链路和高风险场景，先保证每条都标得准；成熟后再扩到上千条，覆盖高频、长尾、安全和历史坏 Case。比数量更重要的是覆盖率、标注一致性、版本稳定性和它能不能真实发现回归。很多团队评测集很大，但样本重复、标准不清，反而不可靠。
