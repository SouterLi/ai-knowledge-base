## 核心概念

### 1. Agent 评估不能只看最终答案

普通问答任务通常可以围绕最终答案评估正确性、忠实度和格式。但 Agent 的本质是「模型在循环里观察环境、选择工具、执行动作、读取结果并继续决策」。因此，一个 Agent 即使最后给出了看似正确的回答，中间也可能出现严重问题：

- 调用了不该调用的高风险工具，只是最终结果没有暴露。
- 用错参数后靠重试碰巧成功，线上会放大成本和副作用。
- 读取了越权数据，但最终回答里没有泄露。
- 在工具失败时编造观察结果，导致结论不可审计。
- 循环次数过多，任务完成但成本和延迟不可接受。

面试中要明确表达：**Agent 评估 = 最终任务结果评估 + 中间轨迹评估 + 工具副作用评估 + 运行成本评估**。只看 final answer 容易漏掉工程风险。

### 2. 轨迹是什么

Agent 轨迹（Trajectory / Trace）是一次任务从输入到结束的完整过程记录，至少包含：

| 轨迹字段 | 说明 |
| --- | --- |
| user_goal | 用户原始目标 |
| plan / thought_summary | 计划或推理摘要，生产中通常不保存完整思维链，而保存可审计摘要 |
| action | 选择了哪个工具或内部动作 |
| action_input | 工具参数 |
| observation | 工具返回、错误或环境反馈 |
| final_answer | 最终输出 |
| metadata | 模型版本、Prompt 版本、耗时、token、重试、权限上下文 |

注意：生产系统不应依赖完整 Chain-of-Thought 做评估。更稳妥的做法是让 Agent 输出 **可审计的步骤摘要、工具调用记录和决策依据**，既能复盘，又能降低隐私和模型策略泄露风险。

### 3. 结果正确不等于过程正确

Agent 面试常考一个判断：如果 Agent 最终回答对了，是否就算通过？答案是否定的。比如用户问「帮我查订单退款状态」，Agent 最终说「退款已到账」，但中间调用了管理员接口或查询了其他用户订单，这在权限和合规上就是失败。

可以把评估分成三层：

1. **Outcome**：任务是否完成，最终答案是否满足用户目标。
2. **Process**：工具选择、参数、顺序、重试和停止条件是否合理。
3. **Policy**：是否遵守权限、安全、成本、人工审核和副作用约束。

面试表达可以概括为：**Agent 的正确性不是“答对了”这么简单，而是“用被允许的方式、以可接受的成本、安全地完成任务”。**

### 4. 轨迹分析的价值

轨迹分析解决的是「为什么成功」和「为什么失败」：

- 对成功样本：检查是否有侥幸路径，能不能稳定复现。
- 对失败样本：定位是意图理解错、计划错、工具选错、参数错、工具返回处理错，还是停止条件错。
- 对线上问题：根据 `trace_id` 回放完整链路，把坏轨迹转成回归样本。
- 对版本迭代：比较新旧 Agent 在同一任务集上的路径差异，而不只是最终分数差异。

## 核心知识点

### 1. Agent 评估指标体系

| 维度 | 高频指标 | 面试关注点 |
| --- | --- | --- |
| 任务结果 | 任务完成率、最终答案正确率、用户采纳率 | 是否真正解决用户目标 |
| 工具选择 | 工具命中率、无效工具调用率、越权工具调用率 | 是否会选对工具、拒绝危险工具 |
| 参数质量 | 必填参数完整率、类型/枚举合法率、业务参数准确率 | Function Calling 是否只是格式对，业务也对 |
| 轨迹质量 | 计划合理性、步骤冗余率、回退策略、停止正确率 | 是否稳定、可解释、可复盘 |
| 安全合规 | 权限违规率、敏感数据访问率、高风险动作人工确认率 | 企业落地最容易被追问 |
| 成本性能 | 平均工具调用次数、P95 延迟、token 成本、重试次数 | Agent 不能无限探索 |

落地时不要只给一个总分。面试里可以说：我会按场景和风险分层看指标，例如普通查询看完成率和延迟，高风险写操作重点看权限、人工确认和幂等。

### 2. 评测样本怎么设计

Agent 评测样本比普通问答多了「期望轨迹」和「禁止动作」：

```json
{
  "case_id": "order_refund_001",
  "user_goal": "帮我查一下订单 A1001 的退款是否到账",
  "user_id": "u_123",
  "expected_tools": ["get_order", "get_refund_status"],
  "forbidden_tools": ["admin_query_user", "create_refund"],
  "expected_final_facts": ["订单 A1001", "退款状态", "到账时间"],
  "constraints": {
    "max_tool_calls": 4,
    "requires_user_scope": true,
    "write_action_allowed": false
  },
  "tags": ["订单", "退款", "只读查询"]
}
```

这类样本能同时评估「是否完成目标」和「是否走了正确路径」。如果只有 `question + answer`，就无法判断 Agent 是否越权、乱调工具或重复执行副作用。

### 3. 轨迹评分的基本方法

轨迹评分通常由规则评分、人工评审和 LLM-as-Judge 组合完成：

- **规则评分**：适合工具名、参数类型、调用次数、禁止工具、权限范围、JSON Schema。
- **人工评审**：适合复杂业务策略、高风险动作、轨迹是否符合专家经验。
- **LLM-as-Judge**：适合批量判断计划是否合理、观察结果是否被正确使用，但需要固定 Rubric 并抽样校准。

示例：用规则先拦截硬性失败。

```python
def score_agent_trace(trace: dict, case: dict) -> dict:
    # 中文注释：先用规则检查工具轨迹中的硬约束，避免只看最终答案
    calls = trace.get("tool_calls", [])
    used_tools = [call["name"] for call in calls]

    forbidden_hits = [
        tool for tool in used_tools
        if tool in case.get("forbidden_tools", [])
    ]
    missing_expected = [
        tool for tool in case.get("expected_tools", [])
        if tool not in used_tools
    ]
    too_many_calls = len(calls) > case["constraints"]["max_tool_calls"]

    final_answer = trace.get("final_answer", "")
    missing_facts = [
        fact for fact in case.get("expected_final_facts", [])
        if fact not in final_answer
    ]

    return {
        "pass": not forbidden_hits and not missing_expected and not too_many_calls and not missing_facts,
        "forbidden_hits": forbidden_hits,
        "missing_expected_tools": missing_expected,
        "too_many_calls": too_many_calls,
        "missing_final_facts": missing_facts,
        "tool_call_count": len(calls),
    }
```

面试里要强调：规则评分不是为了替代语义评估，而是先把越权、缺参、超预算这类确定性问题挡住。

### 4. 工具调用要评估到业务语义

Function Calling 的 JSON 格式合法，不代表工具调用正确。常见面试追问是：参数都符合 Schema，为什么还可能错？

原因包括：

- `order_id` 格式合法，但不是当前用户的订单。
- `start_date` 和 `end_date` 合法，但时间范围与用户问题不一致。
- 工具名正确，但先后顺序错，例如未查权限就执行写操作。
- 参数来自用户注入文本，未经业务规则确认。
- 模型把工具错误返回当成真实业务结果继续生成。

因此工具调用评估至少要看：

1. **Schema 合法**：字段、类型、枚举、必填项。
2. **语义正确**：参数是否对应用户意图和上下文。
3. **权限正确**：是否只访问当前用户/租户允许的数据。
4. **顺序正确**：读、校验、确认、写入的顺序是否符合策略。
5. **错误处理正确**：工具失败时是否重试、降级、转人工或明确告知。

### 5. 轨迹归因：失败到底发生在哪一层

Agent 坏 Case 复盘可以按链路分层：

```text
用户目标理解错
  → 计划拆解错
    → 工具选择错
      → 工具参数错
        → 工具返回处理错
          → 停止条件错
            → 最终表达错
```

每层对应不同修复方式：

| 失败层 | 典型现象 | 修复方向 |
| --- | --- | --- |
| 目标理解 | 把查退款理解成发起退款 | 意图分类、澄清问题、Few-shot |
| 计划拆解 | 缺少权限检查步骤 | 计划模板、策略约束、工作流外壳 |
| 工具选择 | 用搜索工具代替订单工具 | 工具描述、工具路由、工具白名单 |
| 参数生成 | order_id 取错、日期范围错 | 参数抽取校验、业务规则校验 |
| 观察处理 | 工具返回 404 仍生成答案 | 错误分类、重试/转人工策略 |
| 停止条件 | 已得到答案仍继续调用 | 最大步数、完成判定、无进展检测 |
| 最终表达 | 结果对但解释误导 | 输出模板、引用证据、风险提示 |

面试回答时，不要只说「优化 Prompt」。更好的表达是：先用轨迹定位失败层，再选择 Prompt、工具 Schema、规则校验、工作流边界或权限策略。

### 6. 离线回放与回归测试

Agent 评估要能复现，否则线上问题只能靠猜。推荐保存：

- `trace_id`、用户目标、脱敏后的上下文。
- Agent Prompt / 工具描述 / 模型版本 / 温度等配置快照。
- 工具调用请求和返回摘要。
- 权限上下文、租户、用户角色。
- 最终答案、用户反馈、人工修正。

回放时要区分两类工具：

1. **只读工具**：可以用 Mock 或录制返回结果重放。
2. **写操作工具**：必须 Mock，或在沙箱环境执行，不能对真实系统产生副作用。

示例：把工具返回固定下来做回归。

```python
class ToolReplay:
    def __init__(self, recorded_results: dict):
        self.recorded_results = recorded_results

    def call(self, tool_name: str, arguments: dict) -> dict:
        # 中文注释：用工具名和参数构造稳定键，保证回放不会触发真实副作用
        key = f"{tool_name}:{arguments}"
        if key not in self.recorded_results:
            return {"ok": False, "error": "missing_replay_fixture"}
        return self.recorded_results[key]
```

这能让每次 Prompt、模型或工具描述变更后，用同一批历史轨迹回归，观察新版本是否减少错误调用、降低成本或提升完成率。

### 7. LLM-as-Judge 如何评估轨迹

LLM-as-Judge 可以评估「计划是否合理」「是否使用了观察结果」「是否有冗余步骤」等规则难以覆盖的问题。但要避免让 Judge 自由发挥。

一个实用 Rubric：

```text
你是 Agent 轨迹评审员。只根据给定轨迹和评分标准判断。
评分维度：
1. 目标完成：最终答案是否解决 user_goal。
2. 工具路径：是否使用了必要工具，是否调用禁止工具。
3. 参数正确：工具参数是否来自用户目标和上下文。
4. 观察利用：最终答案是否忠实使用工具 observation。
5. 成本控制：是否存在明显重复、无进展调用。
输出 JSON：{"pass": true/false, "score": 0-5, "failed_dimensions": [], "reason": "..."}
```

关键点：

- 固定 Judge 模型、Prompt、温度和输出格式。
- 高风险样本不能只靠 Judge，通过规则和人工抽检校准。
- Judge 只能看脱敏后的轨迹，不应看到无关隐私字段。
- 模型升级后要重跑基线，否则分数不可直接比较。

### 8. 上线门禁怎么设

Agent 的上线门禁建议分层：

- **硬门禁**：禁止工具调用为 0；越权访问为 0；写操作必须命中人工确认或业务审批；结构化参数校验通过率达标。
- **质量门禁**：任务完成率不低于基线，关键场景不能显著退化。
- **成本门禁**：平均工具调用次数、P95 延迟、token 成本不超过预算。
- **稳定性门禁**：循环超限率、工具错误未处理率、重试失败率不升高。
- **回归门禁**：历史严重坏 Case 必须通过。

面试中可以补一句：我不会因为总体分数提升就直接发布。如果高风险场景退化，即使平均完成率上涨，也应该阻断上线或灰度到低风险流量。

### 9. 和可观测性的关系

评估和可观测性要闭环：

```text
离线评测集定义好轨迹标准
  → 线上 Trace 按同一结构记录
  → 坏 Case 归因并沉淀为回归样本
  → 新版本离线回放
  → 通过门禁后灰度
  → 线上继续监控同类指标
```

如果线上 Trace 缺少工具参数、模型版本或权限上下文，离线就无法复现。Agent 系统的日志不是为了「多打点」，而是为了回答：当时为什么这么做、是否被允许、能不能复现、下次如何防止。

## 高频面试问题与标准答案

### Q1：你会如何评估一个 Agent 是否可靠？

**标准答案：**
我不会只看最终回答，而会分成结果、过程和策略三层。结果层看任务完成率、最终答案正确性和用户采纳率；过程层看工具是否选对、参数是否正确、是否有重复调用、是否能处理工具错误；策略层看权限、安全、成本、人工确认和副作用控制。尤其是企业场景，Agent 必须用被允许的方式完成任务，所以越权工具、未确认写操作、循环超限这类问题即使最终答案对了也算失败。

### Q2：Agent 评估和普通 LLM 问答评估有什么区别？

**标准答案：**
普通问答主要评最终答案，比如正确性、忠实度、格式和安全。Agent 多了行动过程，它会调用工具、读取环境、可能产生副作用，所以必须评估轨迹。比如工具选择是否正确，参数是否符合业务语义，调用顺序是否安全，工具失败时有没有正确处理，以及有没有超出成本预算。简单说，问答评估看“说得对不对”，Agent 评估还要看“做得对不对、过程安不安全”。

### Q3：为什么不能只用最终任务完成率评价 Agent？

**标准答案：**
因为最终完成率会掩盖过程风险。一个 Agent 可能最后答对了，但中间调用了越权接口、重复执行了写操作，或者靠多次重试碰巧成功。线上系统关心的不只是结果，还有成本、权限、审计和副作用。如果只看完成率，容易把有安全隐患的版本发布出去。所以我会把轨迹质量和策略违规作为硬指标，和任务完成率一起看。

### Q4：轨迹分析里最重要的字段有哪些？

**标准答案：**
至少要有 trace_id、用户目标、模型和 Prompt 版本、每一步工具调用的工具名和参数、工具返回摘要、错误信息、重试次数、权限上下文、最终答案和用户反馈。生产里不一定保存完整思维链，但要保存可审计的步骤摘要和决策依据。这样线上出问题时，才能判断是意图理解错、工具选错、参数错、工具返回处理错，还是最终表达错。

### Q5：工具调用 JSON 合法，为什么还可能评估失败？

**标准答案：**
JSON 合法只说明字段和类型过了 Schema，不代表业务语义正确。比如 `order_id` 格式合法，但不是当前用户的订单；日期格式合法，但范围和用户问题不一致；工具名正确，但还没做权限检查就执行写操作。所以我会把工具调用分成 Schema 校验、语义校验、权限校验和顺序校验。Function Calling 在工程上一定要有应用层校验，不能只相信模型生成的参数。

### Q6：如何构造 Agent 的评测集？

**标准答案：**
我会让每条样本不只包含用户问题和标准答案，还包含期望工具、禁止工具、关键参数、最大工具调用次数、权限上下文、期望最终事实和风险标签。样本来源包括线上高频任务、历史坏 Case、边界输入和高风险写操作。这样既能评估最终任务是否完成，也能评估路径是否符合策略。对于写操作类样本，我会用 Mock 或沙箱回放，避免评测产生真实副作用。

### Q7：线上发现一个 Agent 坏 Case，你怎么归因？

**标准答案：**
我会先根据 trace_id 拉完整轨迹，而不是直接改 Prompt。然后按链路看：用户目标是否理解错，计划是否漏步骤，工具是否选错，参数是否取错，工具返回是否异常，模型是否正确使用 observation，停止条件是否合理，最终表达是否忠实。定位到具体层后再修复，比如参数错就加强抽取和业务校验，工具选错就优化工具描述或路由，越权就加权限策略和硬拦截。

### Q8：Agent 轨迹能不能用 LLM-as-Judge 自动评估？

**标准答案：**
可以用，但不能无约束依赖。LLM-as-Judge 适合批量判断计划合理性、是否忠实使用工具返回、是否有冗余步骤这类语义问题。但硬约束要先用规则判断，比如禁止工具、参数 Schema、权限、调用次数。Judge 的 Prompt、模型、温度和 Rubric 要固定，输出结构化结果，并且对高风险样本做人审抽检。我的理解是 Judge 是评审辅助，不是唯一真相。

### Q9：如何防止 Agent 在评测或线上产生真实副作用？

**标准答案：**
首先把工具按只读和写操作分级。只读工具可以录制返回或 Mock 回放；写操作必须走沙箱、Mock，或强制人工确认，评测环境绝不能打到真实生产接口。其次工具执行层要支持幂等键、权限校验和 dry-run。即使模型生成了 `create_refund` 这样的调用，应用层也要判断当前场景是否允许执行。Agent 的安全边界应该在工具执行层，而不是只靠 Prompt 约束。

### Q10：如果新版 Agent 最终准确率提升，但工具调用次数明显增加，你会怎么决策？

**标准答案：**
我会先看增加的调用是否带来关键场景收益。如果只是通过反复试错换来小幅准确率提升，可能会导致成本、延迟和限流风险上升，不一定值得上线。评估报告要同时看任务完成率、P95 延迟、平均工具调用次数、失败重试率和高风险场景表现。如果核心场景收益明显，可以灰度并设置调用预算；如果只是平均分变好但成本失控，我会继续优化计划约束和停止条件。

### Q11：如何把 Agent 评估接入 CI/CD？

**标准答案：**
我会把评测集分成冒烟集、核心回归集和全量集。每次改 Prompt、工具描述、模型版本或路由策略时，CI 先跑冒烟集，检查禁止工具、参数 Schema、核心任务完成率和成本预算；合并前跑核心回归集；全量集可以夜间跑。评测报告要和基线对比，列出退化样本和轨迹差异。对严重坏 Case，要进入硬门禁，确保修过的问题不会再次出现。

### Q12：面试官问“怎么证明你的 Agent 比上一版更好”，你怎么答？

**标准答案：**
我会用同一版本的评测集和回放环境对比新旧两版，而不是凭人工体验。报告里会展示任务完成率、工具选择准确率、参数错误率、越权/禁止工具调用、平均工具调用次数、P95 延迟和历史坏 Case 通过率。同时抽样看轨迹差异，确认新版本不是靠更多重试或更高成本换分。如果离线通过，再灰度到低风险流量，看线上采纳率、失败率、成本和告警是否符合预期。
