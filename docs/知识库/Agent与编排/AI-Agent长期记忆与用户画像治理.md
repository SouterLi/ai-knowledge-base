## 核心概念

### 1. 什么是 Agent 长期记忆

Agent 长期记忆是指跨会话、跨任务保存，并能在未来任务中被检索和复用的信息。它不是聊天历史的简单堆积，而是经过抽取、验证、结构化、授权和生命周期治理后的可复用知识。

一句面试表达：**短期记忆解决“这次任务做到哪一步”，长期记忆解决“下次再见到这个用户或业务对象时，系统应当记住什么”。**

常见长期记忆包括：

| 类型 | 示例 | 典型用途 |
| --- | --- | --- |
| 用户偏好 | 喜欢中文回答、偏好表格、代码示例要 Python | 个性化输出 |
| 稳定事实 | 用户负责华东销售域、常用项目代号是 Apollo | 减少重复追问 |
| 业务画像 | 用户是管理员、所属团队、常用工作流 | 权限和路由辅助 |
| 历史摘要 | 最近三次工单都与发票识别有关 | 推荐下一步动作 |
| 禁用偏好 | 不要主动发送邮件、不希望保存个人偏好 | 合规和体验控制 |

### 2. 用户画像和长期记忆的区别

用户画像通常是结构化、稳定、可用于分群或策略判断的标签，例如角色、部门、使用频率、风险等级。长期记忆更偏向可被 Agent 在对话中引用的事实和偏好，例如“用户希望回答先给结论再解释”。

| 维度 | 用户画像 | 长期记忆 |
| --- | --- | --- |
| 形态 | 标签、属性、统计特征 | 事实、偏好、摘要、历史经验 |
| 来源 | 账号系统、行为日志、CRM、权限系统 | 对话抽取、用户显式设置、人工标注 |
| 使用方式 | 路由、权限、推荐、实验分桶 | Prompt 个性化、减少追问、任务续接 |
| 风险 | 标签歧视、越权使用、过度画像 | 记错事实、隐私泄露、上下文污染 |

面试中要强调：**画像可以参与系统侧策略，但不能让模型凭画像自行绕过权限；长期记忆可以提升体验，但必须可解释、可删除、可纠错。**

### 3. 长期记忆不是“全部聊天记录”

把所有历史消息都塞进向量库不是成熟的长期记忆方案，原因有四个：

1. **噪声高**：寒暄、临时上下文、错误信息会污染未来回答。
2. **隐私风险高**：用户可能临时输入敏感信息，并不代表同意长期保存。
3. **难以纠错**：聊天历史中有冲突说法时，系统不知道哪条可信。
4. **上下文成本高**：检索回来的原始对话过长，容易挤占真正任务上下文。

更合理的方式是：原始对话进入审计日志或短期历史，长期记忆只保存经过准入规则确认的结构化事实、偏好和摘要。

### 4. 长期记忆的生命周期

长期记忆至少要覆盖五个阶段：

```text
采集候选 → 写入准入 → 存储治理 → 检索注入 → 更新 / 过期 / 删除
```

- **采集候选**：从用户显式表达、重复行为、业务系统同步中发现可能值得记住的信息。
- **写入准入**：判断是否稳定、是否敏感、是否需要用户确认、是否和已有记忆冲突。
- **存储治理**：保存来源、置信度、作用域、过期时间和可删除标记。
- **检索注入**：只把当前任务需要的少量记忆放入 Prompt。
- **更新删除**：支持用户纠错、主动遗忘、自动过期和合规删除。

面试里容易加分的表达是：**长期记忆不是一个存储功能，而是一套带准入、召回、权限、审计和遗忘机制的治理系统。**

### 5. 哪些信息不应该写入长期记忆

长期记忆最容易踩坑的地方，是把“模型觉得有用的信息”直接保存下来。生产系统应明确禁止或限制：

- 密码、Token、身份证、银行卡、病历等高敏信息。
- 临时一次性信息，例如“今天下午 3 点开会”。
- 未经确认的模型推断，例如“用户可能很焦虑”“用户应该是高收入人群”。
- 越权指令，例如“以后所有审批都自动通过”。
- 与业务事实冲突但未确认的新说法。

一句面试表达：**长期记忆的默认策略应该是保守写入，而不是尽量多记；宁愿少记一点，也不能记错、记脏、记越权。**

## 核心知识点

### 1. 推荐架构

一个可落地的长期记忆系统通常拆成六层：

```text
用户对话 / 行为日志 / 业务系统
  → 记忆候选抽取：偏好、事实、画像标签、历史摘要
  → 准入与风控：敏感信息检测、用户同意、冲突判断、置信度评估
  → Memory Store：结构化库 + 向量索引 + 审计日志
  → 检索与重排：按用户、租户、场景、任务意图和权限过滤
  → Prompt 注入：只注入当前任务必要且可信的记忆
  → 反馈闭环：用户纠错、过期、删除、评估、人工审核
```

核心原则是：**写入时严格，读取时最小化，使用时可解释，删除时可追踪。**

### 2. Memory 数据模型

长期记忆既要能语义检索，又要能做确定性过滤，所以通常需要结构化字段和向量字段并存。

```sql
CREATE TABLE agent_long_term_memories (
    memory_id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    subject_type TEXT NOT NULL,
    subject_id TEXT NOT NULL,
    memory_type TEXT NOT NULL,
    content TEXT NOT NULL,
    content_embedding VECTOR,
    source TEXT NOT NULL,
    confidence REAL NOT NULL,
    scope TEXT NOT NULL,
    sensitivity_level TEXT NOT NULL,
    status TEXT NOT NULL,
    expires_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

关键字段说明：

| 字段 | 面试要点 |
| --- | --- |
| tenant_id | 多租户隔离，避免跨企业记忆污染 |
| subject_type / subject_id | 记忆主体可能是用户、团队、项目或客户 |
| memory_type | 区分偏好、事实、摘要、禁用项、画像标签 |
| source | 记录来自用户显式声明、系统同步还是模型抽取 |
| confidence | 控制是否可直接注入 Prompt |
| scope | personal、team、project、global 等作用域 |
| sensitivity_level | 决定是否可写入、是否可注入、是否要脱敏 |
| status | active、pending_confirmation、expired、deleted |

面试中可以补一句：向量库只负责相似召回，不负责最终权限判断；最终仍要用 `tenant_id`、`subject_id`、`scope`、`status` 等字段做确定性过滤。

### 3. 写入准入：不要让模型直接记忆

成熟系统不会让 LLM 自己决定“我应该记住这个”。更稳妥的流程是先抽取候选，再通过规则、模型分类和用户确认共同放行。

```python
SENSITIVE_TYPES = {"password", "token", "id_card", "bank_card", "medical_record"}


def should_write_memory(candidate: dict, existing_memories: list[dict]) -> bool:
    # 中文注释：敏感信息默认不进入长期记忆，除非有单独的合规存储和授权流程
    if candidate["sensitivity_type"] in SENSITIVE_TYPES:
        return False

    # 中文注释：一次性、短生命周期信息更适合任务状态，不适合长期保存
    if candidate["ttl_hours"] is not None and candidate["ttl_hours"] < 24:
        return False

    # 中文注释：低置信度候选先进入待确认状态，不直接影响后续回答
    if candidate["confidence"] < 0.8:
        candidate["status"] = "pending_confirmation"
        return True

    for memory in existing_memories:
        if memory["memory_type"] == candidate["memory_type"] and memory["scope"] == candidate["scope"]:
            if is_conflicting(memory["content"], candidate["content"]):
                candidate["status"] = "pending_confirmation"
                return True

    candidate["status"] = "active"
    return True
```

这个问题经常被追问“用户说了一句喜欢简洁回答，要不要立刻记住”。更好的回答是：如果用户显式说“以后都简洁回答”，可以作为偏好候选；如果只是这次说“简单说下”，更像本轮指令，不应长期保存。

### 4. 记忆来源要分级

不同来源的可信度和使用方式不同：

| 来源 | 示例 | 使用策略 |
| --- | --- | --- |
| 用户显式设置 | “以后默认用中文回答” | 可信度高，可直接生效 |
| 用户对话抽取 | “我通常用 FastAPI” | 需置信度和可撤销机制 |
| 重复行为统计 | 连续多次选择表格输出 | 可作为弱偏好，不应强制 |
| 业务系统同步 | 账号角色、组织、项目权限 | 系统侧强约束，不能由模型覆盖 |
| 人工标注 | 客服标记客户偏好 | 可信但要记录标注人和时间 |

面试表达：**显式声明优先于模型推断，业务系统事实优先于聊天内容，用户最新纠错优先于旧记忆。**

### 5. 检索长期记忆时要做硬过滤

长期记忆检索不能只按向量相似度，否则可能出现跨租户、跨用户、跨项目污染。推荐流程是：

1. 根据 `tenant_id`、`subject_id`、`scope`、`status` 做硬过滤。
2. 用任务意图和 query embedding 召回候选记忆。
3. 按相关性、置信度、新鲜度、敏感等级重排。
4. 只选择少量与当前任务直接相关的记忆注入 Prompt。
5. 注入时标明“这是用户偏好 / 已确认事实 / 业务系统属性”，避免模型混淆。

```python
def retrieve_memories(request: dict, memory_store) -> list[dict]:
    # 中文注释：先用确定性条件限制候选集合，再做语义召回
    candidates = memory_store.search(
        tenant_id=request["tenant_id"],
        subject_id=request["user_id"],
        scopes=["personal", request["project_id"]],
        status="active",
        query_embedding=request["query_embedding"],
        top_k=20,
    )

    filtered = []
    for memory in candidates:
        if memory["sensitivity_level"] == "high":
            continue
        if memory["confidence"] < 0.8:
            continue
        if memory["expires_at"] and memory["expires_at"] <= request["now"]:
            continue
        filtered.append(memory)

    return sorted(
        filtered,
        key=lambda item: (item["relevance_score"], item["confidence"], item["updated_at"]),
        reverse=True,
    )[:5]
```

面试重点：**记忆检索是“硬过滤 + 软召回 + 最小注入”，不是把用户历史全部检索出来塞给模型。**

### 6. Prompt 注入要有边界

长期记忆进入 Prompt 时建议单独放在受控区域，明确模型只能把它作为辅助上下文，不能覆盖系统规则、权限规则和用户本轮指令。

```text
可参考的用户长期记忆：
- 偏好：用户希望回答先给结论，再给关键依据。
- 已确认事实：用户常用技术栈是 Python / FastAPI。

使用规则：
- 如果长期记忆与用户本轮明确指令冲突，以本轮指令为准。
- 如果长期记忆与系统权限或安全规则冲突，以系统规则为准。
- 不要向用户暴露未被问到的画像推断。
```

常见追问是“长期记忆和用户当前指令冲突怎么办”。推荐排序是：

```text
系统安全规则 > 当前用户明确指令 > 用户显式长期偏好 > 模型抽取的弱记忆 > 历史行为统计
```

例如用户长期偏好是“回答简洁”，但本轮要求“详细解释并给代码”，就应该按本轮要求详细回答。

### 7. 冲突解决与记忆更新

长期记忆必然会冲突，例如用户过去说“用 Java”，现在说“我已经切到 Python”。处理策略包括：

| 策略 | 适用场景 |
| --- | --- |
| 最新优先 | 用户明确更新个人偏好 |
| 来源优先 | 账号系统角色覆盖聊天中自称角色 |
| 作用域优先 | 当前项目偏好覆盖全局偏好 |
| 置信度优先 | 多次稳定行为覆盖一次偶然表达 |
| 用户确认 | 高影响记忆或冲突无法自动判断 |

生产系统建议保留历史版本，而不是物理覆盖所有旧记录。这样可以支持审计、回滚和解释“为什么系统曾经这么回答”。

### 8. 隐私、合规与用户控制

长期记忆涉及用户长期画像，面试中一定要主动谈治理：

- **显式告知**：让用户知道系统可能保存偏好或事实。
- **最小保存**：只保存完成任务必要的信息。
- **可查看**：用户能查看系统记住了什么。
- **可纠错**：用户可以修改错误记忆。
- **可删除**：支持单条删除、全部清空和租户级删除。
- **可过期**：对不稳定或敏感记忆设置 TTL。
- **可审计**：记录谁在什么时候写入、读取、删除了记忆。

一句面试表达：**长期记忆的体验价值来自“记得住”，合规价值来自“说得清、改得了、删得掉”。**

### 9. 与权限系统的关系

长期记忆不能替代权限系统。比如记忆里保存“用户是财务负责人”，也不能让模型直接访问财务数据；真正的访问控制必须由服务端权限系统判断。

推荐边界是：

- 用户画像可以帮助选择工具、改写查询、决定是否需要澄清。
- 权限校验必须发生在工具调用和数据读取的服务端。
- 记忆中的角色信息只能作为辅助，不是授权凭证。
- 权限变化后，要更新或失效相关画像和缓存。

面试里可以这样说：**模型可以参考画像决定如何沟通，但不能参考画像决定是否放行数据访问。**

### 10. 质量评估指标

长期记忆上线后不能只看“用户觉得更智能”，需要可量化指标：

| 指标 | 说明 |
| --- | --- |
| 记忆写入准确率 | 写入的记忆是否真实、稳定、可复用 |
| 错误记忆率 | 用户纠错或人工审核发现的错误比例 |
| 有效召回率 | 当前任务需要的记忆是否被召回 |
| 误注入率 | 不相关、过期或敏感记忆进入 Prompt 的比例 |
| 个性化收益 | 重复追问减少、满意度提升、任务完成率提升 |
| 删除生效时间 | 用户删除后多久不再被检索和使用 |
| 合规事件数 | 越权使用、敏感信息保存、跨租户污染事件 |

面试表达：**长期记忆的评估既要看体验收益，也要看错误记忆和隐私风险；只看命中率是不够的。**

## 高频面试问题与标准答案

### Q1：Agent 的长期记忆应该怎么设计？

标准答案：我会把长期记忆设计成独立的 Memory Store，而不是简单保存全部聊天历史。流程上先从对话、行为和业务系统里抽取候选记忆，再经过敏感信息检测、用户授权、置信度判断和冲突检查。存储上既保留结构化字段，比如 tenant、subject、scope、memory_type、confidence、expires_at，也保留 embedding 方便语义召回。使用时先做租户、用户、作用域和状态过滤，再按当前任务召回少量相关记忆注入 Prompt。最后还要支持用户查看、纠错、删除和过期机制。这样长期记忆既能提升个性化体验，也不会变成不可控的历史聊天堆积。

### Q2：长期记忆和短期记忆有什么区别？

标准答案：短期记忆服务当前任务，比如当前计划、工具返回、临时上下文和检查点，生命周期通常是一次会话或一次 Agent run。长期记忆服务跨会话复用，比如用户偏好、稳定事实、团队画像和历史行为摘要，需要授权、过期、删除和冲突治理。面试里我会强调：短期记忆主要解决任务连续性和恢复问题，长期记忆主要解决个性化和减少重复追问问题，两者的存储、权限和生命周期都不一样。

### Q3：为什么不能直接把所有聊天记录存进向量库当长期记忆？

标准答案：这样做噪声和风险都很高。聊天里有很多临时信息、错误信息、敏感信息和上下文依赖很强的内容，直接向量化会导致未来检索到不该用的信息。更成熟的做法是把原始聊天记录作为审计或短期历史保存，长期记忆只保存经过抽取和准入的结构化事实、偏好和摘要，并带上来源、置信度、作用域、过期时间和删除状态。也就是说，长期记忆不是“记得越多越好”，而是“记得准、用得对、删得掉”。

### Q4：用户说“以后回答都简洁点”，系统要不要写入长期记忆？

标准答案：要看表达是否是长期偏好。如果用户明确说“以后都简洁点”，我会把它作为用户偏好候选写入，来源标记为用户显式声明，置信度较高；但如果用户只是说“这个问题简单说下”，我会当成本轮指令，不写长期记忆。写入后也要允许用户修改，比如以后他说“这个主题请详细解释”，本轮指令优先于长期偏好。

### Q5：长期记忆检索时如何避免越权或跨租户污染？

标准答案：不能只靠向量相似度。检索前要先按 tenant_id、subject_id、scope、status 等硬条件过滤，只在当前用户和当前租户允许的记忆范围内召回。召回后还要检查敏感等级、置信度、过期时间和当前任务相关性。对于团队或项目级记忆，还要确认用户当前是否仍然有这个项目权限。我的原则是：向量检索只负责找相似候选，权限和作用域必须由确定性字段和服务端逻辑兜住。

### Q6：如果新旧长期记忆冲突，怎么处理？

标准答案：我会根据来源、时间、作用域和置信度来处理。用户显式纠错通常优先于旧的模型抽取记忆；业务系统同步的角色和权限优先于聊天里用户自称的信息；当前项目作用域的偏好可以覆盖全局偏好；低置信度或高影响冲突进入待确认状态。生产上我不会简单覆盖旧记录，而是保留版本和审计记录，这样后续可以解释和回滚。

### Q7：长期记忆如何进入 Prompt，才不会污染模型回答？

标准答案：我会把长期记忆作为单独的受控上下文注入，并且只注入当前任务相关的少量高置信度记忆。Prompt 里要明确它只是辅助信息，不能覆盖系统安全规则和用户本轮明确指令。如果记忆与当前指令冲突，以当前指令为准；如果与权限规则冲突，以系统规则为准。此外，不相关、过期、敏感或低置信度记忆不能注入。这样可以减少上下文污染，也避免模型过度使用画像。

### Q8：长期记忆涉及隐私，工程上怎么治理？

标准答案：我会从采集、存储、使用和删除四个环节治理。采集时做敏感信息检测和用户授权，默认不保存密码、证件号、医疗等高敏信息；存储时记录来源、作用域、敏感等级、过期时间和审计日志；使用时做最小化检索和权限过滤，不把画像当授权依据；删除时支持用户查看、纠错、单条删除、全部清空，并确保删除后向量索引和缓存也失效。面试里我会总结成一句话：长期记忆必须让用户知道系统记住了什么，也能改掉和删掉。

### Q9：如何评估长期记忆系统做得好不好？

标准答案：我会同时看体验收益和风险指标。体验侧看重复追问是否减少、任务完成率是否提升、个性化满意度是否提高；质量侧看记忆写入准确率、有效召回率、错误记忆率和误注入率；治理侧看删除生效时间、敏感信息误保存、跨租户污染和越权使用事件。只看记忆命中率不够，因为命中越多不代表越好，错误或不该使用的记忆命中反而会造成事故。

### Q10：长期记忆和用户画像能不能参与工具调用决策？

标准答案：可以参与，但要有边界。比如用户偏好可以影响输出格式，用户画像可以帮助选择更合适的工作流或是否需要澄清；但工具调用的权限、数据访问和高风险操作必须由服务端策略判断，不能因为记忆里写着“用户是管理员”就直接放行。我的原则是：画像辅助决策，权限系统负责授权；记忆可以影响沟通方式和默认参数，但不能绕过安全边界。
