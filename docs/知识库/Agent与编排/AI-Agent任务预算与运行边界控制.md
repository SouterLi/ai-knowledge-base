## 核心概念

### 1. 什么是 Agent 任务预算

Agent 任务预算是指在一次 Agent run 开始前或运行中，为它设置明确的资源和行为边界，例如：

- 最多可以规划多少步；
- 最多调用多少次工具；
- 最多消耗多少 token 或金额；
- 最长运行多久；
- 能否调用写操作工具；
- 失败后最多重试几次；
- 什么时候必须追问用户、转人工或安全失败。

一句面试表达：**Agent 任务预算不是单纯为了省钱，而是为了防止 Agent 在不确定任务里无限推理、无限调用工具或执行超出权限的动作。**

没有预算的 Agent 很容易出现三类问题：

| 问题 | 表现 | 风险 |
| --- | --- | --- |
| 无限循环 | 反复计划、反复检索、反复自我反思 | 延迟失控、成本失控 |
| 工具滥用 | 一个问题调用几十次搜索、数据库或业务 API | 压垮依赖、触发限流 |
| 行为越界 | 低置信度时继续执行写工具 | 数据错误、合规风险 |

### 2. 运行边界包含哪些内容

Agent 的运行边界通常分为四层：

```text
业务边界
  用户要完成什么任务，风险等级是什么，是否允许自动执行

权限边界
  当前用户、租户、角色能访问哪些工具和数据

资源边界
  token、费用、时长、工具次数、并发数、重试次数

状态边界
  当前任务是否已取消、超时、等待用户确认、转人工或已完成
```

面试中要强调：**预算控制不能只放在 Prompt 里写一句“不要调用太多工具”，必须由运行时服务、工具网关和状态机共同 enforce。**

### 3. Agent 预算和普通后端超时的区别

普通后端接口通常是一次请求、一次函数调用，超时比较简单。Agent 则不同，它可能包含多轮 LLM 调用、多次工具调用、并行子任务、人工确认和检查点恢复。

| 维度 | 普通后端接口 | Agent 任务 |
| --- | --- | --- |
| 执行形态 | 单次调用为主 | 多步骤、多工具、多状态 |
| 超时对象 | HTTP 请求或数据库查询 | 整体任务、每个步骤、每个工具、每次模型调用 |
| 取消语义 | 客户端断开即可终止 | 需要向模型、工具、队列、子任务传播取消信号 |
| 副作用风险 | 由业务代码控制 | 模型可能建议执行写工具，必须加外部边界 |
| 恢复方式 | 重试接口 | 从 checkpoint 恢复，并避免重复执行副作用 |

所以 Agent 的预算控制更像一个 **运行时治理系统**，而不是一个简单的 timeout 参数。

### 4. 为什么面试常考这个主题

Agent Demo 往往只展示“能自动完成任务”，但生产面试会追问“能不能稳住边界”。常见追问包括：

- 如果 Agent 一直没有找到答案，怎么停下来？
- 工具调用失败后是无限重试还是降级？
- 用户关闭页面后，后端还会继续烧 token 吗？
- 一个复杂任务超过预算，是返回半成品、转人工，还是让用户追加确认？
- 如何证明某次 Agent 失败是规划问题、工具问题，还是预算策略太紧？

成熟回答要体现：**Agent 能力越强，越需要明确的预算、权限、状态和审计边界。**

## 核心知识点

### 1. 预算维度要分层设计

Agent 预算不能只设置一个总超时时间，建议至少包含以下维度：

| 预算维度 | 示例 | 设计重点 |
| --- | --- | --- |
| 时间预算 | 总 deadline 60 秒，单工具 3 秒 | 防止长尾阻塞用户 |
| 步数预算 | 最多 8 个 reasoning step | 防止规划循环 |
| 工具预算 | 最多调用 5 次只读工具、1 次写工具 | 控制外部依赖和副作用 |
| Token 预算 | 输入 + 输出 + 中间推理总量上限 | 控制成本和上下文膨胀 |
| 费用预算 | 单次任务最高 0.2 元或 0.05 美元 | 面向多模型、多租户成本治理 |
| 重试预算 | 读工具最多 2 次，写工具不盲重试 | 避免雪崩和重复副作用 |
| 风险预算 | 高风险动作必须人工确认 | 保护资金、权限、数据变更类操作 |

面试重点：**预算要按场景、租户、用户等级、任务风险动态生成，而不是所有 Agent 共用一套固定阈值。**

例如：

```python
from dataclasses import dataclass
from enum import Enum

class RiskLevel(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"

@dataclass
class AgentBudget:
    max_steps: int
    max_tool_calls: int
    max_tokens: int
    deadline_ms: int
    allow_write_tools: bool
    require_human_confirm: bool

def build_budget(risk: RiskLevel, is_vip_tenant: bool) -> AgentBudget:
    if risk == RiskLevel.HIGH:
        return AgentBudget(
            max_steps=4,
            max_tool_calls=3,
            max_tokens=6000,
            deadline_ms=20_000,
            allow_write_tools=False,
            require_human_confirm=True,
        )

    if is_vip_tenant:
        return AgentBudget(
            max_steps=10,
            max_tool_calls=8,
            max_tokens=16_000,
            deadline_ms=90_000,
            allow_write_tools=True,
            require_human_confirm=False,
        )

    return AgentBudget(
        max_steps=6,
        max_tool_calls=5,
        max_tokens=8_000,
        deadline_ms=45_000,
        allow_write_tools=True,
        require_human_confirm=False,
    )
```

代码背后的面试表达：**预算不是写死在 Prompt 里，而是在任务进入 Agent 前，根据风险和租户策略生成，再由运行时逐步扣减。**

### 2. 停止条件要显式定义

Agent 的停止条件至少包括：

1. 已经得到满足用户目标的结果；
2. 达到最大步骤数；
3. 达到 token、费用或时间预算；
4. 连续多次工具失败或无新信息；
5. 证据不足，需要追问用户；
6. 需要高风险确认，进入人工审批；
7. 用户主动取消；
8. 系统进入降级或熔断状态。

一个常见错误是只让模型自己判断 `final_answer`，但模型可能过度自信或继续循环。更稳的做法是 **模型判断 + 运行时硬限制 + 业务状态机**。

```python
def should_stop(state: dict, budget: AgentBudget) -> tuple[bool, str]:
    if state.get("cancelled"):
        return True, "user_cancelled"

    if state["elapsed_ms"] >= budget.deadline_ms:
        return True, "deadline_exceeded"

    if state["steps"] >= budget.max_steps:
        return True, "max_steps_exceeded"

    if state["tool_calls"] >= budget.max_tool_calls:
        return True, "max_tool_calls_exceeded"

    if state["tokens_used"] >= budget.max_tokens:
        return True, "token_budget_exceeded"

    if state.get("need_human_confirm"):
        return True, "waiting_human_confirm"

    if state.get("answer_ready") and state.get("evidence_checked"):
        return True, "completed"

    return False, "continue"
```

面试中可以补一句：**停止原因要结构化记录，不能只记录 failed，否则后续无法区分是用户取消、预算不足、依赖超时还是模型规划失败。**

### 3. 总 deadline 与分段 timeout 要同时存在

Agent 需要两种超时：

- **整体 deadline**：保护用户体验和总成本，例如一次在线任务最多 60 秒；
- **分段 timeout**：保护单个依赖，例如检索 1 秒、工具 API 3 秒、模型调用 20 秒。

```text
总 deadline: 60s
  ├─ 意图识别: 1s
  ├─ 规划模型: 8s
  ├─ 检索工具: 2s
  ├─ 业务 API: 3s
  ├─ 总结生成: 15s
  └─ 预留取消、日志、降级处理时间
```

如果只有单工具 timeout，没有总 deadline，Agent 仍可能通过多次工具调用拖很久；如果只有总 deadline，没有分段 timeout，某个慢工具会吃掉全部预算。

### 4. 取消信号要全链路传播

用户关闭页面、点击取消、会话超时或系统熔断时，不能只让前端停止显示。生产系统需要把取消信号传到：

```text
前端
  → API 网关
  → Agent Runtime
  → LLM 调用
  → 工具执行器
  → 异步队列 / 子任务
  → 状态存储与审计日志
```

要注意两种场景：

| 场景 | 处理方式 |
| --- | --- |
| 只读任务 | 尽快取消下游请求，释放 token、连接和队列资源 |
| 写操作任务 | 不能简单杀进程，要进入安全检查点，确认是否已经提交、是否需要补偿 |

面试表达：**取消不是 kill 掉线程这么简单。对只读任务要快速释放资源，对写任务要先判断副作用是否已经发生，再决定补偿、回放或人工处理。**

### 5. 工具调用预算要区分读写和风险等级

工具预算不能只看次数，还要看工具类型：

| 工具类型 | 示例 | 预算策略 |
| --- | --- | --- |
| 只读低风险 | 搜索文档、查询 FAQ | 可适度重试，可并发 |
| 只读高成本 | 全库检索、复杂 SQL、外部搜索 | 限制次数和超时，必要时降级 |
| 写操作 | 创建订单、发送邮件、修改权限 | 默认需要确认、幂等键和审计 |
| 高风险写操作 | 转账、删除数据、审批通过 | 不允许 Agent 直接自动执行 |

运行时要在工具执行前检查预算：

```python
def before_tool_call(state: dict, tool: dict, budget: AgentBudget) -> None:
    if state["tool_calls"] >= budget.max_tool_calls:
        raise RuntimeError("tool budget exceeded")

    if tool["kind"] == "write" and not budget.allow_write_tools:
        raise PermissionError("write tools are disabled for this task")

    if tool["risk"] == "high" and not state.get("human_approved"):
        raise PermissionError("high risk tool requires human confirmation")

    # 中文注释：预算扣减应发生在运行时，不能依赖模型自觉少调用工具
    state["tool_calls"] += 1
```

这类代码体现的是：**模型只负责提出工具调用意图，最终能不能执行由服务端策略决定。**

### 6. Token 预算要覆盖中间过程

Agent 的 token 成本不只来自最终回答，还包括：

- 系统 Prompt；
- 历史对话；
- 规划过程；
- 工具 schema；
- 工具返回结果；
- 多轮反思和自我校验；
- 最终回答。

常见问题是只限制最终输出长度，忽略工具结果和中间上下文，导致上下文越来越大。工程上可以做：

1. 工具返回先结构化裁剪，只保留必要字段；
2. 长工具结果先摘要或分页；
3. 对历史步骤保留关键 observation，而不是完整日志；
4. 接近 token 上限时停止继续检索，转为总结已有证据；
5. 大任务转异步，让用户确认是否继续消耗预算。

面试中要说清楚：**Token 预算既是成本控制，也是可靠性控制；上下文越膨胀，模型越容易忽略关键约束。**

### 7. 预算耗尽时要有产品化结果

预算耗尽不等于直接报错。不同原因应该有不同返回：

| 停止原因 | 用户侧表达 | 后端动作 |
| --- | --- | --- |
| 证据不足 | “目前信息不足，需要补充 xxx” | 保存上下文，等待用户输入 |
| 时间超限 | “任务较复杂，已转为后台处理” | 进入异步队列 |
| 工具失败 | “依赖系统暂时不可用，可稍后重试” | 记录失败工具和降级结果 |
| 预算耗尽 | “已完成部分分析，继续需要确认” | 暂停并请求用户确认 |
| 高风险操作 | “需要人工确认后执行” | 生成审批单或转人工 |

面试表达：**预算策略的目标不是粗暴中断，而是在成本、体验和安全之间给出可解释的下一步。**

### 8. 检查点要和预算状态一起保存

Agent 支持恢复时，不能只保存消息历史，还要保存预算消耗：

```yaml
run_id: "agent_run_20260628_001"
status: "waiting_user_confirm"
budget:
  max_steps: 8
  used_steps: 5
  max_tool_calls: 6
  used_tool_calls: 4
  max_tokens: 12000
  used_tokens: 8700
stop_reason: "budget_continue_requires_confirm"
last_safe_checkpoint: "after_readonly_tools"
```

如果恢复时重新给一份完整预算，Agent 可能绕过原有限制；如果不记录 checkpoint，就可能重复执行已经成功的写工具。

### 9. 观测指标要能解释预算策略是否合理

建议重点监控：

| 指标 | 用途 |
| --- | --- |
| stop_reason 分布 | 看是正常完成多，还是预算耗尽多 |
| 平均 step 数 / P95 step 数 | 发现规划循环和任务复杂度变化 |
| 工具调用次数与失败率 | 定位工具滥用或依赖不稳定 |
| token_used 与 cost | 控制成本和上下文膨胀 |
| deadline_exceeded 比例 | 判断超时策略是否过紧 |
| user_cancelled 比例 | 判断等待时间和体验问题 |
| human_confirm_rate | 判断风险策略是否过保守或过宽松 |
| resume_success_rate | 判断检查点恢复能力 |

这些指标要按场景、租户、模型版本、Prompt 版本和工具版本切分，否则平均值会掩盖某类 Agent 任务的预算问题。

### 10. 常见设计误区

1. **只靠 Prompt 限制 Agent 行为**：模型可能不遵守，必须服务端强制。
2. **只设总超时，不设单步骤 timeout**：一个慢工具拖垮全链路。
3. **预算耗尽直接失败**：用户体验差，也浪费已经完成的中间结果。
4. **恢复时重置预算**：绕过原有成本和风险限制。
5. **读写工具同等重试**：写工具可能产生重复副作用。
6. **只看成功率，不看停止原因**：无法判断失败是策略合理拒绝，还是系统能力不足。

## 高频面试问题与标准答案

### 问题 1：为什么 Agent 需要任务预算？不能让模型自己判断什么时候结束吗？

标准答案：不能只靠模型自己判断。Agent 面对复杂任务时可能会反复规划、反复检索、反复调用工具，尤其是证据不足或工具失败时，容易出现循环。任务预算的作用是给运行时设置硬边界，包括最大步骤数、工具调用次数、token、总耗时、重试次数和高风险动作限制。模型可以建议下一步，但最终是否继续执行要由服务端预算、权限和状态机决定。这样既控制成本，也避免无限循环和越权执行。

### 问题 2：如果让你设计 Agent 的预算系统，你会包含哪些维度？

标准答案：我会分成资源预算、行为预算和风险预算。资源预算包括总 deadline、单步骤 timeout、token、费用和并发；行为预算包括最大 step 数、最大工具调用次数、重试次数和停止条件；风险预算包括是否允许写工具、是否需要人工确认、是否能访问敏感数据。预算不是固定写死的，会根据任务类型、租户等级、用户权限和风险等级动态生成，并在每一步执行前由运行时扣减和校验。

### 问题 3：Agent 一直调用工具但没有得到答案，怎么让它停下来？

标准答案：我会设置多个停止条件，而不是只等模型输出最终答案。比如最大工具次数、最大 step 数、总时间、连续无新信息次数、检索证据不足、同类工具重复失败等。运行时每一步都检查这些条件，如果触发就停止继续调用工具，并根据原因返回不同结果：证据不足就追问用户，依赖失败就降级或稍后重试，复杂任务超时就转异步。关键是 stop_reason 要结构化记录，后续才能分析是预算太紧、工具不好用，还是规划策略有问题。

### 问题 4：用户关闭页面或点击取消后，Agent 后端应该怎么处理？

标准答案：取消信号要全链路传播，不能只是前端不展示。后端要通知 Agent Runtime 停止后续步骤，取消正在进行的模型流式生成和只读工具调用，释放连接、token 和队列资源。如果已经进入写操作，就不能简单 kill，要检查是否到达安全检查点：写入是否已经提交、是否需要补偿、是否要记录人工处理。最后状态要标记为 cancelled，并记录取消发生在哪一步，方便分析用户是因为等待太久取消，还是产品交互导致误取消。

### 问题 5：总 timeout 和每个工具的 timeout 应该怎么配合？

标准答案：两者都需要。总 timeout 或 deadline 控制一次 Agent 任务的用户体验和总成本，比如在线任务最多 60 秒；单工具 timeout 控制每个依赖的长尾，比如检索 1 秒、业务 API 3 秒、模型调用 20 秒。如果只有总 timeout，某个慢工具可能吃掉全部时间；如果只有工具 timeout，Agent 仍可能通过多次调用拖很久。实际设计里还会预留降级和日志处理时间，接近 deadline 时就不再开启新的长耗时步骤。

### 问题 6：Agent 的工具调用预算为什么要区分读工具和写工具？

标准答案：因为两类工具的风险完全不同。读工具失败通常可以有限重试，最多影响延迟和成本；写工具可能产生真实业务副作用，比如创建订单、发邮件、改权限，不能盲目重试，也不能只听模型说要执行就执行。写工具需要服务端权限校验、参数校验、幂等键、审计日志，高风险写操作还要人工确认。预算上也应该更严格，比如只读工具允许多次，写工具最多一次或必须进入审批。

### 问题 7：Token 预算在 Agent 里怎么控制？

标准答案：我会把 token 预算覆盖整个过程，而不是只限制最终回答。Agent 的 token 消耗包括系统 Prompt、工具 schema、历史消息、规划过程、工具返回、反思和最终答案。控制方式包括裁剪工具返回字段、长结果摘要、历史步骤只保留关键 observation、接近上限时停止继续检索并总结已有证据。还要把 token_used 记录到 Trace 中，按模型、工具和场景统计，避免某个工具返回过大内容导致上下文膨胀。

### 问题 8：预算耗尽时，应该直接返回失败吗？

标准答案：不应该一概返回失败，要看耗尽原因。如果是证据不足，可以追问用户补充条件；如果是时间超限，可以把任务转成异步并返回 task_id；如果是工具失败，可以返回降级答案或建议稍后重试；如果是高风险操作，需要人工确认。更好的体验是返回已经完成的部分结果、明确说明缺什么、下一步怎么继续。预算控制的目标是可解释地收口任务，而不是粗暴中断。

### 问题 9：Agent 支持中断恢复时，预算状态要不要持久化？

标准答案：要持久化，而且非常关键。检查点里不仅要保存消息和工具 observation，还要保存已经消耗的 step、工具次数、token、费用、stop_reason 和最后一个安全检查点。如果恢复时重新给完整预算，相当于绕过了原来的限制；如果不保存写工具执行状态，可能恢复后重复提交副作用。所以恢复逻辑必须和幂等、预算扣减、状态机一起设计。

### 问题 10：你会用哪些指标判断 Agent 预算设计是否合理？

标准答案：我会看 stop_reason 分布、平均和 P95 step 数、工具调用次数、工具失败率、deadline_exceeded 比例、token_used、单次成本、用户取消率、人工确认率和恢复成功率。比如预算耗尽比例很高，可能是预算太紧，也可能是任务被错误路由到 Agent；用户取消率高可能说明 deadline 太长或没有流式反馈；工具调用次数异常可能是规划循环。指标要按场景、租户、模型版本和工具版本切分，不能只看全局平均值。

### 问题 11：如果一个 Agent 任务快超时了，但还差最后一步总结，你怎么处理？

标准答案：我会在运行时预留收尾时间，接近 deadline 时不再发起新的长耗时工具调用，而是基于已有证据生成阶段性结论。如果证据足够，就给出答案并说明范围；如果证据不足，就告诉用户还缺哪些信息，提供继续异步处理或补充条件的入口。对于高风险任务，宁可暂停等待确认，也不要为了赶时间执行不可靠动作。这个策略比等到硬超时后直接报错更可控。

### 问题 12：如何防止 Agent 通过多次小调用绕过预算？

标准答案：预算扣减必须在运行时统一完成，而不是分散在各工具里。每次模型调用、工具调用、重试、子任务启动前，都要经过同一个 budget manager 检查并扣减；预算状态按 run_id 持久化，恢复后继续沿用剩余额度。并且要限制并行子任务的总预算，不能每个子 Agent 都拿一份完整预算。这样可以防止 Agent 把一个大任务拆成很多小调用来绕过总成本和总时长限制。

### 问题 13：Agent 预算控制和权限控制有什么关系？

标准答案：预算控制解决“能消耗多少资源、能执行多久”，权限控制解决“能访问什么数据、能调用什么工具”。两者要一起生效。比如用户有查询订单权限，也不代表可以无限查询；预算允许调用工具，也不代表能调用越权工具。高风险工具通常同时受权限和预算约束：权限判断用户是否有资格，预算和风险策略判断这次任务是否允许自动执行，必要时再进入人工确认。

### 问题 14：面试中如何回答“Agent 会不会失控”这个问题？

标准答案：我会回答 Agent 本身确实有失控风险，所以生产系统不能把控制权完全交给模型。我们会在入口做任务风险识别和预算生成，在运行时限制 step、tool call、token、时间和重试，在工具网关做权限、参数和幂等校验，在状态机里处理取消、超时、等待确认和转人工，并通过 Trace 记录每一步的 stop_reason 和预算消耗。也就是说，模型负责推理和提出行动建议，系统负责边界、审计和最终执行控制。
