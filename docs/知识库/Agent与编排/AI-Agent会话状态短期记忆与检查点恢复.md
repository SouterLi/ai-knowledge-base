## 核心概念

### 1. Agent 会话状态是什么

Agent 会话状态不是简单的聊天历史，而是一次 Agent 任务在执行过程中需要持续携带、更新和审计的运行时快照。它通常包含：

| 状态字段 | 说明 |
| --- | --- |
| user_goal | 用户原始目标和约束 |
| messages | 可传给模型的对话上下文 |
| plan | 当前计划、已完成步骤、待执行步骤 |
| tool_calls | 工具调用记录、参数、返回、错误 |
| scratchpad | Agent 的阶段性工作区，生产中常保存摘要而不是完整思维链 |
| artifacts | 中间产物，如检索结果、草稿、文件 ID、SQL 查询结果 |
| policy_context | 用户身份、租户、权限、预算、工具白名单 |
| runtime_meta | 模型版本、Prompt 版本、trace_id、token、耗时、重试次数 |

面试中要强调：**聊天历史服务于模型续写，会话状态服务于系统恢复、审计和控制**。如果只保存 messages，系统很难判断上一步工具是否已经执行、是否需要重试、是否越权、是否超预算。

### 2. 短期记忆、长期记忆和检查点的边界

很多候选人会把 memory 混在一起讲。更清晰的分层是：

- **短期记忆**：服务当前任务，例如本轮目标、已查到的订单状态、上一步工具返回、当前草稿。生命周期通常是一次会话或一次任务。
- **长期记忆**：跨任务复用，例如用户偏好、组织知识、历史行为摘要。需要用户授权、可删除、可过期。
- **检查点**：服务可靠性恢复，例如第 3 步工具调用前后的状态快照、已产生副作用的外部 request_id、可恢复的 node/step 指针。

一句面试表达：**短期记忆让 Agent 知道“这次做到哪了”，长期记忆让 Agent 知道“这个用户通常偏好什么”，检查点让系统知道“挂了以后从哪里安全继续”。**

### 3. 为什么 Agent 需要检查点

Agent 往往不是一次模型调用，而是「模型决策 → 工具调用 → 观察结果 → 再决策」的循环。任何一步都可能失败：

- 模型返回格式错误，需要修复或重试。
- 工具超时、429、网络中断。
- Worker 重启，内存里的状态丢失。
- SSE 连接断开，用户前端不知道任务是否还在跑。
- 写操作已经成功，但响应丢失，如果从头重跑会重复下单、重复退款或重复发邮件。

检查点的价值是把 Agent 从「一次性脚本」变成「可恢复的运行实例」。每个关键步骤前后保存状态，恢复时根据 `checkpoint_id`、`current_step` 和幂等键继续，而不是盲目从第一轮重新执行。

### 4. 生产系统不应保存完整思维链

面试里容易被问到：既然要恢复，那是不是要把模型的完整思维链都存下来？答案通常是否定的。

生产系统更推荐保存：

- 用户可见或可审计的步骤摘要。
- 工具名、参数、结果、错误码、耗时。
- 模型决策所依赖的结构化依据，例如置信度、引用证据 ID、风险标签。
- 下一步动作和停止原因。

原因是完整 Chain-of-Thought 可能包含隐私、模型策略细节和不可控推理内容，也未必稳定可复现。工程上要保存的是**可审计决策证据**，而不是把所有内部推理原文落库。

## 核心知识点

### 1. Agent 状态的分层设计

一个可落地的 Agent 状态可以拆成四层：

| 层级 | 保存内容 | 典型用途 | 是否进入 Prompt |
| --- | --- | --- | --- |
| Conversation | 用户消息、助手回复、必要上下文摘要 | 多轮对话延续 | 部分进入 |
| Execution State | 当前 step、plan、tool_calls、artifacts | 控制循环和恢复 | 摘要进入 |
| Policy State | user_id、tenant_id、权限、预算、工具白名单 | 安全、限流、成本控制 | 通常不直接进入 |
| Observability State | trace_id、span_id、模型版本、token、延迟 | 排障、评估、回放 | 不进入 |

面试中可以这样说：我不会把所有状态都塞进 Prompt。Prompt 只拿完成任务必要的上下文；权限、预算、trace 这类控制信息由系统侧强约束，模型不能自行决定是否绕过。

### 2. 短期记忆压缩策略

Agent 跑多轮后，工具观察和历史消息会很快膨胀。常见策略是：

1. **保留结构化事实**：订单号、用户 ID、检索证据 ID、工具返回关键字段。
2. **丢弃低价值过程文本**：重复寒暄、已完成步骤的长日志。
3. **对历史步骤做摘要**：保留「做过什么、得到什么、下一步为什么」。
4. **关键证据引用化**：Prompt 中放 evidence_id 和摘要，原文存对象存储或检索系统。
5. **窗口内保留最近轮次**：最近用户补充和最近工具错误通常更重要。

示例：把工具结果转成可控摘要，而不是原样注入。

```python
def summarize_tool_observation(tool_name: str, result: dict) -> dict:
    # 中文注释：只保留下一轮决策需要的字段，避免把大段工具返回塞进 Prompt
    if tool_name == "get_order":
        return {
            "order_id": result["order_id"],
            "status": result["status"],
            "paid_amount": result["paid_amount"],
            "refundable": result["refundable"],
        }
    if tool_name == "search_docs":
        return {
            "top_evidence_ids": [item["doc_id"] for item in result["hits"][:3]],
            "summary": result["answer_hint"],
        }
    return {"summary": str(result)[:500]}
```

高频追问是「摘要会不会丢信息」。回答时要补一句：摘要不是替代原始记录，原始 observation 仍然落库用于审计和回放，只是进入 Prompt 的内容要经过压缩和选择。

### 3. 检查点保存时机

检查点不是随便定时保存，关键是保存能支撑恢复的边界：

- **模型决策后、工具执行前**：记录即将调用的工具、参数、幂等键。
- **工具执行后**：记录工具结果、外部系统 request_id、是否产生副作用。
- **状态迁移后**：记录当前 step、下一步候选、停止原因。
- **进入等待态前**：例如等待用户补充信息、等待人工确认、等待异步任务完成。
- **失败分类后**：记录是可重试、不可重试、需要人工，避免恢复时重复判断。

最重要的是副作用工具。比如发送邮件、创建工单、退款、改权限，必须在执行前生成业务幂等键，并在执行后保存外部结果。否则 Worker 在「工具成功但响应未返回」时重启，恢复逻辑就可能再次执行同一写操作。

### 4. Checkpoint 数据模型

一个简化的检查点表可以这样设计：

```sql
CREATE TABLE agent_checkpoints (
    checkpoint_id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    run_id TEXT NOT NULL,
    step_index INTEGER NOT NULL,
    status TEXT NOT NULL,
    state_json JSON NOT NULL,
    idempotency_key TEXT,
    model_version TEXT NOT NULL,
    prompt_version TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

`session_id` 表示用户会话，`run_id` 表示一次 Agent 任务运行。两者不要混淆：同一个会话里可能发起多次 Agent run；同一个 run 里可能有多个 checkpoint。

状态中还应包含工具调用的稳定标识：

```json
{
  "current_step": "call_refund_status_api",
  "next_action": {
    "tool": "get_refund_status",
    "args": {"order_id": "A1001"},
    "idempotency_key": "refund-status:A1001:run-7788"
  },
  "completed_tools": [
    {
      "tool_call_id": "tool-001",
      "tool": "get_order",
      "args_hash": "sha256:9b2...",
      "status": "success",
      "result_ref": "obs-001"
    }
  ]
}
```

面试中可以说明：大对象不一定直接放 `state_json`，可以放引用，例如 `result_ref` 指向对象存储或日志系统，状态表只保留恢复所需的最小快照。

### 5. 恢复流程怎么设计

恢复不是简单 reload messages 再调用模型，而是要先判断上一次停在哪个安全点。

```python
def resume_agent_run(run_id: str) -> None:
    checkpoint = load_latest_checkpoint(run_id)
    state = checkpoint["state"]

    # 中文注释：先检查上一步是否已经产生副作用，避免恢复时重复执行写操作
    pending_action = state.get("next_action")
    if pending_action and pending_action.get("side_effect") is True:
        existing = query_tool_by_idempotency_key(pending_action["idempotency_key"])
        if existing:
            state["completed_tools"].append(existing)
            save_checkpoint(run_id, state, status="tool_reconciled")
            continue_agent_loop(state)
            return

    if checkpoint["status"] == "waiting_for_user":
        notify_client_waiting(run_id, state["required_input"])
        return

    if checkpoint["status"] == "retryable_error":
        retry_with_backoff(run_id, state)
        return

    continue_agent_loop(state)
```

这段逻辑体现三个面试关键词：**恢复前对账、幂等键防重复、按错误类型决定继续/等待/重试/人工介入**。

### 6. 幂等、重试与补偿

Agent 恢复最容易考副作用场景。可以按工具类型回答：

| 工具类型 | 示例 | 恢复策略 |
| --- | --- | --- |
| 纯读工具 | 查询订单、搜索文档 | 可重试，但要记录数据版本和时间 |
| 可幂等写工具 | 创建工单、发送通知 | 必须带 idempotency_key，恢复时先查询是否已执行 |
| 不可幂等写工具 | 第三方无幂等接口 | 外层加业务锁、执行记录和人工确认 |
| 长耗时异步工具 | 批量解析文档、生成报告 | 保存 job_id，恢复时查询 job 状态 |
| 高风险工具 | 退款、权限变更 | 人工确认、审批记录、补偿流程 |

重试只解决临时失败，不解决重复执行；幂等解决重复请求的一致性；补偿解决已经产生部分副作用但后续失败的问题。面试时把这三者区分清楚，会比只说「失败就重试」专业很多。

### 7. 与 LangGraph / 状态图框架的关系

像 LangGraph 这类状态图框架，会把 Agent 任务建模为 State + Node + Edge，并提供 checkpoint saver。它的优势是：

- 每个节点读写同一个结构化 state。
- 节点之间的迁移显式可控，不只是 Prompt 自由续写。
- 可在节点边界持久化 checkpoint。
- 支持中断、恢复、人工输入和回放。

但面试里不要只回答「用 LangGraph」。更好的表达是：框架帮我管理状态图和 checkpoint，但我仍然要设计 state schema、权限上下文、工具幂等、存储策略和回放评估。框架不能替业务决定哪些工具可重试、哪些操作必须人工确认。

### 8. 可观测性与回放

Agent 状态如果只用于恢复还不够，还要支持排障和评估。建议记录：

- `run_id / trace_id / checkpoint_id` 的关联。
- 每一步的输入摘要、输出摘要、工具参数 hash。
- 模型版本、Prompt 版本、温度、工具版本。
- token、耗时、重试次数、错误分类。
- 最终状态：成功、失败、用户取消、等待输入、转人工。

线上坏 case 处理流程可以是：根据 `run_id` 拉取 checkpoint 序列 → 定位失败步骤 → 判断是模型决策错、工具返回错、状态压缩丢信息还是权限策略拦截 → 修复后用同一 checkpoint 回放。这样回答能体现你不是只会写 Agent Demo，而是考虑了生产排障闭环。

### 9. 常见设计误区

1. **只存聊天记录**：无法恢复工具进度，也无法判断副作用是否已发生。
2. **把所有历史塞进 Prompt**：成本高、延迟高，还会让模型关注无关信息。
3. **保存完整思维链**：有隐私、合规和安全风险，也不一定对恢复有帮助。
4. **失败从头重跑**：读操作还能忍，写操作可能造成重复副作用。
5. **没有状态版本**：Prompt、工具 schema、模型升级后，旧 checkpoint 无法安全恢复。
6. **会话状态和业务权限混在一起交给模型判断**：权限必须系统侧校验。

## 高频面试问题与标准答案

### 问题 1：Agent 的会话状态和普通聊天历史有什么区别？

标准答案：普通聊天历史主要是给模型延续上下文，通常就是 user/assistant messages。Agent 会话状态更像一次任务的运行时快照，除了消息，还包括目标、计划、当前步骤、工具调用记录、工具返回、错误、权限上下文、预算、trace 信息和检查点。

我在生产里不会只靠 messages 恢复 Agent，因为 messages 不能可靠说明某个工具是否已经成功执行，也不能表达幂等键、外部 job_id、权限校验结果这些系统信息。我的做法是把可传给模型的上下文和系统控制状态分开：模型只看到必要摘要，系统侧维护结构化 state 来做恢复、审计和安全控制。

### 问题 2：短期记忆和长期记忆怎么区分？

标准答案：短期记忆服务当前任务，比如用户这次要查哪个订单、前面工具返回了什么、当前计划执行到哪一步；生命周期通常是一次会话或一次 Agent run。长期记忆是跨任务复用的信息，比如用户偏好、常用格式、长期项目背景，它需要授权、过期和删除机制。

我会再单独区分检查点：检查点不是为了让模型更懂用户，而是为了系统可靠性。它记录当前步骤、状态快照、工具结果和幂等键，保证服务重启或工具失败后能从安全位置继续。

### 问题 3：Agent 执行到一半服务重启了，你怎么恢复？

标准答案：我会先从持久化存储里加载最新 checkpoint，而不是直接重放完整对话。然后判断 checkpoint 停在哪个阶段：如果是工具执行前，就可以根据状态继续调用；如果是工具执行后但响应丢失，要先用幂等键或外部 request_id 去对账，确认副作用是否已经发生；如果是等待用户或人工输入，就恢复到等待态并通知前端；如果是可重试错误，就按退避策略继续。

关键点是不要一律从头重跑。尤其是退款、发邮件、创建工单这种写操作，必须有幂等键和执行记录，恢复前先查是否已经执行过。

### 问题 4：检查点应该保存哪些内容？什么时候保存？

标准答案：检查点至少保存 run_id、session_id、当前 step、状态摘要、下一步 action、已完成工具调用、工具参数 hash、幂等键、模型和 Prompt 版本、错误分类和 trace 信息。大对象可以只存引用，比如检索原文或大文件结果放对象存储。

保存时机我一般放在关键边界：模型决定调用工具之后、工具执行之前；工具执行完成之后；状态迁移之后；进入等待用户或人工之前；失败分类之后。这样恢复时能判断下一步该继续、重试、等待还是人工处理。

### 问题 5：为什么不能把所有工具返回和历史消息都放回 Prompt？

标准答案：主要有四个问题。第一是上下文窗口和成本，工具结果很容易膨胀；第二是噪声，模型看到太多无关历史会影响决策；第三是权限和隐私，有些工具返回不该直接暴露给模型；第四是可控性差，Prompt 里的文本不等于系统状态，不能替代幂等、权限和审计。

我的做法是原始结果落库用于审计，进入 Prompt 的是经过选择的摘要和证据引用。比如订单工具只给订单状态、金额、是否可退款；检索工具只给 top evidence 的摘要和 ID。这样既保留可追溯性，又控制上下文质量。

### 问题 6：工具调用失败时，Agent 是直接重试吗？

标准答案：不会直接无脑重试。我会先做错误分类：网络超时、429 这类临时错误可以退避重试；参数非法说明模型生成的参数有问题，要让模型修正或走规则兜底；权限不足不能重试，应该拒绝或转人工；写操作响应不确定时要先用幂等键对账。

重试前还要看工具是否有副作用。只读工具可以相对安全地重试；写工具必须带 idempotency_key；高风险操作如退款、改权限，还要有人工确认和审计记录。面试里我会强调：重试解决临时失败，幂等解决重复执行，补偿解决部分成功后的回滚问题。

### 问题 7：如果 Agent 摘要压缩把关键信息丢了怎么办？

标准答案：我不会让摘要成为唯一事实来源。原始 observation、检索证据和工具结果会保存为可追溯记录，摘要只是进入下一轮 Prompt 的工作上下文。如果线上发现摘要丢关键信息，可以根据 run_id 回看原始结果，调整摘要模板或把某些字段提升为结构化必保留字段。

另外我会对摘要做约束，比如订单场景必须保留 order_id、status、amount、owner_user_id、refundable 这些字段；RAG 场景必须保留 evidence_id 和来源。也就是说，重要信息不靠模型自由总结，而是结构化抽取和 schema 约束。

### 问题 8：LangGraph 这类框架的 checkpoint 能解决所有问题吗？

标准答案：不能。LangGraph 这类框架能很好地帮我们把 Agent 建成状态图，在节点边界保存 checkpoint，也支持中断和恢复。但框架只提供机制，不替你做业务语义判断。

真正落地时，我还要自己设计 state schema、checkpoint 存储、工具幂等键、权限上下文、状态版本、失败分类和回放评估。比如一个退款工具是否能重试、是否必须人工审批、外部接口如何对账，这些都不是框架自动知道的。

### 问题 9：如何避免 Agent 恢复时重复执行副作用工具？

标准答案：我会在工具执行前生成业务幂等键，并把「准备调用什么工具、参数 hash、幂等键」写入 checkpoint。工具执行后保存外部 request_id 和执行结果。恢复时如果发现上次停在写工具附近，不会直接再调一次，而是先根据幂等键查询执行记录或外部系统状态。

如果外部系统支持幂等，就复用同一个 idempotency_key；如果不支持，就在应用层做执行表和业务锁；如果是高风险动作，还要加人工确认。核心原则是：Agent 可以重新思考，但副作用不能随便重复发生。

### 问题 10：你会如何设计一个可恢复的客服工单 Agent？

标准答案：我会把一次工单处理建成一个 Agent run。状态里保存用户问题、工单 ID、当前计划、已调用工具、检索证据、草稿回复、权限上下文和预算。每次模型决定调用工具后先落 checkpoint，再执行工具；工具返回后保存 observation 和摘要。

对于只读工具，比如查订单、查知识库，可以有限重试；对于写工具，比如创建工单、发送通知，必须带幂等键；涉及退款或改权限时进入人工确认。服务重启后，从最新 checkpoint 恢复：如果已经创建了工单，就根据 idempotency_key 查到原工单继续生成回复，而不是再创建一个。最终每个 run 都有 trace，失败 case 可以回放成评测样本。
