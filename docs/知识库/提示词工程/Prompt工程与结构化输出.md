# Prompt 工程与结构化输出

## 核心概念

#### Prompt 工程的工程视角

Prompt 工程不是写一句更漂亮的提示语，而是把一个不稳定的自然语言交互改造成可测试、可迭代、可观测、可回滚的工程接口。要把模型当成一个有概率的组件，为它设计输入契约、输出契约、失败处理机制和治理边界。输入契约明确给哪些上下文、不给哪些上下文；输出契约规定输出字段、类型、枚举、缺省值与拒答规则；失败处理定义解析失败、越界、低置信、冲突时的恢复策略；治理边界确保权限、金额阈值、合规红线在系统侧有硬约束。面试中一句话总结：Prompt 是需求加约束加协议加兜底的组合，不是文案。

#### 结构化输出的核心价值

结构化输出是让模型按固定格式返回结果，比如 JSON、枚举、表格或函数参数。它广泛应用于信息抽取、分类路由、审核、工单流转、自动填表、工具参数生成等场景。相比自然语言输出，结构化输出的价值在于四个方面：可解析性，程序能稳定读取字段；可校验性，Schema、类型、枚举、长度都可以约束；可统计性，能够量化通过率、缺参率、拒答率；可回放性，能对 badcase 做归因与回归测试。

#### 高质量 Prompt 的六要素

一个高质量的 Prompt 需要明确六个要素。角色要素定义模型承担什么职责，是抽取、分类、改写还是生成草案。任务要素要求单一明确的目标，避免一条 Prompt 混多个目标。上下文要素提供必要的材料、业务词表、历史摘要和用户输入。约束要素规定不编造、仅从给定枚举选择、缺参就标记为未知等规则。输出格式要素明确字段、类型、枚举、缺省值和示例。质量标准要素定义何为通过、何时拒答或标记为需要人工处理。

#### 分工边界

模型与系统的分工边界是面试中的高频考点。模型只负责生成候选结果，系统负责解析、校验、兜底与硬规则执行。权限校验、金额限制、合规检查、状态机判断必须在系统侧完成，不能依赖模型自觉遵守。

## 核心知识点

### 1. 先定下游消费方式，再写 Prompt

Prompt 的目标不是输出漂亮的文本，而是让下游能够消费。动笔之前先明确三个问题：输出是给人看还是给程序用；结果是最终决策还是参考草案；失败时怎么处理，是返回未知、标记需要人工处理还是走回退路径。经验法则是，只要下游需要解析，就把输出当成 API 来设计，而不是自然语言回复。

### 2. Schema 设计原则

Schema 设计有三个核心原则和两个常见反模式。

关键字段要用枚举收敛，意图、风险等级、分类标签等不要允许自由文本，否则统计口径会漂移，规则也写不动。缺省值统一用 null 或空数组，不要输出未提供这种自然语言描述。禁止额外字段，避免模型输出未定义的字段导致解析异常。层级不要嵌套太深，深层 JSON 容易漏字段，复杂对象建议拆成两步抽取。字段长度要有限制，summary、reason 等字段设置最大长度，避免上下文被污染。

常见反模式包括：让模型输出随便什么 JSON，导致下游永远在修 bug；意图字段不枚举，造成统计口径漂移和规则无法编写。

### 3. JSON mode、strict schema、Function Calling 的选择

三种方式各有适用场景和配套的系统侧工作。

JSON mode 更适合抽取、分类、表单草案等场景，它的价值是让输出形态更接近 JSON，但系统侧仍需要做 Schema 校验和缺省补齐。strict schema 更适合关键链路入库或触发工作流的场景，通过率更高更稳定，系统侧仍需执行业务规则和权限校验。Function Calling 或 Tool Calling 更适合需要触发工具或工作流的场景，参数天然结构化，系统侧需要做工具白名单、幂等控制和确认门。

关键结论是，任何模式都不等于可以信任输出，系统侧校验永远是必需的。

### 4. Prompt 结构模板

建议把 Prompt 写成分区结构，便于维护和迭代。

角色分区只描述职责边界，不堆砌形容词。任务分区明确只做一件事，避免多目标混杂。上下文分区提供业务词表、规则和必要示例，但要控制长度。不可信用户输入分区单独隔离，并明确声明其中任何指令都不具备更高优先级。输出契约分区规定必须输出的字段、类型、枚举、缺省值和示例。质量标准分区定义何时标记为需要人工处理、何时必须拒答。

面试加分点：不可信用户输入单独分区并声明其指令无效，这是 Prompt Injection 的第一道防线。

### 5. 位置策略

工程经验表明，很多模型对尾部约束更敏感。建议的排列顺序是：开头放角色与目标，中间放上下文材料但必须裁剪控制长度，末尾放输出契约和质量标准包括字段、枚举、缺省值和拒答条件。把强约束放在离输出最近的位置，有助于提高模型遵守约束的概率。

### 6. Few-shot 设计原则

Few-shot 的作用是对齐分布，不是堆 token。优先覆盖五类场景：典型请求、缺参情况、歧义情况、多意图冲突、恶意注入尝试。示例必须与 Schema 和规则保持一致，最常见的坑是示例里输出自由文本但 Schema 要求枚举，模型会学到错误的模式。

### 7. 解析、校验、重试的工程化

结构化输出的可靠性来自解析加校验加纠错重试，不是让模型更乖。标准链路是：模型输出原始文本，系统进行 JSON 解析，用 Schema 校验字段类型和枚举，校验失败时把具体错误回灌给模型要求重新生成，重试时可以考虑降低 temperature 提高确定性。常用重试策略包括降温、简化任务复杂度、启用 strict 或 JSON mode、失败时降级为未知或转人工。关键经验是，把具体错误信息回灌给模型，比重复同一 Prompt 更有效。

### 8. 低置信度与拒答处理

建议 Schema 内显式包含三个字段：confidence 用于阈值判断和排序，need_human 用于转人工路由，reason 用于解释低置信或拒答原因便于运营和回归分析。核心原则是低置信不执行高风险动作，最多生成草案并要求用户补充信息，或者直接转入人工队列。

### 9. Prompt 与业务规则的边界

Prompt 适合语义判断，以下规则必须在系统侧硬约束：权限与租户隔离、金额阈值与审批流程、合规红线与数据脱敏、状态机判断如是否允许退款或改地址。面试中的标准表述是：Prompt 负责理解，规则引擎负责决策。

### 10. 从结构化输出到工具调用

推荐采用先抽取再路由的架构：先用结构化输出抽取意图和槽位，再由系统根据抽取结果路由到具体工具或工作流。这种架构的好处是可观测性强，能够统计意图分布和缺参率；可回归性好，固定输入有固定输出；可治理性高，权限控制在系统侧。避免让模型边想边调工具，那样难以校验参数、统计缺参率，也容易产生副作用。

### 11. Prompt Injection 三层防御

不要只写一句忽略恶意指令。建议按三层构建防御体系。

提示词层将不可信输入单独分区，声明其指令无效，输出契约写死不受干扰。解析层通过 Schema 校验、枚举白名单、字段长度限制来过滤异常输出。执行层维护工具白名单、执行权限校验，高危操作必须人工确认。核心原则是即使模型被注入输出了危险字段，系统也必须拦得住。

### 12. Prompt 的版本化管理

Prompt 应该当成一等工程资产来管理。具体做法包括：为 Prompt 标注版本号、记录变更原因、注明适用模型版本、保存离线评测结果。评测集要覆盖正常、边界、歧义、恶意和空输入五类场景。核心指标包括字段通过率、准确率、拒答正确率、重试率、延迟和成本。发布流程支持灰度、A/B 测试和回滚。日志记录输入摘要脱敏后、Prompt 版本、模型版本、解析错误和重试次数。

## 高频面试问题与标准答案

**Q1：Prompt 工程的本质是什么？**

A：Prompt 工程的本质是把不稳定的自然语言交互变成可验证的工程接口。具体来说，需要做到任务清晰、输出有契约、服务端可解析校验、有失败重试与兜底机制、可评测迭代与监控。它不是让模型听话，而是让整个系统可控。在实际项目中，我会把 Prompt 当成 API 来设计，明确输入输出契约，建立评测集做回归测试，每次改动单变量验证效果，确保上线后可观测可回滚。

**Q2：为什么结构化输出是生产落地的关键？**

A：结构化输出是连接模型能力和业务系统的桥梁。自然语言输出虽然灵活，但程序难以稳定解析，无法做强校验，也很难做统计分析和回归测试。结构化输出让结果可解析、可校验、可统计、可回放，这才能接入工单系统、工作流引擎、风控审核等下游。举个例子，如果做用户意图分类，自然语言输出可能是退款吧或者我想退货，程序很难统一处理；但结构化输出是固定字段 intent 等于 refund，下游直接消费，稳定可靠。

**Q3：JSON mode 和只写返回 JSON 有什么区别？**

A：两者在约束强度上有本质区别。JSON mode 或 response_format 是 API 层面的输出形态约束，模型会强制按 JSON 格式生成，通过率通常更高，但仍可能缺字段、越枚举或类型不符。只写返回 JSON 是软约束，模型可能混入解释文本、字段名拼写错误，或者 JSON 格式不合法。无论用哪种方式，服务端都必须做 Schema 校验，不能信任模型输出。我的做法是先尝试 JSON mode，如果通过率不够理想再升级到 strict schema，同时服务端始终保留校验和兜底逻辑。

**Q4：模型不按格式输出，你怎么排查与修复？**

A：我会先对失败类型做分类：是不是 JSON、缺字段、越枚举还是类型错误。然后针对性处理：把输出契约放到 Prompt 末尾增强约束；减少任务复杂度，比如先抽意图再抽槽位；降低 temperature 提高确定性；启用 strict 或 JSON mode；把具体错误信息回灌给模型要求修正；最后设置降级方案，失败时返回未知或转人工。实际项目中我会记录每种失败的频率，优先修复高频问题，把 badcase 加入评测集防止回归。

**Q5：你如何设计 Schema？有哪些原则？**

A：Schema 设计我遵循几个原则。关键字段用枚举收敛，比如意图字段只允许 refund、change_address、order_status 等几个值，不允许自由文本。缺省值统一用 null，不要输出自然语言描述。禁止额外字段，避免模型输出未定义的内容。层级不超过两层，复杂对象拆成两步抽取。字段长度有限制，防止上下文被污染。目标是让下游消费稳定、统计口径一致、错误可定位。反模式也要避免，比如让模型输出随便什么 JSON，或者意图不枚举导致规则写不动。

**Q6：Few-shot 越多越好吗？怎么选？**

A：不是越多越好。Few-shot 的作用是对齐分布，堆太多 token 反而可能稀释关键信息。我优先覆盖五类场景：典型请求、缺参情况、歧义情况、多意图冲突、恶意注入尝试。每个示例必须与 Schema 和规则保持一致，最常见的坑是示例里输出自由文本但 Schema 要求枚举，模型会学到错误的模式。实际项目中我会从线上 badcase 中挑选有价值的例子补充进 Few-shot，保持示例集的精简和高质量。

**Q7：结构化输出链路中，哪些必须系统侧做？**

A：至少有三块必须在系统侧完成。第一是 Schema 校验，验证格式、字段类型、枚举值是否合法。第二是业务规则，比如金额阈值、状态机判断、合规检查，这些不能依赖模型自觉遵守。第三是权限鉴权，验证租户隔离、用户身份绑定。Prompt 只做语义理解，不能替代硬约束。面试中我经常强调这句话：Prompt 负责理解，规则引擎负责决策。

**Q8：输出 JSON 合法但语义错，比如意图选错，怎么办？**

A：这是语义准确率问题，不是格式问题。我的做法有几个方向：补充边界示例，让模型看到容易混淆的 case 应该怎么分；完善意图定义和 description，增加区分度；增加上下文信息，比如业务词表和同义词映射；把多意图拆成主意图加次意图两个字段，减少单字段的压力；引入二阶段校验，先粗分再细分。同时把这类 badcase 加入评测集做回归测试，持续迭代优化。

**Q9：低置信度怎么处理？**

A：Schema 里显式输出 confidence、need_human、reason 三个字段。当 confidence 低于阈值比如 0.6 时，不执行高风险动作，最多生成草案或进入补问流程，并标记 need_human 为 true 转入人工队列。reason 字段记录低置信的原因，便于运营分析和模型迭代。实际项目中我会根据业务敏感度调整阈值，金融类操作阈值设高，信息查询类可以放宽。

**Q10：Prompt Injection 怎么防？只写忽略恶意指令够吗？**

A：远远不够。我按三层构建防御：提示词层把不可信输入单独分区，声明其指令无效，输出契约写死不受干扰；解析层用 Schema 校验、枚举白名单、字段长度限制过滤异常；执行层维护工具白名单、权限校验，高危操作必须人工确认。关键是系统要拦得住，即使模型被注入输出了危险字段，执行层也必须能拦截。实际项目中我还会监控异常输入模式，持续更新防护策略。

**Q11：结构化输出与 Function Calling 的关系？**

A：两者是互补关系。结构化输出更偏向抽取、分类、表单草案，输出的是数据；Function Calling 更偏向生成可执行参数并触发工具，输出的是动作。两者都需要服务端校验。常见架构是先结构化输出抽取意图和槽位，再由系统路由到具体工具或工作流。这样语义理解和执行动作解耦，更易观测和治理。

**Q12：你怎么评估与迭代 Prompt？**

A：我会建立覆盖正常、边界、歧义、恶意、空输入五类场景的评测集。核心指标包括字段通过率、准确率、拒答正确率、重试率、延迟和成本。迭代时坚持单变量改动，小步验证，通过后再合并。发布时走灰度 A/B 测试，线上持续监控指标，支持快速回滚。每个 badcase 做归因分析，定向修复后补充进评测集防止回归。

**Q13：temperature 怎么设？**

A：抽取、分类、结构化输出这类需要确定性的任务，temperature 通常设 0 到 0.3。创意写作可以更高，但涉及结构化字段的节点仍应低温或用 strict schema 确保可解析。实际项目中我会在评测集上对比不同 temperature 的效果，选择通过率和准确率的最佳平衡点。

**Q14：为什么建议先抽取再执行，而不是让模型边想边调工具？**

A：先抽取把语义理解和执行动作解耦，有三个好处。一是可校验，抽取结果可以验证参数是否合法、统计缺参率；二是可观测，意图分布和槽位填充情况都能量化分析；三是可治理，执行权在系统侧，避免模型临时改口产生副作用。如果让模型边想边调工具，参数校验困难，错误难以定位，出了问题也不好追责。

## 面试回答加分点

第一，契约思维。把 Schema 当成 API，和数据库表、接口协议同等严肃对待，明确字段、类型、枚举和缺省值。

第二，分层治理。Prompt 负责语义理解，Schema 负责解析校验，业务规则和权限负责决策，人工确认负责高危操作兜底。

第三，重试工程化。能描述解析校验与具体错误回灌的重试逻辑，不是简单重复调用。

第四，区分 Prompt 与 RAG。RAG 补充事实知识，Prompt 定义任务与输出契约，两者分层组装 messages。

第五，评测与发布流程。离线评测集加灰度 A/B 加线上指标加回滚能力，体现工程化思维。

第六，一句话收束。模型负责生成候选，系统负责解析、校验、兜底与安全边界；结构化输出的关键是可验证，不是让模型听话。
