## 一、为什么这是高频考点

LLM 应用上线后，用户最容易感知的问题不是模型参数，而是“慢、不稳定、偶发超时”。面试官问性能优化，通常不是想听“换更快的模型”这么简单，而是在考察候选人是否能：

- 把端到端延迟拆成可观测、可定位的分段指标。
- 理解 token 数、上下文长度、模型排队、工具调用、检索链路对延迟的影响。
- 在质量、成本、延迟、稳定性之间做工程取舍。
- 设计流式输出、缓存、并发、降级、超时、重试和队列机制。
- 用数据证明优化有效，而不是凭感觉调 Prompt。

面试中高质量回答的关键是：先定位瓶颈，再选择手段；先定义指标，再谈优化。

## 二、核心概念

### 1. 端到端延迟

端到端延迟是从用户发起请求到系统完成响应的总耗时。LLM 应用里它通常不是单次模型调用耗时，而是一条链路：

```text
请求接入
  -> 鉴权与参数校验
  -> 会话与上下文加载
  -> 检索 / 工具调用 / 规则判断
  -> Prompt 组装
  -> 模型排队与推理
  -> 输出解析与安全检查
  -> 写日志 / 写状态 / 返回前端
```

面试中不要只说“模型慢”。更专业的表达是：把总耗时拆成接入层、检索层、模型层、后处理层和传输层。

### 2. TTFT 与完整响应耗时

- **TTFT（Time To First Token）**：从请求发出到收到第一个 token 的时间，决定用户是否觉得系统“有反应”。
- **Time To Last Token**：从请求发出到完整答案生成结束的时间，决定任务整体完成速度。
- **感知延迟**：用户主观感受到的等待时间，流式输出、进度提示和分阶段反馈能降低感知延迟。

同样是 8 秒完成：

- 一次性 8 秒后返回：用户会觉得卡死。
- 1 秒内返回首 token，持续流式输出：用户更容易接受。

### 3. P50、P95、P99

平均延迟在面试中参考价值有限，因为线上体验经常被长尾请求拖垮。

| 指标 | 含义 | 面试关注点 |
| --- | --- | --- |
| P50 | 50% 请求低于该耗时 | 普通用户的典型体验 |
| P95 | 95% 请求低于该耗时 | 线上 SLA 常用指标 |
| P99 | 99% 请求低于该耗时 | 长尾、抖动、超时风险 |

回答性能问题时，要主动提 P95 / P99，而不是只谈平均值。

### 4. 吞吐与并发

- **并发数**：同一时刻系统正在处理的请求数量。
- **吞吐量**：单位时间内完成的请求数，常见指标是 QPS / RPM / TPM。
- **排队时间**：请求进入系统后等待执行的时间，供应商限流、本地 GPU 队列、数据库连接池都会导致排队。
- **背压**：下游处理不过来时，上游必须减速、排队或拒绝，否则会雪崩。

LLM 应用的吞吐瓶颈经常不是 Web 服务本身，而是模型 API 的 RPM / TPM、检索服务、reranker、工具调用或数据库连接池。

### 5. Token 预算

LLM 延迟通常与输入 token、输出 token、模型规模和推理策略相关。常见经验：

- 输入越长，prefill 越慢。
- 输出越长，decode 越慢。
- 上下文越复杂，模型更容易生成冗长或偏离目标的答案。
- 同样任务，小模型通常更快但质量可能下降。

面试中可以用一句话概括：LLM 性能优化的第一原则是减少无效 token。

## 三、核心知识点

### 1. 延迟分段诊断

性能优化第一步不是改代码，而是打点。一个可落地的 Trace 应该记录：

| 分段 | 指标示例 | 常见瓶颈 |
| --- | --- | --- |
| 接入层 | request_received、auth_ms | 鉴权服务慢、网关排队 |
| 上下文加载 | session_load_ms、memory_fetch_ms | Redis / DB 慢、历史消息过长 |
| 检索链路 | embedding_ms、vector_search_ms、rerank_ms | 候选过多、reranker 慢、索引冷热不均 |
| 工具调用 | tool_count、tool_ms、tool_timeout | 外部 API 慢、串行调用过多 |
| Prompt 构建 | prompt_tokens、build_ms | 拼接上下文过多、模板逻辑复杂 |
| 模型调用 | queue_ms、ttft_ms、decode_ms、output_tokens | 模型排队、输入过长、输出过长 |
| 后处理 | parse_ms、guardrail_ms | JSON 修复、安全检查、正则复杂 |
| 返回链路 | stream_flush_ms、client_disconnect | 网络、前端缓冲、代理配置 |

一个简单的 Python 打点结构：

```python
import time
from contextlib import contextmanager


class Trace:
    def __init__(self):
        self.spans = []

    @contextmanager
    def span(self, name):
        start = time.perf_counter()
        try:
            yield
        finally:
            cost_ms = (time.perf_counter() - start) * 1000
            # 生产环境中应写入 trace 系统，并关联 request_id / tenant_id
            self.spans.append({"name": name, "cost_ms": round(cost_ms, 2)})


trace = Trace()

with trace.span("context_load"):
    session = load_session()

with trace.span("retrieval"):
    docs = retrieve_documents(session.query)

with trace.span("llm_call"):
    answer = call_llm(docs, session.query)
```

面试加分点：每个 span 不只记录耗时，还要记录输入规模，例如 token 数、候选文档数、工具调用次数、模型名称和降级原因。

### 2. 建立延迟预算

性能目标不能只说“越快越好”，要拆成预算。例如在线问答系统：

| 阶段 | 目标预算 |
| --- | --- |
| 鉴权与参数校验 | 50ms |
| 会话加载 | 100ms |
| 向量检索 | 150ms |
| rerank | 300ms |
| Prompt 构建 | 50ms |
| LLM TTFT | 800ms |
| 流式输出完整答案 | 3s - 8s |
| 后处理与日志 | 100ms |

预算不是拍脑袋，而是为了定位责任边界：当 P95 超标时，能快速知道是检索慢、模型慢、工具慢还是输出过长。

### 3. 减少输入 token

输入 token 优化通常比换模型更稳定。

常见方法：

1. **历史消息裁剪**：只保留与当前任务相关的最近轮次和关键摘要。
2. **RAG 上下文压缩**：先检索，再 rerank，再只注入必要片段。
3. **模板去冗余**：系统 Prompt 不要反复塞重复规则。
4. **结构化上下文**：用 JSON / 表格表达关键字段，少写长自然语言。
5. **按任务路由上下文**：分类任务不需要塞全文，抽取任务只塞目标字段附近内容。

反例：

```text
把用户全部历史对话、所有候选文档、完整工具返回和冗长系统规则一次性塞进 Prompt。
```

更好的做法是：

```text
任务识别 -> 选择必要上下文 -> 检索候选 -> rerank -> 压缩证据 -> 生成
```

### 4. 控制输出 token

输出 token 直接影响完整响应时间和成本。

可落地手段：

- 设置合理的 `max_tokens`，不要默认给很大。
- 在 Prompt 中明确回答格式和长度。
- 对列表型答案限制条数，例如“最多给 5 条”。
- 对摘要任务区分短摘要、详细摘要和结构化摘要。
- 对内部链路使用短中间结果，最终面向用户再组织语言。

示例：

```python
request = {
    "model": "fast-chat",
    "messages": messages,
    "temperature": 0.2,
    # 限制输出长度，避免模型生成冗长答案拖慢链路
    "max_tokens": 600,
}
```

面试中要注意：不能为了快盲目压缩输出。如果任务是合同审查、医疗解释、财务分析，过短答案可能漏掉关键风险。

### 5. 流式输出优化感知体验

流式输出不能减少完整推理耗时，但能显著降低感知延迟。

实现时关注：

- 服务端尽快 flush 首个 chunk。
- 代理层不要缓冲 SSE / chunked 响应。
- 前端支持增量渲染、取消和重试。
- 流式过程中记录 TTFT、chunk 间隔、用户取消率。
- 结构化输出场景要处理半截 JSON，不能边流边当完整结果使用。

SSE 示例：

```python
def stream_answer(llm_stream):
    for chunk in llm_stream:
        if not chunk.text:
            continue
        # 每个片段都应尽快返回，避免被应用层缓冲
        yield f"data: {chunk.text}\n\n"

    # 显式结束事件，方便前端关闭 loading 状态
    yield "event: done\ndata: {}\n\n"
```

面试中可以补一句：流式输出是体验优化，不等于后端已经完成；涉及工具结果、支付、下单等动作时，必须等真实结果完成后再展示确定性结论。

### 6. 并发与并行

LLM 应用里很多步骤可以并行，但并行不是越多越好。

适合并行：

- 多路只读检索：向量检索、关键词检索、权限过滤候选。
- 多个独立工具查询：查订单、查库存、查用户画像。
- 多模型竞赛或候选生成：高价值离线任务或低频任务。
- 前置准备：会话加载和部分静态配置加载。

不适合盲目并行：

- 会触发供应商限流的模型调用。
- 共享写状态的工具调用。
- 强依赖前一步结果的工作流。
- 高成本但收益不明确的多模型调用。

Python 异步示例：

```python
import asyncio


async def build_context(query):
    # 只读任务可以并发执行，但要设置超时和降级策略
    vector_task = asyncio.create_task(vector_search(query))
    keyword_task = asyncio.create_task(keyword_search(query))
    profile_task = asyncio.create_task(load_user_profile())

    results = await asyncio.gather(
        vector_task,
        keyword_task,
        profile_task,
        return_exceptions=True,
    )

    return merge_context(results)
```

面试回答要强调：并行的前提是任务独立、结果可合并、失败可降级、下游有容量。

### 7. 缓存策略

缓存能优化延迟和成本，但 LLM 应用缓存要非常谨慎。

常见缓存层：

| 缓存对象 | 适用场景 | 风险 |
| --- | --- | --- |
| Embedding 缓存 | 相同文本重复向量化 | 文本归一化不一致导致命中低 |
| 检索结果缓存 | 热门 FAQ、固定知识库 | 权限变化后泄露数据 |
| Prompt 片段缓存 | 系统规则、工具 schema | 配置更新后版本不一致 |
| 模型响应缓存 | 确定性、低风险、公开问题 | 个性化问题误命中 |
| 工具结果缓存 | 商品、政策、配置查询 | 数据时效性问题 |

缓存 key 不能只用 query 文本，至少考虑：

- tenant_id / user_id / permission_scope
- knowledge_base_version
- prompt_version
- model_alias / model_version
- locale
- task_type
- normalized_query

示例：

```python
def build_cache_key(req):
    # 缓存 key 必须带权限和版本，避免跨租户或旧知识库误命中
    parts = [
        req.tenant_id,
        req.permission_hash,
        req.knowledge_base_version,
        req.prompt_version,
        req.task_type,
        normalize_query(req.query),
    ]
    return ":".join(parts)
```

面试中要主动说：带权限的数据默认不做全局响应缓存，除非缓存 key 和失效机制都经过设计。

### 8. 模型选择与路由

性能优化经常需要模型路由配合：

- 简单任务走小模型或 fast model。
- 复杂推理走强模型。
- 结构化抽取走稳定输出能力强的模型。
- 低价值请求限制上下文和输出长度。
- 高价值请求允许更高延迟和成本。
- Provider P95 升高时切换备用模型。

路由不是只看模型速度，还要看任务成功率。一个快但经常答错的模型会制造更多重试和人工修复成本。

### 9. 超时、重试与降级

超时和重试是性能系统的边界保护，不是简单“失败再试一次”。

建议：

- 每个外部调用都设置超时，不允许无限等待。
- 对读操作可以重试，对写操作必须幂等。
- 重试要指数退避并限制次数。
- 超时后提供降级结果，例如短答案、部分结果、异步任务或人工介入。
- 记录降级原因，避免静默质量下降。

错误示例：

```text
模型 30 秒不返回 -> 立即重试 3 次 -> 三个请求同时占用供应商限额 -> 更多请求排队 -> 系统雪崩
```

更好的策略：

```text
设置请求总 deadline -> 分配各阶段 timeout -> 超时后取消下游请求 -> 降级或排队 -> 记录 trace
```

### 10. 队列与背压

当请求量超过处理能力时，系统必须有明确策略：

- 在线交互：优先快速失败或降级，不要让用户无期限等待。
- 离线任务：进入队列，返回 task_id，支持查询进度。
- 高优先级租户：独立队列或配额，避免被低价值任务挤占。
- 模型供应商限流：本地令牌桶、排队、熔断和备用 Provider。

面试中可以用“容量保护”来回答：保护模型、数据库、检索服务和用户体验，避免局部慢变成全局不可用。

### 11. RAG 链路性能优化

RAG 是 LLM 应用中最常见的延迟来源之一。

优化方向：

1. **Embedding 缓存**：相同 query 或规范化 query 不重复向量化。
2. **索引分区**：按租户、业务域、时间或权限缩小搜索范围。
3. **候选数控制**：top_k 不是越大越好，过大会拖慢 rerank 和增加噪声。
4. **混合检索并行**：向量检索和关键词检索并行，再合并去重。
5. **轻重 rerank 分层**：先轻量规则 / embedding 分数过滤，再 cross-encoder 精排。
6. **上下文压缩**：只注入能回答问题的片段。

面试回答要避免“把 top_k 调小就行”。top_k 变小会影响召回，必须配合评估集验证。

### 12. 工具调用性能优化

Agent 和工作流场景中，工具调用常成为长尾瓶颈。

常见优化：

- 合并批量接口，减少 N+1 查询。
- 对只读工具并行调用。
- 对慢工具设置独立超时。
- 对工具结果做结构化摘要，不把大 JSON 全塞给模型。
- 对高风险写工具使用同步确认，对低风险长任务转异步。
- 记录每个 tool 的耗时、错误率、重试次数和结果大小。

工具返回很大时，模型延迟也会变慢，因为这些结果最终会变成输入 token。

### 13. 前端与网关层优化

后端快不代表用户感知快。还要检查：

- Nginx / API Gateway 是否缓冲流式响应。
- 前端是否等完整响应后才渲染。
- 移动端弱网是否导致 chunk 堆积。
- 浏览器是否支持取消请求。
- 首屏 loading、进度提示、部分结果展示是否合理。

如果用户说“很慢”，但后端 trace 显示模型 1 秒返回首 token，要继续查网关、代理、前端渲染和客户端网络。

### 14. 性能优化的验证方法

优化必须用实验验证：

- 固定评估集和压测场景。
- 对比优化前后的 P50 / P95 / P99、TTFT、总耗时、错误率、成本。
- 分任务类型看指标，不要只看全局平均。
- 观察质量指标是否下降，例如准确率、引用命中率、结构化输出通过率。
- 小流量灰度，确认线上真实分布下也有效。

常见反例：只在单条样例上感觉快了，但线上 P95 没降，甚至质量下降。

## 四、典型系统设计回答模板

如果面试官问“如何优化一个 LLM 问答系统的响应速度”，可以按下面顺序回答：

1. **定义指标**：TTFT、完整响应耗时、P95 / P99、错误率、成本、质量指标。
2. **链路打点**：接入、会话、检索、rerank、Prompt、模型、后处理、返回。
3. **定位瓶颈**：看 trace 和分位数，区分模型慢、检索慢、工具慢、前端慢。
4. **短期优化**：流式输出、上下文裁剪、max_tokens、缓存、并行只读任务。
5. **中期优化**：模型路由、RAG 分层检索、批量工具接口、队列和背压。
6. **稳定性治理**：超时、重试、熔断、降级、Provider 切换。
7. **验证与灰度**：压测、A/B、质量回归、线上监控。

一句话总结：

> LLM 性能优化不是单点调参，而是围绕“分段观测、token 控制、并发治理、模型路由和降级保护”的系统工程。

## 五、高频面试问题与参考答案

### Q1：LLM 应用响应慢，你会怎么排查？

**参考答案：**

我会先做端到端 trace，而不是直接换模型。把链路拆成鉴权、会话加载、检索、rerank、Prompt 构建、模型 TTFT、模型输出、后处理和前端传输。每段记录耗时、token 数、候选文档数、工具调用次数、模型名称和错误码。

然后看 P95 / P99，而不是只看平均值。如果 TTFT 高，重点查模型排队、输入 token、供应商状态；如果 TTFT 正常但完整耗时高，重点查输出 token 和流式 chunk；如果模型不慢，继续查检索、工具调用、代理缓冲和前端渲染。定位瓶颈后再做针对性优化。

### Q2：TTFT 和完整响应耗时有什么区别？

**参考答案：**

TTFT 是首 token 返回时间，影响用户是否觉得系统有响应；完整响应耗时是最后一个 token 返回时间，影响任务完成速度。

流式输出主要优化 TTFT 和感知体验，但不一定减少完整耗时。完整耗时更多受输出 token 数、模型 decode 速度、工具调用和后处理影响。面试中可以说：在线交互要同时关注 TTFT 和完整耗时，不能只看其中一个。

### Q3：为什么平均延迟不够？为什么要看 P95 / P99？

**参考答案：**

平均值会掩盖长尾问题。LLM 应用里少量请求可能因为上下文很长、工具超时、供应商排队或 rerank 候选过多而非常慢，这些请求对用户体验和 SLA 影响很大。

P95 / P99 能反映线上稳定性。比如平均 2 秒但 P99 30 秒，说明系统存在长尾风险，需要查慢请求分布、超时策略、队列和下游依赖。

### Q4：如何减少 LLM 输入 token？

**参考答案：**

我会从四层做：

1. 会话层：历史消息摘要和相关性筛选，不把全部对话塞进去。
2. RAG 层：先检索和 rerank，再只注入必要证据片段。
3. Prompt 层：压缩重复规则，把稳定规则做成简洁模板。
4. 工具层：工具结果先结构化摘要，不把大 JSON 原样放进上下文。

减少 token 不能牺牲关键信息，所以需要用评估集验证准确率、引用命中率和结构化输出通过率。

### Q5：如何控制输出 token？

**参考答案：**

可以设置合理的 `max_tokens`，在 Prompt 中约束答案格式、条数和长度。比如要求“最多 5 条，每条不超过 50 字”，或者让模型输出 JSON 字段而不是长篇自然语言。

但要区分任务风险。客服 FAQ 可以短答案优先，合同审查、医疗解释、金融分析不能为了快漏掉必要风险说明。

### Q6：流式输出能解决性能问题吗？

**参考答案：**

流式输出主要解决感知延迟，让用户更快看到首 token，不等于模型推理更快。它适合聊天、写作、问答等逐步展示场景。

但结构化输出、工具调用和高风险业务不能简单边生成边执行。比如下单、退款、审批必须等工具真实结果和业务校验完成后，再展示确定性结果。实现时还要确保网关不缓冲、前端能增量渲染、用户能取消请求。

### Q7：什么时候用缓存？缓存 key 怎么设计？

**参考答案：**

适合缓存的对象包括 embedding、热门公开 FAQ 的检索结果、稳定 Prompt 片段、低风险确定性回答和工具配置查询。

缓存 key 不能只用 query，要带 tenant_id、permission_scope、knowledge_base_version、prompt_version、model_version、task_type 和规范化 query。涉及权限的数据默认不能做全局缓存，否则容易跨租户泄露。还要设计失效机制，比如知识库更新、权限变更、Prompt 版本升级时主动失效。

### Q8：如何优化 RAG 系统的延迟？

**参考答案：**

我会先拆 embedding、向量检索、关键词检索、权限过滤、rerank、上下文压缩和生成各阶段耗时。优化方向包括 embedding 缓存、索引分区、混合检索并行、控制候选数量、轻重 rerank 分层、只注入必要片段。

不能只把 top_k 调小，因为这可能降低召回。正确做法是用评估集同时看召回率、答案准确率、引用命中率、P95 延迟和成本。

### Q9：Agent 工具调用很慢怎么办？

**参考答案：**

先看工具调用 trace：调用了哪些工具、是否串行、每个工具耗时多少、是否有超时和重试。对只读且独立的工具可以并行，对 N+1 查询要改成批量接口，对慢工具要设置超时和降级。

同时要控制工具结果大小，工具返回的大 JSON 进入 Prompt 后会增加模型输入 token。高风险写工具不能为了快盲目并行，必须保证幂等、确认和审计。

### Q10：如何设计超时和重试？

**参考答案：**

我会设置总 deadline，再给每个阶段分配 timeout。外部模型、检索、工具调用都不能无限等待。

读操作可以有限重试，使用指数退避和抖动；写操作必须有幂等键，否则不能简单重试。超时后要取消下游请求，避免后台继续消耗资源。重试失败后根据场景降级：返回部分结果、切备用模型、转异步任务或提示稍后重试。

### Q11：如何在低延迟和高质量之间权衡？

**参考答案：**

先按任务分级。低风险、高频、简单任务可以用小模型、短上下文和较短输出；高风险、复杂推理任务用强模型、更完整上下文和更严格校验。

也可以做两阶段策略：先用快模型处理，低置信度或校验失败时升级到强模型。关键是要记录路由原因和质量指标，不能只看延迟下降。

### Q12：怎么做压测？

**参考答案：**

LLM 应用压测要模拟真实请求分布，包括短问答、长上下文、RAG、多工具调用和结构化输出。指标看 QPS、TPM、TTFT、完整耗时、P95 / P99、错误率、超时率、取消率、成本和质量指标。

压测还要覆盖供应商限流、下游工具慢、检索服务抖动等故障场景，验证背压、降级和熔断是否生效。

### Q13：为什么“换更快模型”不一定能解决慢？

**参考答案：**

因为慢可能不在模型本身。瓶颈可能是检索、rerank、工具调用、数据库、前端缓冲、代理配置或输出 token 过多。即使模型更快，如果上下文过长、工具串行、缓存命中低，端到端延迟仍然很高。

换模型还可能降低质量，导致更多重试和人工修正。因此要先 trace 定位，再结合模型路由和质量评估决定是否切换模型。

### Q14：如何处理长尾慢请求？

**参考答案：**

长尾慢请求要看 P95 / P99 的 trace 分布，按任务类型、租户、模型、知识库、工具和 token 数分组。常见治理手段包括限制最大上下文、限制候选数、设置阶段 timeout、慢工具转异步、供应商熔断、队列隔离和高低优先级配额。

如果某些任务天然耗时长，就不要伪装成在线短请求，应该改成异步任务并给用户进度。

### Q15：性能优化后如何证明没有损害质量？

**参考答案：**

要用固定评估集和线上灰度验证。除了延迟，还要看答案准确率、引用命中率、结构化输出通过率、用户满意度、人工介入率和坏 case 数。

例如减少 RAG top_k 后 P95 降了，但引用命中率下降，说明优化不可接受。性能优化必须和质量回归一起看。

## 六、容易踩坑的点

1. **只看平均延迟**：忽略 P95 / P99，线上长尾无法解释。
2. **盲目换模型**：没有 trace 证据，可能治标不治本。
3. **无限重试**：供应商慢时放大流量，导致雪崩。
4. **缓存不带权限**：跨租户泄露风险极高。
5. **top_k 一味调小**：延迟下降但召回变差。
6. **流式输出误当完成**：用户看到文本不代表工具调用已经成功。
7. **并发不设上限**：压垮模型 API、数据库或外部工具。
8. **只优化后端**：忽略网关缓冲、前端渲染和客户端网络。
9. **只看单条样例**：没有固定评估集，无法证明优化有效。
10. **降级无记录**：质量下降但线上不可追踪。

## 七、面试速记

- 性能优化先打点，后优化。
- 核心指标：TTFT、完整响应耗时、P50 / P95 / P99、吞吐、错误率、成本、质量。
- LLM 延迟常见来源：输入 token、输出 token、模型排队、检索、rerank、工具调用、后处理、前端缓冲。
- 第一优先级：减少无效 token。
- 流式输出优化感知，不等于减少完整耗时。
- 缓存必须带权限、版本和任务维度。
- 并行适合独立只读任务，不适合无脑多模型调用。
- 重试必须有 timeout、退避、次数限制和幂等保护。
- 长任务要异步化，在线请求要有 deadline。
- 所有优化都要用质量评估集回归，不能只看速度。
