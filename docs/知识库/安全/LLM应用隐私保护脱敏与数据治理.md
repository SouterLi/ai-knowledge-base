## 核心概念

### 1. 隐私数据与敏感数据

LLM 应用里的隐私风险不只来自最终回答，也来自**中间过程**：用户输入、历史消息、RAG 文档、工具返回、Prompt 日志、评测样本、人工审核台和训练数据。

| 类型 | 例子 | 主要风险 |
| --- | --- | --- |
| PII | 姓名、手机号、身份证、邮箱、地址 | 用户身份被识别 |
| 凭证密钥 | API Key、访问 Token、Cookie | 账号或系统被接管 |
| 业务敏感 | 合同价格、工单内容、病历、财务数据 | 商业泄密或合规违规 |
| 行为数据 | 对话历史、点击、反馈、审核意见 | 可被组合推断个人偏好 |

面试中要强调：**模型上下文也是数据处理环节**，只要敏感信息进入 Prompt、日志或评测集，就已经形成合规和泄露风险。

### 2. 数据最小化

数据最小化是隐私保护的第一原则：只收集、传递、保存完成任务所必需的数据。

```text
少收集 → 少入模 → 少落盘 → 短保留 → 可追溯删除
```

例如客服摘要只需要订单状态和问题类型，就不要把身份证、完整地址、银行卡号一起传给模型。

### 3. 脱敏、匿名化与假名化

| 方法 | 含义 | 是否可恢复 | 适用场景 |
| --- | --- | --- | --- |
| 脱敏 | 用掩码替换部分内容 | 通常不可恢复 | 展示、日志、审核台 |
| 假名化 | 用稳定 ID 替代真实身份 | 可通过映射恢复 | 排障、数据分析 |
| 匿名化 | 去除可识别个人的信息 | 不应恢复 | 统计报表、公开数据 |

面试里要说清楚：**脱敏不是万能匿名化**。多个字段组合后仍可能重新识别用户，所以要配合权限、保留周期和访问审计。

### 4. 隐私治理的工程目标

隐私治理不是简单加一个正则过滤器，而是把敏感数据控制嵌入 LLM 链路：

```text
分类分级 → 输入拦截/改写 → 上下文最小化 → 输出脱敏
        → 日志分级 → 评测/训练前再脱敏 → 保留周期与删除
```

## 核心知识点

### 1. 敏感数据分类分级

先定义哪些数据能进模型、能进日志、能进评测集：

| 等级 | 数据 | 处理策略 |
| --- | --- | --- |
| L0 公开 | FAQ、公开文档 | 可直接检索和评测 |
| L1 内部 | 普通工单、内部知识 | 租户/角色过滤后使用 |
| L2 敏感 | 手机、邮箱、合同金额 | 入模前最小化，日志脱敏 |
| L3 高敏 | 身份证、银行卡、密钥、病历 | 默认不入模，确需使用需审批和强审计 |

### 2. 输入侧脱敏与最小化

用户输入进入 LLM 前，应先做敏感检测、字段裁剪和业务改写。

```python
import re

PATTERNS = {
    "phone": re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),
    "id_card": re.compile(r"(?<!\d)\d{17}[\dXx](?!\d)"),
    "api_key": re.compile(r"sk-[A-Za-z0-9]{20,}"),
}

def mask_sensitive_text(text: str) -> tuple[str, list[str]]:
    hits: list[str] = []
    masked = text

    for name, pattern in PATTERNS.items():
        if pattern.search(masked):
            hits.append(name)
            # 中文注释：高敏字段不进入模型上下文，只保留类型占位
            masked = pattern.sub(f"[{name}_MASKED]", masked)

    return masked, hits

masked_prompt, sensitive_types = mask_sensitive_text(
    "帮我查 13812345678 的订单，身份证 110101199001011234"
)
```

注意：正则只能覆盖显式模式，真实系统通常还会结合字典、NER、规则引擎和业务字段元数据。

### 3. RAG 与工具返回的隐私控制

RAG 文档和工具结果不能原样塞进 Prompt：

- 检索前按租户、权限、敏感等级过滤。
- chunk 元数据记录 `sensitivity_level`、`contains_pii`、`retention_policy`。
- 工具返回做字段级裁剪，只把完成任务需要的字段传给模型。
- 对高敏字段采用摘要或标签，例如「用户已完成实名验证」，而不是返回身份证号。

```python
def sanitize_order_for_llm(order: dict) -> dict:
    # 中文注释：模型只需要判断售后策略，不需要看到完整个人信息
    return {
        "order_id": order["order_id"],
        "status": order["status"],
        "paid_at": order["paid_at"],
        "refund_count": order["refund_count"],
        "real_name_verified": bool(order.get("id_card_hash")),
    }
```

### 4. 日志与链路追踪

LLM 应用为了排障通常需要记录 Prompt、检索结果、工具调用和输出，但日志是最常见的泄露入口。推荐记录：

| 字段 | 推荐做法 |
| --- | --- |
| 用户标识 | 记录哈希或内部 ID，不记录手机号/邮箱 |
| Prompt | 默认记录哈希、模板版本和脱敏摘要 |
| RAG 证据 | 记录 doc_id/chunk_id/版本，不记录全文 |
| 工具参数 | 记录字段白名单和摘要，过滤 Token/密钥 |
| 输出 | 记录脱敏文本、结构化校验结果和安全拦截原因 |

```python
import hashlib

def stable_hash(value: str) -> str:
    # 中文注释：哈希用于关联排障，不用于恢复原始隐私数据
    return hashlib.sha256(value.encode("utf-8")).hexdigest()

def build_privacy_safe_log(request: dict, output: str) -> dict:
    masked_input, sensitive_types = mask_sensitive_text(request["user_input"])
    masked_output, output_sensitive_types = mask_sensitive_text(output)
    return {
        "request_id": request["request_id"],
        "tenant_id": request["tenant_id"],
        "user_hash": stable_hash(request["user_id"]),
        "prompt_version": request["prompt_version"],
        "input_summary": masked_input[:200],
        "input_sensitive_types": sensitive_types,
        "output_summary": masked_output[:200],
        "output_sensitive_types": output_sensitive_types,
    }
```

### 5. 评测集、训练集与数据闭环

线上坏 Case 进入评测或训练前，需要二次治理：

1. 去除重复和不可复现样本。
2. 脱敏用户身份、联系方式、密钥、订单号等字段。
3. 保留任务相关事实，例如「是否实名」「是否超售后期」，而不是保留原始证件号。
4. 标注数据来源、授权范围、保留周期和可删除状态。
5. 对外包标注和人工审核台做字段级遮罩、下载限制和访问审计。

面试重点：**不要把线上日志直接倒进微调或评测**。这会把一次性生产数据变成长期资产，隐私风险被放大。

### 6. 保留周期、删除与审计

隐私治理需要可操作的生命周期：

```yaml
privacy_policy:
  raw_prompt:
    retention_days: 7
    storage: encrypted_restricted
  masked_trace:
    retention_days: 90
    storage: analytics
  eval_case:
    retention_days: 365
    require_pii_scan: true
  deletion:
    user_request: cascade_by_user_hash
```

关键点：

- 原始数据短保留，脱敏摘要长保留。
- 删除要能覆盖日志、向量索引、评测集、缓存和人工审核记录。
- 审计记录谁在何时查看了哪些敏感字段，以及查看理由。
- 用 KMS/密钥轮换、分级授权和导出审批降低内部泄露风险。

### 7. 常见架构落点

```text
请求入口
  → PII 检测与策略引擎
  → 输入最小化/脱敏
  → 权限过滤后的 RAG/工具
  → LLM 推理
  → 输出敏感检测与脱敏
  → 隐私安全日志
  → 脱敏后进入评测/数据闭环
```

面试表达可以总结为：**高敏数据默认不入模，必须入模时要有最小字段、明确目的、短保留、可审计、可删除**。

## 高频面试问题与标准答案

**Q1：LLM 应用里隐私泄露通常发生在哪些环节？**

不只发生在最终回答。更常见的是用户原始输入、RAG 文档、工具返回、Prompt 日志、链路追踪、人工审核台、评测集和微调数据里泄露。我的处理思路是先做数据分类分级，再在输入、上下文、输出、日志和数据闭环各层做最小化、脱敏、权限和保留周期控制。

**Q2：为什么不能把完整 Prompt 都打进日志，排障不是更方便吗？**

完整 Prompt 里可能包含用户隐私、内部知识、工具结果和系统指令，长期明文落盘风险很高。更合理的是记录 request_id、Prompt 版本、模型版本、检索 chunk ID、工具摘要、脱敏输入输出和上下文哈希。遇到高等级事故时，可以在受控权限下短期查看原始数据，而不是默认全量保存。

**Q3：输入脱敏会不会影响模型效果？**

会，所以不能机械替换所有字段。原则是看任务是否真的需要原值：判断退款资格可能只需要「是否实名」和「支付时间」，不需要身份证号；但生成寄件地址确认时可能需要部分地址。工程上通常做字段级策略：高敏默认不入模，必要字段最小化传递，输出和日志再脱敏。

**Q4：RAG 场景如何防止敏感文档泄露？**

第一，入库时给 chunk 打 tenant、ACL、敏感等级和保留策略。第二，召回前或召回时强制权限过滤，不能先召回再让模型保密。第三，进入 Prompt 前做字段裁剪或摘要化。第四，日志只记录 doc_id、chunk_id、版本和分数，不默认记录全文。

**Q5：线上坏 Case 能直接拿来做评测集或微调数据吗？**

不能直接用。线上坏 Case 要经过筛选、去重、脱敏、授权范围确认和保留周期标记。尤其是微调数据会长期影响模型行为，必须避免把手机号、身份证、密钥、客户合同等生产数据固化进去。面试里我会强调：数据闭环要先治理，再评测或训练。

**Q6：如何设计一套隐私安全的 LLM 日志方案？**

我会分层记录：业务上记录 request_id、tenant_id、脱敏 user_id；模型侧记录 prompt_version、model_alias、生成参数；RAG 记录 chunk ID 和版本；工具记录白名单参数摘要；输入输出存脱敏摘要和敏感类型。原文只在强权限、短保留、加密存储下用于事故排查，并且所有访问都要审计。

**Q7：脱敏和匿名化有什么区别？**

脱敏通常是把手机号、证件号等字段遮掉，降低直接暴露风险；匿名化要求不能再识别个人，标准更高；假名化是用稳定 ID 替代真实身份，便于关联分析但可通过映射恢复。面试回答时要补一句：脱敏数据也可能通过多字段组合被重新识别，所以还要有访问控制和保留周期。

**Q8：如果业务确实需要把敏感信息传给模型怎么办？**

先确认是否有替代方案，比如传验证结果、摘要或标签。如果必须传，就要做到目的明确、字段最小、链路加密、供应商和模型边界可控、日志脱敏、短保留、访问审计，并尽量使用私有化部署或合规承诺明确的模型服务。高风险场景还应加人工审批或合规门禁。

**Q9：如何验证隐私治理真的生效？**

我会建立隐私回归集，覆盖手机号、身份证、API Key、跨租户文档、工具返回敏感字段等样例；在输入、RAG、工具、输出、日志各阶段断言敏感字段没有越权传播。同时在线上监控敏感拦截率、日志 PII 扫描结果、人工导出行为和删除请求处理结果。

**Q10：面试官问“隐私保护会不会拖慢研发效率”，怎么回答？**

我会说短期会增加策略配置和数据治理成本，但长期能减少事故和返工。关键是把规则平台化：统一 PII 检测、脱敏 SDK、日志白名单、数据分级元数据和评测前扫描，而不是让每个业务线手写一套正则。这样既能保证合规，也能让新应用复用同一套隐私基线。
