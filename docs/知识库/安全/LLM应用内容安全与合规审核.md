## 核心概念

### 1. 什么是 LLM 应用内容安全与合规审核

LLM 应用内容安全与合规审核，是指在用户输入、检索内容、工具结果、模型输出和日志回流等环节，对可能违反法律法规、平台政策、行业规范或企业安全红线的内容进行识别、拦截、降级、改写、转人工和审计。

一句面试表达：**内容安全不是在最后加一个敏感词过滤器，而是把风险识别、策略决策、模型生成、人工复核和线上反馈做成一条可配置、可审计、可评估的链路。**

典型链路如下：

```text
用户输入
  → 输入审核：意图、风险类别、严重等级
  → 业务路由：拒答 / 安全改写 / 正常处理 / 转人工
  → RAG/工具调用：过滤高风险上下文和工具结果
  → 模型生成：安全指令 + 业务回答
  → 输出审核：违规检测、事实风险、免责声明
  → 审计与回流：样本标注、策略优化、模型评估
```

### 2. 内容安全和传统安全的区别

| 维度 | 传统安全 | 内容安全与合规审核 |
| --- | --- | --- |
| 核心目标 | 防入侵、防越权、防数据泄露 | 防违规生成、防有害建议、防政策越界 |
| 判断对象 | 请求参数、权限、网络、数据访问 | 自然语言、图片、文档、对话上下文、模型回答 |
| 判断难点 | 边界较确定 | 语义模糊、上下文相关、行业政策变化快 |
| 常见手段 | 鉴权、ACL、WAF、审计 | 规则、分类模型、LLM Judge、人工复核、策略引擎 |

面试中要讲清楚：**传统安全回答“能不能访问”，内容安全回答“能不能说、怎么说、说到什么程度”。**

### 3. 常见内容风险类别

企业级 LLM 应用通常会把风险拆成可配置标签：

| 风险类别 | 示例 | 处理重点 |
| --- | --- | --- |
| 违法违规 | 制作武器、诈骗脚本、绕过监管 | 高置信拒答，保留审计 |
| 暴恐极端 | 暴力组织、恐吓、煽动伤害 | 拒答或安全引导 |
| 色情低俗 | 成人内容、未成年人相关内容 | 分级策略，未成年人风险零容忍 |
| 自伤自杀 | 自残计划、求死表达 | 温和支持、危机资源、必要时转人工 |
| 仇恨辱骂 | 针对群体攻击、歧视言论 | 拒绝扩散，改为中性表达 |
| 医疗金融法律建议 | 诊断、投资建议、法律结论 | 提供一般信息，增加免责声明，建议咨询专业人士 |
| 版权与品牌风险 | 复刻受保护作品、冒充品牌 | 限制生成，转为概括或原创替代 |
| 企业内部合规 | 未授权披露、敏感业务承诺 | 权限校验、话术约束、人工审批 |

成熟系统不会只用“通过/拒绝”两个结果，而是会按风险等级输出不同动作。

### 4. 内容审核的核心矛盾

内容审核的核心矛盾是 **安全、体验、召回、成本、延迟、可解释性**：

- 拦截太松：违规内容漏放，带来法律、品牌和平台风险。
- 拦截太严：正常用户被误拒，产品可用性和转化下降。
- 只用规则：可解释但覆盖不了语义变体和上下文风险。
- 只用模型：覆盖更强但成本高、延迟高、边界不稳定。
- 只审输出：危险输入、检索文档和工具结果已经污染上下文。
- 流式输出：用户看到 token 后再拦截，可能已经造成风险。

面试中要避免说“加一个审核模型就行”。更好的回答是：**低成本规则做硬拦截，分类模型做风险分级，LLM Judge 处理复杂语义，人工复核兜底高风险灰区，策略引擎统一决策。**

## 核心知识点

### 1. 审核点要覆盖输入、上下文和输出

内容安全常见错误是只在最终回答后做审核。真实系统至少要覆盖四个点：

```text
输入审核：用户是不是在请求违规内容
上下文审核：检索文档、网页、工具返回是否包含高风险内容
生成约束：系统 Prompt 和业务策略是否要求安全表达
输出审核：最终回答是否违规、是否需要免责声明或转人工
```

面试表达：**输入审核决定“要不要进入生成链路”，上下文审核决定“能不能把资料给模型看”，输出审核决定“能不能把回答给用户看”。三者职责不同，不能互相替代。**

### 2. 策略分级比简单拒答更重要

内容审核的结果通常不应该只有 `allow` 和 `deny`。更合理的动作包括：

| 动作 | 适用场景 | 示例 |
| --- | --- | --- |
| allow | 正常低风险问题 | 产品介绍、知识问答 |
| allow_with_disclaimer | 医疗、金融、法律等专业建议 | “以下仅供参考，请咨询专业人士” |
| safe_completion | 用户有高风险意图但可以安全替代 | 把“怎么自残”改为“如何获得帮助” |
| rewrite | 用户表达粗暴但业务意图正常 | 将辱骂客服改写为中性投诉摘要 |
| block | 明确违法违规或高危内容 | 制毒、诈骗、暴恐细节 |
| escalate | 高风险但需要人工判断 | 自伤危机、重大投诉、监管敏感问题 |

策略可以用配置表达：

```yaml
content_policy:
  self_harm:
    low: safe_completion
    medium: escalate
    high: escalate
  illegal_activity:
    low: block
    medium: block
    high: block
  financial_advice:
    low: allow_with_disclaimer
    medium: allow_with_disclaimer
    high: escalate
```

面试加分点：**策略要可配置、可灰度、可回滚，不能把所有安全边界硬编码在 Prompt 里。**

### 3. 审核实现通常是多层组合

不同审核手段各有优缺点：

| 手段 | 优点 | 局限 | 适合场景 |
| --- | --- | --- | --- |
| 关键词/正则 | 快、便宜、可解释 | 容易绕过，误杀高 | 密钥、手机号、明确违禁词 |
| 分类模型 | 延迟低、稳定、适合批量 | 需要训练/标注，泛化有限 | 色情、辱骂、暴恐等分类 |
| LLM Judge | 理解上下文强 | 成本高、可能不稳定 | 灰区语义、多轮上下文判断 |
| 业务规则 | 与企业政策一致 | 维护成本高 | 行业合规、地区策略、用户分层 |
| 人工复核 | 最可靠 | 成本和时效压力 | 高风险、争议、申诉样本 |

一个简化的审核决策代码可以这样写：

```python
from dataclasses import dataclass


@dataclass
class ModerationSignal:
    category: str
    severity: str
    confidence: float
    source: str


def decide_action(signals: list[ModerationSignal]) -> str:
    # 中文注释：先处理高置信硬风险，避免被后续模型判断覆盖
    for signal in signals:
        if signal.category in {"illegal_activity", "child_safety"} and signal.confidence >= 0.8:
            return "block"

    # 中文注释：自伤场景更适合安全引导或人工升级，不能简单冷冰冰拒答
    if any(signal.category == "self_harm" for signal in signals):
        return "escalate"

    # 中文注释：专业建议类内容允许回答通用信息，但必须降低承诺性
    if any(signal.category in {"medical_advice", "financial_advice", "legal_advice"} for signal in signals):
        return "allow_with_disclaimer"

    # 中文注释：中低风险辱骂可以改写为中性表达，保留业务处理能力
    if any(signal.category == "abuse" and signal.severity != "high" for signal in signals):
        return "rewrite"

    return "allow"
```

面试重点：**审核链路要有优先级。高危硬规则优先，灰区交给语义模型或人工，业务可处理内容尽量安全改写而不是一刀切拒绝。**

### 4. 流式输出审核要特别设计

LLM 应用常用流式输出，但内容安全不能等全部输出结束后才处理。常见做法有三类：

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| 生成前审核 | 先审输入和上下文，再决定是否生成 | 延迟低，但不能发现生成阶段偏航 |
| 缓冲窗口审核 | 先缓存若干 token 或句子，通过审核后再释放 | 更安全，但牺牲首 token 延迟 |
| 生成后补审 | 完整输出后审核，不通过则替换 | 实现简单，但用户可能已看到风险内容 |

更稳妥的流式链路：

```text
用户输入审核通过
  → 模型开始生成
  → 服务端按句子/窗口缓存
  → 对窗口做规则和分类检测
  → 低风险窗口释放给前端
  → 高风险窗口停止生成并返回安全替代话术
```

示例伪代码：

```python
def stream_with_moderation(token_stream, moderator, window_size=80):
    buffer = ""
    for token in token_stream:
        buffer += token
        if len(buffer) < window_size and not buffer.endswith(("。", "！", "？", "\n")):
            continue

        risk = moderator.check(buffer)
        if risk["action"] == "block":
            # 中文注释：不要继续下发已缓存的高风险内容，直接切换为安全替代话术
            yield "抱歉，这部分内容我不能提供。我可以帮你改为安全、合规的方向。"
            return

        yield buffer
        buffer = ""

    if buffer:
        risk = moderator.check(buffer)
        if risk["action"] != "block":
            yield buffer
```

面试表达：**流式审核要在首 token 延迟和安全风险之间取舍。高风险业务宁可牺牲一点流畅度，也不能把违规片段先发给用户。**

### 5. RAG 和 Agent 场景要审外部内容

RAG 和 Agent 内容安全不能只审用户问题，还要审外部输入：

```text
RAG：上传文档、网页抓取内容、检索片段、引用标题、元数据
Agent：工具返回、第三方 API 内容、邮件正文、网页内容、MCP 工具描述
```

典型风险：

1. 检索文档包含违规内容，模型总结时扩散风险。
2. 网页内容诱导模型绕过平台策略。
3. 工具返回包含辱骂、隐私或非法信息，模型原样转述。
4. 用户要求对高风险文档做“优化、润色、扩写”，实际是在帮助传播。

处理方式：

- 入库前给文档打风险标签，严重违规内容不入库或隔离。
- 检索时过滤与用户角色、业务场景不匹配的高风险 chunk。
- 输出引用前检查引用片段是否允许展示。
- 工具返回进入模型前做字段裁剪和内容审核。

面试重点：**RAG 的内容安全不是“回答时小心点”，而是文档入库、召回、上下文拼接和引用展示都要带风险标签。**

### 6. 不同行业策略要分场景

同一句话在不同业务里风险不同。例如“如何处理伤口”在医疗咨询、客服报修和小说创作里的处理方式不同。

| 场景 | 策略重点 |
| --- | --- |
| 医疗健康 | 不做诊断结论，不开药，给一般建议和就医提醒 |
| 金融投顾 | 不承诺收益，不给个股买卖指令，提示风险 |
| 法律咨询 | 不替代律师意见，区分法律常识与具体案件判断 |
| 教育陪伴 | 未成年人保护、心理危机识别、家长/老师协同 |
| 企业客服 | 不承诺合同外权益，不泄露内部政策，不激化冲突 |
| 内容创作 | 版权、低俗、暴力、品牌安全、平台社区规则 |

面试表达：**内容安全策略必须结合业务域、用户身份、地区法规和产品形态，不能所有场景套同一套敏感词。**

### 7. 评估指标要同时看漏放和误杀

内容安全上线后要持续看指标：

| 指标 | 含义 | 面试关注点 |
| --- | --- | --- |
| unsafe_pass_rate | 违规样本漏放比例 | 高风险类别应尽量低 |
| false_block_rate | 正常样本被误杀比例 | 直接影响体验和业务转化 |
| escalation_rate | 转人工比例 | 太高说明自动策略不够准或过严 |
| appeal_success_rate | 用户申诉成功比例 | 衡量误杀问题 |
| policy_latency_p95 | 审核链路 P95 延迟 | 影响首 token 和整体体验 |
| moderation_cost_per_request | 单请求审核成本 | 决定能否全量上线 |
| category_drift | 风险类别分布变化 | 识别攻击、热点事件或策略漂移 |

面试中可以这样说：**我会把内容安全当成一个分类和决策系统来运营，不只看拦截量，还要看漏放、误杀、转人工、申诉、延迟和成本。**

### 8. 人工复核和申诉闭环不能缺失

纯自动审核很难处理灰区内容，尤其是医疗、金融、法律、自伤、未成年人和公众事件。成熟系统通常要有：

- 高风险自动升级：置信度低但风险高的样本转人工。
- 双人复核：高影响处置需要交叉确认。
- 申诉机制：用户可对误杀结果申诉。
- 标注规范：明确标签定义、边界样例和冲突处理规则。
- 样本回流：误杀和漏放进入评测集、训练集和策略回归集。
- 审计记录：保存策略版本、模型版本、输入摘要、动作结果和复核人。

面试表达：**内容安全不是一次性规则配置，而是“策略 - 执行 - 复核 - 申诉 - 回流 - 评测”的运营闭环。**

## 高频面试问题与标准答案

**Q1：LLM 应用里内容安全审核应该放在哪些环节？**

我一般会放在输入、上下文和输出三个层面。输入审核判断用户是不是在请求违法违规或高风险内容；上下文审核检查 RAG 文档、网页、工具返回这些外部内容是否能进入模型；输出审核判断最终回答能不能展示给用户。只在最后做过滤不够，因为风险内容可能已经进入 Prompt，影响模型行为，也可能在流式过程中提前发给用户。

**Q2：为什么不能只靠敏感词过滤？**

敏感词过滤便宜、可解释，适合拦截明确词汇、密钥、手机号这类确定模式，但它不理解上下文，容易被同音、拆字、编码、隐喻绕过，也容易误杀正常讨论。工程上我会把敏感词作为第一层硬规则，再叠加分类模型、LLM Judge 和人工复核，尤其对医疗、金融、法律、自伤这类语义相关风险，要结合上下文判断。

**Q3：内容安全策略是直接拒答越多越好吗？**

不是。安全系统要同时控制漏放和误杀。明确违法、高危、未成年人相关风险可以强拒答；但专业建议类问题可以给一般性信息和免责声明；辱骂投诉可以改写为中性表达后继续处理；自伤问题要安全引导或转人工。面试里我会强调“分级处置”，而不是把所有风险都一刀切拒绝。

**Q4：流式输出场景怎么做内容审核？**

流式场景不能等完整答案生成完再审核，因为违规 token 可能已经展示给用户。常见做法是输入先审，生成过程中按句子或 token 窗口缓冲审核，通过后再释放给前端；如果检测到高风险，就停止生成并返回安全替代话术。对高风险业务，比如医疗、金融、未成年人场景，我会接受一点首 token 延迟，换更强的安全控制。

**Q5：RAG 场景的内容安全有什么特殊点？**

RAG 的风险不只来自用户问题，也来自知识库文档。文档里可能有违规内容、过期政策、恶意指令或不适合当前用户展示的片段。所以我会在入库时打风险标签，检索时结合权限和风险过滤，拼 Prompt 前再校验上下文，最终输出引用时检查片段是否允许展示。不能简单地让模型“不要说违规内容”，因为不可信文档已经进入上下文后会影响生成。

**Q6：Agent 工具返回的内容要审核吗？**

要。Agent 工具返回经常来自第三方系统、网页、邮件或数据库，里面可能包含隐私、辱骂、违规内容或恶意指令。我的做法是工具返回先做字段裁剪，只保留完成任务必要的信息，再做内容风险检测；高风险内容不直接进入模型上下文，或者只给模型结构化摘要。最终给用户展示前还要做输出审核和权限校验。

**Q7：LLM Judge 可以作为内容审核的最终依据吗？**

一般不建议完全依赖 LLM Judge。它适合判断复杂语义和上下文灰区，但会有不稳定、成本高和裁判偏差的问题。高危场景应该有规则或分类模型做硬门禁，LLM Judge 做辅助判定，人工复核兜底。面试里我会说：可确定的风险用确定性规则，语义灰区用模型辅助，重大风险由人工或强策略收口。

**Q8：怎么评估内容安全系统做得好不好？**

我会分风险类别看漏放率、误杀率、转人工率、申诉成功率、审核延迟和单次成本。只看拦截量没有意义，因为拦得多可能只是误杀多。更合理的是维护一套正常样本和攻击/违规样本的评测集，发布前跑回归，线上把漏放、误杀和人工复核样本回流，持续更新策略和模型。

**Q9：如果业务方觉得审核太严格影响转化，怎么处理？**

我会先用数据拆开看是哪类内容误杀高，是规则问题、模型阈值问题，还是策略本身过严。然后按风险分级调整：法律红线和平台红线不能放松；低风险业务话术可以改成安全改写或免责声明；灰区可以提高转人工而不是直接拒答。这样既能保护安全底线，也能减少不必要的体验损失。

**Q10：面试让你设计一个内容安全架构，你会怎么回答？**

我会先说整体链路：入口输入审核、RAG/工具内容审核、模型输出审核、策略引擎决策、人工复核和样本回流。实现上用规则处理确定模式，用分类模型做常见风险识别，用 LLM Judge 判断复杂语义，用人工复核兜底高风险灰区。策略上不是简单 allow/deny，而是 allow、免责声明、安全改写、拒答、转人工。最后补充监控指标，包括漏放、误杀、延迟、成本和申诉结果，这样架构才可上线、可运营、可迭代。
