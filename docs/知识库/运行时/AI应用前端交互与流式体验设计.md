## 核心概念

### 1. AI 应用前端不是普通聊天框

传统 Web 前端通常等待接口返回完整 JSON 后一次性渲染；AI 应用前端面对的是一个逐步发生的生成过程：

- 模型可能先返回 token，再补充工具调用状态；
- RAG 场景可能先检索、再重排、再生成引用答案；
- Agent 场景可能经历规划、工具执行、等待用户确认和继续生成；
- 用户可能在生成中途停止、编辑问题、重新生成或追问；
- 输出可能部分成功，例如正文已生成但引用加载失败。

所以面试中要先说明：**AI 前端要管理的是一次生成任务的生命周期，而不是一次普通 HTTP 请求的完成态**。它既要提升感知速度，也要把不确定状态清楚地反馈给用户。

### 2. 流式体验的核心目标

流式不是为了炫技，而是为了解决三个体验问题：

| 目标 | 说明 | 面试关注点 |
| --- | --- | --- |
| 降低首字等待 | 先展示模型开始工作，减少用户焦虑 | TTFT、骨架屏、阶段状态 |
| 暴露过程进展 | 告诉用户正在检索、调用工具或生成 | 事件协议、状态机 |
| 支持中途控制 | 用户可以停止、重试、复制、反馈 | 取消、幂等、局部失败 |

一句面试表达：**流式体验不是把 token 打出来这么简单，而是让用户理解系统正在做什么、做到哪一步、失败后还能怎么继续。**

### 3. 前端状态机比布尔变量更可靠

很多项目一开始只用 `loading=true/false`，很快就会失控。AI 应用至少需要区分：

```text
idle
  → submitting
  → retrieving
  → generating
  → tool_running
  → waiting_user_confirm
  → completed
  → failed
  → cancelled
```

状态机的价值是明确每个状态允许哪些用户操作：

- `generating`：允许停止、复制已生成内容，但不允许重复提交同一个输入。
- `tool_running`：可展示工具进度，高风险工具需要确认。
- `waiting_user_confirm`：显示确认卡片，不继续自动执行。
- `failed`：允许重试、查看错误摘要、保留已生成内容。
- `cancelled`：停止继续追加 token，保留当前草稿。

面试里要强调：**状态机是前端体验和后端任务状态之间的契约**，不是单纯 UI 变量。

### 4. 流式事件协议

前后端不能只约定“后端不断返回文本”。成熟做法是定义结构化事件：

```json
{"type":"message_start","message_id":"msg_1001"}
{"type":"stage","name":"retrieving","text":"正在检索知识库"}
{"type":"delta","content":"根据"}
{"type":"delta","content":"合同条款"}
{"type":"citation","doc_id":"doc_88","chunk_id":"c_12","title":"退款政策"}
{"type":"usage","input_tokens":820,"output_tokens":156}
{"type":"message_end","finish_reason":"stop"}
```

这样前端可以分别渲染正文、阶段、引用、工具结果、用量和结束原因。面试中可以说：**流式协议要传语义事件，不要只传字符串；否则工具调用、引用、错误和重试都很难做。**

### 5. 停止生成不等于关闭页面连接

用户点击“停止”后，前端通常会中断当前流，但后端也要知道这个任务已取消。否则会出现：

- 前端不显示了，后端仍在消耗 token；
- 工具调用继续执行，产生副作用；
- 用户马上重试，两个任务并发写同一条消息；
- 审计日志显示生成完成，但用户实际只看到了半截。

因此取消需要前后端协作：前端 `AbortController` 中断连接，后端收到取消信号或取消接口后停止模型调用、标记任务状态，并对已开始的工具执行做安全处理。

## 核心知识点

### 1. 推荐的前后端事件流

一个典型 AI 问答前端链路如下：

```text
用户提交问题
  → 前端创建本地 user message 和 assistant 占位消息
  → 请求后端创建 generation run
  → 建立 SSE / fetch stream / WebSocket
  → 根据事件更新状态机和消息内容
  → 收到 message_end 后落到 completed
  → 失败或取消时保留可恢复状态
```

关键点：

1. 前端先创建占位消息，避免页面空白。
2. 每次生成有独立 `run_id` 或 `message_id`，防止旧流覆盖新消息。
3. 后端事件要带序号或可恢复偏移，网络断开时便于排查和重连。
4. 前端要能处理乱序、重复结束、连接断开和部分失败。

### 2. SSE、fetch stream 和 WebSocket 怎么选

| 方案 | 适合场景 | 优点 | 风险 |
| --- | --- | --- | --- |
| SSE | 服务端单向推送 token 和状态 | 简单、浏览器原生、适合问答 | 不适合复杂双向交互 |
| fetch stream | 需要更灵活地解析流式 body | 可配合 AbortController | 兼容和封装成本更高 |
| WebSocket | 多 Agent 实时协作、语音、双向控制 | 双向、低延迟、可复用连接 | 状态管理和网关治理复杂 |

面试表达建议：**普通文本生成优先 SSE 或 fetch stream；如果需要实时双向控制、语音或多人协作，再考虑 WebSocket。不要为了“高级”把简单问答做成复杂长连接系统。**

### 3. 前端流式消费示例

下面是一个简化的 `fetch stream` 示例，重点体现取消、事件解析和消息归属：

```ts
type StreamEvent =
  | { type: "message_start"; message_id: string }
  | { type: "stage"; name: string; text: string }
  | { type: "delta"; content: string }
  | { type: "citation"; doc_id: string; chunk_id: string; title: string }
  | { type: "message_end"; finish_reason: string }
  | { type: "error"; code: string; message: string };

async function startGeneration(question: string, assistantMessageId: string) {
  const controller = new AbortController();
  const response = await fetch("/api/chat/stream", {
    method: "POST",
    signal: controller.signal,
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question, assistant_message_id: assistantMessageId }),
  });

  if (!response.body) {
    throw new Error("stream_not_supported");
  }

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";

  async function readLoop() {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      buffer += decoder.decode(value, { stream: true });
      const lines = buffer.split("\n");
      buffer = lines.pop() ?? "";

      for (const line of lines) {
        if (!line.trim()) continue;
        const event = JSON.parse(line) as StreamEvent;
        // 中文注释：只更新当前 assistant 消息，避免旧请求的流式片段覆盖新消息
        applyStreamEvent(assistantMessageId, event);
      }
    }
  }

  return {
    stop: () => controller.abort(),
    done: readLoop(),
  };
}
```

面试里不用背代码，但要说出三点：**可取消、可区分 message/run、按结构化事件更新 UI**。

### 4. 增量渲染要处理 Markdown 和代码块

LLM 输出常含 Markdown、表格和代码块。流式渲染时容易出现：

- 代码块还没闭合，页面高亮错乱；
- Markdown 表格生成一半，布局抖动；
- 数学公式或 HTML 标签未闭合；
- 每个 token 都触发重排，页面卡顿。

常见优化：

1. **节流渲染**：按 30～100ms 合并 token 更新，而不是每个 token setState。
2. **正文和最终渲染分离**：生成中用轻量 Markdown 渲染，结束后再做完整高亮。
3. **代码块容错**：检测未闭合三反引号，临时补齐再渲染。
4. **滚动策略**：用户停留在底部才自动滚动；用户向上查看历史时不要强制拉到底。

简化示例：

```ts
function normalizeStreamingMarkdown(content: string): string {
  const fenceCount = (content.match(/```/g) ?? []).length;
  if (fenceCount % 2 === 1) {
    // 中文注释：生成中的代码块可能尚未闭合，临时补齐以避免 Markdown 渲染错乱
    return `${content}\n\`\`\``;
  }
  return content;
}
```

### 5. 工具调用和 RAG 检索要展示过程，但不能泄露内部细节

AI 应用常需要展示“正在检索”“正在查询订单”“正在生成总结”等状态。展示策略要分层：

| 阶段 | 建议展示 | 不建议展示 |
| --- | --- | --- |
| RAG 检索 | 正在检索知识库、命中几类资料 | 原始向量分数、内部索引名 |
| 工具调用 | 正在查询订单状态、已完成 | 完整工具参数、内部接口地址 |
| 高风险动作 | 待用户确认的操作摘要 | 自动执行退款、改权限 |
| 失败状态 | 可理解的错误和下一步 | 堆栈、供应商原始报错 |

面试中可以说：**过程透明不是把内部日志暴露给用户，而是把用户关心的阶段和可操作状态表达清楚。**

### 6. 取消、重试和重新生成

这三个操作很容易混在一起：

- **取消**：停止当前 run，保留已生成内容，状态标记为 `cancelled`。
- **重试**：用同一个用户问题重新发起 run，通常生成新的 assistant message 或覆盖旧草稿。
- **重新生成**：保留用户消息，创建新的候选答案，方便用户在多个版本间切换。

实现注意点：

1. 每次 run 都要有独立 ID。
2. 前端取消连接后，最好调用后端取消接口或让后端感知断连。
3. 重试要避免旧流继续写 UI，可以在前端校验 active run。
4. 写工具不能因为“重试回答”重复执行，后端要依赖工具幂等和审批。

示例状态保护：

```ts
function applyDelta(state: ChatState, runId: string, content: string) {
  if (state.activeRunId !== runId) {
    // 中文注释：旧流返回的片段直接丢弃，防止覆盖用户最新一次重新生成
    return state;
  }

  return {
    ...state,
    assistantDraft: state.assistantDraft + content,
  };
}
```

### 7. 引用、来源和可追溯体验

RAG 应用面试常问：“前端怎么展示引用，才能让用户信任？”

建议设计：

- 正文生成时可先显示引用占位，例如 `[1]`、`[2]`；
- 流结束后展示来源卡片：标题、摘要、更新时间、权限范围；
- 点击引用定位到对应片段，而不是只打开整篇文档；
- 引用加载失败时不影响正文展示，但要提示“来源暂不可用”；
- 不要展示用户无权访问的文档标题或片段。

面试表达：**引用是可追溯体验的一部分，既要帮助用户核验答案，也要受权限控制，不能因为前端展示来源而绕过 ACL。**

### 8. 错误体验要按失败类型设计

AI 应用常见失败不是一个统一 toast 能解决的：

| 失败类型 | 用户提示 | 系统动作 |
| --- | --- | --- |
| 网络断开 | 连接中断，可重试 | 保留草稿，允许继续或重新生成 |
| 模型超时 | 当前生成较慢，请稍后重试 | 后端取消或转异步 |
| 内容安全拦截 | 该请求无法处理 | 显示合规原因，不暴露规则细节 |
| 引用加载失败 | 答案已生成，来源暂不可用 | 单独重试引用接口 |
| 工具执行失败 | 查询订单失败，可稍后再试 | 不伪造工具结果，记录错误码 |

面试里要强调：**错误体验要保留上下文和用户可操作路径，不要让用户只看到“系统异常”。**

### 9. 感知性能指标

AI 前端除了普通接口耗时，还要关注：

| 指标 | 含义 | 优化方向 |
| --- | --- | --- |
| TTFT | 从提交到首个 token/首个事件 | Prompt 裁剪、预连接、先发 stage |
| 首屏可读时间 | 用户看到有意义内容的时间 | 阶段提示、增量渲染 |
| token 渲染平滑度 | 是否卡顿、跳字、批量闪现 | 节流、虚拟列表、减少重排 |
| 取消生效时间 | 点击停止到不再追加内容 | Abort、后端取消、active run 校验 |
| 错误恢复率 | 失败后用户是否能继续完成任务 | 重试入口、保留草稿 |

注意：TTFT 不一定等于真实模型首 token。前端可以先展示“正在检索知识库”来降低焦虑，但不能用假进度条欺骗用户。

### 10. 前端安全边界

AI 前端不能信任模型输出：

- Markdown 中的 HTML 要过滤，避免 XSS。
- 链接要做白名单或安全跳转提示。
- 模型返回的工具卡片只能作为展示，真正执行要走后端权限校验。
- 引用内容要按用户权限重新校验。
- 不要把系统 Prompt、密钥、内部工具参数放到前端。

简化示例：

```ts
function isSafeUrl(url: string): boolean {
  try {
    const parsed = new URL(url);
    // 中文注释：只允许 http/https 链接，避免 javascript: 这类注入载荷
    return parsed.protocol === "https:" || parsed.protocol === "http:";
  } catch {
    return false;
  }
}
```

面试金句：**模型输出是内容来源，不是可信前端代码；所有可执行动作仍然要经过确定性校验。**

## 高频面试问题与标准答案

### 问题 1：AI 聊天前端接流式输出时，你会怎么设计？

标准答案：我会先定义结构化流式事件，而不是只传纯文本 token。事件里至少包括 message_start、stage、delta、citation、usage、message_end 和 error。前端为每次生成维护 run_id/message_id，用状态机管理 submitting、retrieving、generating、completed、failed、cancelled 等状态。

实现上可以用 SSE 或 fetch stream，普通问答优先选简单的单向流；如果是语音或复杂双向控制，再考虑 WebSocket。前端收到 delta 时增量追加正文，收到 stage 时展示“正在检索/正在生成”，收到 citation 时更新来源卡片。还要支持 AbortController 取消，并防止旧 run 的事件覆盖新答案。

### 问题 2：用户点击“停止生成”，前后端分别要做什么？

标准答案：前端要立即中断当前流，比如调用 AbortController，并把当前 run 标记为 cancelled，停止继续追加 token。但这还不够，后端也要感知取消：停止模型调用、释放资源、标记任务状态。如果已经进入工具调用，尤其是写操作，不能简单杀掉进程，要根据工具幂等、执行记录和风险等级处理。

我还会在前端用 activeRunId 做保护，即使旧连接稍后返回了片段，也不能再写入 UI。面试里我会强调：停止生成不是只隐藏 loading，而是一次生成任务生命周期的取消动作。

### 问题 3：SSE、WebSocket、普通 HTTP 你怎么选？

标准答案：如果只是聊天文本生成，普通 HTTP 一次性返回首字等待太长，体验不好；SSE 或 fetch stream 更适合，因为服务端单向推送 token 和阶段事件就够了，成本也低。WebSocket 适合更复杂的双向场景，比如实时语音 Agent、多人协作、浏览器持续发送控制指令。

我不会默认上 WebSocket，因为它会带来连接管理、鉴权续期、心跳、断线恢复和网关治理成本。选型核心看交互是否需要双向实时，而不是看哪个技术更“高级”。

### 问题 4：流式 Markdown 渲染有哪些坑？

标准答案：LLM 输出 Markdown 时，内容是逐步到达的，代码块、表格、列表和公式经常处于未闭合状态。如果每个 token 都触发完整 Markdown 渲染，会导致页面抖动、代码高亮错乱和性能卡顿。

我的做法是生成中做轻量渲染和节流更新，比如每几十毫秒合并一次；对未闭合代码块临时补齐，结束后再做完整 Markdown、高亮和目录处理。滚动也要注意，只有用户停留在底部时才自动滚动，用户回看历史时不要强制拉到底。

### 问题 5：RAG 应用前端怎么展示引用？

标准答案：我会把引用作为独立事件和独立 UI 数据处理，而不是让模型在正文里随便写来源。生成过程中可以先显示引用编号，流结束后展示来源卡片，包括标题、摘要、更新时间和片段定位。用户点击引用时最好定位到具体 chunk，而不是只打开整篇文档。

同时引用展示必须走权限控制。用户无权访问的文档，即使参与了内部检索也不能在前端暴露标题或片段。引用加载失败时可以让正文先展示，但要明确提示“来源暂不可用”，不要假装有依据。

### 问题 6：AI 应用的错误提示怎么设计，不能只说“系统异常”吗？

标准答案：不能只给一个通用异常，因为 AI 应用失败类型很多，用户下一步操作也不同。网络断开可以保留草稿并允许重试；模型超时可以提示稍后再试或转异步；内容安全拦截要说明无法处理但不暴露规则细节；工具失败要说明哪个业务查询失败，不能编造结果；引用失败可以单独重试来源。

我会把错误分成可重试、不可重试、需用户补充信息、需人工处理几类。好的错误体验应该保留上下文，让用户知道能不能继续、怎么继续，而不是把之前生成的内容清空。

### 问题 7：如何避免旧的流式响应覆盖新的回答？

标准答案：每次生成都要有独立 run_id 或 message_id，前端状态里维护 activeRunId。所有流式事件到达时先校验它属于当前 run，只有匹配才更新 UI；不匹配说明可能是旧连接、重试残留或用户重新生成后的过期事件，应该丢弃。

后端也应该用 run_id/message_id 标识事件，最好有单调递增序号，方便排查丢包和重复事件。这个问题本质上是并发状态管理，不是简单加一个 loading 就能解决。

### 问题 8：AI 前端如何体现“系统正在工作”，又不泄露内部实现？

标准答案：我会展示用户能理解的阶段，比如“正在检索知识库”“正在查询订单”“正在生成总结”“等待你确认退款信息”，而不是展示内部向量库名称、原始工具参数、Prompt 或供应商报错。过程透明的目标是降低用户焦虑和支持下一步操作，不是把内部日志暴露出去。

对高风险工具，前端只展示操作摘要和确认入口，真正执行必须回到后端做权限、审批和幂等校验。也就是说，前端负责表达状态和收集确认，安全边界仍在后端。

### 问题 9：你会关注哪些 AI 前端体验指标？

标准答案：我会关注 TTFT，也就是用户提交到首个 token 或首个阶段事件的时间；还会看首屏可读时间、流式渲染是否平滑、取消生效时间、错误后重试成功率和用户反馈率。单纯平均响应时间不够，因为 AI 应用用户感知更依赖首字等待和中途是否有进展反馈。

优化上，前端可以先展示真实阶段事件、节流渲染、减少大段重排；后端要优化 Prompt 组装、检索和模型调用。需要注意不能用假进度条欺骗用户，阶段提示应该来自真实链路。

### 问题 10：模型输出里有 Markdown、HTML 或链接，前端安全怎么做？

标准答案：我不会把模型输出当可信 HTML 直接渲染。Markdown 渲染要过滤危险标签和属性，链接要校验协议和域名，至少拦截 `javascript:` 这类注入。模型生成的按钮或工具卡片只能作为展示或建议，真正执行动作要由后端根据权限、参数和业务规则重新校验。

另外，系统 Prompt、密钥、内部工具参数和用户无权访问的引用不能下发给前端。面试里我会总结：模型输出是内容，不是代码；前端展示要防 XSS，后端执行要防越权。

### 问题 11：重新生成回答时，应该覆盖旧答案还是保留多个版本？

标准答案：这取决于产品场景。普通聊天可以覆盖当前 assistant 草稿，但更好的方式是保留多个候选版本，用户可以切换或选择更满意的一版。无论哪种方式，底层都应该创建新的 run_id，避免新旧流混在一起。

如果回答过程包含工具调用，要特别小心。只读工具可以重新查询，但写工具不能因为重新生成而重复执行。后端需要工具幂等和执行记录，前端也要清楚区分“重新表达答案”和“重新执行业务动作”。

### 问题 12：如果让你优化一个 AI 问答页面的体感速度，你会怎么做？

标准答案：我会先拆指标，看慢在首个阶段事件、首 token、整体完成还是前端渲染。前端侧可以提交后立即创建占位消息，展示真实阶段状态；流式内容做节流渲染，避免每个 token 重排；长答案用虚拟列表或分块渲染；Markdown 结束后再完整高亮。

后端侧要减少无效上下文、优化检索和 Prompt 组装，必要时把慢工具转成异步或先返回阶段事件。我的思路不是只追求总耗时，而是让用户尽早看到系统开始工作，并且在等待过程中有明确进展和可取消能力。
