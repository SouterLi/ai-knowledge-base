## 核心概念

**RAG 答案生成** 不是把检索片段简单拼进 Prompt 后让模型自由发挥，而是把候选证据组织成可被引用、可被校验、可拒答的上下文，让模型在证据边界内完成回答。

完整链路通常是：

```text
用户问题
  -> 查询理解
  -> 混合检索
  -> rerank
  -> 上下文压缩与证据打包
  -> 受约束答案生成
  -> 引用归因
  -> 一致性校验 / 低置信拒答
  -> 日志、评估与坏 Case 回流
```

面试里要强调：**RAG 的最终交付物不是一段看似流畅的文字，而是“答案 + 证据 + 置信边界 + 可追溯链路”**。企业知识库、客服、法务、金融、医疗等场景里，答案是否有依据通常比语言是否优美更重要。

几个核心术语：

| 概念 | 含义 | 面试关注点 |
| --- | --- | --- |
| Grounded Answer | 基于检索证据生成的答案 | 每个关键事实都能回到原文 |
| Citation | 引用来源 | 文档、页码、chunk、原文 span 的粒度 |
| Faithfulness | 忠实度 | 答案是否被上下文支持 |
| Abstention | 拒答 | 证据不足时不编造 |
| Attribution | 归因 | 哪句话来自哪条证据 |
| Verification | 校验 | 生成后检查事实、引用和权限 |

一个合格的 RAG 答案通常包含三层信息：

1. **直接回答**：先回答用户问题，不绕圈。
2. **依据引用**：关键结论后附来源，能定位到原文。
3. **不确定性边界**：证据不足、版本过旧、权限受限时明确说明。

## 核心知识点

### 1. 生成阶段的输入不是“文本拼接”，而是证据包

进入 LLM 的上下文最好保留结构，而不是把所有 chunk 拼成一坨文本。结构化证据包能帮助模型区分来源、版本、权限、时间和可信度。

```json
{
  "question": "企业版是否支持单点登录？",
  "evidence": [
    {
      "id": "E1",
      "title": "企业版安全能力说明",
      "doc_id": "sec_enterprise_2026",
      "page": 4,
      "published_at": "2026-04-18",
      "score": 0.91,
      "text": "企业版支持基于 SAML 2.0 的单点登录，并可配置企业身份提供商。"
    },
    {
      "id": "E2",
      "title": "版本功能对比表",
      "doc_id": "plan_compare_2026",
      "page": 2,
      "published_at": "2026-04-20",
      "score": 0.88,
      "text": "专业版不支持 SSO；企业版支持 SSO、SCIM 和审计日志。"
    }
  ]
}
```

Prompt 中要明确约束：

```text
你只能根据 evidence 回答。
每个关键事实后必须标注证据 id，例如 [E1]。
如果 evidence 不能支持结论，回答“当前知识库没有足够依据”。
不要使用模型自身记忆补充产品能力。
```

面试回答时可以说：我会把证据做成带 id 的结构化上下文，要求模型引用 evidence id，并在后处理阶段检查引用 id 是否存在、答案是否覆盖原文事实。

### 2. 引用归因要到“关键事实”粒度

引用不是在答案末尾随便挂几个链接。更可靠的方式是把**关键事实**和证据绑定。

错误示例：

```text
企业版支持 SSO、SCIM、审计日志和私有化部署。[参考文档]
```

问题是无法知道每个结论分别来自哪里，其中“私有化部署”可能并没有被证据支持。

更好的示例：

```text
企业版支持基于 SAML 2.0 的单点登录 [E1]，同时支持 SCIM 和审计日志 [E2]。
当前证据没有说明企业版是否支持私有化部署，因此不能直接确认。
```

引用粒度常见有四层：

| 粒度 | 优点 | 风险 |
| --- | --- | --- |
| 文档级 | 实现简单 | 难定位具体依据 |
| 页码 / 段落级 | 适合 PDF、手册 | 解析质量影响定位 |
| chunk 级 | 与向量库天然对应 | chunk 过大时仍不精确 |
| span 级 | 最可解释 | 实现成本高，需要原文偏移 |

生产系统常用 **chunk 级起步，高风险场景做 span 级定位**。面试中可以补一句：引用必须通过权限过滤后的证据生成，不能把用户无权访问的文档标题或摘要泄露出来。

### 3. 幻觉控制先看证据覆盖，不要只改 Prompt

RAG 幻觉常见来源：

1. **检索没召回正确证据**：模型只能根据噪声猜。
2. **证据召回了但排序靠后**：有效信息没有进入上下文。
3. **压缩丢了条件或数字**：金额、日期、例外条款被删。
4. **Prompt 约束弱**：模型把常识或参数知识混进答案。
5. **引用后处理缺失**：答案引用了不存在或不相关的来源。

排障顺序建议：

```text
问题是否有标准答案
  -> top_100 是否召回正确 chunk
  -> rerank top_5 是否包含答案
  -> 压缩后证据是否仍保留关键条件
  -> 生成答案是否每个关键事实都有引用
  -> 引用是否真的支持该事实
```

面试里不要回答成“加一句不要胡说”。更专业的说法是：我会把幻觉拆成检索侧、上下文侧、生成侧、校验侧四层分别定位。

### 4. 拒答策略是 RAG 质量的一部分

企业场景里，**不知道就说不知道** 比编造更重要。拒答不是失败，而是风险控制。

常见拒答触发条件：

| 条件 | 处理 |
| --- | --- |
| 检索最高分低于阈值 | 提示知识库无足够依据 |
| rerank 后证据互相矛盾 | 给出差异并提示需人工确认 |
| 用户问题超出知识库范围 | 说明范围限制 |
| 涉及高风险操作 | 要求确认或转人工 |
| 命中权限边界 | 只说明无权限或无法访问，不泄露文档内容 |

示例逻辑：

```python
from dataclasses import dataclass


@dataclass
class Evidence:
    id: str
    rerank_score: float
    text: str


def should_abstain(evidence: list[Evidence], min_score: float = 0.62) -> bool:
    if not evidence:
        return True

    best_score = max(item.rerank_score for item in evidence)
    if best_score < min_score:
        return True

    return False


def build_answer_prompt(question: str, evidence: list[Evidence]) -> str:
    if should_abstain(evidence):
        return "当前知识库没有足够依据回答该问题，请提示用户补充信息或转人工。"

    evidence_text = "\n".join(f"[{item.id}] {item.text}" for item in evidence)
    return f"""请仅根据以下证据回答问题，并在关键事实后标注证据 id。

问题：{question}

证据：
{evidence_text}
"""
```

实际系统不会只靠一个分数阈值，还会结合召回覆盖度、证据数量、业务风险等级、用户意图和历史坏 Case 调整。

### 5. 生成后校验要检查“答案-引用-原文”的一致性

常见校验项：

1. **引用合法性**：答案中的 `[E1]` 是否存在于证据包。
2. **引用相关性**：引用的 evidence 是否真的支持前面的句子。
3. **数值一致性**：金额、日期、版本号、比例是否和原文一致。
4. **否定与条件**：是否遗漏“不支持”“仅企业版”“需开通插件”等限制。
5. **权限一致性**：答案是否泄露无权限证据。

可以用规则、小模型或 LLM-as-judge 做二次检查，但不要把 LLM 校验当成绝对真理。高风险场景更建议保留原文 span，并对关键字段做确定性比对。

```python
import re


def extract_citation_ids(answer: str) -> set[str]:
    return set(re.findall(r"\[(E\d+)\]", answer))


def validate_citations(answer: str, evidence_ids: set[str]) -> list[str]:
    errors: list[str] = []
    cited_ids = extract_citation_ids(answer)

    for citation_id in cited_ids:
        if citation_id not in evidence_ids:
            errors.append(f"引用 {citation_id} 不存在于证据包")

    if not cited_ids:
        errors.append("答案缺少引用，无法追溯来源")

    return errors
```

这段代码只能检查引用是否存在，不能证明引用支持答案。面试时可以继续补充：引用支持性需要句子级 NLI、LLM judge、关键词/数值校验或人工抽检结合。

### 6. 答案格式要服务用户场景

不同场景的答案风格不同：

| 场景 | 推荐答案结构 |
| --- | --- |
| 客服问答 | 先给结论，再给操作步骤和注意事项 |
| 政策制度 | 先给适用条件，再给条款依据 |
| 技术排障 | 先列可能原因，再给排查顺序 |
| 对比问题 | 表格对比，并分别引用证据 |
| 无答案问题 | 明确说明缺证据，给补充信息建议 |

示例：

```text
结论：企业版支持单点登录。

依据：
1. 企业版支持基于 SAML 2.0 的单点登录 [E1]。
2. 版本对比表显示企业版支持 SSO、SCIM 和审计日志，专业版不支持 SSO [E2]。

注意：当前证据只说明 SAML 2.0，没有说明是否支持 OIDC，因此 OIDC 支持情况需要查更具体的身份集成文档。
```

这种回答既回答了问题，也控制了证据边界。

### 7. 评估指标要覆盖引用质量

只看答案相似度不够，RAG 生成阶段至少要评估：

| 指标 | 解释 |
| --- | --- |
| Answer Correctness | 答案是否正确 |
| Faithfulness | 答案是否被上下文支持 |
| Citation Accuracy | 引用是否指向支持该结论的证据 |
| Unsupported Claim Rate | 无依据断言比例 |
| Abstention Precision | 拒答是否该拒才拒 |
| Abstention Recall | 应该拒答的问题是否拒了 |
| Conflict Handling Rate | 证据冲突时是否说明冲突 |

评测集最好包含：

1. 有明确答案的问题。
2. 知识库没有答案的问题。
3. 多文档合成问题。
4. 证据冲突或版本过期问题。
5. 权限受限问题。

面试中可以说：我会把“答案正确但引用错”单独算失败，因为企业知识库要的是可追溯可信答案。

### 8. 工程落地要记录完整链路

线上排障需要记录：

```text
request_id
用户问题与改写后问题
召回 query
召回候选及分数
rerank 分数
最终进入 prompt 的 evidence id
生成答案
引用 id
拒答原因
模型版本、Prompt 版本、索引版本
用户反馈
```

这样坏 Case 才能定位是“没检到”“排错了”“压缩丢了”“生成编了”“引用挂错了”。

注意日志中要做脱敏和权限控制，尤其是企业知识库、客服工单、合同、医疗等场景。

## 高频面试问题与标准答案

### 1. RAG 已经检索到文档了，为什么还会幻觉？

**标准答案：**
检索到文档不等于答案一定可靠。可能是正确 chunk 没进 top_k，rerank 排错，压缩时删掉了关键数字或限制条件，也可能是 Prompt 没约束模型只能基于证据回答。我的排查顺序会先看 top_100 有没有金标准，再看 rerank top_5、最终上下文、生成答案和引用是否一致，而不是一上来只换模型或加一句“不要胡说”。

### 2. 如何让 RAG 答案可溯源？

**标准答案：**
我会把检索结果组织成带 evidence id、doc_id、页码、版本、原文片段的结构化证据包，Prompt 要求关键事实后标注引用，比如 `[E1]`。生成后还要校验引用 id 是否存在、引用是否支持对应句子。高风险场景会做到原文 span 级定位，并保留索引版本和文档版本，方便审计和回放。

### 3. 引用不准确怎么办？

**标准答案：**
先区分两类问题：引用格式错，还是引用内容不支持结论。格式错可以通过结构化输出、引用 id 白名单和后处理校验解决；内容不支持就要做句子级校验，比如 NLI、LLM judge、关键词/数值比对，必要时要求模型逐句生成并绑定证据。业务上我会把“答案对但引用错”也算失败，因为用户和审计方看的是证据链。

### 4. 知识库没有答案时，RAG 应该怎么回答？

**标准答案：**
应该明确说当前知识库没有足够依据，而不是编一个看起来合理的答案。工程上可以结合检索分数、rerank 阈值、证据覆盖度、业务风险等级来触发拒答。回答时可以建议用户补充范围、关键词、时间，或者转人工。线上要记录无答案问题，回流给知识建设或标注流程。

### 5. 你会如何设计 RAG 的拒答阈值？

**标准答案：**
我不会只拍一个固定阈值。会先用评测集看不同阈值下的正确率、拒答率、幻觉率，再按场景分层：客服 FAQ 可以稍微积极回答，法务、金融、医疗这类高风险场景宁可多拒答。阈值还要结合 rerank 分、证据数量、证据一致性和问题意图。上线后用坏 Case 和人工反馈持续校准。

### 6. RAG 引用应该做到文档级、chunk 级还是 span 级？

**标准答案：**
看风险和成本。文档级实现简单，但用户很难定位依据；chunk 级和向量库最容易结合，是很多系统的起点；span 级最可信，适合法务、合同、医疗、金融等高风险场景，但需要解析质量、原文偏移和前端展示支持。我的建议是普通知识库先 chunk 级，关键业务逐步升级到 span 级。

### 7. 如何评估 RAG 生成质量？

**标准答案：**
我会分开评估答案正确性、忠实度、引用准确率、无依据断言比例和拒答质量。评测集里要有有答案、无答案、多文档合成、证据冲突、权限受限这些样本。只看 BLEU、ROUGE 或答案相似度不够，因为 RAG 的关键是答案是否被证据支持，引用是否能追溯。

### 8. 如果多个证据互相矛盾，模型应该怎么回答？

**标准答案：**
不要强行合成一个确定结论。应该展示冲突：比如 A 文档说支持，B 文档说不支持，同时标出文档版本、发布时间和来源。如果能根据版本新旧、权威等级判断，就说明采用哪个依据；如果不能判断，就提示需要人工确认。工程上可以给文档权威度、新鲜度和业务来源打标签。

### 9. 如何避免模型使用自身知识而不是知识库？

**标准答案：**
Prompt 要明确“只能基于证据回答”，证据不足就拒答；同时要求关键事实必须带引用。后处理检查没有引用的断言，必要时让模型先列 answer plan 或逐句绑定 evidence id。对于产品政策、价格、权限这类企业私有知识，我会禁止模型用参数记忆补全，因为参数知识可能过时或和企业配置不一致。

### 10. 面试官问“RAG 怎么降低幻觉”，你怎么完整回答？

**标准答案：**
我会从四层回答。第一，检索侧保证正确证据能召回：混合检索、query 改写、rerank。第二，上下文侧保证关键条件不丢：合理压缩、去重、保留数字和例外条款。第三，生成侧要求只基于证据回答、关键事实带引用、无证据拒答。第四，校验与评估侧做引用合法性、faithfulness、无依据断言率和坏 Case 回流。这样回答能体现这是系统工程，不是只靠 Prompt。
