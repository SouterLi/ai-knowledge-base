# AI 应用开发面试主题：RAG 系统设计与评估

## 核心概念

**RAG（Retrieval-Augmented Generation，检索增强生成）** 先从外部知识库检索与问题相关的内容，再把这些内容作为上下文交给大模型生成答案。它是企业知识库问答、客服助手、合规问答等场景最常见的落地架构之一。

RAG 主要解决三类问题：

1. **知识过时**：参数知识无法覆盖企业最新制度、产品手册。
2. **幻觉风险**：需要外部证据约束回答，并支持引用溯源。
3. **私有知识**：不能把全部企业数据训练进模型，RAG 可低成本接入且可更新。

完整 RAG 可拆成两条链路：

```text
离线索引：接入 -> 清洗 -> 切分 -> Embedding -> 建索引 -> 增量更新
在线问答：鉴权 -> Query 改写 -> 权限过滤 -> 混合检索 -> Rerank -> 上下文组装 -> 生成 -> 引用 -> 监控评估
```

面试要记住：**RAG 是系统工程**，不是「向量库 + 大模型 API」。效果差时先区分是检索问题还是生成问题，不要一上来只改 Prompt。

## 核心知识点

### 1. 检索策略（必考）

| 方式 | 擅长 | 薄弱 |
| --- | --- | --- |
| 向量检索 | 语义相似、换说法提问 | 错误码、SKU、API 名等精确匹配 |
| BM25 / 关键词 | 专有名词、编号、代码符号 | 同义表达、口语化问法 |
| 混合检索 | 企业知识库主流方案 | 需分数融合与去重 |
| metadata 过滤 | 租户、权限、时间、文档类型 | 过滤过严会空召回 |

```python
def hybrid_search(query: str, tenant_id: str, roles: list[str]):
  # 权限必须在检索层前置，不能先召回再让模型「别回答」
  filters = {"tenant_id": tenant_id, "acl": {"$overlap": roles}}

  vector_hits = vector_store.search(embed(query), filters=filters, top_k=50)
  keyword_hits = bm25.search(query, filters=filters, top_k=50)
  return merge_dedupe(vector_hits, keyword_hits)
```

### 2. Query 改写与多轮

用户常说「它怎么配置？」——需结合历史改写成独立问题再检索。常见手段：指代补全、多查询生成（Multi-Query）、**HyDE**（先生成假想答案再 Embedding 检索，适合短问/措辞差异大，但多一次 LLM 调用且可能引入噪声）。

### 3. Rerank 与上下文组装

- **初召**：追求 Recall，候选可 50–200。
- **Rerank**：Cross-Encoder 等精排，把「能回答问题」的片段排到前面。
- **上下文**：控制 top_k、token 预算、去重；Prompt 要求「仅基于上下文回答，不知道则说明」。

### 4. RAG 评估（分层必答）

**检索侧**：Recall@K、Precision@K、MRR、NDCG。  
**生成侧**：Faithfulness（忠实上下文）、Answer Relevance、Citation Accuracy。  
**工程侧**：延迟、成本、无答案率、幻觉率、用户采纳率。

建立带「问题 + 标准答案 + 相关文档标注」的评测集，切分/Embedding/top_k/Prompt 变更时做回归。

### 5. 权限、增量与排障

| 现象 | 常见根因 | 方向 |
| --- | --- | --- |
| 答非所问 | 召回偏、query 不清 | 混合检索、改写、rerank |
| 找不到 | chunk 不合理、数据缺 | 调切分、补数据、提高 Recall@K |
| 幻觉 | 上下文不足、约束弱 | 拒答策略、引用、事实校验 |
| 权限泄露 | 检索后过滤 | metadata 前置过滤、租户隔离 |

增量更新：新增写入；修改按 `document_id` 删旧 chunk 再写新；删除需同步向量库与关键词索引。记录 `document_version`、`embedding_model_version` 便于灰度回滚。

## 高频面试问题与标准答案

### 1. 什么是 RAG？解决了什么问题？

**标准答案：**  
RAG 就是检索增强生成：先查知识库，再把查到的片段塞进 Prompt 让模型回答。它解决知识过时、需要可溯源证据、以及企业私有数据不能全量微调这三类问题。我会强调 RAG 是「检索质量 + 生成约束 + 评估闭环」一起决定的，不是只换一个向量库。

### 2. RAG 和微调怎么选？

**标准答案：**  
事实性、频繁变化、要引用的知识用 RAG，比如制度、手册、工单。要改的是行为、格式、语气、分类习惯，更适合微调。线上常见是组合：微调提升遵循指令和领域表达，RAG 提供最新可追溯知识。我不会说「什么都微调」或「什么都 RAG」。

### 3. 如何设计企业知识库 RAG？

**标准答案：**  
离线：连接器同步、解析清洗、结构化切分、metadata（租户、ACL、版本、页码）、Embedding、向量+关键词+metadata 索引、版本化发布。在线：鉴权、多轮改写、权限过滤、混合召回、rerank、按 token 预算组上下文、生成带引用、日志与评测。还会主动提权限隔离、增量更新、成本 SLA 和坏 Case 回流补库。

### 4. chunk size 怎么定？

**标准答案：**  
没有万能数字。先按标题、段落、条款切，超长再递归拆；FAQ 可一条一块，政策按条款，代码别截断函数。用评测集看 Recall@K、片段能否单独回答问题、引用准确率。太小缺上下文，太大向量模糊且费 token；overlap 适量防断裂，过大则索引膨胀。

### 5. 为什么常用混合检索？

**标准答案：**  
向量擅长「忘记密码」和「重置密码」这种语义近义；BM25 擅长错误码、型号、人名。企业库里专有名词多，单靠向量容易召回到「看起来像」但答不上的段落，所以生产里向量+关键词再融合 rerank 是常态。

### 6. Reranker 作用？为何不直接取向量 top_k？

**标准答案：**  
向量检索为速度用 ANN，且「向量近」不等于「能回答问题」。Reranker 对 query 和候选做细粒度交互打分，把真正含答案的片段排到前面，通常能明显提升答案质量，代价是延迟和算力。所以常见是粗召 50–100，rerank 后只留 3–8 条进 Prompt。

### 7. 如何降低 RAG 幻觉？

**标准答案：**  
先保证检索里有正确答案；Prompt 约束只依据上下文；无证据时拒答；输出引用；可做答案与上下文一致性校验；用评测集盯幻觉率。我会说幻觉往往是检索、组装、评估缺失导致的系统问题，不全是模型「爱编」。

### 8. 知识库没有答案时怎么办？

**标准答案：**  
应明确说「当前知识库没有足够依据」，可建议补充信息或转人工。实现上结合检索分阈值、rerank 低分、上下文覆盖度，LLM 自检只能辅助不能唯一依赖。线上要把高频无答案问题回流做知识建设。

### 9. 如何评估 RAG？

**标准答案：**  
分四层：检索 Recall@K/MRR/NDCG；生成忠实度、相关性、引用准确；业务解决率、满意度；工程延迟成本。任何策略改动都在固定评测集上回归，避免凭感觉调 top_k。

### 10. 权限怎么做？

**标准答案：**  
chunk 写入 tenant、角色、文档 ACL；查询时在检索层带过滤条件，最好索引分区按租户隔离。不能在召回敏感内容后只靠 Prompt 让模型不说——内容可能进日志、rerank 或缓存。我会补一句要做越权召回的自动化测试。

### 11. 多轮对话怎么处理？

**标准答案：**  
先把当前轮结合历史改写成独立 query 再检索；区分「用于检索的历史」和「用于生成的历史」，避免整段历史塞进检索。可保留关键槽位或最近几轮摘要。

### 12. HyDE 是什么？何时用？

**标准答案：**  
先让模型生成假想文档再对其做向量检索，适合用户问法与文档措辞差很多的短问。缺点是多一次调用，假想方向错了会带偏检索，要配合阈值和评测看是否值得。

### 13. 答案质量差如何排查？

**标准答案：**  
按链路：数据是否全且新 → 切分是否碎 → Embedding 是否匹配领域 → top_k 里有没有金标准 chunk → rerank 是否排前 → 上下文是否被截断 → Prompt 是否要求 grounded → 模型能力。先定位检索侧还是生成侧，再改。

### 14. 增量更新怎么做？

**标准答案：**  
稳定 document_id；变更用 hash/etag 检测；修改则删旧 chunk 再写新，或版本号只查生效版；删除要清向量、BM25、metadata；任务幂等；重要库用 index alias 先建 v2 评测再切流。

### 15. 如何优化延迟和成本？

**标准答案：**  
缓存高频 query/答案；多路召回并行；限制 rerank 候选数；小模型做改写分类；控制注入 token；分层索引或摘要索引；按问题复杂度路由不同模型。质量、延迟、成本要一起看指标，不单边极致。

## 面试回答加分点

- 主动画 **离线 / 在线** 两条链路，体现工程全貌。
- 区分 **检索差** 与 **生成差**，排查有顺序感。
- 提到 **权限前置、引用溯源、评测集回归、监控告警**，不像只会调 API。
- 说清混合检索、rerank、HyDE 的 **适用边界**，不堆名词。
- 用 **Recall@K、Faithfulness** 等指标谈优化，而非「感觉变好了」。
- 承认 RAG 要持续迭代：无答案回流、文档更新、模型/索引版本治理。
