# AI 应用开发面试主题：GraphRAG 与知识图谱增强检索

## 核心概念

**GraphRAG** 在 RAG 中显式建模 **实体、关系、路径与社区结构**，把图遍历、社区摘要与向量检索结合，为 LLM 提供更有组织的上下文。核心不是「把向量库换成图数据库」，而是让系统能围绕 **关系** 和 **全局结构** 检索。

普通 RAG 擅长「答案就在某一两个 chunk 里」；GraphRAG 更适合：

- 跨文档、多实体的 **多跳推理**（A→B→C 因果链）。  
- **全局总结**（某产品线整体风险、故障共性）。  
- 关系密集文档（架构依赖、组织汇报、事件时间线）。

典型知识结构：

```text
(订单服务)-[:依赖]->(支付服务)-[:调用]->(风控服务)
```

**知识图谱** = 实体 + 关系 + 属性 + **可追溯证据**（来自哪段原文）。错误关系比漏召回更危险。

**Local Search**：围绕某实体的邻居、路径、证据 chunk——适合「X 为什么影响 Y」。  
**Global Search**：社区摘要、主题聚合——适合「整体有哪些风险/趋势」。

一句话：GraphRAG = **图谱构建 + 混合检索 + 证据回原文 + 质量与权限治理** 的闭环。

## 核心知识点

### 1. 适用与不适用

**适合**：问题围绕实体关系；需多跳或跨文档汇总；要解释「如何关联」。  
**不适合**：文档少、单片段事实问答、数据剧变但无力维护图谱一致性、业务根本不依赖关系——此时普通 RAG 更简单便宜。

### 2. 离线构建链路

```text
文档接入 -> 切分 -> 实体抽取 -> 关系抽取 -> 实体消歧/合并
  -> 图谱入库 -> 实体/社区摘要 -> 向量索引同步
```

工程要点：记录 Prompt/模型/文档版本；关系 **必须有原文 evidence**；文档删除时要传播删除节点、边、摘要与向量；增量更新而非每次全量瞎重建。

### 3. 实体抽取与消歧（高频）

| 文本写法 | 归一实体 |
| --- | --- |
| gpt4-turbo / GPT-4 Turbo | GPT-4 Turbo |
| CSP / 客服系统 | Customer Support Platform |

手段：别名表、规则、Embedding 相似、LLM 判断、高价值实体人工审核；保留 merge history 便于回滚。「苹果」需上下文消歧。

### 4. 关系抽取与质量控制

关系类型宜 **业务白名单**（依赖、调用、导致、发布…），避免满图「相关于」。结构化输出 + 置信度阈值 + 无证据不入库 + 抽样评估 + 多跳问答回归集。

```json
{
  "source": "支付服务",
  "relation": "依赖",
  "target": "风控服务",
  "evidence": "支付链路会调用风控判断交易风险。",
  "doc_id": "incident_2026_04_12",
  "confidence": 0.86
}
```

### 5. 社区检测与社区摘要

大图按连接聚类（业务域、事故链、政策主题），预计算 **社区摘要** 服务全局问法。风险：摘要过期、过度概括、混入无权限内容——需记依赖的数据版本与生成时间，必要时 **按租户/权限分别生成**。

### 6. 在线检索策略

```text
问题 -> 意图(实体型/关系型/全局) -> 实体链接
  -> 选策略：邻居扩展 / 两实体路径 / 社区摘要 / 向量兜底
  -> 加载原文 evidence chunk -> rerank -> 组装上下文 -> 生成+引用
```

- 图遍历限制：**跳数、边类型、时间、权限、top-k**，防噪声爆炸。  
- **最终答案必须能回到原文**，不能只喂抽取的三元组。

### 7. 存储选型

| 组件 | 作用 |
| --- | --- |
| 图数据库 Neo4j/Nebula 等 | 频繁路径查询 |
| 关系型库 | 节点边表，小规模可先 PG 模拟 |
| 向量库 + ES | 语义召回与关键词 |
| 对象存储 | 原文与解析结果 |

小规模可用 **PostgreSQL 节点表+边表**，不必为了架构而上图数据库。

### 8. 向量与图融合

- **向量 → 图**：先召回 chunk，再扩展关联实体邻居。  
- **图 → 向量**：实体链接后遍历，再加载 evidence chunk 用 rerank。  
融合分：向量分、rerank 分、图距离、边置信度、新鲜度（需归一化调参）。

```python
def rank_candidate(c):
    graph_score = 1 / (1 + c.graph_distance)
    freshness = 1 - min(c.days_since_update, 365) / 365
    return 0.40 * c.vector_score + 0.25 * c.rerank_score + 0.20 * graph_score + 0.10 * c.edge_confidence + 0.05 * freshness
```

### 9. 多跳推理示例

问：「订单成功率下降和风控策略发布有什么关系？」  
路径：订单成功率下降 ← 支付失败 ↑ ← 风控拦截 ↑ ← 策略 v3 发布。  
每条边要带 **事故报告、监控、发布记录** 等 evidence chunk，不能只给 LLM 一条路径字符串。

### 10. 权限与多租户（GraphRAG 更易泄露）

风险：跨租户实体误合并；遍历越权边；社区摘要混入无权文档；缓存摘要跨用户复用。  
要求：节点、边、证据、摘要均带 ACL；遍历各阶段过滤；缓存 key 含租户+角色+数据版本。

### 11. 更新与一致性

文档删了但边还在、摘要未重算、别名未合并、图索引与向量版本不一致——都要有软删除、异步清理、快照版本查询、高价值边人工审核。

```cypher
// 两跳内依赖/调用/因果，带租户过滤
MATCH path = (s:Entity {name: $name})-[r:DEPENDS_ON|CALLS|CAUSES*1..2]-(n)
WHERE all(e IN relationships(path) WHERE e.tenant_id = $tenant_id)
RETURN path LIMIT 20
```

### 12. 三层评估

- **图谱**：实体/关系 Precision&Recall、证据覆盖率、错误合并率。  
- **检索**：Path Recall、多跳证据完整性、权限违规率。  
- **生成**：Faithfulness、引用准确、关系幻觉率。

## 高频面试问题与标准答案

### 1. GraphRAG 和普通 RAG 区别？

**标准答案：**  
普通 RAG 主要对文本 chunk 做语义检索；GraphRAG 还把实体关系建成图，检索时可以用邻居、路径、社区摘要。它更适合多跳和全局总结，但构建维护成本更高。我会强调最终仍要回到原文证据，图是组织检索的手段不是唯一真相。

### 2. 一定需要图数据库吗？

**标准答案：**  
不一定。小规模用关系表存节点边也能做；图数据库适合关系密、路径查询多、遍历深的场景。选型看查询模式、规模、权限能力和团队运维经验，不是「有 GraphRAG 就必须 Neo4j」。

### 3. 离线构建链路怎么设计？

**标准答案：**  
接入切分后抽实体关系，JSON Schema 校验，实体消歧，低置信边审核或丢弃，证据绑定后入库，再生成实体/社区摘要并同步向量索引。全程记录文档版本、模型版本、任务 id，支持重放和回滚。

### 4. 如何降低关系抽取幻觉？

**标准答案：**  
Prompt 写死只许从原文抽；关系白名单；每条边带 evidence 和 confidence；低分不入库；抽样评估和多跳回归集持续看。比事后让 LLM「编关系」可靠得多。

### 5. 实体消歧怎么做？

**标准答案：**  
别名表和规范化规则先做，再用上下文 Embedding 和 LLM 判断是否同一实体，关键实体人工审核。保留 alias 和 merge 记录，合并错了要能回滚。多义词必须结合上下文，不能只看字符串相等。

### 6. 多跳问题怎么处理？

**标准答案：**  
实体链接后，多实体查路径，单实体扩展 1–2 跳邻居；按边类型、距离、置信度、时间、权限过滤；每条边加载对应原文 chunk；rerank 后组上下文。答案里要解释路径且引用证据，不能只丢三元组。

### 7. GraphRAG 和知识图谱问答区别？

**标准答案：**  
KGQA 更偏结构化查询直接出答案；GraphRAG 把图当检索增强，仍结合 chunk、摘要和 LLM 生成，强调从非结构化文档自动建图和图文混合检索。

### 8. 权限怎么设计？

**标准答案：**  
节点、边、证据、摘要全流程带 ACL；实体链接、遍历、加载 chunk、读缓存都要过滤；租户内才允许实体合并；社区摘要按权限范围生成或仅内部高权限场景使用。

### 9. 如何评估 GraphRAG？

**标准答案：**  
分三层：图谱准确率与证据覆盖；路径召回和多跳完整性；生成忠实度、引用准确和关系幻觉率。只看端到端分数定位不了是抽取错了还是检索路径错了。

### 10. 什么时候不该用 GraphRAG？

**标准答案：**  
单片段事实问、文档很少、关系不重要，或数据变化快但团队维护不动图谱一致性——这时普通 RAG 更划算。为架构复杂度而上 GraphRAG 不划算。

### 11. 如何与向量检索融合？

**标准答案：**  
两种主流：向量先召回 chunk 再沿实体扩展图；或先实体链接图遍历再拉 evidence 用向量/rerank 精排。排序融合向量、图距离、边置信度和新鲜度，按问题类型和延迟选路径。

### 12. 社区摘要的价值与风险？

**标准答案：**  
价值是全局问法时压缩大量关系，降低在线成本。风险是过期、过度概括、权限混入。要存依赖版本、生成时间和来源证据，必要时按租户分摘要，不能当不可审计的静态真理。

### 13. 如何设计 GraphRAG 系统？（综合题）

**标准答案：**  
先判断业务是否真有多跳/全局需求；离线强调证据和白名单关系；在线做意图路由、实体链接、图+向量混合、路径裁剪、rerank、引用溯源；全链路权限与版本；增量更新和删除传播；三层指标驱动迭代。简短版：图负责组织关系和路径，向量负责语义兜底，答案必须回到原文。

## 面试回答加分点

- 反对 **「LLM 抽三元组 + Neo4j」** 式简化，强调消歧、证据、评估、更新。
- 能区分 **Local / Global** 检索与问题类型的映射。
- 强调 **图遍历要裁剪**，以及 **不能只给关系不给原文**。
- 主动提 **跨租户误合并、摘要缓存越权** 等 GraphRAG 特有风险。
- 评估分 **图谱 / 检索 / 生成** 三层，体现可观测与可定位。
- 选型务实：小数据 **PG 边表** 也可，不盲目上图数据库。
