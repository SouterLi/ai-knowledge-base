## 核心概念

**RAG 查询理解** 是把用户自然语言问题转换成更适合检索系统处理的结构化查询过程。它不直接回答问题，而是在检索前完成意图识别、实体抽取、指代消解、查询改写、查询扩展和路由决策。

典型在线链路如下：

```text
用户问题
  -> 会话补全/指代消解
  -> 意图分类
  -> 实体与约束抽取
  -> 查询改写/多查询生成/HyDE
  -> 检索路由
  -> 向量/BM25/结构化检索/图检索
  -> rerank
  -> 上下文组装与生成
```

面试里要强调：**查询理解决定“查什么、去哪查、用什么策略查”**。如果这一步做得差，后面的向量索引、rerank、Prompt 再强，也可能只是在错误候选上做优化。

常见例子：

| 用户原始问题 | 查询理解后的检索表达 |
| --- | --- |
| “这个怎么开通？” | 结合上一轮主题改写为“企业微信智能客服插件如何开通？” |
| “退款多久到账？” | 意图：售后规则；实体：退款；约束：到账时间；路由：售后知识库 + 规则表 |
| “QPS 超了会怎样？” | 保留专有词 QPS，启用 BM25 + 技术文档向量检索 |
| “对比专业版和企业版权限” | 生成两个子查询，分别检索专业版、企业版权限，再做对比回答 |

## 核心知识点

### 1. 查询理解解决的核心问题

1. **短问题缺上下文**：用户常说“它”“这个”“怎么配置”，需要结合历史补全。
2. **口语表达与文档表达不一致**：用户说“登不上”，文档写“登录失败排查”。
3. **意图混杂**：一句话里既有咨询、对比、排障，也可能有操作请求。
4. **检索源不同**：制度问知识库，订单问业务数据库，配置问 API 文档。
5. **检索策略不同**：专有名词适合 BM25，语义问法适合向量，对比题适合多查询。

面试回答时不要只说“用 LLM 改写一下”，要说清楚改写前后的输入输出、置信度、回退策略和评估方式。

### 2. 意图分类与路由

意图分类决定是否进入 RAG，以及进入哪条检索链路。

| 意图类型  | 处理方式                        |
| ----- | --------------------------- |
| 知识问答  | 走 RAG：混合检索 + rerank + 引用    |
| 业务查询  | 走结构化查询：Text-to-SQL/API/规则引擎 |
| 操作执行  | 走 Agent 工具调用，并加权限与确认        |
| 闲聊/无关 | 走闲聊模型或拒答                    |
| 高风险合规 | 走受控知识库、低置信拒答或人工审核           |

```python
from dataclasses import dataclass


@dataclass
class QueryIntent:
    name: str
    confidence: float
    route: str


def route_query(question: str) -> QueryIntent:
    # 实际生产中可用小模型、规则和 LLM 组合，这里只展示路由思想
    technical_terms = {"qps", "sdk", "api", "webhook", "token"}
    if any(term in question.lower() for term in technical_terms):
        return QueryIntent("技术文档问答", 0.86, "tech_docs_hybrid_search")

    if any(word in question for word in ["订单", "余额", "发票"]):
        return QueryIntent("业务数据查询", 0.82, "structured_api_query")

    return QueryIntent("通用知识问答", 0.70, "knowledge_base_rag")
```

关键点：**低置信度不要硬路由**。可以走澄清问题、并行多路召回，或用保守答案提示“需要补充业务范围”。

### 3. 多轮指代消解与独立查询改写

RAG 检索通常需要一个**独立问题**，不能直接把完整聊天历史丢给向量库。

```text
历史：用户刚问“企业版如何接入飞书？”
当前：它支持单点登录吗？

改写后：企业版接入飞书后是否支持单点登录？
```

工程上要区分两类上下文：

- **用于检索的历史**：最近主题、关键实体、用户约束，尽量短。
- **用于生成的历史**：回答风格、已确认条件、对话状态，可摘要保留。

错误做法是把十几轮对话全部拼进检索 query，容易引入噪声，导致召回偏移。

### 4. 查询改写、扩展与纠错

常见策略：

| 策略 | 适用场景 | 风险 |
| --- | --- | --- |
| 指代补全 | 多轮对话、省略主语 | 历史主题判断错会改偏 |
| 同义词扩展 | 口语与文档术语不一致 | 扩展过多降低精度 |
| 拼写纠错 | 产品名、错误码、英文缩写 | 不能误改专有名词 |
| Multi-Query | 对比、总结、开放问法 | 成本升高，候选去重复杂 |
| HyDE | 用户问题很短、文档措辞差异大 | 假想答案可能带偏召回 |

```python
def build_search_queries(question: str, topic: str | None) -> list[str]:
    # 先得到一个稳定主查询，再少量扩展，避免把召回范围放得过宽
    main_query = f"{topic} {question}" if topic else question

    expansions = []
    if "登不上" in question:
        expansions.append(main_query.replace("登不上", "登录失败"))
    if "慢" in question:
        expansions.append(main_query.replace("慢", "延迟 高 响应时间"))

    return [main_query, *expansions[:2]]
```

面试中可以补一句：查询扩展不是越多越好，应该通过 Recall@K、MRR、NDCG 和最终答案忠实度验证收益。

### 5. 实体、槽位与过滤条件抽取

查询理解不只生成文本 query，还要抽取结构化约束。

```json
{
  "rewritten_query": "企业版退款多久到账",
  "intent": "售后规则问答",
  "entities": {
    "product": "企业版",
    "topic": "退款",
    "attribute": "到账时间"
  },
  "filters": {
    "tenant_id": "t_001",
    "doc_type": "policy",
    "version": "latest"
  }
}
```

这些字段用于 metadata 过滤、索引分区、权限控制和后续引用。注意：权限、租户、密级不能只靠 LLM 抽取，必须来自可信身份上下文。

### 6. 检索路由设计

复杂 AI 应用通常不是一个向量库打天下，而是多个知识源并存。

```text
技术问题 -> API 文档索引 + 代码片段索引
制度问题 -> 企业制度库 + FAQ
订单问题 -> 业务 API / SQL
概念解释 -> 通用知识库
关联分析 -> GraphRAG / 知识图谱
```

路由有三种常见做法：

1. **规则优先**：命中订单号、发票号、错误码时直接走对应通道。
2. **轻量分类模型**：低成本判断意图和知识域。
3. **LLM 路由**：适合长问题和复杂语义，但要有结构化输出与置信度。

生产上常用组合方案：先规则兜底强特征，再小模型或 LLM 分类，低置信时多路并行召回并让 reranker 做二次选择。

### 7. 查询理解的质量评估

不能只看最终答案，要分层评估：

| 层级 | 指标 |
| --- | --- |
| 意图分类 | Accuracy、Macro-F1、低置信样本覆盖 |
| 改写质量 | 是否保留原意、是否补全必要上下文、是否引入幻觉实体 |
| 召回质量 | Recall@K、MRR、NDCG、正确 chunk 是否进入候选 |
| 路由质量 | 目标知识源命中率、多路召回成本、错误路由率 |
| 线上效果 | 无答案率、澄清率、用户采纳率、坏 Case 类型分布 |

面试中可以说：改写策略上线前要跑固定评测集，并抽样看“原问题 -> 改写问题 -> 召回结果”的链路日志，避免只凭最终回答感觉调参。

### 8. 常见工程坑

- **改写过度**：把“退款多久到账”扩写成“退款申请流程、到账、失败原因”，导致召回太散。
- **专有名词被纠错**：把产品代号、错误码、缩写改成常见词。
- **历史污染**：上一轮话题带入当前新问题。
- **路由单点决策**：分类错了就完全查不到，缺少并行召回或回退。
- **权限来源不可信**：让模型根据文本猜租户和权限。
- **缺少链路日志**：坏 Case 只能看到最终答案，看不到改写和路由原因。

## 高频面试问题与标准答案

### 1. RAG 里为什么需要查询理解？

**标准答案：**
因为用户问题通常不是天然适合检索的。真实场景里会有省略、指代、口语表达、错别字、多个意图和不同知识源。查询理解负责把问题变成“可检索、可路由、可过滤”的表达。我会把它放在检索前面：先判断查什么、去哪查、怎么查，再进入向量/BM25/rerank。如果不做这层，后面往往是在错误候选上优化。

### 2. 查询改写和 Prompt 改写有什么区别？

**标准答案：**
查询改写是为了提高检索质量，输出给检索系统；Prompt 改写是为了约束模型回答，输出给生成模型。比如“它支持吗”要先改写成“企业版是否支持 SSO”去检索；生成 Prompt 再要求“只基于证据回答并给引用”。两者目标不同，不能混在一起。

### 3. 多轮对话中的指代问题怎么处理？

**标准答案：**
我会先从最近几轮提取当前主题和关键实体，把当前问题改写成独立查询，而不是把完整历史直接塞进向量库。比如上一轮问“企业版飞书接入”，这一轮问“它支持单点登录吗”，改写为“企业版飞书接入是否支持单点登录”。同时要防止历史污染，如果用户明显切换主题，就不要继续沿用旧实体。

### 4. 如何判断问题应该查哪个知识库？

**标准答案：**
靠检索路由。强特征可以规则判断，比如订单号走业务 API，错误码走技术文档；一般问题用轻量分类模型或 LLM 输出结构化意图、知识域和置信度。低置信时我不会强行单路由，而是并行查多个候选源，后面用 rerank 或阈值决定是否回答或澄清。

### 5. Multi-Query 有什么用？有什么风险？

**标准答案：**
Multi-Query 是把一个问题拆成多个检索问法，提高召回，适合对比、总结、用户表达很宽泛的场景。风险是成本和延迟增加，候选重复或跑偏也会增加。所以要控制查询数量，做去重和分数融合，并用 Recall@K、NDCG、最终忠实度验证，不是生成越多 query 越好。

### 6. HyDE 是什么？在查询理解里怎么用？

**标准答案：**
HyDE 是先让模型生成一段“假想答案/假想文档”，再用这段文本做向量检索。它适合短问题或者用户表达和文档措辞差距很大的场景。缺点是多一次模型调用，而且假想内容如果方向错，会把检索带偏。我的做法是只在特定意图下启用，并和原始 query、BM25 结果混合，而不是完全依赖 HyDE。

### 7. 查询改写会不会改变用户原意？怎么控制？

**标准答案：**
会，这是查询理解最大的风险之一。控制方式是改写输出保留原问题和改写问题，抽取实体和约束时要求可解释；高风险问题不要扩写太多；专有名词、数字、否定词要保护；上线前用样本集评估“是否引入新实体、是否丢失约束”。如果改写置信度低，可以用原问题和改写问题并行检索。

### 8. 用户问题很短，比如“怎么配置”，系统怎么处理？

**标准答案：**
先看会话状态里有没有明确主题，有的话补全成独立问题；没有的话不要瞎猜，可以反问用户要配置哪个产品或模块。工程上会设置一个置信度门槛：主题明确就改写检索，主题不明确就澄清。这样比直接拿“怎么配置”去查全库更稳定。

### 9. 查询理解和 rerank 的边界是什么？

**标准答案：**
查询理解负责检索前的意图、改写、扩展和路由，决定候选从哪里来；rerank 负责候选回来之后判断哪些片段最能回答问题。一个是“召回前决策”，一个是“召回后排序”。如果路由错了，rerank 可能根本看不到正确证据；如果查询理解没问题但候选排序差，再优化 rerank。

### 10. 如何评估查询理解模块？

**标准答案：**
我会分层评估：意图分类看 Accuracy/F1；改写看是否保留原意、是否补全上下文、是否引入幻觉实体；检索侧看 Recall@K、MRR、NDCG；最终看答案忠实度、引用准确率、无答案率和用户采纳率。线上坏 Case 要保留原问题、改写问题、路由结果、召回 top_k，才能定位是改写错、路由错还是排序错。

### 11. 查询理解应该用规则、小模型还是大模型？

**标准答案：**
我一般会组合使用。强规则适合订单号、错误码、产品 SKU 这类确定特征；小模型适合高频意图分类，成本低延迟稳；大模型适合长问题、多约束抽取和复杂改写。生产里不会所有请求都上大模型路由，成本和稳定性都不划算。

### 12. 如何处理低置信度查询？

**标准答案：**
低置信度不要硬答。可以反问澄清，也可以用原始 query、改写 query、多知识源并行召回，再根据 rerank 分和证据覆盖度决定是否回答。涉及权限、金额、法务这类场景，我会更保守，宁可提示信息不足或转人工，也不在低置信证据上生成确定答案。

### 13. 查询理解会增加延迟，怎么优化？

**标准答案：**
先分流：简单短句和强规则命中的问题不用大模型；高频问题缓存改写结果；意图分类用小模型；多路召回并行；Multi-Query 限制数量；路由和检索可以流水线化。关键是质量收益要能覆盖延迟成本，不能为了链路复杂而复杂。

### 14. 如果线上出现“答非所问”，你会怎么排查？

**标准答案：**
我会按链路看：原始问题是否清楚；改写有没有引入错误实体；意图分类和知识库路由是否正确；正确 chunk 是否进入初召；rerank 是否把它排前；最终 Prompt 是否包含关键证据。这样能区分是查询理解问题、检索问题还是生成问题，而不是一上来就调 Prompt。

### 15. 设计一个生产级查询理解模块，你会包含哪些字段？

**标准答案：**
我会输出结构化结果：原问题、独立改写问题、意图、知识域、实体槽位、过滤条件、建议检索策略、置信度和改写理由。权限和租户来自登录态，不让模型猜。每次请求记录这些字段，方便评测、回放和坏 Case 归因。
