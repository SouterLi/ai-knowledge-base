# AI 应用开发面试主题：RAG 系统设计与评估

## 一、为什么 RAG 是 AI 应用开发高频主题

RAG 是大模型应用落地中最常见的架构之一。它通过外部知识检索补足大模型参数知识的不足，常用于企业知识库问答、客服助手、代码助手、合规问答、合同审查、内部搜索等场景。

面试中考察 RAG，通常不是只问“向量数据库怎么用”，而是考察候选人是否理解完整链路：文档处理、切分、Embedding、索引、召回、重排、上下文组装、生成、引用溯源、评估、监控和持续优化。

## 二、核心知识点

### 1. RAG 基本链路

典型 RAG 流程如下：

1. 数据接入：导入 PDF、网页、Markdown、数据库、工单、代码库等资料。
2. 数据清洗：去除噪声、页眉页脚、乱码、重复内容、无效表格。
3. 文档切分：将长文档拆成适合检索和上下文注入的 chunk。
4. 向量化：使用 Embedding 模型把 chunk 转成向量。
5. 建立索引：写入向量数据库或搜索引擎。
6. 查询理解：对用户问题做改写、扩展、意图识别或多查询生成。
7. 检索召回：用向量检索、关键词检索或混合检索找到候选内容。
8. 重排序：用 reranker 或规则对候选内容重新排序。
9. 上下文组装：控制 token 预算，拼接最相关的上下文。
10. LLM 生成：基于检索上下文生成答案。
11. 引用与溯源：返回引用片段、文档标题、URL、页码等。
12. 评估与监控：衡量检索质量、生成质量、延迟、成本和用户满意度。

### 2. 文档切分策略

常见切分方式：

- 固定长度切分：实现简单，但容易切断语义。
- 按段落/标题切分：更符合人类文档结构。
- 递归切分：优先按标题、段落、句子切分，超长再按字符或 token 拆分。
- 语义切分：根据语义相似度或主题边界切分。
- 父子 chunk：小 chunk 用于召回，大 chunk 或父文档用于提供完整上下文。

关键参数：

- chunk size：过小会丢上下文，过大会降低检索精度并增加 token 成本。
- overlap：适量重叠能减少语义断裂，但过大会增加索引体积和重复召回。
- metadata：文档来源、标题、章节、页码、权限、更新时间等信息对过滤和溯源很重要。

### 3. Embedding 与索引

Embedding 负责把文本映射到语义向量空间。选择 Embedding 模型时要关注：

- 是否支持中文或多语言。
- 向量维度和存储成本。
- 领域适配能力。
- 查询与文档是否使用同一个模型。
- 是否需要微调或使用领域专用模型。

索引常见方案：

- 向量数据库：Milvus、Qdrant、Weaviate、Pinecone、Chroma 等。
- 搜索引擎：Elasticsearch/OpenSearch，支持 BM25、稀疏检索和混合检索。
- 数据库扩展：pgvector，适合数据规模中小、系统想保持简单的场景。

### 4. 检索策略

常见检索方式：

- 向量检索：适合语义相似问题，但对精确术语、编号、错误码可能不如关键词检索。
- 关键词检索：如 BM25，适合精确匹配、专有名词、代码符号、产品型号。
- 混合检索：结合向量检索和关键词检索，通常是企业 RAG 的主流方案。
- metadata 过滤：根据租户、权限、文档类型、时间范围等过滤。
- 多路召回：从不同索引、不同 query rewrite、不同粒度 chunk 中召回，再合并去重。

### 5. Query Rewrite 与多轮对话

用户问题往往不完整。例如用户在多轮对话中问“它怎么配置？”，系统需要结合历史上下文改写为完整问题。

常见技术：

- 问题改写：把省略指代补全。
- 多查询生成：从不同表达角度生成多个查询，提高召回率。
- HyDE：先让模型生成一个假想答案，再用假想答案做检索。
- 意图识别：判断是知识问答、流程查询、代码检索还是任务执行。

### 6. Reranker 重排序

初步召回通常追求高召回率，可能包含噪声。Reranker 根据 query 与候选文档的相关性重新打分，提升最终注入上下文的质量。

常见做法：

- Cross-Encoder reranker：效果好但延迟较高。
- LLM rerank：灵活但成本更高，适合复杂判断。
- 规则 rerank：结合标题匹配、时间新鲜度、权限、点击反馈等业务信号。

### 7. 上下文组装与生成控制

上下文组装要平衡相关性、完整性、成本和安全性。

常见策略：

- 控制 top_k 和 token budget。
- 对同一文档片段去重，避免重复信息浪费上下文。
- 优先保留高相关片段和结构化 metadata。
- 明确提示模型“只能基于上下文回答，无法判断时说明不知道”。
- 要求输出引用，便于用户核验。

### 8. RAG 评估指标

RAG 评估要分开看检索和生成。

检索侧指标：

- Recall@K：正确文档是否出现在前 K 个结果中。
- Precision@K：前 K 个结果中相关内容比例。
- MRR：第一个正确结果出现得越靠前越好。
- NDCG：考虑相关性等级和排序位置。

生成侧指标：

- Faithfulness：答案是否忠实于检索上下文。
- Answer Relevance：答案是否回答了用户问题。
- Context Relevance：注入上下文是否与问题相关。
- Citation Accuracy：引用是否准确支持答案。
- Human Evaluation：专家人工评分，适合关键业务场景。

工程侧指标：

- 端到端延迟。
- 单次请求成本。
- 无答案识别率。
- 幻觉率。
- 用户点击率、采纳率、追问率。

### 9. 常见问题与优化方向

| 问题 | 可能原因 | 优化方向 |
| --- | --- | --- |
| 答非所问 | 召回内容不相关、query 表达不清 | Query rewrite、混合检索、rerank |
| 找不到答案 | chunk 切分不合理、索引缺失 | 调整切分、补充数据、提高 recall@K |
| 答案幻觉 | Prompt 约束弱、上下文不足 | 强化基于上下文回答、无答案拒答 |
| 引用不准确 | 片段与答案未对齐 | 生成时绑定引用、答案后校验 |
| 延迟过高 | 检索链路太长、rerank 太慢 | 缓存、并行召回、减少候选数量 |
| 成本过高 | 上下文过长、模型过大 | 压缩上下文、分级模型、缓存 |
| 权限泄露 | 检索前未做权限过滤 | metadata 权限过滤、租户隔离 |

## 三、高频面试题及参考答案

### 1. 什么是 RAG？它解决了大模型应用中的什么问题？

RAG 是检索增强生成。它先从外部知识库检索与用户问题相关的内容，再把这些内容作为上下文交给大模型生成答案。

它主要解决三类问题：

1. 大模型参数知识过时，无法知道企业最新数据。
2. 大模型容易幻觉，需要外部证据约束回答。
3. 企业私有知识不能全部训练进模型，RAG 可以低成本接入私有知识。

### 2. RAG 和微调有什么区别？什么时候用 RAG，什么时候用微调？

RAG 适合注入事实性、频繁变化、需要溯源的知识，例如制度文档、产品手册、工单记录。优点是更新快、成本低、可引用来源。

微调适合改变模型行为、输出风格、任务格式或领域表达习惯，例如固定格式抽取、客服语气、分类判断。微调不适合频繁更新大量事实知识。

实际项目中二者可以结合：用微调提升模型遵循指令和领域表达能力，用 RAG 提供最新、可追溯的知识。

### 3. 如何设计一个企业知识库 RAG 系统？

可以从离线和在线两条链路回答。

离线链路包括：文档接入、清洗、切分、metadata 提取、Embedding、索引构建和定期更新。

在线链路包括：用户鉴权、问题改写、权限过滤、混合检索、rerank、上下文组装、LLM 生成、引用溯源、日志记录和质量评估。

还要强调工程约束：权限隔离、增量更新、延迟控制、成本控制、评估集建设和监控告警。

### 4. chunk size 应该如何选择？

chunk size 没有固定答案，要结合文档结构、模型上下文窗口和检索效果调参。

一般原则：

- 太小：语义不完整，模型拿不到足够上下文。
- 太大：召回不精准，占用 token，成本更高。
- 有结构文档优先按标题、段落、列表切分。
- 可以用 overlap 减少跨段信息断裂。
- 用 Recall@K、答案准确率和人工评估来验证效果。

### 5. 为什么 RAG 经常使用混合检索？

因为向量检索和关键词检索各有优势。

向量检索擅长语义相似，例如“如何重置密码”和“忘记密码怎么办”。关键词检索擅长精确匹配，例如错误码、产品型号、人名、API 名称。

企业知识库中大量问题包含专有名词、编号和术语，因此混合检索通常比单纯向量检索更稳。

### 6. Reranker 的作用是什么？为什么不直接取向量检索 top_k？

向量检索为了速度，通常用近似最近邻算法，且 Embedding 相似度不一定等于真实问答相关性。直接取 top_k 可能把语义相近但不能回答问题的片段放在前面。

Reranker 会对 query 和候选文档做更精细的相关性判断，把真正能回答问题的片段排到前面。它通常能显著提升最终答案质量，但会增加延迟和计算成本。

### 7. 如何降低 RAG 的幻觉？

可以从多个层面处理：

1. 提升检索质量，确保上下文包含正确答案。
2. Prompt 明确要求只基于上下文回答。
3. 对无答案场景要求模型拒答，而不是猜测。
4. 输出引用，让答案可核验。
5. 对答案做事实一致性校验。
6. 建立评估集，持续监控幻觉率。

核心观点是：幻觉不只是模型问题，也可能是检索、上下文组装和评估缺失导致的系统问题。

### 8. 如果用户问的问题在知识库中不存在，RAG 应该怎么处理？

系统应该识别无答案场景，并明确回答“当前知识库没有足够信息”，可以给出建议的下一步，例如让用户补充问题、联系人工或查看相关文档。

实现上可以结合：

- 检索分数阈值。
- reranker 相关性阈值。
- 上下文覆盖度判断。
- LLM 自检，但不能只依赖 LLM 自检。
- 线上日志回流，把高频无答案问题纳入知识库建设。

### 9. 如何评估一个 RAG 系统的效果？

需要分层评估：

1. 检索评估：Recall@K、Precision@K、MRR、NDCG。
2. 生成评估：答案正确性、忠实度、相关性、引用准确性。
3. 业务评估：问题解决率、用户满意度、人工转接率、平均响应时间。
4. 工程评估：延迟、吞吐、成本、稳定性。

最好建立一套包含问题、标准答案、相关文档标注的评估集，并在切分策略、Embedding 模型、top_k、reranker、Prompt 变更时做回归评估。

### 10. RAG 中如何处理权限控制？

权限控制必须在检索阶段就生效，而不是生成后再过滤。

常见做法：

- 为 chunk 写入租户、部门、角色、用户、文档权限等 metadata。
- 查询时根据用户身份添加过滤条件。
- 不同租户使用独立索引或逻辑隔离。
- 日志中避免记录敏感上下文。
- 对越权召回进行测试和审计。

如果先召回敏感内容再让模型“不要回答”，仍然存在泄露风险。

### 11. 如何处理 RAG 中的多轮对话？

多轮对话要解决上下文省略和指代问题。常见做法是先把用户当前问题结合历史对话改写成独立问题，再用改写后的问题检索。

同时要避免把过长历史直接塞进检索和生成链路。可以保留关键槽位、摘要或最近几轮对话，并区分“用于检索的历史”和“用于生成的历史”。

### 12. 什么是 HyDE？它适合什么场景？

HyDE 是 Hypothetical Document Embeddings。它先让模型根据用户问题生成一个假想答案或假想文档，再对这个假想文档做 Embedding 检索。

它适合用户问题很短、表达模糊、与文档措辞差异较大的场景。缺点是会增加一次 LLM 调用，也可能因为假想答案方向错误而引入噪声。

### 13. 如果 RAG 答案质量不好，你会如何排查？

可以按链路逐层排查：

1. 数据是否完整、干净、及时更新。
2. 文档切分是否破坏语义。
3. Embedding 模型是否适合语言和领域。
4. 检索 top_k 中是否包含正确片段。
5. reranker 是否把正确片段排前。
6. 上下文是否被截断或拼接混乱。
7. Prompt 是否约束模型基于上下文回答。
8. 模型是否具备完成任务所需能力。

面试时要强调先定位问题在检索侧还是生成侧，不要一上来只改 Prompt。

### 14. 如何做 RAG 的增量更新？

增量更新一般包括新增、修改和删除三种情况。

- 新增文档：清洗、切分、向量化后写入索引。
- 修改文档：根据文档 ID 删除旧 chunk，再写入新 chunk，或维护版本号。
- 删除文档：从向量库和元数据存储中删除对应 chunk。

工程上要保证文档 ID、chunk ID、版本号和更新时间可追踪。对于重要知识库，还要处理索引构建失败、重试和一致性校验。

### 15. 如何优化 RAG 系统的延迟和成本？

可以从以下方向优化：

- 缓存高频问题的检索结果或最终答案。
- 并行执行多路召回。
- 限制候选数量，rerank 前先粗筛。
- 使用更小的模型做 query rewrite 或分类。
- 控制上下文 token 数量。
- 对长文档做摘要索引或分层索引。
- 根据问题复杂度选择不同模型。

要注意质量、延迟和成本之间的平衡，不能只追求单一指标。

## 四、面试回答加分点

- 能把 RAG 拆成离线索引链路和在线问答链路。
- 能区分检索质量问题和生成质量问题。
- 能主动提到权限控制、引用溯源、评估集和监控。
- 能说明混合检索、reranker、query rewrite 的适用场景。
- 能用指标而不是主观感觉评价优化效果。
- 能意识到 RAG 是系统工程，不只是调用向量数据库和大模型 API。

## 五、一分钟总结

RAG 是 AI 应用开发中最常见、最容易深入考察的主题。好的 RAG 系统不仅要能“搜到内容并生成答案”，还要做到数据可靠、检索准确、答案忠实、引用可追溯、权限安全、延迟和成本可控，并且具备持续评估和迭代能力。面试中回答 RAG 问题时，建议始终围绕完整链路、质量评估和工程落地展开。
