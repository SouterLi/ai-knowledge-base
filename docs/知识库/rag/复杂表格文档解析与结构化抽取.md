## 核心概念

**复杂表格文档解析** 是把 PDF、扫描件、Excel 截图、合同附件、票据清单等材料中的表格，还原成可计算、可校验、可追溯的数据结构。难点不只是 OCR 识别文字，而是恢复 **行列关系、表头层级、合并单元格、跨页延续、单位继承、脚注说明和坐标证据**。

**结构化抽取** 是在表格和正文中抽取业务字段，比如供应商、合同金额、税率、付款节点、物料清单、发票号码、费用明细，并输出符合 Schema 的 JSON。它面向系统消费，所以必须关注字段类型、枚举、空值、置信度、证据页码和人工复核。

典型链路可以概括为：

```text
文档上传 -> 质量检测 -> OCR/版面分析 -> 表格检测 -> 表格结构恢复
  -> 单元格语义归一 -> 字段抽取 -> Schema 校验 -> 业务规则校验
  -> 证据绑定 -> 人工复核 -> 落库与样本回流
```

面试里要强调一句话：**文档抽取系统的目标不是让模型“看懂大概”，而是让结果能入库、能追溯、能被业务规则拦住错误。**

## 核心知识点

### 1. 表格解析不能只转 Markdown

Markdown 表格适合展示简单二维表，但遇到以下情况会丢信息：

| 场景 | 风险 |
| --- | --- |
| 合并单元格 | 上级表头、分类字段、单位说明容易丢失 |
| 多级表头 | 模型不知道某列对应哪个业务口径 |
| 跨页表格 | 第二页缺少表头或延续标记 |
| 单元格换行 | OCR 顺序可能打乱 |
| 脚注/单位 | 金额单位、税率说明可能不在表体里 |

生产中更推荐保留结构化单元格：

```json
{
  "table_id": "contract-001#table-03",
  "page": 5,
  "cell": {
    "row": 4,
    "col": 3,
    "row_span": 1,
    "col_span": 2,
    "text": "人民币 120,000 元",
    "normalized_value": 120000,
    "headers": ["费用明细", "含税金额"],
    "bbox": [420, 610, 690, 650],
    "ocr_confidence": 0.94
  }
}
```

这样后续既可以生成 Markdown 给模型阅读，也可以按行列和坐标做校验、回显、人工复核。

### 2. OCR、版面分析和表格结构恢复要分层

面试中不要把「OCR」泛化成所有文档解析能力。更准确的拆法是：

1. **OCR**：识别文字、位置、置信度。
2. **版面分析**：识别标题、段落、表格、图片、页眉页脚、签章区域。
3. **表格检测**：定位表格区域，区分有线表、无线表、嵌套表。
4. **结构恢复**：恢复行列、合并单元格、表头层级、跨页关系。
5. **语义归一**：金额、日期、单位、税率、币种、数量等标准化。

```python
def parse_document_table(pdf_path: str) -> list[dict]:
    pages = render_pages(pdf_path)
    parsed_tables = []

    for page in pages:
        # 中文注释：OCR 只负责文字和坐标，不能直接当作表格结构
        ocr_blocks = ocr_engine.recognize(page.image)

        # 中文注释：版面模型先定位表格区域，减少模型处理整页的噪声
        table_regions = layout_model.detect_tables(page.image, ocr_blocks)

        for region in table_regions:
            # 中文注释：结构恢复阶段保留行列、合并单元格和原始坐标
            table = table_parser.recover_structure(region, ocr_blocks)
            parsed_tables.append(table)

    return parsed_tables
```

### 3. 跨页表格要识别“延续关系”

很多合同、对账单、物料清单会出现跨页表格。常见问题是第二页没有完整表头，或者页尾有「续下页」。处理方式：

1. 基于页码、表格标题、列数、列名相似度判断是否同一张表。
2. 如果下一页缺表头，继承上一页表头，但要记录 `header_inherited_from_page`。
3. 对页眉页脚、页码、重复水印做清洗，避免混入表格行。
4. 对跨页合并单元格保留上级分类，比如「软件服务费」这一分类可能只出现在上一页。

```python
def merge_cross_page_tables(tables: list[dict]) -> list[dict]:
    merged = []
    current = None

    for table in tables:
        if current and is_continuation(current, table):
            # 中文注释：跨页延续时继承表头，但保留证据来源页，方便复核
            table["headers"] = table.get("headers") or current["headers"]
            table["header_inherited_from_page"] = current["page_end"]
            current["rows"].extend(table["rows"])
            current["page_end"] = table["page_end"]
        else:
            if current:
                merged.append(current)
            current = table

    if current:
        merged.append(current)

    return merged
```

### 4. 字段抽取要带证据和置信度

字段抽取不能只返回值，至少要返回：

- `value`：标准化后的字段值。
- `raw_text`：原始文本。
- `page` / `bbox`：证据位置。
- `confidence`：综合 OCR、模型、规则的置信度。
- `reason`：为什么需要复核或为什么拒绝抽取。

示例 Schema：

```python
from pydantic import BaseModel, Field, field_validator


class Evidence(BaseModel):
    page: int = Field(ge=1)
    bbox: list[float]
    raw_text: str


class ExtractedAmount(BaseModel):
    value: float | None = Field(default=None, ge=0)
    currency: str | None = None
    evidence: Evidence | None = None
    confidence: float = Field(ge=0, le=1)
    needs_review: bool = False

    @field_validator("currency")
    @classmethod
    def validate_currency(cls, value):
        # 中文注释：币种必须是系统可识别的枚举，避免自由文本入库
        if value is not None and value not in {"CNY", "USD", "EUR"}:
            raise ValueError("unsupported currency")
        return value
```

面试时要说清楚：如果证据不存在、证据和字段值对不上、金额规则不通过，就宁可返回 `null` 或进入人工复核，也不要让模型补全。

### 5. 业务规则校验比 Prompt 更可靠

Prompt 可以要求模型「不要编造」，但真正的强约束必须放在服务端：

- 金额：小计之和是否等于合计，含税价与税率是否一致。
- 日期：开始日期不能晚于结束日期，付款节点不能早于合同签署日。
- 发票：税号格式、发票号长度、金额大小写一致性。
- 清单：数量、单价、总价是否满足 `数量 * 单价 = 金额`。
- 合同：主体名称是否与印章或签署页一致。

```python
def validate_invoice_rows(rows: list[dict]) -> list[str]:
    errors = []

    for index, row in enumerate(rows, start=1):
        quantity = row.get("quantity")
        unit_price = row.get("unit_price")
        amount = row.get("amount")

        if None in {quantity, unit_price, amount}:
            errors.append(f"第 {index} 行缺少数量、单价或金额")
            continue

        # 中文注释：金额校验使用容差，避免小数四舍五入导致误判
        expected = round(quantity * unit_price, 2)
        if abs(expected - amount) > 0.01:
            errors.append(f"第 {index} 行金额不一致：期望 {expected}，实际 {amount}")

    return errors
```

### 6. 人工复核是产品能力，不是失败兜底

文档抽取涉及财务、合同、报销、供应链时，不应该追求 100% 自动化。合理设计是：

1. 高置信字段自动通过。
2. 低置信字段、高风险字段、规则冲突字段进入人工复核。
3. 复核界面展示原图区域、OCR 文本、模型输出和规则错误。
4. 人工修改结果回流为评测样本，用于后续回归测试。

这类回答能体现你知道生产系统的边界：**模型负责候选结果，系统负责校验与治理，人负责高风险确认。**

### 7. 评估要按字段、表格和业务结果分层

不要只说「准确率」。更完整的指标包括：

- OCR 层：字符错误率、字段区域识别率、低置信占比。
- 表格层：表格检测召回率、行列结构准确率、合并单元格恢复率、跨页合并准确率。
- 字段层：字段 Precision / Recall / F1，关键字段单独统计。
- 证据层：页码命中率、bbox 命中率、字段值与证据一致率。
- 业务层：自动通过率、人工复核率、人工修改率、下游入库失败率。
- 工程层：单文档耗时、P95 延迟、单页成本、失败重试率。

## 高频面试问题与标准答案

### 1. 如果 PDF 里有跨行跨列的复杂表格，你会怎么处理？

**标准答案：**  
我不会直接把表格粗暴转成 Markdown，因为合并单元格、多级表头和单位说明会丢。我的做法是先 OCR 拿到文字和坐标，再做版面分析定位表格区域，然后用表格结构恢复模型或规则恢复行列、rowspan、colspan 和表头层级。内部存储用结构化 cell JSON，保留 row、col、span、headers、bbox 和置信度。给大模型阅读时可以再渲染成 Markdown 或 HTML，但落库和校验要依赖结构化结果。

### 2. 为什么复杂表格不建议只用 Markdown 表示？

**标准答案：**  
Markdown 只表达简单二维表，对合并单元格、多级表头、跨页延续、脚注和单位继承表达能力不足。比如一个金额列的单位在上级表头里，转 Markdown 后模型可能不知道是万元还是元。所以我会把 Markdown 当展示格式，而不是事实源；事实源应该是带坐标、表头路径和单元格关系的结构化数据。

### 3. 跨页表格怎么判断是同一张表？

**标准答案：**  
可以综合判断：表格标题是否相同，列数和列宽是否接近，表头文本是否相似，上一页是否有「续下页」标记，下一页是否缺表头但行结构一致。合并后要记录页码范围，并且如果继承了上一页表头，要把继承来源也记录下来。这样后续人工复核时能解释为什么这两页被合成一张表。

### 4. 表格里的金额、数量、税率如何保证抽取准确？

**标准答案：**  
首先字段要结构化输出，金额转数值，币种、税率、单位标准化。其次每个字段要带原文证据、页码和 bbox。最后服务端做业务规则校验，比如数量乘单价是否等于金额，小计是否等于合计，含税金额和税率是否匹配。规则冲突或证据不足时进入人工复核，而不是让模型自己解释过去。

### 5. OCR 识别错了，后面的 LLM 能不能修正？

**标准答案：**  
LLM 可以利用上下文纠正一部分明显错误，比如金额格式或日期格式，但不能把它当作 OCR 纠错的主防线。生产里我会保留 OCR 置信度，低置信区域触发高清重渲染、局部裁剪、备用 OCR 或人工复核。高风险字段不能让模型凭常识猜，必须能回到原图证据。

### 6. 合同关键信息抽取系统你会怎么设计？

**标准答案：**  
我会先定义字段 Schema，比如合同主体、金额、期限、付款条件、违约条款和签署日期，并要求关键字段带 page、bbox 和原文 quote。链路上先做文档质量检测、OCR、版面分析和表格恢复，再按字段类型召回相关页面或表格，让模型抽取候选 JSON。服务端做 Schema 校验、金额日期规则校验和证据一致性校验。低置信字段进入人工复核，复核结果回流评测集。

### 7. 什么时候用视觉大模型，什么时候用 OCR + 文本模型？

**标准答案：**  
如果任务主要是密集文字和表格字段抽取，我优先用 OCR + 版面分析 + 文本模型，因为成本低、可追溯、容易评估。如果依赖视觉语义，比如印章、签名、截图布局、勾选框、手写内容，才会引入视觉模型。实际项目常常是混合路线：OCR 提供文字证据，视觉模型补充版面和图像判断。

### 8. 如何设计人工复核流程？

**标准答案：**  
我会把复核触发条件做成规则：低 OCR 置信度、Schema 校验失败、金额规则冲突、关键字段缺证据、模型置信度低都进入复核。复核界面要展示抽取值、原文、原图 bbox、错误原因和修改入口。人工修改后不能只改库，还要记录样本、字段、错误类型和模型版本，用于后续评测和回归。

### 9. 表格抽取效果怎么评估？

**标准答案：**  
我会分层评估。OCR 看字符错误率和区域识别率；表格结构看检测召回、行列准确率、合并单元格和跨页合并准确率；字段抽取看关键字段的 Precision、Recall、F1；证据看页码和 bbox 命中率；业务上看自动通过率、复核修改率和入库失败率。这样能定位到底是 OCR、结构恢复、模型抽取还是业务规则出了问题。

### 10. 如果抽取结果和业务规则冲突，应该相信谁？

**标准答案：**  
强业务规则优先于模型输出。比如小计不等于合计，或者合同结束日期早于开始日期，这类结果不能直接入库。我的处理是标记字段异常，保留模型输出和证据，进入人工复核或要求用户重新上传更清晰的文件。模型可以生成候选答案，但最终能不能进入业务系统，要由 Schema、规则和权限控制。
