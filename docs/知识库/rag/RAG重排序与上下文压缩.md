# RAG 重排序与上下文压缩

## 核心概念

在企业 RAG 的在线链路里，向量检索或混合检索完成之后、大模型生成答案之前，还有一层往往决定「能不能答对」的质量控制：从一批候选证据里，挑出真正能够回答问题、在 token 预算内装得下、并且还能溯源到原文的内容。这一层通常由**重排序（Rerank）**和**上下文压缩（Context Compression）**共同完成。

可以把整条检索链路理解成两阶段思路。第一阶段是**初召（Recall）**，目标是在可接受的延迟内尽量别把正确答案漏掉，所以往往会用向量检索、BM25、多查询改写等多路召回，候选数量常常是几十到上百。第二阶段是**精排（Rerank）**，目标不再是「像不像」，而是「能不能用来回答这道题」，所以会更愿意用 query 和候选片段联合理解的方式，把真正含答案的段落排到最前面。在这之后，还要做**上下文压缩与组装**：在有限的上下文窗口里，把证据塞进去，但塞进去的内容必须仍然忠实于原文，并且最好保留引用位置，而不是为了省 token 把关键数字、例外条款裁没。

面试里可以用三句话概括：**初召要覆盖，精排要准，压缩要保真。** 向量 top_k 更像粗筛网，reranker 像精筛，压缩负责在「装得下」的前提下「装得对」。如果只把向量相似度最高的几条直接塞进 Prompt，在真实业务里经常会出现：片段主题相关但答非所问、同一文档重复占满窗口、或者 ANN 优化的是距离而不是最终答题质量——这些都不是靠换一个更大的生成模型能彻底解决的。

重排序常见有几类实现思路。**Cross-Encoder** 把用户问题和候选片段拼在一起编码，让 token 之间可以交互，对限定词、否定和实体对应更敏感，精排质量高，但算力随候选数线性增长，所以只适合在初召之后的较小集合上使用。**Bi-Encoder 或直接用向量分做二次排序** 速度快，但细粒度判断弱，更适合候选规模极大、只能做轻量过滤的场景。**用通用大模型做 Rerank** 灵活、能处理复杂语义，但成本高、延迟高、输出也不够稳定，一般不作为生产主链路默认方案，更适合小候选集、难例分析或离线评测。**规则与学习排序** 则把标题命中、文档权威度、新鲜度、历史点击率等业务信号叠加上去，在企业知识库里很常见，但权限类约束不能靠「降权」代替「过滤」，无权限内容必须在进入 rerank 之前就剔除。

上下文压缩的目标也不是「越短越好」。压缩之后，生成阶段仍然要能够依据证据作答，引用仍要能指回原文 span；尤其在法务、合同、退款规则、配置参数等场景，纯生成式摘要一旦改写了数字或条件，Faithfulness 和合规风险都会上升。因此压缩的验收标准，往往是答案是否仍可由上下文推出、引用是否准确、以及 token 和延迟是否确实下降——而不是单纯看字符数少了多少。

## 核心知识点

### 1. 为什么不能把向量 top_k 直接交给大模型

向量检索解决的是「语义上是否相近」，而用户问的是「这段材料能否支撑我的答案」。这两者在大量真实 badcase 里并不等价。典型情况包括：用户问「退款多久到账」，召回到的是「如何申请退款」——主题同属退款，但缺少到账时间这一关键事实；或者用户问企业版配置，召回到个人版说明，局部关键词相似而对象错误。此外，多路召回合并后经常出现同一文档的相邻 chunk 高度重复，若不做去重和精排，会白白占用宝贵的上下文窗口。ANN 索引优化的是近似最近邻距离，并不直接优化「最终答案是否正确」；再叠加长上下文模型「装得下」并不等于「信噪比高」，噪声段落越多，模型越容易错误引用或胡编细节。

因此生产上的默认姿势是：初召可以偏大、偏快，宁可多拿一些候选；在交给生成模型之前，必须用 rerank 和压缩把证据质量拉上来。跳过重排序，往往表现为：评测集上 Recall 不低，但线上用户反馈「引用了无关段落」「答案张冠李戴」——这通常是精排和压缩层缺失，而不是生成模型不够大。

### 2. Cross-Encoder 精排：原理、规模与适用边界

Cross-Encoder 的做法，是把用户问题和每一个候选片段当作一对文本输入，让模型在联合编码时建立 query 与 passage 之间的细粒度交互，再输出一个相关性分数。相比双塔 Embedding「各编码各的、再算距离」，Cross-Encoder 更能处理「不是」「仅在企业版」「截至 2026 年 5 月」这类需要同时对照问题和证据的语义。

代价是明显的：每多一条候选，就要多跑一次联合编码，延迟和成本大致随候选数线性增长。因此业界常见配置是：初召拿到五十到两百条候选，rerank 其中二十到一百条，最终只把三到十条最相关、且通过压缩后仍能装下的证据放进 Prompt。若你发现评测集里的金标准 chunk 经常不在 rerank 的输入集合里，问题多半在初召或混合检索，而不是 rerank 模型本身；若金标准已经在 rerank 输入里，但总是排在很后面，才需要换 reranker、调整融合权重或补充 BM25 等信号。

Cross-Encoder 适合作为企业知识库、客服问答、内部制度查询等主链路默认精排方案。不适合单独依赖的场景包括：候选规模极大且延迟极敏感、只能做粗过滤时——此时可以先用向量分或轻量规则缩小范围，再对缩小后的集合做 Cross-Encoder。

### 3. 多路召回合并、去重与分数融合

混合检索之后，往往会同时拿到向量一路和 BM25 一路的命中结果。合并时首先要按 chunk 标识去重，同一 chunk 只保留一条记录，但要**保留每一路的来源分数和排名**，不要过早丢掉向量分或 BM25 分，因为 rerank 模型之外，这些信号对专有名词、错误码、SKU 等仍然有价值。若同一文档有多个相邻 chunk 同时命中，可以根据业务选择合并成更完整的段落，或限制每个 document_id 最多进入最终上下文几条，避免一篇长文占满窗口。

分数融合时切忌把不同量纲的分数直接相加。向量相似度、BM25 分、Cross-Encoder 分、标题是否命中、文档新鲜度、权威度等，通常要先做归一化或采用按排名融合的方式，再按权重合成最终分。权重不要长期拍脑袋固定，应结合离线 NDCG、线上用户点击引用片段、以及 badcase 回归逐步调整。需要反复强调的一点是：**租户隔离和 ACL 必须在融合和 rerank 之前完成**，无权限文档不能先进入候选池再靠低分「自然沉底」，否则可能已经进入日志、rerank 服务或后续的上下文组装环节，带来合规风险。

### 4. MMR：在相关性与多样性之间取舍

最大边际相关性（MMR）的核心想法是：在已经选中的片段之外，再选下一条时，不仅要看它和问题的相关度，还要看它和已选片段是否过于相似。这样能缓解「top_k 全是同一篇文档的五个相邻 chunk」的问题，对需要对比多个产品、汇总多来源观点、写综述类回答的场景有帮助。

MMR 并不适用于所有题型。若用户问的是单一精确事实，例如「退款到账需要几个工作日」，通常只需要权威来源中相关度最高的那一条，强行做多样性反而可能把次相关但含干扰信息的片段拉进来。调参时，相关性权重越大，行为越接近纯按 rerank 分排序；多样性权重越大，越倾向从不同文档各取一点。是否启用 MMR，应结合评测集上的 Context Precision 和引用准确率来判断，而不是默认所有业务都开。

### 5. 上下文压缩：策略、风险与「保真」标准

上下文压缩是在 token 预算固定的前提下，决定「哪些句子、哪些段落、哪些字段」进入最终 Prompt。常见手段包括：**句子级窗口**，在命中 chunk 周围扩展若干句，成本低且保留原文表述，适合叙述性文档，但对跨段落、跨表格的答案可能仍不完整。**抽取式压缩**，只保留与问题最相关的句段或结构化字段，适合政策、配置、费率表等，关键是要能指回原文位置。**生成式摘要**，能明显降低 token，但容易丢掉数字、日期、版本号和例外条款，还可能产生「摘要幻觉」——摘要里出现了原文没有的归纳。对高风险场景，应优先抽取式并保留引用 span，而不是让摘要成为唯一证据来源。

压缩是否成功的判断，不能只看 token 降了多少。要问：压缩后的上下文是否仍能推出标准答案；金额、日期、版本号是否还在；生成答案的引用是否仍能对应到原文；Faithfulness 和 Citation Accuracy 是否相比不压缩反而下降。若变短了但引用错了，说明压缩策略有问题，需要收紧裁剪规则或改为保留完整 chunk 的头部加命中句。

### 6. Token 预算分配与低置信拒答

总上下文窗口需要在一开始就做拆分：系统提示、用户问题、多轮历史、检索证据、以及留给模型输出的部分，都要先占位。实践中通常会先预留输出 token，再分配给检索证据；对每个文档或每个来源设置上限，防止单篇长文垄断窗口。对于 rerank 之后分数仍然很低、或最高分与次高分差距极小的情况，更稳妥的做法是触发拒答、请用户澄清或转人工，而不是硬把低相关证据塞给模型生成——这在金融、法务、医疗等场景尤其重要，因为低置信硬答的幻觉和合规风险都更高。

长上下文模型能装下更多字，但**不能替代 rerank 和压缩**。长窗口解决的是容量问题，不自动解决该装什么、以什么顺序装的问题。证据仍应把最相关、最可回答的片段靠前放置，并控制噪声比例。

### 7. 分层排障：先别急着换大模型

线上 RAG 效果不好时，建议按层排查，避免一上来就换更大的生成模型。第一步，金标准答案是否存在于知识库的某个 chunk 中；若不存在，问题在数据、解析或切分。第二步，初召 top 一百左右是否包含该 chunk；若不包含，问题在 Embedding、混合检索、过滤过严或 query 太短。第三步，rerank 之后该 chunk 是否进入前五；若进不了，问题在精排模型或分数融合。第四步，最终 Prompt 里关键句是否还在，压缩是否删掉了数字或条件；若证据都在但答错，再查 Prompt 约束和生成模型。第五步，才考虑生成侧的温度、模型能力等。

评估上，排序层关注 Recall、MRR、NDCG、以及 RAG 评测里的 Context Precision 和 Context Recall；生成层关注 Faithfulness、Citation Accuracy、拒答是否合理。压缩策略调整时，应同时看 token 成本和忠实度是否 trade-off 失控。

## 高频面试问题与标准答案

### 1. Reranker 和 Embedding 检索有什么区别？

**标准答案：**  
我会把它们说成检索链路里两个不同阶段的分工。Embedding 检索是双塔结构，query 和文档分别编码，再用向量距离在百万级 chunk 里做粗召，优势是快、能覆盖大量候选，但 query 和 passage 之间没有 token 级交互，对「能不能回答这道题」判断比较粗。Reranker，尤其是 Cross-Encoder，是在初召之后对几十条候选做精排，把 query 和片段放在一起看，更关注可回答性和细粒度匹配。所以一般说法是：Embedding 负责别漏，Reranker 负责别脏。生产上常见向量先召五十到一百条，再 rerank 出最相关的几条进 Prompt。

### 2. Cross-Encoder 为什么通常比向量检索更准？

**标准答案：**  
因为 Cross-Encoder 在打分的时候，用户问题和候选片段是在同一个编码过程里交互的，模型能同时对齐限定词、否定词和实体，比如「企业版」和「个人版」的区别，或者「多久到账」和「如何申请」的区别。向量检索是把两边各自压成一个向量再比距离，信息在压缩过程中会损失，更擅长「主题相近」，不擅长「是否包含答案」。代价是慢、贵，所以只能用在初召之后的小候选集上，不会拿它去扫全库。

### 3. rerank 的候选数量一般怎么定？

**标准答案：**  
我会先看延迟预算和初召质量，没有固定数字，但有常见区间。初召可以上百条，真正送进 Cross-Encoder 的往往是几十条，最终进 Prompt 的通常个位数。定数量时我会看评测集：如果金标准 chunk 经常不在 rerank 输入里，应该加大初召或加强 BM25、query 改写，而不是盲目加 rerank 条数；如果已经在 rerank 输入里但排名靠后，才考虑换 rerank 模型或调融合权重。线上还要卡 P95 延迟，必要时对 rerank 做批处理或限制候选上限。

### 4. 多路召回之后，你会怎么合并和排序？

**标准答案：**  
多路召回之后我首先按 chunk_id 去重，同一条只保留一份，但会保留它来自向量还是 BM25、以及各自的分数和排名。权限和租户过滤一定在这之前就做完，无权限文档不会进入候选。合并后先用 Cross-Encoder 做语义精排，再视情况叠加标题命中、新鲜度、权威度等业务信号，分数要先归一化再加权，不能不同量纲硬加。对比类、综述类问题可以再加 MMR 控制多样性；精确事实类问题我一般不做 MMR，只取得分最高的权威来源。最后再做上下文压缩，把 token 控制在预算内，并保留引用信息。

### 5. MMR 解决什么问题？什么时候不该用？

**标准答案：**  
MMR 主要是解决 top 结果里多篇高度重复、都来自同一文档相邻 chunk 的问题。它在「还要不要多样性」上和纯按相关度排序不一样，会在相关性和已选片段的差异性之间折中，适合对比、多来源总结这类需要多个视角的场景。如果是查一个明确数字或一条政策原文，通常不需要 MMR，只要最相关、最权威的那一条就行，开了反而可能引进噪声。是否使用我会用评测集看 Context Precision 和引用准确率，而不是默认全开。

### 6. 上下文压缩和摘要是一回事吗？

**标准答案：**  
不是。压缩是目标，摘要是实现压缩的一种手段。还可以用句子窗口扩展、只抽取相关句段、合并重复 chunk 等方式达到压缩目的。摘要的问题在于可能改写原文，数字、日期、例外条款容易丢，甚至出现摘要里多出来的信息。所以在法务、合同、退款规则这类场景，我更倾向抽取式并保留原文引用，让生成阶段仍然对着可追溯的 span 说话。验收压缩效果时，我看的不只是 token 少了多少，而是 Faithfulness 和引用准确率有没有掉。

### 7. 有了长上下文模型，还需要 rerank 吗？

**标准答案：**  
需要。长上下文解决的是能装多少，不解决该装什么。如果把初召回来的几十条未经精排的证据全塞进去，噪声多、成本高，模型还容易错误引用靠后的无关段落。Rerank 和压缩管的是信噪比和顺序，让最可能含答案的片段排在前面，并且在预算内保真。所以长上下文和 rerank 是叠加关系，不是替代关系。

### 8. 你怎么判断问题出在召回、排序还是生成？

**标准答案：**  
我习惯分层看。先看正确答案在不在知识库的某个 chunk 里，不在就是数据或切分问题。在的话，看初召 top 一百左右包不包含它，不包含就查向量、BM25、过滤和 query。包含但 rerank 后进不了前五，就查精排和融合权重。进了前五但 Prompt 里关键信息被压缩裁掉，就查压缩策略。证据都齐但答错，再看 Prompt 是否要求仅依据上下文、是否要求引用，以及生成模型本身。这套说法和线上排障是一致的，面试官一般也会认可你有工程经验。

### 9. rerank 分数很低或者最高分也不高，你会怎么处理？

**标准答案：**  
这种情况说明模型对现有证据把握不高，我不倾向于硬生成。可以走拒答或请用户补充信息，比如澄清产品版本、订单号、时间范围。工程上可以同时排查：初召是否太窄、要不要开 BM25 或多查询改写、metadata 过滤是否过严、query 是否太短。若是金融、法务类，低置信还会转人工。核心原则是宁可少答或澄清，也不要在低质量证据上编一个看起来流畅的答案。

## 面试回答加分点

- 用「初召要覆盖、精排要准、压缩要保真」三句话串起全链路，体现你对 RAG 中间层的系统理解，而不是只会调 top_k。
- 主动区分「语义相似」和「可回答性」，并能举退款到账、企业版与个人版等具体反例。
- 强调权限必须在 rerank 之前过滤，分数融合不能替代 ACL，体现企业级合规意识。
- 对 MMR、摘要、句子窗口能说清适用场景和风险，尤其在高风险场景坚持抽取式与引用保真。
- 对长上下文有清醒认识：容量不等于证据质量，长窗口不能替代 rerank。
- 排障用分层 checklist 表述，并提到 Context Precision、Faithfulness、Citation Accuracy 等指标，显得做过评测和线上 badcase 闭环。
