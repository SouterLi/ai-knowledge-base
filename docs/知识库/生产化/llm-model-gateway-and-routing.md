# AI 应用开发面试主题：LLM 模型网关与多模型路由

## 主题选择记录

- 本次主题：LLM 模型网关与多模型路由
- 所属分类：生产化工程
- 已回顾历史主题：RAG、Agent、Prompt 工程、评估观测、安全防护、上下文工程、流式异步、多模态、成本缓存限流
- 不重复原因：已有生产化主题聚焦成本、缓存和限流；本主题聚焦统一模型接入层、多模型调度、降级熔断、灰度发布和 SLA 治理

## 一、为什么这是高频考点

真实 AI 应用很少只调用一个模型。上线后会遇到模型供应商不稳定、不同任务需要不同模型、部分租户需要专属模型、成本和延迟目标冲突、模型升级需要灰度验证等问题。

面试官问模型网关，本质是在考察候选人是否具备从“直接调 API”升级到“可治理模型调用平台”的能力。优秀答案不能只说封装 SDK，而要覆盖路由策略、降级兜底、观测指标、权限隔离、配置治理和上线变更风险。

## 二、核心概念

### 1. 模型网关

模型网关是业务系统和模型供应商之间的统一调用层，常见职责包括：

- 统一请求协议：屏蔽 OpenAI、Claude、Gemini、本地模型等接口差异。
- 统一鉴权和审计：按用户、租户、业务线记录调用来源。
- 统一治理能力：限流、重试、超时、熔断、降级、缓存、日志。
- 统一配置入口：模型别名、版本、供应商、权重、灰度规则。

面试中要强调：模型网关不是简单代理，核心价值是“治理模型调用的复杂度”。

### 2. 模型路由

模型路由是根据任务、上下文和运行时状态选择模型的过程。常见维度包括：

- 任务类型：分类、抽取、总结、代码生成、推理、图像理解。
- 质量要求：强一致、低幻觉、高推理、多语言、结构化输出。
- 性能目标：低延迟、高吞吐、流式响应、批处理。
- 成本约束：免费用户、小模型优先，高价值任务强模型兜底。
- 可用性状态：供应商故障、区域不可用、限流、P95 延迟升高。

一个成熟回答应包含静态路由和动态路由：静态路由靠配置，动态路由根据实时指标调整。

### 3. 模型别名

业务方不应直接依赖具体模型名，而应依赖稳定别名，例如：

- `chat_fast`：低延迟对话。
- `chat_reasoning`：复杂推理。
- `json_extract`：结构化抽取。
- `vision_qa`：图片问答。

别名背后可以映射到不同供应商和版本。这样模型升级、供应商切换和灰度实验都不需要改业务代码。

### 4. 降级、熔断与兜底

- 降级：强模型失败时切到小模型、短答案、异步任务或模板回复。
- 熔断：某个供应商错误率或超时率超过阈值后，短时间内停止请求它。
- 兜底：返回可解释的失败信息、排队处理、人工介入或让用户稍后重试。

注意：降级不能破坏安全边界。例如医疗、金融、法务场景不能因为强模型不可用就切到未经验证的小模型直接给结论。

## 三、核心知识点

### 1. 推荐架构

典型调用链：

1. 业务服务发起请求，只传模型别名和任务参数。
2. 模型网关完成鉴权、参数校验、Prompt 版本记录。
3. 路由器根据配置和运行时状态选择候选模型。
4. 执行器调用模型供应商，设置超时、重试和幂等键。
5. 结果进入结构化校验、内容安全检查和日志采样。
6. 指标系统记录延迟、token、成本、错误码、降级原因。

```text
业务服务
  -> 模型网关
  -> 路由器
  -> Provider Adapter
  -> OpenAI / Claude / Gemini / 本地模型
  -> 校验、审计、观测
```

核心原则：业务只感知能力，不绑定供应商。

### 2. 路由策略设计

常见路由策略可以分层组合：

| 策略 | 适用场景 | 面试回答要点 |
| --- | --- | --- |
| 规则路由 | 明确任务类型 | 简单、可解释、容易灰度 |
| 权重路由 | A/B 测试、灰度发布 | 需要按租户和用户稳定分桶 |
| 成本优先路由 | 大量低风险请求 | 低价模型先试，不达标再升级 |
| 质量优先路由 | 高价值或高风险请求 | 强模型优先，成本换质量 |
| 延迟优先路由 | 在线交互 | 选择 P95 稳定的模型 |
| 健康状态路由 | 供应商波动 | 自动避开错误率高的 Provider |

不要把路由写死在业务代码里。更好的方式是配置化，并记录每次路由决策原因，方便回放和排查。

### 3. Provider Adapter

不同模型供应商的接口字段、错误码、流式协议和工具调用格式不同。Adapter 层负责统一它们：

- 输入统一：messages、temperature、max_tokens、tools、response_format。
- 输出统一：content、tool_calls、usage、finish_reason、raw_response。
- 错误统一：超时、限流、鉴权失败、内容安全拒绝、模型内部错误。
- 流式统一：把不同 SSE chunk 转成统一事件。

```python
class ProviderAdapter:
    def complete(self, request):
        raise NotImplementedError


class OpenAIAdapter(ProviderAdapter):
    def complete(self, request):
        # 生产代码中应在这里转换字段、设置超时、解析 usage 和错误码
        return {
            "content": "统一后的回答",
            "usage": {"input_tokens": 120, "output_tokens": 80},
            "provider": "openai",
        }
```

面试时可以说：Adapter 层越稳定，业务层越不容易被供应商接口变化影响。

### 4. 超时、重试与幂等

模型调用的重试不能无脑做：

- 只对短暂网络错误、429、部分 5xx 做有限重试。
- 内容安全拒绝、参数错误、鉴权失败不应重试。
- 流式响应已经向用户输出内容后，重试会造成重复片段，需要特殊处理。
- 工具调用或写操作场景必须有幂等键，避免重复扣费、重复下单、重复写库。

```python
RETRYABLE_ERRORS = {"timeout", "rate_limited", "provider_5xx"}


def should_retry(error_code, attempt, max_attempts=2):
    # 只重试可恢复错误，避免把业务错误放大成流量风暴
    return error_code in RETRYABLE_ERRORS and attempt < max_attempts
```

回答时要补充“重试会增加成本和延迟”，所以要有上限、退避和监控。

### 5. 熔断与健康检查

熔断判断指标通常包括：

- 最近 N 分钟错误率。
- P95/P99 延迟。
- 429 或 5xx 数量。
- 流式连接中断率。
- 供应商状态页或探活请求结果。

熔断后不要永久关闭，应进入半开状态，用少量探测请求验证恢复。

```python
def select_provider(candidates, health):
    available = [
        provider for provider in candidates
        if health[provider]["state"] != "open_circuit"
    ]
    if not available:
        raise RuntimeError("no_available_provider")
    return min(available, key=lambda p: health[p]["p95_latency_ms"])
```

### 6. 灰度发布与回滚

模型升级不能直接全量替换。推荐流程：

1. 离线评测：用固定评测集比较准确率、格式遵循率、拒答率和成本。
2. 影子流量：线上请求同时发给新模型，但不返回给用户。
3. 小流量灰度：按租户、用户或请求哈希稳定分桶。
4. 指标对比：关注质量投诉、解析失败率、工具调用失败率、P95 延迟。
5. 快速回滚：配置层切回旧模型，业务无需发版。

面试回答要避免“新模型更强就直接换”。模型升级本质是一次生产变更。

### 7. 可观测性

模型网关至少记录这些字段：

- 请求维度：request_id、tenant_id、user_id、feature、model_alias、prompt_version。
- 路由维度：selected_provider、selected_model、route_rule、fallback_reason。
- 资源维度：input_tokens、output_tokens、cost、cache_hit。
- 性能维度：首 token 延迟、总延迟、流式中断、重试次数。
- 质量维度：结构化解析失败、人工反馈、评测标签、拒答原因。

注意隐私：日志里不要直接落完整 Prompt、用户隐私和密钥。需要采样、脱敏和权限控制。

## 四、简化路由示例

下面是一个面试中可以手写的简化版本，展示思路即可：

```python
MODEL_ROUTES = {
    "chat_fast": [
        {"provider": "provider_a", "model": "small-chat", "weight": 80},
        {"provider": "provider_b", "model": "small-chat", "weight": 20},
    ],
    "chat_reasoning": [
        {"provider": "provider_a", "model": "strong-reasoning", "weight": 100},
    ],
}


def route_model(alias, tenant_level, health):
    candidates = MODEL_ROUTES[alias]

    if tenant_level == "enterprise" and alias == "chat_fast":
        # 企业用户优先选择稳定性更高的供应商
        candidates = sorted(
            candidates,
            key=lambda item: health[item["provider"]]["p95_latency_ms"],
        )

    for candidate in candidates:
        provider = candidate["provider"]
        if health[provider]["state"] == "healthy":
            return candidate

    raise RuntimeError("no_healthy_model")
```

这段代码能说明三个重点：业务传别名、网关查配置、运行时健康状态影响路由。

## 五、高频面试问题及参考答案

### 1. 为什么需要模型网关？直接在业务里调用模型 API 不行吗？

小规模 Demo 可以直接调用，但生产系统需要统一治理。模型网关可以屏蔽供应商差异，集中处理鉴权、限流、重试、熔断、降级、审计、成本统计和模型灰度。否则每个业务都重复封装 SDK，模型升级和故障切换会变得不可控。

### 2. 如何设计多模型路由？

先定义模型别名，让业务依赖能力而不是具体模型。再按任务类型、租户等级、成本预算、延迟目标和质量要求制定路由规则。线上还要结合健康状态动态避开故障供应商。每次路由要记录命中的规则、模型版本和降级原因，便于追踪问题。

### 3. 如何处理某个模型供应商突然不可用？

先通过错误率、超时率和探活指标触发熔断，把流量切到备用供应商或备用模型。对低风险场景可以降级到小模型或模板回复；对高风险场景应返回可解释失败或转人工。恢复时进入半开状态，用少量请求验证稳定后再逐步恢复流量。

### 4. 模型升级如何灰度？

先做离线评测，确认核心指标没有明显退化。然后用影子流量观察新模型输出，但不影响用户。再按用户或租户稳定分桶放小流量，对比解析失败率、投诉率、成本、P95 延迟和安全拒答率。发现问题时通过配置回滚到旧模型。

### 5. 模型网关的日志应该记录什么？有什么风险？

应该记录请求 ID、租户、业务场景、模型别名、实际模型、Prompt 版本、token、成本、延迟、错误码、重试次数、降级原因。风险是泄露用户隐私、商业数据和系统提示词，所以日志要脱敏、采样、分级授权，敏感字段尽量只存哈希或摘要。

### 6. 多模型路由如何兼顾成本和质量？

可以按任务风险分层：低风险任务用小模型，失败或置信度不足时升级强模型；高风险任务直接使用强模型，并加结构化校验和人工兜底。关键是用评测集和线上指标验证“便宜模型是否足够好”，不能只按价格选模型。

### 7. 重试、降级和熔断之间是什么关系？

重试处理单次短暂失败，降级处理能力或体验下降但服务继续可用，熔断处理某个下游整体不健康。顺序通常是有限重试，失败后按规则降级；如果一段时间内错误率持续升高，就熔断该供应商并切走流量。

### 8. 如何避免供应商锁定？

抽象统一请求和响应协议，用 Provider Adapter 隔离接口差异；业务只使用模型别名，不直接写具体模型名；把路由规则、Prompt 版本和模型参数配置化；保留离线评测和影子流量机制，确保替换供应商时能验证质量。

## 六、面试回答模板

可以用下面结构回答系统设计题：

1. 先说明目标：统一接入多家模型，并保证可用性、成本和质量可控。
2. 再拆架构：业务服务、模型网关、路由器、Provider Adapter、观测系统。
3. 说明路由：按任务、租户、成本、质量、延迟和健康状态选择模型。
4. 说明稳定性：超时、有限重试、熔断、降级、幂等和回滚。
5. 说明上线治理：离线评测、影子流量、小流量灰度、指标对比。
6. 最后补安全和隐私：日志脱敏、权限隔离、敏感场景禁止不安全降级。

## 七、常见错误回答

- 只说“封装一个 SDK”，没有治理能力。
- 只按成本选模型，不讨论质量和风险分层。
- 无脑重试，忽略成本放大、延迟放大和流式重复输出。
- 降级策略没有边界，高风险场景也随意换小模型。
- 灰度只看成功率，不看解析失败、投诉、拒答率和业务指标。
- 日志直接保存完整 Prompt 和用户输入，忽略隐私与合规。

## 八、一分钟总结

LLM 模型网关的核心是把模型调用从“业务内硬编码”变成“平台化治理”。面试时要讲清楚模型别名、Provider Adapter、多模型路由、健康检查、重试熔断、降级兜底、灰度回滚和可观测性。好的答案体现生产化思维：模型可以变，但业务接口稳定；供应商会故障，但系统要有可控退路。
