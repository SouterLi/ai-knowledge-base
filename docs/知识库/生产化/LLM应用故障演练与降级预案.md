## 核心概念

**LLM 应用故障演练**是指在可控环境中主动模拟模型供应商异常、推理服务过载、向量库超时、工具调用失败、流式中断、队列堆积、权限服务不可用等问题，验证系统能否按预案进入限流、降级、转人工、异步排队或只读模式，并且在恢复后能回放、补偿和复盘。

面试中可以用一句话概括：**LLM 应用的高可用不是“模型永远不出错”，而是依赖出错时能识别影响范围、保护核心链路、可解释降级，并且安全恢复。**

与传统后端不同，LLM 应用的故障往往同时影响质量、成本、延迟和合规：

| 故障类型 | 典型表现 | 主要风险 |
| --- | --- | --- |
| 模型供应商不可用 | 5xx、429、连接超时 | 大面积请求失败、重试放大流量 |
| 模型质量漂移 | 同样输入输出变差、结构化失败率升高 | 错答、幻觉、业务决策不稳定 |
| RAG 依赖异常 | 向量库慢、rerank 超时、索引版本错误 | 召回缺失、引用错误、回答无依据 |
| Agent 工具故障 | 工具超时、参数失败、外部 API 不可用 | 循环重试、产生重复副作用 |
| 流式链路中断 | SSE/WebSocket 断开、半截 JSON | 用户体验差、下游解析失败 |
| 权限或审计异常 | 鉴权服务慢、日志不可写 | 越权风险、合规不可追溯 |

**降级预案**不是简单地“换小模型”或“返回默认答案”，而是根据业务风险分层：低风险场景可以缩短上下文、关闭非核心 rerank、切备用模型；高风险场景宁可拒答、排队或转人工，也不能用不可靠答案继续闭环。

一个可落地的故障治理链路通常是：

```text
监控发现异常
  → 识别故障域：模型 / 检索 / 工具 / 权限 / 前端连接
  → 判断业务风险等级和影响范围
  → 启动预案：限流、熔断、降级、排队、转人工
  → 对用户给出可解释状态
  → 持续观测核心指标
  → 恢复后半开探测、小流量放量、回放补偿
  → 复盘并补充演练用例
```

## 核心知识点

### 1. 先按业务风险分级，而不是所有请求统一降级

LLM 应用的降级策略必须和业务风险绑定：

| 风险等级 | 示例 | 可接受降级 |
| --- | --- | --- |
| L0 展示类 | 文案润色、摘要草稿 | 小模型、短答案、排队 |
| L1 低风险问答 | 通用 FAQ、内部知识查询 | 关闭扩展查询、缩短上下文、返回引用不足提示 |
| L2 业务辅助 | 客服建议、工单分类、报表解释 | 降级为建议草稿、要求人工确认 |
| L3 高风险决策 | 金融、医疗、法务、退款、权限变更 | 拒答、转人工、只保留查询不执行 |
| L4 真实副作用 | 发邮件、扣款、删数据、改配置 | 停止自动执行，只允许预览或审批 |

面试重点：**降级不能突破原有安全边界。** 如果原链路要求引用、权限过滤、人工审批，降级后也不能绕过这些约束。

### 2. 常见故障注入点要覆盖 LLM 专属链路

不要只说“压测接口”。LLM 应用至少要覆盖这些演练点：

1. **模型层**：主模型 5xx、429、响应变慢、流式中断、输出格式不合法。
2. **网关层**：路由规则错误、供应商配额耗尽、熔断阈值过低或过高。
3. **RAG 层**：Embedding 服务超时、向量库慢查询、rerank 不可用、索引版本切换失败。
4. **Agent 工具层**：工具返回错误、重复投递、幂等键冲突、外部 API 超时。
5. **数据与权限层**：ACL 服务不可用、权限版本不一致、审计日志写入失败。
6. **前端体验层**：SSE 断连、任务进度丢失、用户刷新页面后无法恢复。

一个简单的故障开关注入示例：

```python
from dataclasses import dataclass

@dataclass
class FaultPolicy:
    provider_timeout: bool = False
    vector_db_slow: bool = False
    tool_error_rate: float = 0.0

def choose_degradation(policy: FaultPolicy, risk_level: str) -> str:
    # 中文注释：高风险场景不使用弱兜底，直接进入人工或拒答
    if risk_level in {"L3", "L4"}:
        return "human_review_or_safe_fail"
    if policy.provider_timeout:
        return "switch_backup_model"
    if policy.vector_db_slow:
        return "use_cached_retrieval_or_answer_with_low_confidence_notice"
    if policy.tool_error_rate > 0.2:
        return "disable_agent_auto_execution"
    return "normal"
```

### 3. 降级策略要分层设计

常见的分层降级顺序：

| 层级 | 策略 | 适用场景 | 注意点 |
| --- | --- | --- | --- |
| 输入层 | 限制上下文长度、限制上传文件大小 | 成本或延迟异常 | 不能裁掉关键约束和权限信息 |
| 检索层 | 减少 top_k、跳过多查询改写、使用缓存召回 | RAG 依赖变慢 | 必须保留权限过滤和引用提示 |
| 模型层 | 切备用供应商、小模型、短输出 | 主模型异常 | 高风险场景要验证质量门槛 |
| 编排层 | 关闭非核心 Agent 步骤、转异步任务 | 工具链不稳定 | 有副作用的步骤不能自动重试 |
| 产品层 | 排队、只读、转人工、明确失败 | 质量或安全无法保证 | 不要返回看似正常但不可靠的答案 |

面试表达可以强调：**降级顺序应先保护系统，再保护核心业务，最后才优化体验。** 体验可以慢一点，但不能越权、错扣款或编造依据。

### 4. 熔断、限流、重试要避免雪崩

LLM 服务常见雪崩来自三件事：上游重试过多、模型 429 后继续放量、流式请求长期占用连接。

设计要点：

- **超时要短而分层**：检索、rerank、模型、工具分别设置预算，不让一个环节拖垮全链路。
- **重试只针对可恢复错误**：网络抖动可以有限重试，结构化输出失败可修复重试；高风险副作用不能盲目重试。
- **熔断要有半开探测**：错误率超过阈值后切走流量，恢复时先小比例探测。
- **限流要按租户和优先级**：不能让低价值批处理挤占在线客服或核心客户额度。
- **排队要给用户状态**：告诉用户“正在排队/已转异步”，不要让请求一直转圈。

配置示例：

```yaml
degradation:
  model_gateway:
    timeout_ms: 12000
    max_retries: 1
    circuit_breaker:
      error_rate_threshold: 0.25
      min_requests: 50
      half_open_probe_ratio: 0.05
  rag:
    retrieval_timeout_ms: 800
    rerank_timeout_ms: 1200
    fallback: "answer_with_evidence_gap_notice"
  tenant_queue:
    high_priority_reserved_ratio: 0.4
    max_wait_ms: 5000
```

### 5. RAG 降级不能牺牲证据和权限

RAG 故障时最容易犯的错误是“检索慢了就直接让模型凭常识答”。这在企业知识库、金融、法务、医疗里风险很高。

更稳妥的做法：

1. 向量检索慢：先尝试关键词检索或缓存召回，但仍带租户和 ACL。
2. rerank 超时：可以使用初召分数排序，但降低置信度并限制回答范围。
3. 证据不足：明确说明“当前没有足够依据”，引导补充条件或转人工。
4. 索引版本异常：回滚到上一稳定索引版本，而不是混查两个不一致版本。
5. 引用校验失败：答案不直接放行，返回低置信或人工审核。

面试回答要点：**RAG 的降级底线是无权限内容不能进 Prompt，无证据结论不能伪装成确定答案。**

### 6. Agent 降级要重点控制副作用

Agent 故障比普通问答更危险，因为它可能会调用工具产生真实动作。

常见预案：

- 工具失败率升高：关闭自动执行，只保留计划生成和参数预览。
- 外部 API 超时：有限重试，必须带幂等键和操作记录。
- 权限服务异常：停止高风险工具，不让模型自行判断权限。
- 循环次数异常：触发预算上限，返回当前进展和失败原因。
- 审计不可用：高风险动作进入暂停队列，等审计恢复再执行。

工具执行伪代码：

```python
def execute_tool(tool_name: str, args: dict, risk_level: str, audit_ok: bool):
    # 中文注释：审计不可用时，高风险工具不能继续自动执行
    if risk_level in {"L3", "L4"} and not audit_ok:
        return {"status": "paused", "reason": "audit_unavailable"}

    if risk_level == "L4":
        return {"status": "preview_only", "args": args}

    return {"status": "executed", "tool": tool_name, "args": args}
```

### 7. 演练要有可观测指标和验收标准

一次有效演练至少要回答四个问题：

1. **是否检测到**：告警是否在阈值内触发，Trace 是否能定位到故障环节。
2. **是否正确降级**：路由、限流、转人工、拒答是否按风险等级执行。
3. **用户是否可解释**：前端是否展示明确状态，而不是空白或无限等待。
4. **是否能恢复**：故障解除后是否半开探测、逐步放量、补偿未完成任务。

关键指标：

| 指标 | 说明 |
| --- | --- |
| error_rate / timeout_rate | 模型、检索、工具分层统计 |
| TTFT / P95 / P99 | 识别排队、prefill、decode 或下游慢 |
| fallback_rate | 降级比例，过高说明依赖或容量有问题 |
| safe_fail_rate | 高风险场景安全拒答或转人工比例 |
| retry_amplification | 重试放大倍数，防止雪崩 |
| queue_wait_ms | 异步任务和租户队列等待时间 |
| recovery_success_rate | 半开探测和恢复后成功率 |

### 8. 事故恢复后要回放、补偿和复盘

恢复不是服务返回 200 就结束。LLM 应用还要处理：

- 半截流式输出是否需要重新生成或提示用户重试。
- 异步任务是否卡在中间状态，需要从检查点恢复。
- 工具调用是否已经产生副作用，是否需要补偿。
- 降级期间生成的低置信答案是否需要标记或回收。
- 事故样本是否进入回归集，下一次发布或演练要覆盖。

复盘报告建议包含：故障时间线、影响租户、触发指标、预案是否生效、人工介入点、错误降级案例、缺失监控、需要补充的自动化演练脚本。

## 高频面试问题与标准答案

**Q1：如果线上主模型供应商突然 429 或超时，你怎么处理？**

标准答案：我会先在模型网关层识别是单供应商问题还是全局流量问题。单供应商异常时触发熔断，把低风险请求切到备用模型或小模型，高风险请求不盲目降级，必要时排队或转人工。同时限制重试次数，避免把 429 放大成雪崩。恢复时不会立刻全量切回，而是半开探测、小比例放量，看错误率、P95、结构化输出成功率都恢复后再扩大流量。

**Q2：RAG 的向量库或 rerank 服务超时，能不能直接让大模型回答？**

标准答案：不能一概直接回答。RAG 场景通常要求基于企业知识和引用，检索失败时让模型凭常识答，很容易幻觉或违反合规。我的做法是分风险：低风险 FAQ 可以用缓存召回、关键词检索或初召结果降级，并提示置信度；高风险场景如果证据不足，就明确拒答或转人工。底线是权限过滤不能跳过，无证据结论不能伪装成确定答案。

**Q3：你会怎么设计一次 LLM 应用故障演练？**

标准答案：我会先选故障域，比如主模型超时、向量库变慢、工具 API 失败或 SSE 断连；然后定义影响范围和验收标准，例如告警几分钟内触发、低风险请求切备用模型、高风险请求进入人工审核、前端展示排队状态。演练时通过配置开关或测试环境注入故障，观察 Trace、错误率、fallback_rate、queue_wait 和用户提示。恢复后做半开探测和回放补偿，并把这次样本沉淀成自动化演练用例。

**Q4：模型降级到小模型时，怎么保证质量不出问题？**

标准答案：我不会把所有请求都降级到小模型。首先按任务风险和复杂度分流：摘要、润色、简单分类可以小模型；法务、金融、医疗、权限变更这类高风险任务不安全就拒答或转人工。其次，小模型上线前要跑固定评测集，看准确率、结构化合法率、拒答正确率和安全样例。线上降级时也要打标，记录实际模型和降级原因，方便回放分析。

**Q5：Agent 工具调用失败时，为什么不能简单重试？**

标准答案：因为 Agent 工具可能有副作用，比如发邮件、创建工单、退款、改配置。简单重试可能造成重复执行。我的处理方式是区分可重试和不可重试错误：网络抖动可以有限重试，但必须有幂等键；业务校验失败或权限失败不能重试；高风险动作在工具链异常时只生成预览，不自动执行。每次工具调用都要记录 request_id、参数、结果和审计日志，方便恢复和补偿。

**Q6：流式响应中断了，用户看到半截内容怎么办？**

标准答案：流式中断要分两层处理。后端要能感知客户端断开，及时取消模型生成，避免继续消耗 token；前端要展示“连接中断，可重试或查看已生成内容”，不要把半截 JSON 当完整结果。对于普通文本可以允许用户重试；对于结构化输出或会触发业务动作的场景，必须等完整结果校验通过后才提交下游，不能边流边执行高风险操作。

**Q7：降级预案如何避免越权或合规问题？**

标准答案：降级只能降低体验或能力，不能降低安全约束。比如 RAG 降级时仍然要带 tenant、ACL 和 permission_version；缓存命中也要检查权限维度；审计服务不可用时，高风险工具应该暂停，而不是继续执行后补日志。面试里我会强调：权限、审计、人工审批这些是硬边界，不是可选优化项。

**Q8：怎么判断故障已经恢复，可以把流量切回去？**

标准答案：我会看分层指标，而不是只看接口 200。模型层看错误率、429、P95、流式中断率和结构化输出成功率；RAG 层看检索延迟、召回结果数量、rerank 成功率；业务层看拒答率、转人工率、用户重试率。恢复流程上先半开探测，再按小流量逐步放大，同时保留回滚开关。如果降级期间有异步任务或暂停工具，还要确认补偿和回放完成。

**Q9：如果审计日志服务挂了，LLM Agent 还能继续执行工具吗？**

标准答案：要看工具风险。低风险只读查询可以在本地缓冲审计事件后继续，但要有落盘和补写机制；高风险写操作，比如退款、发外部邮件、修改权限，审计不可用时我会暂停或转人工。原因是这些动作事后必须可追溯，不能为了可用性牺牲合规。这个问题本质上是业务连续性和合规底线的取舍。

**Q10：面试让你设计 LLM 应用高可用方案，你会怎么总结？**

标准答案：我会按“监控识别、分级降级、故障隔离、安全兜底、恢复复盘”来讲。入口做租户限流和优先级队列，模型网关做多供应商路由、熔断和半开探测，RAG 链路有缓存召回和证据不足拒答，Agent 工具有幂等、预算和人工审批。高风险场景宁可安全失败，也不输出不可靠答案或执行副作用。最后用演练和回归集验证预案，而不是等真实事故时才发现不可用。
