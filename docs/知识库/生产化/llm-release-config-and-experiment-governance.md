## 一、为什么这是高频考点

LLM 应用的变更不只来自代码。一次线上效果变化，可能来自：

1. Prompt 改了一句话。
2. 模型从 `gpt-4.1` 切到 `gpt-4.1-mini`。
3. temperature、top_p、max_tokens 等参数被调整。
4. RAG 的召回数量、重排模型、相似度阈值发生变化。
5. 工具调用 schema、权限范围或超时时间被修改。
6. 安全策略、敏感词策略、引用策略、输出格式校验被更新。

面试官问发布治理，本质是在考察候选人是否知道：LLM 应用不能只按传统后端服务发布来管理，必须把 Prompt、模型、配置、评测、实验和回滚纳入统一变更体系。

一句话回答：

> LLM 应用发布治理的核心，是把“会影响模型行为的所有变量”都版本化、可灰度、可评估、可回滚，并通过实验指标和审计链路控制线上风险。

## 二、核心概念

### 1. 行为配置

行为配置是指不改业务代码、但会改变 LLM 输出行为的配置。

常见行为配置包括：

| 配置类型 | 示例 | 风险 |
| --- | --- | --- |
| Prompt 模板 | system prompt、few-shot 示例、输出格式约束 | 幻觉增加、格式不稳定、语气变化 |
| 模型选择 | 强模型、小模型、本地模型、模型版本 | 成本、延迟、质量和合规风险 |
| 生成参数 | temperature、top_p、max_tokens、seed | 稳定性、创造性、截断风险 |
| RAG 参数 | top_k、rerank、阈值、过滤条件 | 召回不足、噪声增加、引用错误 |
| 工具配置 | tools schema、超时、重试、权限 | 错调工具、越权访问、任务失败 |
| 安全策略 | 注入检测、PII 脱敏、内容审核 | 放行风险内容或误杀正常请求 |

面试要点：

- 不要把 Prompt 和配置当作“随手改的字符串”。
- 影响模型行为的内容都应该进入发布流程。
- 配置变更要和代码变更一样具备审批、灰度、审计和回滚能力。

### 2. Prompt 版本

Prompt 版本是对模板内容、变量定义、适用场景、依赖模型和评测结果的快照。

一个合格的 Prompt 版本至少包含：

```yaml
id: customer_service_refund_v12
task: refund_policy_answer
model_alias: chat_quality
template_version: 12
owner: customer_service_ai
status: canary
variables:
  - user_question
  - retrieved_context
  - locale
eval_report:
  golden_set: refund_v3
  pass_rate: 0.94
  format_valid_rate: 0.99
  hallucination_rate: 0.03
created_at: "2026-05-22T20:00:00Z"
```

高分回答：

> Prompt 版本不是只存模板文本，还要记录变量契约、模型依赖、评测结果、发布状态和回滚目标，否则线上出了问题很难定位到底是哪次 Prompt 变更导致的。

### 3. 灰度发布

灰度发布是指先让少量流量使用新版本，观察质量、延迟、成本和错误率，再逐步扩大。

LLM 应用常见灰度维度：

- 按租户：内部租户、低风险客户、试点客户。
- 按用户：1%、5%、10%、50%、100%。
- 按任务：只灰度“摘要”，不灰度“合同审查”。
- 按风险等级：低风险问答先灰度，高风险决策类任务保持旧版本。
- 按渠道：测试环境、员工内测、公开 API、核心线上链路。

注意：LLM 灰度不能只看 HTTP 5xx。更重要的是看输出质量、格式稳定性、工具调用成功率、安全拦截率和人工投诉。

### 4. A/B 实验

A/B 实验用于比较两个或多个策略的线上效果。

LLM 应用实验常见对比项：

- Prompt A vs Prompt B。
- 强模型 vs 小模型。
- 不同 RAG 召回策略。
- 不同工具调用策略。
- 不同结构化输出约束。
- 不同拒答和安全策略。

面试中要强调：

- 实验必须稳定分流，同一个用户或会话不能频繁切版本。
- 实验指标不能只看点击率，还要看质量、安全、成本和延迟。
- 高风险业务不能直接线上裸跑实验，要先离线评测和小流量灰度。

### 5. 回滚

回滚是发布治理的底线能力。

LLM 应用回滚对象不一定是代码，可能是：

- 回滚 Prompt 模板版本。
- 回滚模型别名映射。
- 回滚 RAG 参数。
- 关闭某个工具调用能力。
- 降低新策略流量比例。
- 恢复旧的安全规则。

好答案要说清楚：回滚不应该依赖重新部署代码。高频行为配置应该由配置中心或发布平台托管，支持分钟级切回。

## 三、核心知识点

### 1. 推荐架构

典型架构如下：

```text
业务请求
  -> 实验分流层
  -> 配置解析层
  -> Prompt/模型/RAG/工具版本选择
  -> LLM 编排执行
  -> 输出校验与安全检查
  -> 指标采集与日志审计
  -> 实验分析与回滚决策
```

核心模块：

| 模块 | 职责 |
| --- | --- |
| 配置中心 | 存储 Prompt、模型参数、RAG 策略、工具配置和安全策略 |
| 版本仓库 | 管理配置版本、变更记录、审批状态和回滚目标 |
| 实验平台 | 负责稳定分流、实验组管理、指标归因 |
| 发布控制面 | 管理草稿、评测、灰度、全量、暂停、回滚 |
| 运行时解析器 | 在请求时解析当前用户命中的配置版本 |
| 指标系统 | 记录质量、成本、延迟、错误、安全和业务指标 |
| 审计系统 | 记录谁在何时发布了什么配置、影响了哪些流量 |

### 2. 配置要分层

不要把所有配置放成一个巨大的 JSON。推荐分层：

```text
全局默认配置
  -> 业务线配置
  -> 场景配置
  -> 租户配置
  -> 实验覆盖配置
  -> 紧急开关配置
```

示例：

```json
{
  "task": "refund_policy_answer",
  "default": {
    "prompt_version": "refund_v11",
    "model_alias": "chat_quality",
    "temperature": 0.2,
    "rag_top_k": 5
  },
  "tenant_overrides": {
    "enterprise_a": {
      "prompt_version": "refund_v10",
      "rag_top_k": 8
    }
  },
  "experiments": {
    "refund_prompt_ab_20260522": {
      "traffic": 0.1,
      "variant": {
        "prompt_version": "refund_v12"
      }
    }
  },
  "kill_switch": {
    "disable_tool_calling": false
  }
}
```

面试要点：

- 默认配置保证稳定基线。
- 租户覆盖满足差异化要求。
- 实验覆盖用于灰度和 A/B。
- 紧急开关用于快速止损。
- 配置解析顺序必须明确，否则线上行为不可解释。

### 3. 变更发布流程

推荐流程：

1. 创建配置草稿：修改 Prompt、模型参数或策略。
2. 静态校验：检查变量、schema、敏感词、权限和格式。
3. 离线评测：跑黄金样例、坏 Case、边界样例和安全样例。
4. 人工审核：高风险场景需要业务、法务或安全负责人确认。
5. 小流量灰度：先内部或低风险流量。
6. 指标观察：比较质量、格式、成本、延迟、错误和投诉。
7. 扩大流量：按阈值逐步放量。
8. 全量发布或回滚：根据数据决策。

不要直接把 Prompt 改完就全量上线。面试中可以把这称为“Prompt 变更的 CI/CD”。

### 4. 发布前校验项

上线前至少检查：

- Prompt 变量是否全部提供。
- 输出格式是否能被解析。
- Tool schema 是否向后兼容。
- 新模型是否支持所需能力，例如工具调用、JSON 模式、视觉输入。
- RAG 策略是否满足权限过滤。
- 安全策略是否覆盖提示注入、敏感信息和越权访问。
- 黄金样例是否通过。
- 成本和延迟是否在预算内。
- 是否存在明确回滚版本。

可落地的门禁规则：

```text
如果 golden_set_pass_rate < 0.90，禁止灰度。
如果 pii_leak_case > 0，禁止上线。
如果 p95_latency 增长超过 30%，需要人工审批。
如果 avg_cost_per_request 增长超过 20%，需要业务负责人确认。
如果 output_format_valid_rate < 0.98，禁止全量。
```

### 5. 指标体系

LLM 发布不能只观察服务指标，要把模型质量指标纳入发布决策。

| 指标类型 | 指标示例 | 用途 |
| --- | --- | --- |
| 质量 | 人工评分、事实一致性、引用命中率、任务成功率 | 判断新版本是否真的更好 |
| 格式 | JSON 解析成功率、字段缺失率、schema 校验通过率 | 判断是否影响下游系统 |
| 安全 | 拒答准确率、敏感信息泄露数、注入攻击通过率 | 判断是否引入安全风险 |
| 工具 | 工具调用成功率、错调率、超时率、重试率 | 判断 Agent 或工具链是否稳定 |
| 性能 | 首 token 延迟、总耗时、P95、P99 | 判断用户体验 |
| 成本 | token 消耗、单请求成本、缓存命中率 | 判断经济性 |
| 业务 | 转化率、解决率、客服转人工率、投诉率 | 判断业务收益 |

高分回答：

> LLM 发布看的是多目标优化：质量提升不能以安全失控为代价，成本下降不能导致关键任务失败率上升。

### 6. 实验分流要稳定

错误做法：每次请求随机选择 A/B 版本。

问题：

- 同一个用户体验不一致。
- 多轮对话上下文里版本混用。
- 指标归因混乱。
- 无法判断一个版本对长期行为的影响。

推荐做法：使用用户、租户、会话或任务 ID 做稳定哈希。

```python
import hashlib


def choose_variant(experiment_id: str, subject_id: str, traffic: float) -> str:
    key = f"{experiment_id}:{subject_id}".encode("utf-8")
    bucket = int(hashlib.sha256(key).hexdigest()[:8], 16) / 0xFFFFFFFF

    # 中文注释：稳定哈希保证同一用户在同一实验中持续命中同一组
    if bucket < traffic:
        return "candidate"
    return "control"
```

面试要点：

- 分流键要和业务目标一致：用户体验看 user_id，租户隔离看 tenant_id，多轮对话看 conversation_id。
- 流量比例变更时要考虑样本污染。
- 实验组配置必须写入日志，方便问题追溯。

### 7. 运行时日志必须记录版本

每次模型调用都应该记录命中的关键版本信息：

```json
{
  "request_id": "req_123",
  "tenant_id": "enterprise_a",
  "task": "refund_policy_answer",
  "experiment_id": "refund_prompt_ab_20260522",
  "variant": "candidate",
  "prompt_version": "refund_v12",
  "model_alias": "chat_quality",
  "resolved_model": "provider_x/model_y_2026_05",
  "rag_policy_version": "rag_refund_v4",
  "tool_policy_version": "tool_refund_v3",
  "safety_policy_version": "safety_v9",
  "latency_ms": 1830,
  "input_tokens": 1420,
  "output_tokens": 360,
  "status": "ok"
}
```

没有这些字段，线上坏 Case 很难定位。你只能知道“模型答错了”，但不知道它当时使用的是哪个 Prompt、哪个模型、哪个检索策略和哪个实验组。

### 8. 配置回滚要有优先级

线上事故通常需要快速判断回滚对象：

| 现象 | 优先排查 | 可能回滚 |
| --- | --- | --- |
| 大量 JSON 解析失败 | Prompt 输出格式、模型 JSON 能力、temperature | Prompt 版本或模型别名 |
| 回答引用不存在 | RAG top_k、重排、引用拼接逻辑 | RAG 策略 |
| 工具调用错接口 | Tool schema、工具描述、权限策略 | 工具配置或 Prompt |
| 延迟突然升高 | 模型版本、重试策略、检索策略 | 模型映射或 RAG 参数 |
| 成本突然升高 | max_tokens、上下文长度、模型选择 | 参数配置或模型别名 |
| 敏感信息泄露 | 安全策略、脱敏链路、Prompt 约束 | 安全策略并暂停流量 |

面试中可以说：先止血，再定位。止血动作可以是关闭实验、切回旧 Prompt、降低流量、禁用工具或切换模型。

### 9. 权限与审批

LLM 行为配置不能人人可改。

建议分权限：

- 开发者：创建草稿、运行离线评测。
- 业务负责人：审核业务话术、任务目标和试点范围。
- 安全负责人：审核高风险工具、敏感数据、越权风险。
- 发布负责人：批准灰度、扩量、全量和回滚。
- 审计角色：只读查看变更历史和线上命中记录。

高风险变更要强制审批：

- 新增外部写操作工具。
- 放宽安全拒答策略。
- 切换到未评测模型。
- 修改金融、医疗、法务等高风险场景 Prompt。
- 扩大可访问的数据范围。

### 10. 与模型网关的边界

模型网关负责“怎么调用模型”，发布治理负责“什么时候让谁使用哪个行为版本”。

两者关系：

- 模型网关提供模型别名、Provider Adapter、重试、限流、熔断和计费。
- 发布治理决定某个任务、租户、实验组使用哪个 Prompt、模型别名和参数。
- 运行时最终把发布治理解析出的配置交给模型网关执行。

不要把所有实验逻辑塞进模型网关，否则网关会变成业务策略大杂烩。

## 四、常见系统设计题回答框架

### 题目：设计一个 LLM Prompt 灰度发布平台

可以按下面结构回答：

1. **目标**：Prompt 和模型行为配置可版本化、可评测、可灰度、可回滚、可审计。
2. **配置模型**：Prompt 模板、变量 schema、模型别名、生成参数、RAG 策略、工具策略、安全策略。
3. **发布流程**：草稿 -> 静态校验 -> 离线评测 -> 审批 -> 小流量 -> 扩量 -> 全量。
4. **运行时链路**：请求进入实验分流层，解析用户/租户命中的配置版本，再调用 LLM 编排服务。
5. **指标体系**：质量、格式、安全、工具、性能、成本和业务指标。
6. **回滚机制**：关闭实验、切回旧版本、禁用工具、恢复模型别名，支持无需重新部署。
7. **审计治理**：记录变更人、审批人、发布时间、影响范围和每次请求命中的版本。

示例回答：

> 我会把 Prompt 当作可发布资产，而不是代码里的字符串。平台需要存储 Prompt 版本、变量 schema、模型参数和评测报告。发布前先跑黄金样例和安全样例，通过后进入小流量灰度。运行时根据用户或租户稳定分流，解析出具体 Prompt 版本和模型别名。所有请求日志都记录实验组、Prompt 版本、模型版本和 RAG 策略。如果质量下降、格式错误率升高或安全指标异常，可以直接关闭实验或切回上一版本，不需要重新部署服务。

## 五、代码示例：配置解析与回滚

下面是一个简化版配置解析逻辑，重点体现“默认配置 + 租户覆盖 + 实验覆盖 + 紧急开关”的顺序。

```python
from dataclasses import dataclass


@dataclass
class RuntimeConfig:
    prompt_version: str
    model_alias: str
    temperature: float
    rag_top_k: int
    tool_calling_enabled: bool


def resolve_runtime_config(base: dict, tenant_id: str, experiment_variant: str | None) -> RuntimeConfig:
    config = dict(base["default"])

    tenant_config = base.get("tenant_overrides", {}).get(tenant_id)
    if tenant_config:
        config.update(tenant_config)

    if experiment_variant == "candidate":
        config.update(base["experiments"]["refund_prompt_ab_20260522"]["variant"])

    kill_switch = base.get("kill_switch", {})
    if kill_switch.get("disable_tool_calling"):
        # 中文注释：紧急开关优先级最高，用于事故止血
        config["tool_calling_enabled"] = False

    return RuntimeConfig(
        prompt_version=config["prompt_version"],
        model_alias=config["model_alias"],
        temperature=config["temperature"],
        rag_top_k=config["rag_top_k"],
        tool_calling_enabled=config.get("tool_calling_enabled", True),
    )
```

面试时不要纠结代码细节，关键是讲清楚：

- 配置解析顺序要固定。
- 实验覆盖不能绕过安全开关。
- 每次解析结果要写入日志。
- 回滚应该是配置切换，而不是重新发版。

## 六、高频面试问题与参考答案

### 1. Prompt 为什么需要版本管理？

参考答案：

> 因为 Prompt 会直接影响模型行为，本质上是生产逻辑的一部分。没有版本管理，线上出问题时无法定位是哪次改动导致，也无法稳定复现实验结果。Prompt 版本应该记录模板内容、变量 schema、依赖模型、评测结果、发布状态、创建人和回滚目标。

### 2. LLM 应用灰度和普通后端灰度有什么不同？

参考答案：

> 普通后端灰度主要看错误率、延迟和资源指标；LLM 灰度还要看输出质量、事实一致性、格式稳定性、安全拦截、工具调用成功率和成本。LLM 变更可能不报错但质量变差，所以必须有离线评测、线上质量指标和人工抽检。

### 3. 如何设计 Prompt A/B 实验？

参考答案：

> 先定义实验目标和指标，例如任务成功率、人工满意度、格式通过率、成本和延迟。然后用用户、租户或会话 ID 做稳定分流，保证同一主体持续命中同一版本。实验组和对照组只改变一个关键变量，避免无法归因。请求日志记录 experiment_id、variant、prompt_version、model_version。实验前先跑离线评测，高风险场景只做小流量灰度。

### 4. Prompt 改坏了，线上应该怎么止损？

参考答案：

> 先关闭实验或把流量切回旧版本；如果影响范围不清楚，就通过日志查询异常请求命中的 prompt_version、model_alias、rag_policy_version 和 experiment_id。对于安全事故，可以同时启用紧急开关，例如禁用高风险工具或收紧安全策略。止血后再用坏 Case 回放定位原因，并把样例加入回归集。

### 5. 哪些配置变更必须走人工审批？

参考答案：

> 高风险变更必须审批，包括新增外部写操作工具、放宽安全策略、切换未评测模型、修改金融医疗法务类 Prompt、扩大数据访问权限、提高高成本模型流量比例。审批不是形式主义，而是确认风险、影响范围、回滚方案和评测结果。

### 6. 如何避免 A/B 实验污染？

参考答案：

> 使用稳定分流，不要每次请求随机；多轮对话应按 conversation_id 或 user_id 固定版本；实验期间只改变一个主要变量；日志中记录实验组；扩流时注意不要让同一用户在短时间内频繁切组；如果涉及缓存，要把实验版本纳入缓存 key，避免 A 组读到 B 组结果。

### 7. 模型版本切换需要注意什么？

参考答案：

> 要确认新模型是否支持原有能力，例如工具调用、JSON 模式、上下文长度、视觉输入和流式输出。还要比较质量、延迟、成本、安全表现和格式稳定性。切换时最好通过模型别名完成，业务代码依赖别名而不是具体模型名，这样可以灰度和回滚。

### 8. 为什么要在日志里记录 Prompt 版本和实验组？

参考答案：

> 因为 LLM 输出问题通常无法只靠 request_id 定位。必须知道当时命中了哪个 Prompt、模型、RAG 策略、工具配置和安全策略，才能复现问题、归因实验效果、统计版本质量并执行精准回滚。

### 9. 配置中心和代码仓库如何分工？

参考答案：

> 稳定的编排逻辑、解析器和校验器放代码仓库；高频变化的 Prompt、模型参数、RAG 策略、工具开关放配置中心。配置中心要有版本、审批、灰度和审计能力。对于高风险配置，也可以采用 GitOps，让变更通过 Pull Request 审核后同步到配置平台。

### 10. 如何设置上线门禁？

参考答案：

> 门禁应覆盖静态校验、离线评测和运行时指标。比如变量 schema 必须通过、黄金样例通过率超过阈值、敏感信息泄露为 0、JSON 格式通过率超过 98%、P95 延迟和单请求成本不超过预算。不同任务阈值不同，高风险场景要更严格并要求人工审核。

### 11. 如果新 Prompt 质量更好但成本明显上升，怎么决策？

参考答案：

> 不能只看单一指标。要看业务收益是否覆盖成本增加，是否只对高价值用户或高价值任务启用，是否可以通过缓存、上下文裁剪、小模型预处理降低成本。也可以做分层策略：普通请求使用旧版本，高价值或低置信度请求使用新版本。

### 12. 如何处理配置变更和缓存的关系？

参考答案：

> 缓存 key 必须包含会影响输出的关键版本，例如 prompt_version、model_alias、model_version、rag_policy_version、tool_policy_version 和安全策略版本。否则发布新 Prompt 后可能命中旧缓存，导致实验结果污染或用户看到过期答案。

### 13. 发布治理和 LLMOps 有什么关系？

参考答案：

> 发布治理是 LLMOps 的一部分，关注变更如何安全上线；评估与观测提供发布前后的质量判断；数据闭环把线上坏 Case 反馈到评测集；模型网关提供调用治理；配置平台则把 Prompt、参数和策略变成可控的发布资产。

### 14. 什么情况下应该直接回滚，而不是继续观察？

参考答案：

> 出现安全泄露、越权访问、核心格式大面积失败、关键业务任务失败率明显升高、成本失控或投诉激增时应该直接回滚。LLM 应用的风险在于错误内容可能被用户采纳，所以高风险异常不要等统计显著性，先止血。

### 15. 如何向面试官总结一个成熟的 LLM 发布体系？

参考答案：

> 成熟体系应该做到：所有影响模型行为的资产都版本化；发布前有静态校验、离线评测和审批；运行时有稳定分流和配置解析；线上有质量、安全、成本、性能和业务指标；每次请求有完整版本日志；事故时可以不重新部署就关闭实验或回滚配置；坏 Case 会回流到评测集，形成持续改进。

## 七、面试答题模板

如果面试官问“你们怎么管理 LLM 应用上线变更”，可以按这个模板回答：

> 我会先把 LLM 应用的变更分成代码变更和行为配置变更。行为配置包括 Prompt、模型别名、生成参数、RAG 策略、工具配置和安全策略。它们都需要版本化和发布治理。上线前先做变量校验、schema 校验、安全校验和离线评测；通过后按用户、租户或会话稳定灰度。线上观察质量、格式、安全、工具调用、成本和延迟指标。每次请求都记录命中的 Prompt 版本、模型版本、实验组和策略版本。异常时先关闭实验或切回上一版本，不依赖重新部署。最后把线上坏 Case 回流到评测集，防止同类问题复发。

## 八、易错点总结

1. **只把 Prompt 当文本，不做版本管理**：导致无法复现和回滚。
2. **只看 HTTP 成功率**：LLM 可能服务成功但答案错误。
3. **每次请求随机实验分组**：破坏用户体验和指标归因。
4. **实验变量太多**：无法判断到底是 Prompt、模型还是检索策略带来的变化。
5. **日志不记录版本**：线上坏 Case 无法定位。
6. **缓存 key 不包含版本**：新旧策略结果混用。
7. **没有紧急开关**：事故时只能重新部署，止损太慢。
8. **低风险和高风险场景同一套发布规则**：容易在敏感业务中放大风险。
9. **配置覆盖顺序不清晰**：同一请求为什么命中某个版本无法解释。
10. **没有把坏 Case 回流评测集**：同类事故会反复发生。

## 九、记忆口诀

> 版本先行，评测把关；稳定分流，指标护航；日志可追，配置可回；坏案回流，持续变强。
