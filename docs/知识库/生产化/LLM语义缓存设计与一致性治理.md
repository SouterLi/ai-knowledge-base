## 核心概念

### 1. 什么是 LLM 语义缓存

语义缓存是指不只按字符串完全匹配缓存结果，而是把用户问题、标准化后的意图、检索上下文、工具参数或生成结果转换成向量或结构化特征，判断“语义上是否足够相似”，从而复用历史结果。

一句面试表达：**传统缓存解决“同一个 key 重复请求”，语义缓存解决“表达不同但业务语义相近的请求能否安全复用”。**

例如：

```text
问题 A：请总结这份合同里的付款条款
问题 B：帮我概括合同中跟付款相关的约定
```

如果两次请求对应同一份合同、同一版本、同一用户权限、同一输出格式要求，并且语义相似度足够高，就可能复用缓存；如果合同版本、权限、引用来源、模型输出格式或风险等级不同，即使问题很像，也不能直接复用。

### 2. 语义缓存和普通缓存的区别

| 维度 | 普通缓存 | 语义缓存 |
| --- | --- | --- |
| 命中方式 | 精确 key 匹配 | 向量相似度、意图标签、结构化条件共同判断 |
| 主要收益 | 减少重复计算 | 降低 LLM 调用成本、减少延迟、提升高频问题响应稳定性 |
| 主要风险 | 过期数据 | 错误复用、越权复用、引用不一致、旧知识污染 |
| 适用场景 | 配置、字典、固定查询 | FAQ、摘要、分类、低风险问答、标准解释 |
| 不适合场景 | 强实时写操作 | 高风险决策、个性化强、权限复杂、上下文变化快 |

面试中要强调：**语义缓存不是“相似就返回”，而是相似度、业务边界、数据版本、权限和风险等级共同满足后才返回。**

### 3. 语义缓存可以缓存什么

语义缓存不一定只缓存最终答案，常见缓存粒度有四类：

| 缓存对象 | 示例 | 优点 | 风险 |
| --- | --- | --- | --- |
| 查询理解结果 | 意图、槽位、改写 query | 稳定、风险较低 | 上下文变化时意图可能不同 |
| 检索结果 | doc_id、chunk_id、分数 | 降低向量库和 rerank 成本 | 索引版本、ACL、文档更新会影响可用性 |
| 模型最终答案 | FAQ 回答、摘要、解释 | 成本收益最大 | 最容易出现过期、越权和格式不匹配 |
| 工具调用结果 | 只读 API 查询结果 | 可减少外部依赖压力 | 需要 TTL、租户隔离和业务版本 |

实际落地时通常优先缓存 **低风险、可验证、版本边界清晰** 的中间结果，比如查询改写、分类标签、FAQ 答案、只读检索结果；对有真实业务后果的 Agent 写工具结果，不应该用语义缓存替代幂等和事务记录。

### 4. 语义缓存的核心矛盾

语义缓存的核心矛盾是 **命中率、正确性、安全性、时效性** 之间的取舍：

- 阈值太低：命中率高，但容易把相似问题错当成同一问题。
- 阈值太高：安全性更好，但缓存收益不明显。
- TTL 太长：成本低，但知识更新后可能返回旧答案。
- TTL 太短：一致性更好，但缓存穿透严重。
- 只看向量相似：可能忽略租户、权限、索引版本、输出格式等硬约束。

所以一个成熟回答要把语义缓存描述成“带安全门禁的复用系统”，而不是一个简单的向量 top1 查询。

## 核心知识点

### 1. 语义缓存的典型架构

一个可落地的语义缓存链路通常是：

```text
用户请求
  → 输入标准化：脱敏、归一化、提取意图和槽位
  → 构造硬约束：tenant、user/role、场景、索引版本、模型版本、输出格式、风险等级
  → 查询缓存向量库或缓存索引
  → 候选结果相似度过滤
  → 业务条件校验：权限、版本、TTL、引用、结构化 schema
  → 命中则返回缓存并标记 cache_hit
  → 未命中则走正常 LLM/RAG/工具链路
  → 结果质量通过后写入缓存
```

面试重点：**向量相似度只是召回候选，不是最终放行条件。最终放行必须经过确定性的业务校验。**

### 2. 缓存 key 不能只用 Embedding

语义缓存一般需要“软匹配 + 硬约束”：

```text
软匹配：query_embedding 相似度、意图标签、槽位相似度
硬约束：tenant_id、acl_scope、domain、index_version、prompt_version、model_version、output_schema、risk_level
```

如果只把用户问题向量化后查最近邻，会出现几个问题：

1. **跨租户污染**：两个租户问同一个政策问题，但知识库内容不同。
2. **权限泄露**：普通员工命中管理员曾经生成的答案。
3. **版本错配**：知识库、Prompt、模型或输出 Schema 已变更。
4. **引用错误**：答案引用的文档已经删除或用户不可见。
5. **个性化错用**：同一句“我的订单什么时候到”，不同用户对应不同订单。

简化的缓存记录可以这样设计：

```sql
CREATE TABLE llm_semantic_cache (
    cache_id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    scenario TEXT NOT NULL,
    intent TEXT NOT NULL,
    query_embedding VECTOR,
    query_hash TEXT NOT NULL,
    acl_scope_hash TEXT NOT NULL,
    index_version TEXT,
    prompt_version TEXT NOT NULL,
    model_version TEXT NOT NULL,
    output_schema TEXT NOT NULL,
    answer_json JSON NOT NULL,
    citations_json JSON,
    quality_score REAL NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

### 3. 命中判定要分层

推荐把命中判定拆成三层：

| 层级 | 判断内容 | 作用 |
| --- | --- | --- |
| 硬过滤 | 租户、场景、权限、版本、Schema、风险等级 | 先排除一定不能复用的候选 |
| 语义召回 | query embedding、意图、槽位 | 找到表达不同但含义相近的问题 |
| 质量放行 | 相似度阈值、引用可见性、TTL、置信度、人工审核标记 | 决定是否直接返回 |

示例代码：

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass
class CacheCandidate:
    tenant_id: str
    scenario: str
    acl_scope_hash: str
    index_version: str
    prompt_version: str
    model_version: str
    output_schema: str
    risk_level: str
    similarity: float
    quality_score: float
    expires_at: datetime


def can_use_semantic_cache(candidate: CacheCandidate, request: dict) -> bool:
    # 中文注释：先做硬约束校验，避免相似度高但业务边界不同的错误命中
    hard_fields = [
        "tenant_id",
        "scenario",
        "acl_scope_hash",
        "index_version",
        "prompt_version",
        "model_version",
        "output_schema",
        "risk_level",
    ]
    for field in hard_fields:
        if getattr(candidate, field) != request[field]:
            return False

    # 中文注释：高风险场景不直接使用语义缓存返回最终答案
    if candidate.risk_level in {"high", "critical"}:
        return False

    if candidate.expires_at <= datetime.utcnow():
        return False

    return candidate.similarity >= 0.92 and candidate.quality_score >= 0.85
```

面试追问“阈值怎么定”时，不要只说拍脑袋设 0.9。更合理的回答是：先用历史请求构造正负样本，离线看 precision、recall、误命中案例和节省成本，再按场景分阈值；高风险场景阈值更高或不直接命中，低风险 FAQ 可以适当放宽。

### 4. RAG 场景下的缓存一致性

RAG 里语义缓存最容易踩坑，因为答案依赖知识库版本和引用文档。需要处理：

1. **索引版本绑定**：缓存记录绑定 `index_version` 或 `doc_version_set`，知识库重建后旧缓存不能无条件命中。
2. **引用可见性校验**：命中前重新校验 citation 的 doc_id/chunk_id 对当前用户是否可见。
3. **证据有效性校验**：引用文档删除、过期、撤权时，缓存答案应失效或降级为重新检索。
4. **增量更新失效**：某文档更新后，只失效依赖该文档的缓存，而不是全量清空。
5. **答案与证据一致**：缓存答案不能脱离引用单独复用，否则容易出现“答案对不上出处”。

一个常见做法是保存答案依赖的文档集合：

```json
{
  "cache_id": "cache_001",
  "depends_on": [
    {"doc_id": "policy_2026", "chunk_id": "c12", "doc_version": "v3"},
    {"doc_id": "faq_refund", "chunk_id": "c08", "doc_version": "v7"}
  ]
}
```

当 `policy_2026` 从 `v3` 更新到 `v4` 时，只需要失效依赖 `policy_2026@v3` 的缓存记录。

### 5. Agent 场景下慎用语义缓存

Agent 场景中要区分“可缓存的推理辅助结果”和“不能缓存替代的副作用”：

| Agent 环节 | 是否适合语义缓存 | 说明 |
| --- | --- | --- |
| 意图识别 | 适合 | 同类任务可复用分类结果 |
| 工具选择建议 | 谨慎适合 | 必须结合当前权限和工具可用性 |
| 只读工具结果 | 部分适合 | 需要 TTL、租户、用户和业务对象版本 |
| 写工具执行结果 | 不适合 | 应使用幂等键、执行记录、审批和补偿 |
| 多步计划 | 谨慎适合 | 只适合模板化计划，不能跳过当前状态校验 |

面试表达：**Agent 的语义缓存最多帮助减少推理和只读查询成本，不能替代工具执行层的幂等、权限、审批和审计。**

### 6. 缓存写入也要有质量门槛

不是所有 LLM 输出都应该进缓存。建议设置写入条件：

- 响应成功且结构化解析通过。
- RAG 引用完整，且引用对当前租户可见。
- 低风险或人工审核通过。
- 没有包含敏感个人信息、临时 token、一次性链接。
- 质量评分或用户反馈达到阈值。
- 输出依赖的 Prompt、模型、索引版本可追踪。

写入策略示例：

```python
def should_write_cache(response: dict, context: dict) -> bool:
    # 中文注释：缓存写入要宁缺毋滥，避免把坏答案放大成稳定错误
    if not response.get("ok"):
        return False
    if not response.get("schema_valid"):
        return False
    if context["risk_level"] in {"high", "critical"}:
        return False
    if response.get("contains_sensitive_data"):
        return False
    if context["scenario"] == "rag" and not response.get("citations_verified"):
        return False
    return response.get("quality_score", 0) >= 0.85
```

### 7. 失效策略要组合使用

语义缓存通常不能只靠 TTL，需要组合失效：

| 失效方式 | 适用场景 | 面试关注点 |
| --- | --- | --- |
| TTL | FAQ、摘要、低风险解释 | 简单但不精确 |
| 版本失效 | Prompt、模型、索引、Schema 变更 | 最常见、最可控 |
| 依赖失效 | RAG 文档更新、权限变更 | 需要记录 depends_on |
| 事件失效 | 商品价格、订单状态、合同状态变化 | 由业务事件驱动 |
| 人工失效 | 发现坏 Case 或投诉 | 需要运营后台和审计 |

面试中可以补一句：**对高价值企业知识库，TTL 是兜底，不是主要一致性手段；主策略应该是版本和依赖失效。**

### 8. 语义缓存的评估指标

语义缓存上线前后要看两类指标：

| 指标 | 说明 |
| --- | --- |
| cache_hit_rate | 命中率，体现成本和延迟收益 |
| safe_hit_rate | 通过业务校验后的安全命中率，比原始命中率更重要 |
| false_hit_rate | 错误命中率，必须重点压低 |
| cost_saved_per_1k_requests | 每千次请求节省的模型和检索成本 |
| latency_saved_ms | 命中后节省的 P50/P95 延迟 |
| stale_answer_rate | 过期答案比例 |
| permission_reject_rate | 因权限或版本不匹配被拒绝的候选比例 |
| user_correction_rate | 命中缓存后用户追问、纠错或点踩比例 |

面试重点：**语义缓存不能只汇报命中率。命中率升高但 false hit 上升，实际是在把错误规模化。**

### 9. 常见反模式

1. **只看向量 top1**：相似度高不等于业务可复用。
2. **跨租户共享最终答案**：可能泄露数据或业务规则。
3. **知识库更新后不失效**：容易返回旧政策、旧价格、旧流程。
4. **缓存包含敏感信息**：用户隐私、订单号、临时链接进入公共缓存。
5. **把缓存当兜底答案**：上游故障时直接返回旧答案，但不提示低置信或过期风险。
6. **没有缓存命中 Trace**：出现坏 Case 时无法判断是模型错、检索错还是缓存错。

## 高频面试问题与标准答案

**Q1：什么是 LLM 语义缓存？和普通缓存有什么区别？**

标准答案：语义缓存不是按原始字符串完全匹配，而是通过 Embedding、意图、槽位等方式判断两个请求是否语义接近，再结合租户、权限、知识库版本、Prompt 版本、输出格式等硬约束决定能否复用。普通缓存重点解决同一个 key 的重复请求，语义缓存解决表达不同但业务含义相近的请求复用。它的收益是降低成本和延迟，但风险是错误复用、越权复用和过期答案，所以不能只看相似度。

**Q2：如果两个问题相似度 0.95，能不能直接返回缓存？**

标准答案：不能直接返回。0.95 只能说明语义上很像，还要检查租户、用户权限、业务场景、知识库版本、Prompt 和模型版本、输出 Schema、TTL、引用是否仍可见，以及这个场景是不是高风险。如果是低风险 FAQ，并且这些条件都一致，可以命中；如果是合同、订单、医疗、金融或权限相关问题，即使相似度高，也应该重新检索、要求确认或走人工审核。

**Q3：语义缓存的阈值怎么定？**

标准答案：我不会只凭经验拍一个 0.9。通常先用历史请求构造正负样本，比如同义问法作为正样本、相似但答案不同的问题作为 hard negative，然后离线评估不同阈值下的 precision、recall、false hit 和成本节省。上线时按场景分阈值，低风险 FAQ 可以低一点，高风险业务问题要更高甚至不直接命中。灰度阶段重点看误命中、点踩率、追问率和人工抽检结果。

**Q4：RAG 系统里做语义缓存，怎么避免返回过期答案？**

标准答案：我会让缓存记录绑定索引版本、文档版本和引用 chunk。命中前重新校验当前用户是否还能访问这些引用，文档是否还是同一版本。如果知识库增量更新，就根据 depends_on 失效依赖相关文档的缓存，而不是只靠 TTL。TTL 可以作为兜底，但企业知识库里主要还是靠版本失效、依赖失效和权限校验。

**Q5：语义缓存会不会造成越权？怎么防？**

标准答案：会，如果只按问题相似度查缓存，很容易跨租户或跨权限复用答案。防法是缓存候选召回前后都加租户和权限边界，至少要有 tenant_id、acl_scope_hash、role 或可见文档集合；最终答案命中前还要校验引用是否对当前用户可见。对于包含个人信息、订单信息、合同信息的结果，通常不放公共语义缓存，最多做用户级或会话级缓存，并设置更短 TTL。

**Q6：哪些 LLM 场景适合语义缓存，哪些不适合？**

标准答案：适合低风险、高频、答案相对稳定的场景，比如 FAQ、政策解释、固定分类、查询改写、摘要模板、只读工具查询。不适合强个性化、实时状态、高风险决策和写操作，比如退款、转账、改权限、医疗建议、订单实时状态。我的原则是：可以缓存推理辅助结果和低风险答案，但不能用语义缓存替代权限校验、幂等和业务实时查询。

**Q7：语义缓存命中了，但用户说答案不对，你怎么排查？**

标准答案：先用 request_id 查 Trace，确认这次是缓存命中还是正常生成；如果命中，看命中的 cache_id、相似度、阈值、硬约束、索引版本、引用文档和 TTL。然后判断是阈值过低、问题语义相似但答案不同、知识库更新未失效、权限校验漏了，还是原始缓存答案质量就有问题。修复上会先拉黑或失效这条缓存，再把样本加入 hard negative 或回归集，必要时调整阈值和写入门槛。

**Q8：语义缓存和 Prompt 缓存、KV Cache 是一回事吗？**

标准答案：不是。Prompt 缓存通常是模型服务侧对相同前缀 token 的复用，KV Cache 是推理过程中的注意力状态缓存，主要优化推理性能。语义缓存是应用层缓存，判断相似请求能否复用结果或中间产物，重点是业务正确性、权限、版本和时效性。三者可以同时存在，但解决的问题和风险完全不同。

**Q9：语义缓存写入时要注意什么？**

标准答案：写入要比读取更保守。只有结构化解析通过、引用校验通过、质量分达标、低风险或人工审核通过、没有敏感信息，并且 Prompt、模型、索引版本可追踪时才写入。否则一个坏答案被缓存后，会从一次错误变成多次稳定错误。生产里还要记录 cache_id、命中原因和依赖文档，方便回放和失效。

**Q10：如果面试官让你设计一个语义缓存系统，你会怎么回答？**

标准答案：我会先划定适用场景，只对低风险、高频、答案稳定的请求启用。架构上先做输入标准化和意图识别，再用租户、权限、场景、版本、Schema 做硬过滤，用 Embedding 做候选召回，最后用相似度、TTL、引用可见性和质量分做放行。RAG 场景要绑定文档版本和引用，Agent 场景不能缓存写工具结果。上线时灰度观察 safe hit rate、false hit rate、成本节省和用户纠错率，发现坏 Case 后能按 cache_id 精准失效并进入回归集。
