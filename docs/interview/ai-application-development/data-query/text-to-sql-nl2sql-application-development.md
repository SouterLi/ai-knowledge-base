## 一、为什么这是高频考点

企业里大量数据仍然在关系型数据库、数仓和 BI 系统中。业务方希望直接问：

> “上周新用户留存率环比下降最多的是哪个渠道？”

系统需要理解业务指标、表结构、时间口径、权限范围，并生成正确、可控、可审计的 SQL。面试官问 Text-to-SQL，通常不是考“能不能让模型写 SQL”，而是看你是否知道：

1. 不能把全库 Schema 一股脑塞进 Prompt。
2. 不能相信模型生成的 SQL 可以直接执行。
3. 指标口径必须通过语义层或指标层治理。
4. SQL 正确性要用执行结果、语义等价和业务验收一起评估。
5. 上线后要处理权限、慢查询、方言差异、数据泄露和多轮追问。

一句话回答：

> Text-to-SQL 是把用户自然语言问题转换为数据库查询的 AI 应用能力。工程重点不是“生成一段 SQL”，而是通过语义层、Schema Linking、SQL 校验、权限控制、执行沙箱和评测体系，让 SQL 可解释、可执行、可治理。

## 二、核心概念

### 1. Text-to-SQL 与 NL2SQL

Text-to-SQL 和 NL2SQL 通常可以混用，指从自然语言生成 SQL 的过程。典型链路如下：

```text
用户问题
  -> 意图识别与澄清
  -> 相关表和字段召回
  -> 业务指标与维度匹配
  -> 生成候选 SQL
  -> SQL 语法与安全校验
  -> 试执行或 Explain
  -> 结果解释与可视化
```

面试要点：Text-to-SQL 不是独立模型能力，而是一个数据应用系统，需要连接数据目录、权限系统、查询引擎、指标平台和评测平台。

### 2. Schema Linking

Schema Linking 是把用户问题中的业务词映射到数据库对象的过程。

| 用户表达 | 可能映射 | 风险 |
| --- | --- | --- |
| 新用户 | `dim_user.first_order_date` 或 `user_signup_date` | 口径不一致 |
| 渠道 | `channel_id`、`utm_source`、`sales_channel` | 同名异义 |
| 留存率 | 指标公式，不是单字段 | 需要指标层 |
| 上周 | 自然语言时间范围 | 时区和周起始日 |

高分回答：

> Text-to-SQL 的难点不是 SQL 语法，而是 Schema Linking。模型必须知道业务词和物理表字段之间的映射关系，否则 SQL 语法正确也可能业务含义错误。

### 3. 语义层

语义层把物理表字段封装成业务可理解的指标、维度、过滤条件和口径。

```yaml
metrics:
  retention_rate_7d:
    name: 7日留存率
    expression: retained_users_7d / new_users
    dimensions:
      - channel
      - signup_date
    filters:
      - is_test_user = false
```

语义层的价值：

- 统一指标口径，避免模型临时“发明公式”。
- 缩小生成空间，让模型面向指标和维度生成查询计划。
- 支持权限和血缘治理。
- 便于评测集复用和回归测试。

### 4. SQL 方言

MySQL、PostgreSQL、BigQuery、Snowflake、ClickHouse、Hive 的函数、日期处理、分页、窗口函数语法都不完全一样。

面试中要强调：

- Prompt 或系统配置必须明确 SQL dialect。
- 方言转换不能只靠字符串替换，最好基于 AST 或查询构建器。
- 评测时要按目标查询引擎执行，而不是只看模型输出文本。

### 5. 查询安全

Text-to-SQL 的安全边界不应放在 Prompt 中，而应放在执行前的服务端校验和数据库权限中。

必须限制：

- DDL：`CREATE`、`DROP`、`ALTER`。
- DML：`INSERT`、`UPDATE`、`DELETE`、`MERGE`。
- 高危函数：文件读取、外部网络访问、系统函数。
- 跨租户表、敏感字段、未授权行。
- 无限制全表扫描和超大结果集。

## 三、推荐架构

### 1. 生产级链路

```text
前端对话入口
  -> 查询意图识别
  -> 数据目录 / 语义层检索
  -> Prompt 构造器
  -> LLM 生成候选 SQL
  -> SQL Parser / AST 校验
  -> 权限注入与查询改写
  -> Explain / Dry Run
  -> 查询执行
  -> 结果解释、图表建议、审计日志
```

各模块职责：

| 模块 | 关键职责 | 面试关注点 |
| --- | --- | --- |
| 数据目录 | 表、字段、样例值、血缘、负责人 | 避免全量 Schema 进 Prompt |
| 语义层 | 指标、维度、过滤口径 | 防止指标口径漂移 |
| Prompt 构造器 | 拼接任务、约束、相关 Schema | 控制上下文质量 |
| SQL 校验器 | 语法、只读、表白名单、字段权限 | Prompt 不是安全边界 |
| 查询执行器 | 超时、限流、Explain、结果截断 | 防慢查询和资源滥用 |
| 评测系统 | SQL 正确率、执行正确率、业务验收 | 不能只看 BLEU 或文本相似度 |

### 2. 不推荐的简化方案

```text
用户问题 + 全库 DDL -> LLM -> 直接执行 SQL
```

问题：

1. Prompt 过长，成本和延迟高。
2. 表字段太多，模型容易选错。
3. SQL 可能越权、慢查询或破坏数据。
4. 指标公式由模型临时生成，难以审计。
5. 出错后无法定位是 Schema Linking、SQL 生成还是执行阶段问题。

## 四、核心知识点

### 1. 如何选择相关表和字段

常见做法是多路召回：

1. **关键词召回**：根据表名、字段名、注释、指标名匹配。
2. **向量召回**：把表描述、字段描述、历史查询 embedding 化。
3. **血缘召回**：从指标关联到事实表和维表。
4. **历史样例召回**：找相似问题和对应 SQL。
5. **权限过滤**：召回后先过滤用户无权访问的数据对象。

面试表达：

> 先召回候选 Schema，再让模型做选择和 SQL 生成。不能把全库 DDL 给模型，否则效果、成本、安全都会失控。

### 2. Prompt 应该包含什么

一个实用 Prompt 通常包含：

- 目标 SQL 方言。
- 用户问题和当前时间。
- 相关表字段、字段注释、枚举值样例。
- 可用指标和维度定义。
- 强约束：只读查询、必须加租户过滤、默认限制行数。
- 输出格式：SQL、解释、使用到的表字段、风险提示。

示例：

```text
你是数据分析 SQL 生成器。
SQL 方言：PostgreSQL。
要求：
1. 只能生成 SELECT 查询。
2. 必须使用给定表和字段，不能编造字段。
3. 必须添加 tenant_id = :tenant_id。
4. 默认 LIMIT 200，除非用户明确要求聚合结果。
5. 如果问题缺少关键口径，返回 need_clarification。

可用指标：
- paid_conversion_rate = paid_users / active_users

可用表：
- dws_user_daily(user_id, tenant_id, dt, channel, is_active, is_paid)

用户问题：最近 7 天各渠道付费转化率是多少？
```

### 3. SQL 校验不要靠正则

正则可以做初步拦截，但不能作为主要安全机制。更可靠的方式是解析 SQL AST。

```python
def validate_sql(ast, allowed_tables, allowed_columns):
    # 只允许单条 SELECT，禁止写操作
    if ast.statement_type != "SELECT":
        raise ValueError("只允许 SELECT 查询")

    used_tables = ast.collect_tables()
    for table in used_tables:
        # 表级权限必须在服务端校验，不能相信模型声明
        if table not in allowed_tables:
            raise PermissionError(f"无权访问表: {table}")

    used_columns = ast.collect_columns()
    for table, column in used_columns:
        # 字段级权限用于保护手机号、身份证、收入等敏感字段
        if column not in allowed_columns.get(table, set()):
            raise PermissionError(f"无权访问字段: {table}.{column}")
```

面试要点：

- 解析 AST 后判断语句类型、表、字段、函数、子查询。
- 禁止多语句执行。
- 对表名、字段名做白名单校验。
- 对敏感字段做脱敏或拒绝。
- 最终仍要依赖数据库账号权限和行级权限。

### 4. 权限注入与查询改写

常见做法是在 SQL 生成后、执行前统一注入权限条件。

```sql
SELECT
  channel,
  COUNT(DISTINCT CASE WHEN is_paid THEN user_id END) * 1.0
    / NULLIF(COUNT(DISTINCT CASE WHEN is_active THEN user_id END), 0) AS paid_conversion_rate
FROM dws_user_daily
WHERE dt >= CURRENT_DATE - INTERVAL '7 days'
  AND tenant_id = :tenant_id -- 服务端注入租户隔离条件
GROUP BY channel
ORDER BY paid_conversion_rate DESC
LIMIT 200;
```

注意：

- 租户、部门、数据域权限最好由服务端统一改写，不要只靠 Prompt 要求模型生成。
- 对复杂 SQL，权限条件注入要基于 AST，避免错误注入到子查询或破坏语义。
- 数据库层仍应配置 RLS、视图或专用只读账号，形成双保险。

### 5. 查询成本控制

Text-to-SQL 容易生成“语法正确但很贵”的 SQL。上线必须控制查询成本。

常见手段：

- 执行前 `EXPLAIN` 或 Dry Run，估算扫描行数和数据量。
- 默认加 `LIMIT`，聚合查询限制维度基数。
- 禁止无分区过滤的大表查询。
- 设置查询超时和队列隔离。
- 根据用户等级或租户设置资源配额。
- 对重复问题和稳定指标做结果缓存。

面试表达：

> 生成 SQL 只是第一步，真正上线要把查询引擎当成有限资源治理，避免模型把数据库打爆。

### 6. 多轮追问

数据问答经常是多轮的：

1. “最近 7 天 GMV 多少？”
2. “按渠道拆一下。”
3. “只看华东区域。”
4. “和上周比呢？”

系统需要维护分析上下文：

- 上一轮使用的指标。
- 时间范围。
- 过滤条件。
- 分组维度。
- 结果表或临时查询。

但要避免把历史 SQL 直接拼接给模型执行。更好的方式是维护结构化查询状态：

```json
{
  "metric": "gmv",
  "time_range": "last_7_days",
  "dimensions": ["channel"],
  "filters": {
    "region": "华东"
  },
  "comparison": "previous_period"
}
```

然后由查询构建器重新生成 SQL。

### 7. 错误修复循环

模型第一次生成的 SQL 可能失败。常见修复流程：

```text
生成 SQL
  -> 语法校验失败：把错误类型和相关 Schema 返回给模型修复
  -> Explain 失败：根据数据库错误修复方言或字段
  -> 执行失败：区分权限、超时、字段不存在、类型不匹配
  -> 结果异常：触发澄清、口径提示或人工标注
```

注意不要把完整数据库错误直接暴露给用户或模型，避免泄露内部表结构和权限信息。

## 五、评测方法

### 1. 常见指标

| 指标 | 含义 | 局限 |
| --- | --- | --- |
| Exact Match | 生成 SQL 文本和标准答案完全一致 | SQL 等价写法很多，过于严格 |
| Execution Accuracy | 执行结果是否一致 | 结果碰巧一致不代表语义正确 |
| Valid SQL Rate | SQL 能否解析和执行 | 能执行不代表业务口径正确 |
| Schema Linking Accuracy | 表字段选择是否正确 | 需要标注中间过程 |
| Business Acceptance Rate | 业务人员是否认可结果 | 成本高，但最贴近上线效果 |
| Clarification Rate | 缺口径时能否主动追问 | 需要区分该问和不该问 |

### 2. 面试推荐回答

> Text-to-SQL 评测不能只看 SQL 字符串相似度。我会分层评测：先看 SQL 是否可解析、是否只读、是否命中正确表字段；再看执行结果是否和标准答案一致；最后用业务 Case 验证指标口径是否正确。线上还要监控失败率、慢查询率、澄清率、人工纠错率和高风险拦截率。

### 3. 评测集设计

评测集要覆盖：

- 简单单表查询。
- 多表 Join。
- 聚合、排序、TopN。
- 时间范围和同比环比。
- 指标口径查询。
- 需要澄清的问题。
- 权限拒绝问题。
- 方言差异问题。
- 高基数维度和慢查询风险。

示例：

```json
{
  "question": "上周各渠道新用户 7 日留存率是多少？",
  "expected_tables": ["dws_user_retention_daily"],
  "expected_metrics": ["retention_rate_7d"],
  "must_have_filters": ["tenant_id", "signup_date"],
  "expected_behavior": "generate_sql"
}
```

## 六、常见面试问题与参考答案

### Q1：Text-to-SQL 最大难点是什么？

**参考答案：**

最大难点不是 SQL 语法，而是业务语义到物理 Schema 的映射。用户说“新用户”“留存”“渠道”，数据库里可能有多个字段和多种口径。如果没有数据目录、语义层和指标治理，模型很容易生成语法正确但业务错误的 SQL。工程上要做 Schema Linking、指标层约束、权限过滤和执行校验。

### Q2：为什么不能把整个数据库 Schema 都放进 Prompt？

**参考答案：**

原因有四个：

1. 上下文太长，成本和延迟高。
2. 干扰信息太多，模型更容易选错表字段。
3. 可能泄露用户无权访问的表和字段。
4. Schema 变化后 Prompt 维护困难。

更好的做法是通过数据目录、向量召回、关键词召回和权限过滤，选出少量相关表字段再生成 SQL。

### Q3：如何防止模型生成危险 SQL？

**参考答案：**

不能只靠 Prompt。要在服务端做多层防护：

- 使用 SQL Parser 解析 AST，只允许单条 `SELECT`。
- 禁止 DDL、DML、高危函数和多语句。
- 表、字段、函数白名单。
- 执行前注入租户和行级权限条件。
- 使用只读数据库账号。
- 执行前 `EXPLAIN` 或 Dry Run，限制扫描量和超时。
- 记录审计日志，便于追责和回放。

### Q4：Text-to-SQL 和 RAG 有什么关系？

**参考答案：**

两者可以结合，但目标不同。RAG 主要从非结构化或半结构化文档中检索上下文，Text-to-SQL 面向结构化数据库生成查询。Text-to-SQL 可以用 RAG 召回相关表、字段、指标定义和历史 SQL，但最终还要经过 SQL 校验、权限控制和查询执行。

### Q5：语义层为什么重要？

**参考答案：**

因为企业指标有固定口径。没有语义层时，模型可能临时编公式，比如把“活跃用户”理解成登录用户，也可能理解成有交易用户。语义层把指标、维度、过滤条件、时间口径和权限封装起来，让模型围绕受控对象生成查询，减少口径漂移，也方便评测和审计。

### Q6：如何处理模型生成 SQL 后执行报错？

**参考答案：**

先分类错误：语法错误、字段不存在、类型不匹配、权限错误、超时、方言不兼容。语法和方言问题可以把脱敏后的错误信息、相关 Schema 和原 SQL 交给模型修复；权限错误不能让模型绕过，而应直接拒绝或提示无权限；超时问题要改写查询、增加分区过滤或让用户缩小范围。

### Q7：如何评估 Text-to-SQL 系统效果？

**参考答案：**

离线看 SQL 可执行率、执行结果准确率、表字段命中率、澄清准确率和安全拦截率。线上看查询成功率、慢查询率、用户采纳率、人工纠错率、重复提问率和高风险 SQL 拦截。SQL 文本完全一致不是核心指标，因为不同 SQL 可能语义等价。

### Q8：多轮数据问答怎么做？

**参考答案：**

不要只把历史对话拼进 Prompt。更稳的方式是维护结构化查询状态，包括指标、时间范围、过滤条件、分组维度、排序和比较方式。用户追问时更新状态，再重新生成 SQL。这样更容易解释、校验和回放，也能避免历史 SQL 被错误继承。

### Q9：如何处理“上周”“最近一个月”这类时间表达？

**参考答案：**

系统要明确当前时间、业务时区、周起始日和数据延迟。例如“上周”在中国业务里通常是周一到周日，但在部分海外业务可能以周日开始。时间解析最好由服务端确定成结构化范围，再传给模型或查询构建器，避免模型每次自行解释。

### Q10：如何防止 Text-to-SQL 泄露敏感数据？

**参考答案：**

要做字段分级和权限控制。手机号、身份证、邮箱、收入等字段默认不暴露给模型和普通用户。即使用户问到了，也要拒绝、脱敏或走审批流程。服务端要在 Schema 召回阶段过滤敏感字段，在 SQL 校验阶段拦截未授权字段，数据库层再用只读账号、视图或行列级权限兜底。

### Q11：什么时候需要向用户澄清，而不是直接生成 SQL？

**参考答案：**

当问题缺少关键口径时要澄清，例如“活跃用户”没有定义、“最近”没有时间范围、“转化率”没有分子分母、“收入”没有含税或退款口径。如果只是字段映射有多个候选，也可以给出选项让用户确认。澄清比生成错误 SQL 更可靠。

### Q12：如何设计 Text-to-SQL 的上线灰度？

**参考答案：**

先从低风险只读分析场景开始，只开放少量数据集和指标。灰度期间默认展示 SQL 和解释，不自动执行高成本查询；记录用户采纳、修改和反馈。对高频问题沉淀标准样例和缓存结果。等评测集和安全拦截稳定后，再扩大到更多业务域。

## 七、面试回答模板

如果面试官让你设计一个 Text-to-SQL 系统，可以按这个结构回答：

1. **入口层**：用户输入问题，系统识别是否是数据查询意图，缺口径时先澄清。
2. **语义层**：通过数据目录和指标平台召回相关表、字段、指标和历史 SQL。
3. **生成层**：Prompt 中只放相关 Schema、SQL 方言、业务约束和输出格式。
4. **校验层**：用 SQL Parser 做 AST 校验，限制只读、白名单、权限和高危函数。
5. **执行层**：执行前 Explain，限制扫描量、超时、结果行数和租户隔离。
6. **反馈层**：把 SQL、结果、解释、错误和用户反馈写入日志，用于评测和数据闭环。

高分收尾：

> 我不会把 Text-to-SQL 当成“模型写 SQL”来做，而会把它当成数据平台能力。模型负责理解和生成候选查询，系统负责语义约束、安全校验、权限治理、执行控制和持续评测。

## 八、速记清单

- Text-to-SQL 的核心难点是业务语义，不是 SQL 语法。
- 全库 Schema 进 Prompt 是反模式。
- 语义层负责统一指标、维度、过滤和权限口径。
- Schema Linking 决定表字段是否选对。
- Prompt 不是安全边界，SQL 执行前必须 AST 校验。
- 只允许只读查询，数据库账号也必须只读。
- 租户和行级权限由服务端注入，不要依赖模型自觉。
- 慢查询治理要有 Explain、超时、扫描量限制和结果截断。
- 评测看执行正确率、业务口径、权限拦截和用户采纳，不只看文本相似度。
- 多轮追问应维护结构化查询状态，而不是简单拼历史 SQL。
