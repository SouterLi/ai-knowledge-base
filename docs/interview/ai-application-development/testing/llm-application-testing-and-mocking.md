## 一、为什么这是高频考点

LLM 应用不是传统后端接口，也不是单纯调用一个模型 API。它通常包含 Prompt、模型、检索、工具调用、外部系统、流式输出、缓存和人工审核。面试官问测试策略时，重点不是“会不会写单元测试”，而是看你是否知道：

1. LLM 输出天然非确定，不能只用字符串完全匹配。
2. 单元测试不能每次都真实调用大模型，否则成本高、速度慢、结果不稳定。
3. Prompt、Tool Schema、检索上下文、模型参数都属于可测试契约。
4. 线上坏 Case 应该沉淀为回归样例，避免同类问题反复出现。
5. 不同层级的测试要隔离变量，否则失败时无法定位是模型、Prompt、检索还是业务代码的问题。

一句话回答：

> LLM 应用测试的核心是把不可控的模型输出拆成可控的工程边界：对业务逻辑做确定性单元测试，对模型调用做 Mock 和契约测试，对关键链路做黄金样例回放，对高风险场景做离线评测和人工抽检。

## 二、核心概念

### 1. 测试金字塔在 LLM 应用中的变化

传统测试金字塔强调：单元测试多、集成测试适中、端到端测试少。LLM 应用仍然适用，但需要重新定义每层的边界。

```text
端到端回放测试：真实 Prompt + 真实检索 + 可选真实模型
集成测试：真实业务编排 + Mock 模型或 Mock 工具
契约测试：Prompt 输入输出、Tool Schema、结构化响应协议
单元测试：解析、校验、权限、路由、重试、缓存等确定性逻辑
```

面试要点：

- 不要把所有测试都压到真实模型调用上。
- 越靠近底层，越要确定、快速、低成本。
- 越靠近端到端，越关注真实质量，但数量要受控。

### 2. Mock、Stub、Fake 的区别

| 类型 | 作用 | LLM 应用例子 |
| --- | --- | --- |
| Stub | 返回固定结果 | 模型客户端固定返回一段 JSON |
| Mock | 验证调用行为 | 检查是否传入正确 model、temperature、tools |
| Fake | 可运行的轻量实现 | 本地向量库、内存版工具注册表 |
| Replay | 回放历史响应 | 用录制的模型响应替代真实 API |

高分回答：

> Mock 不是为了假装模型没问题，而是为了隔离变量。测试业务编排时 Mock 模型；测试 Prompt 效果时固定检索上下文；测试工具执行时 Mock 外部系统。

### 3. 黄金样例

黄金样例是经过人工确认、能代表关键业务场景的测试输入与期望结果。

```json
{
  "id": "refund_policy_001",
  "input": "企业客户如何申请退款？",
  "expected_facts": ["提交退款申请", "财务审核", "原路退回"],
  "forbidden_facts": ["直接联系数据库管理员"],
  "tags": ["客服", "退款", "高频问题"]
}
```

黄金样例不一定要求逐字匹配，而是检查：

- 必须包含的事实点是否出现。
- 禁止出现的错误内容是否缺失。
- 输出格式是否符合协议。
- 工具调用路径是否正确。

### 4. 契约测试

LLM 应用的契约不只包括 HTTP API，还包括：

- Prompt 模板变量是否完整。
- 模型输出 JSON Schema 是否稳定。
- Function Calling 参数是否符合工具定义。
- 检索返回字段是否满足 Prompt 依赖。
- 错误码、重试、降级语义是否一致。

示例：结构化输出契约。

```json
{
  "type": "object",
  "required": ["answer", "confidence", "citations"],
  "properties": {
    "answer": { "type": "string" },
    "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
    "citations": {
      "type": "array",
      "items": { "type": "string" }
    }
  }
}
```

面试要点：只要下游系统依赖某种字段、格式或调用行为，它就是契约，必须测试。

## 三、核心知识点

### 1. 哪些逻辑必须做确定性单元测试

LLM 应用里有很多部分不依赖模型，应该用普通单元测试覆盖：

- Prompt 变量渲染：变量缺失、转义、多语言模板。
- 响应解析：JSON 修复、Schema 校验、字段默认值。
- 权限判断：用户是否可访问某个知识库、工具或数据源。
- 路由逻辑：大模型、小模型、降级模型选择。
- 重试逻辑：超时、限流、临时错误的退避策略。
- 缓存逻辑：缓存键、命中条件、过期策略。
- 工具参数校验：类型、范围、必填字段、危险参数过滤。

示例：测试工具调用参数校验。

```python
def validate_search_args(args):
    if not args.get("query"):
        raise ValueError("query 不能为空")
    limit = args.get("limit", 5)
    if limit < 1 or limit > 20:
        raise ValueError("limit 必须在 1 到 20 之间")
    return {"query": args["query"], "limit": limit}


def test_validate_search_args_rejects_empty_query():
    try:
        validate_search_args({"query": "", "limit": 5})
        assert False, "应该拒绝空查询"
    except ValueError as error:
        assert "query 不能为空" in str(error)


def test_validate_search_args_adds_default_limit():
    result = validate_search_args({"query": "退款政策"})
    assert result == {"query": "退款政策", "limit": 5}
```

面试回答要强调：能确定的部分不要交给模型测试，先把工程逻辑测稳。

### 2. 如何 Mock 模型客户端

推荐把模型调用封装成接口，不要在业务代码里直接调用 SDK。

```python
class LLMClient:
    def chat(self, messages, tools=None, temperature=0):
        raise NotImplementedError


class FakeLLMClient(LLMClient):
    def __init__(self, response):
        self.response = response
        self.calls = []

    def chat(self, messages, tools=None, temperature=0):
        # 记录调用参数，方便测试 Prompt 和工具声明是否正确
        self.calls.append({
            "messages": messages,
            "tools": tools,
            "temperature": temperature,
        })
        return self.response
```

业务测试示例：

```python
def answer_question(llm, question):
    response = llm.chat(
        messages=[
            {"role": "system", "content": "你是企业知识库助手，只能基于已知信息回答。"},
            {"role": "user", "content": question},
        ],
        temperature=0,
    )
    return response["content"]


def test_answer_question_uses_low_temperature():
    llm = FakeLLMClient({"content": "请提交退款申请并等待财务审核。"})

    answer = answer_question(llm, "怎么退款？")

    assert "退款申请" in answer
    assert llm.calls[0]["temperature"] == 0
    assert llm.calls[0]["messages"][0]["role"] == "system"
```

这里测的不是模型能力，而是业务代码是否正确构造请求。

### 3. 如何测试 Prompt

Prompt 测试分三类：

1. **模板测试**：变量是否完整、是否有注入风险、是否包含关键约束。
2. **样例回归测试**：固定输入下，输出必须满足事实点和格式要求。
3. **对抗测试**：输入包含提示注入、越权请求、恶意格式时是否拒绝。

不要只断言整段文本完全相等，可以用更稳定的断言：

```python
def assert_answer_quality(answer):
    assert "退款申请" in answer
    assert "财务审核" in answer
    assert "数据库管理员" not in answer
    assert len(answer) <= 300
```

对结构化输出，优先用 JSON Schema 或 Pydantic 校验，而不是肉眼看字符串。

### 4. 如何测试 Tool Calling

Tool Calling 常见失败点：

- 选错工具。
- 参数字段名错误。
- 参数值越权或不合法。
- 工具执行失败后没有恢复策略。
- 模型连续重复调用同一个失败工具。

测试重点：

```text
用户问题：帮我查一下订单 A1001 的物流状态
期望行为：
1. 调用 get_order_shipping_status
2. 参数 order_id = A1001
3. 不调用 refund_order
4. 工具失败时返回可理解的错误，不编造物流结果
```

示例断言：

```python
def test_agent_calls_shipping_tool():
    fake_tool_result = {"status": "运输中", "carrier": "顺丰"}
    tool = FakeTool(name="get_order_shipping_status", result=fake_tool_result)
    agent = Agent(tools=[tool], llm=FakeLLMClient({
        "tool_call": {
            "name": "get_order_shipping_status",
            "arguments": {"order_id": "A1001"}
        }
    }))

    agent.run("帮我查一下订单 A1001 的物流状态")

    assert tool.calls == [{"order_id": "A1001"}]
```

面试要点：Tool Calling 测试要同时看“选了什么工具”和“工具结果如何被使用”。

### 5. 如何处理非确定性

LLM 输出非确定，测试时可以通过几种方式降低波动：

- temperature 设为 0 或较低。
- 固定模型版本，不使用浮动别名。
- 固定 Prompt、检索上下文和工具结果。
- 使用结构化输出，减少自由文本空间。
- 断言事实点、字段、工具调用，而不是逐字匹配。
- 对少量关键样例做多次采样，统计通过率。

错误做法：

```text
每次 CI 都真实调用最新模型，然后断言完整回答字符串完全一致。
```

更好的做法：

```text
单元测试使用 FakeLLMClient。
集成测试使用录制响应。
每日或发布前运行真实模型评测集。
```

### 6. 如何做回放测试

回放测试适合把线上坏 Case 固化下来。

记录内容：

- 用户输入。
- 会话上下文。
- 检索结果。
- Prompt 版本。
- 模型版本和参数。
- 工具调用请求与响应。
- 最终输出。
- 人工标注的失败原因和期望修复结果。

回放测试的目标不是复刻所有线上流量，而是覆盖：

- 高频问题。
- 高风险问题。
- 历史坏 Case。
- 新功能影响范围。
- 安全和权限边界。

### 7. CI 中怎么安排 LLM 测试

推荐分层运行：

| 阶段 | 测试内容 | 是否真实调用模型 | 触发频率 |
| --- | --- | --- | --- |
| Pull Request | 单元测试、契约测试、Mock 集成测试 | 否 | 每次提交 |
| 合并前 | 小规模黄金样例回放 | 可选 | 合并前 |
| 发布前 | 完整离线评测、安全样例、成本统计 | 是 | 发布前 |
| 线上 | 抽样监控、坏 Case 回流 | 是 | 持续 |

面试回答：

> CI 里不能把真实模型评测跑得太重，否则会慢、贵、不稳定。PR 阶段保证工程契约不坏，发布阶段再跑真实模型质量评测。

## 四、典型测试方案设计

### 方案 1：客服 RAG 应用

测试重点：

1. Query 改写是否保留用户意图。
2. 检索结果是否包含正确文档。
3. 回答是否只基于引用内容。
4. 没有答案时是否拒答。
5. 引用来源是否可追溯。

关键断言：

```text
输入：试用版能开发票吗？
检索上下文：试用版不支持开具发票，付费版可在订单中心申请发票。
期望：
- 回答包含“试用版不支持开具发票”
- 回答包含“付费版可在订单中心申请”
- 不出现“联系客服人工开票”
- citations 至少包含一条发票政策文档 ID
```

### 方案 2：Agent 工具调用应用

测试重点：

1. 是否选择正确工具。
2. 是否传入合法参数。
3. 工具失败是否重试或降级。
4. 多工具链路是否保持状态一致。
5. 是否防止越权工具调用。

典型坏 Case：

```text
用户：帮我取消最近一笔订单
风险：用户没有明确订单号，Agent 不能直接调用 cancel_order。
正确行为：先询问用户确认订单，或者列出候选订单等待确认。
```

### 方案 3：结构化抽取应用

测试重点：

1. 输出 JSON 是否符合 Schema。
2. 字段是否来自原文。
3. 缺失字段是否返回 null 或低置信度。
4. 金额、日期、身份证号等格式是否标准化。
5. 不确定内容是否避免猜测。

示例期望：

```json
{
  "invoice_no": "INV-2026-001",
  "amount": 1280.5,
  "currency": "CNY",
  "confidence": 0.92
}
```

## 五、高频面试问题与参考答案

### 1. LLM 输出不稳定，怎么写自动化测试？

参考答案：

> 先分层。业务代码、参数校验、权限、缓存、重试用确定性单元测试；模型调用通过 Mock 或 Replay 隔离；结构化输出用 Schema 校验；自然语言答案用事实点、禁用项、引用和长度等规则断言；关键场景再用真实模型跑黄金样例评测。不要在所有测试里逐字匹配完整回答。

### 2. 为什么不能所有测试都真实调用大模型？

参考答案：

> 成本高、速度慢、结果有波动，还会受到网络、限流、模型版本变化影响。真实模型测试适合做发布前评测和关键回归，不适合替代单元测试。工程逻辑测试应该 Mock 模型，这样失败时能定位到业务代码，而不是混在模型不确定性里。

### 3. 如何 Mock 一个 LLM 客户端才合理？

参考答案：

> 先把模型 SDK 封装成稳定接口，例如 `chat(messages, tools, temperature)`。测试时注入 Fake 或 Mock 客户端，固定返回内容，同时记录调用参数。这样既能测试业务代码如何构造 Prompt、模型参数和工具定义，也能避免真实 API 带来的不稳定。

### 4. Prompt 修改后如何防止回归？

参考答案：

> 建立黄金样例集，覆盖高频问题、边界问题、坏 Case 和安全样例。每次修改 Prompt 后，跑回放测试：固定输入、检索上下文和工具结果，检查事实点、格式、引用、拒答和禁用内容。对真实模型效果再做小规模评测，必要时人工抽检。

### 5. Tool Calling 应用怎么测试？

参考答案：

> 至少测试三层：第一，模型是否选择正确工具；第二，工具参数是否符合 Schema 和权限约束；第三，工具返回后最终回答是否正确使用结果。还要覆盖工具失败、超时、重复调用、参数缺失、用户未确认危险操作等场景。

### 6. LLM-as-Judge 可以用于自动化测试吗？

参考答案：

> 可以作为辅助，尤其适合开放式回答的初筛和大规模回归，但不能完全依赖。高风险场景要结合规则校验、结构化断言和人工评审。使用 LLM-as-Judge 时要固定评分标准、模型版本、温度，并抽样检查裁判一致性。

### 7. 如何设计一个 LLM 应用的测试金字塔？

参考答案：

> 底层是大量确定性单元测试，覆盖解析、校验、路由、权限、缓存、重试；中层是 Mock 模型和 Mock 工具的集成测试，验证编排链路；再上层是契约测试和黄金样例回放；最上层是少量真实模型端到端测试，用于发布前质量把关。

### 8. 线上发现坏 Case 后应该怎么处理？

参考答案：

> 先补充上下文：用户输入、检索结果、Prompt 版本、模型版本、工具调用和最终输出。然后归因是检索、Prompt、工具、权限、数据还是模型问题。修复后把这个 Case 加入回归集，定义必须包含和禁止出现的断言，避免同类问题再次出现。

### 9. 怎么测试流式输出？

参考答案：

> 流式测试不要只看最终文本，还要测试事件协议。比如是否按 `start -> delta -> done` 顺序输出，异常时是否发送 error 事件，取消时后台任务是否停止，增量片段拼接后是否等于最终内容。模型部分可以用 Fake Stream 逐块返回固定 token。

### 10. 面试中如何总结 LLM 测试的核心原则？

参考答案：

> 核心原则是分层、隔离、契约化和回归化。分层是区分单元、集成、回放和端到端；隔离是用 Mock 固定模型、检索和工具变量；契约化是把 Prompt、Schema、工具参数都当成接口测试；回归化是把线上坏 Case 沉淀为长期测试资产。

## 六、面试答题模板

当面试官问“你们怎么测试 LLM 应用”时，可以按这个结构回答：

```text
1. 我会先分层，不会所有测试都真实调模型。
2. 业务确定性逻辑用单元测试，比如权限、解析、缓存、重试。
3. 模型调用封装成客户端接口，在测试里用 Mock 或 Replay。
4. Prompt 和结构化输出做契约测试，检查变量、Schema、Tool 参数。
5. 关键业务场景维护黄金样例，断言事实点、禁用内容、引用和格式。
6. 发布前跑真实模型评测，线上坏 Case 回流到回归集。
7. 对高风险场景结合人工抽检，避免完全依赖自动评分。
```

加分点：

- 提到固定模型版本和参数，避免测试漂移。
- 提到 Mock 的目的是隔离变量，不是证明模型质量。
- 提到 Tool Calling 的危险操作必须有人类确认或二次校验。
- 提到 CI 阶段要控制真实模型调用成本和稳定性。

## 七、常见误区

1. **误区：只要线上跑得通就行。**  
   真实用户问题分布会变化，没有回归测试很容易改一个 Prompt 坏一片场景。

2. **误区：LLM 不确定，所以没法测。**  
   不能逐字测，不代表不能测。事实点、结构化字段、工具调用和权限行为都可以测。

3. **误区：Mock 模型没有意义。**  
   Mock 模型不测模型能力，但能测试业务编排、Prompt 构造、参数传递和异常处理。

4. **误区：评测集越大越好。**  
   更重要的是分层和代表性。高质量黄金样例比大量低质量样例更有价值。

5. **误区：LLM-as-Judge 可以替代人工。**  
   它适合提效，不适合在高风险业务里单独作为最终裁判。

## 八、实践清单

开发一个 LLM 功能前，可以用这份清单自查：

- [ ] 模型 SDK 是否封装在可替换接口后面。
- [ ] 是否能用 FakeLLMClient 跑通核心业务测试。
- [ ] Prompt 模板是否有变量完整性测试。
- [ ] 结构化输出是否有 Schema 校验。
- [ ] Tool Calling 是否覆盖选工具、参数、失败和越权场景。
- [ ] 是否有黄金样例覆盖高频、边界、安全和历史坏 Case。
- [ ] CI 中是否区分 Mock 测试和真实模型评测。
- [ ] 线上坏 Case 是否能回流到回归测试。
- [ ] 测试日志是否记录 Prompt 版本、模型版本和工具调用链路。

## 九、一句话记忆

> LLM 应用不是不能测试，而是要把“模型质量评测”和“工程行为测试”分开：工程行为用 Mock 做确定性验证，模型质量用黄金样例和真实评测做阶段性把关。
