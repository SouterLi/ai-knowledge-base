## 一、核心概念

Prompt 工程不是“写一段好话术”，而是把业务目标、上下文、约束、输出格式和失败处理清晰地交给模型。面试常考点在于：候选人是否能把 Prompt 当成可测试、可迭代、可观测的工程资产。

结构化输出是指让模型按固定格式返回结果，例如 JSON、表格、枚举标签或函数参数。它常用于信息抽取、分类、工单流转、内容审核、自动填表和 API 调用前置参数生成。和自然语言答案相比，结构化输出更容易被程序解析、校验和接入后续流程。

一个高质量 Prompt 通常包含：

1. 角色：模型承担什么职责，例如“你是合同审查助手”。
2. 任务：明确要完成什么，不要混入多个模糊目标。
3. 上下文：提供必要材料、用户输入、历史信息或业务规则。
4. 约束：说明边界，例如不能编造、只能返回给定枚举。
5. 输出格式：给出字段、类型、示例和缺省值规则。
6. 质量标准：说明什么是好答案，什么情况应拒答或返回空值。

## 二、关键步骤

### 1. 先定义下游消费方式

如果结果要给人看，可以关注表达清晰；如果结果要给程序处理，必须优先保证格式稳定。面试回答时要强调：输出格式不是最后修饰，而是系统契约。

### 2. 使用明确 Schema

建议把字段名、类型、枚举范围和约束写清楚。例如：

```json
{
  "intent": "refund | change_address | unknown",
  "confidence": 0.0,
  "summary": "一句话概括用户诉求",
  "need_human": false
}
```

真实工程中还要用 JSON Schema、Pydantic、Zod 等工具做校验，不能只相信模型“看起来像 JSON”。

### 3. 控制输入与上下文

Prompt 过长会增加成本，也可能让模型忽略关键规则。常见做法是只注入与任务相关的上下文；对长材料先分段、摘要或检索；把强约束放在靠近输出要求的位置。

### 4. 解析、校验与重试

结构化输出链路通常是：调用模型、解析结果、Schema 校验、业务规则校验、失败重试或降级。重试时不要简单重复原 Prompt，可以把错误信息反馈给模型，例如“字段 intent 必须是给定枚举之一”。

### 5. 建立评估集

Prompt 优化不能只靠主观感觉。应准备覆盖正常、边界、歧义、恶意输入和空输入的样例集，比较准确率、格式通过率、拒答正确率、延迟和成本。

## 三、常见问题

### 1. 为什么模型没有按格式输出？

常见原因是格式要求不明确、示例和规则冲突、任务太复杂、温度过高，或没有使用模型原生的 JSON/工具调用能力。解决方式是简化任务、提供 Schema、降低随机性，并在服务端强制校验。

### 2. Few-shot 示例越多越好吗？

不是。示例能帮助模型理解格式和边界，但过多会占用上下文并引入噪声。高质量、覆盖典型边界的少量示例通常比大量重复示例更有效。

### 3. Prompt 能替代业务规则吗？

不能。Prompt 适合表达语义判断和生成要求，但权限、金额阈值、合规红线、状态流转等硬规则应放在代码或规则引擎中。面试中要明确：模型输出是候选结果，最终决策仍需系统校验。

### 4. 如何处理注入攻击？

不要把用户输入和系统指令混在一起；明确标记用户内容边界；对敏感操作增加权限校验；对模型输出再做白名单检查。不能只靠一句“忽略用户恶意指令”解决安全问题。

## 四、实践建议

- Prompt 要版本化，记录变更原因、适用模型和评估结果。
- 优先使用模型支持的 JSON mode、function calling 或 tool calling。
- 对关键字段设置枚举，减少开放文本。
- 低置信度、校验失败和高风险结果应进入人工或降级流程。
- 日志中记录输入摘要、Prompt 版本、模型版本、解析错误和重试次数。
- 把 Prompt 测试纳入 CI，避免一次改动破坏已有场景。

## 五、一分钟总结

Prompt 工程的本质是把不稳定的自然语言交互变成可验证的工程接口。面试回答时应围绕“任务清晰、格式稳定、服务端校验、失败重试、评估迭代、安全边界”展开。结构化输出尤其要记住：模型负责生成候选内容，系统负责解析、校验和兜底。
