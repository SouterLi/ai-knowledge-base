## 一、为什么这是高频考点

企业落地大模型时，不一定能直接使用公有云模型 API。常见原因包括数据不能出域、客户要求私有化交付、成本需要可控、需要接入行业模型、需要在内网环境长期运行，或者希望对推理性能做更细粒度优化。

面试中问私有化部署，通常不是只问“会不会用 Ollama 跑模型”，而是在考察候选人是否理解完整工程链路：

1. 如何选择模型和推理引擎。
2. 如何估算 GPU 显存、并发和吞吐。
3. 如何处理长上下文、KV Cache、批处理和流式输出。
4. 如何把模型封装成稳定 API，接入网关、RAG、Agent 和权限系统。
5. 如何上线、监控、降级、灰度和排障。

一个成熟回答要体现：私有化部署不是“把模型跑起来”，而是把模型变成一个可治理、可观测、可扩展的生产服务。

## 二、核心概念

### 1. 私有化部署

私有化部署是指把模型权重、推理服务、向量库、业务服务和运维组件部署在企业自有云、专有云、内网机房或客户环境中。

常见目标包括：

- 数据合规：敏感数据不离开企业边界。
- 成本可控：高频调用场景用自建推理降低边际成本。
- 可定制：使用行业模型、微调模型或内部蒸馏模型。
- 可控 SLA：根据业务峰值配置 GPU、队列、限流和降级。
- 离线可用：在无法访问外网的客户环境中运行。

面试中要补一句：私有化并不天然更便宜，只有在调用量、硬件利用率、运维能力和模型质量匹配时，成本优势才会出现。

### 2. 推理服务

推理服务负责加载模型权重，接收请求，执行 token 生成，并以同步或流式方式返回结果。

典型推理服务能力：

- 模型加载：权重格式、张量并行、量化权重。
- 请求调度：排队、动态批处理、优先级、超时。
- 生成控制：temperature、top_p、max_tokens、stop words。
- KV Cache 管理：复用注意力缓存，提升自回归生成效率。
- API 兼容：OpenAI-compatible API、gRPC、HTTP、SSE。
- 观测指标：QPS、TTFT、TPOT、吞吐、显存、失败率。

### 3. 推理引擎

推理引擎是私有化部署的核心组件。常见选择：

| 推理引擎 | 特点 | 典型场景 |
| --- | --- | --- |
| vLLM | PagedAttention、连续批处理、OpenAI API 兼容度高 | 通用在线推理服务 |
| Text Generation Inference | Hugging Face 生态友好，部署成熟 | HF 模型服务化 |
| TensorRT-LLM | NVIDIA 深度优化，性能上限高 | 大规模 GPU 推理 |
| llama.cpp | CPU / 边缘设备友好，量化生态成熟 | 轻量、本地、边缘部署 |
| Ollama | 易用，适合开发和原型验证 | 本地开发，不建议直接作为高并发生产核心 |

面试回答时要避免“某个工具万能”。更合理的表述是：先根据模型规模、并发、延迟、硬件和运维复杂度选择推理引擎。

### 4. 显存、上下文与 KV Cache

LLM 推理显存主要由三部分组成：

1. 模型权重：模型参数占用，例如 7B FP16 约 14GB。
2. KV Cache：随 batch size、上下文长度、层数、隐藏维度增长。
3. 运行时开销：CUDA kernel、框架缓存、临时张量、碎片。

常见误区是只看模型权重显存。例如 7B 模型权重能放进 24GB 显卡，不代表可以支撑长上下文和高并发。并发越高、上下文越长，KV Cache 压力越大。

### 5. TTFT 与 TPOT

面试中常用两个指标描述用户体验：

- TTFT（Time To First Token）：从请求进入服务到返回第一个 token 的时间，影响“是否秒回”。
- TPOT（Time Per Output Token）：生成每个输出 token 的平均耗时，影响流式输出速度。

优化 TTFT 通常关注排队、prefill、首包返回和模型调度；优化 TPOT 通常关注 decode 阶段吞吐、batching、GPU 利用率和采样开销。

## 三、核心知识点

### 1. 推荐架构

私有化 LLM 服务通常不要让业务系统直接访问推理引擎，而是分层治理：

```text
业务应用 / RAG / Agent
  -> 模型网关
  -> 推理服务 API
  -> 推理引擎 vLLM / TGI / TensorRT-LLM
  -> GPU 节点
  -> 指标、日志、审计、告警
```

各层职责：

- 业务层：只表达任务需求，如模型别名、消息、工具、输出格式。
- 模型网关：鉴权、限流、路由、灰度、降级、审计、成本归因。
- 推理服务：协议适配、请求队列、流式输出、错误标准化。
- 推理引擎：模型加载、batching、KV Cache、GPU 计算。
- 运维层：监控 GPU、延迟、吞吐、失败率和容量水位。

核心原则：业务关注能力，网关关注治理，推理引擎关注性能。

### 2. 模型选择

模型选择要同时看质量、成本和可运维性：

| 维度 | 面试回答要点 |
| --- | --- |
| 任务匹配 | 问答、总结、代码、抽取、多语言、长文档是否适配 |
| 模型规模 | 7B/8B 成本低，32B/70B 质量高但硬件压力大 |
| 上下文长度 | 长上下文会显著增加 KV Cache 和延迟 |
| 许可证 | 是否允许商用、再分发、私有化交付 |
| 工具调用能力 | 是否稳定输出 function call 或结构化 JSON |
| 中文能力 | 中文企业知识库不能只看英文 benchmark |
| 部署生态 | 是否被 vLLM/TGI/TensorRT-LLM 良好支持 |

更稳妥的做法是用业务测试集评估候选模型，而不是只看公开榜单。公开榜单能做初筛，最终要用真实问答、坏 Case、延迟和成本来决策。

### 3. 显存估算

粗略估算模型权重显存：

```text
权重显存约等于 参数量 * 每个参数字节数

7B FP16 约 7 * 10^9 * 2 bytes = 14GB
7B INT8 约 7GB
7B INT4 约 3.5GB
```

实际部署还要预留 KV Cache 和运行时空间。可以用下面的思路解释：

```python
def estimate_weight_memory_gb(params_billion, bytes_per_param):
    # 面试中用于解释估算思路，生产环境还要加 KV Cache 和运行时冗余
    return params_billion * 1_000_000_000 * bytes_per_param / (1024 ** 3)


print(round(estimate_weight_memory_gb(7, 2), 1))   # 约 13.0GB
print(round(estimate_weight_memory_gb(14, 2), 1))  # 约 26.1GB
```

面试表达可以这样说：

> 我会先估算权重显存，再结合最大上下文、并发、batch size 估算 KV Cache，最后预留 20%～30% 运行时余量。只要线上需要长上下文或多并发，就不能只按权重大小选显卡。

### 4. 量化取舍

量化通过降低参数精度减少显存和计算成本。常见类型：

- FP16/BF16：质量稳定，硬件要求较高。
- INT8：显存约减半，质量损失通常可控。
- INT4：显存更低，适合资源受限场景，但复杂推理和结构化输出可能变差。
- GPTQ/AWQ/GGUF：不同生态下的量化格式和算法。

面试重点是取舍：

1. 量化能降低显存和成本，但可能损失质量。
2. 对客服问答、分类、摘要等任务，INT8/INT4 可能足够。
3. 对代码生成、复杂推理、金融法务等高精度任务，需要更谨慎评估。
4. 量化后必须重新跑业务评测集，不能只看模型能否启动。

### 5. 请求调度与动态批处理

LLM 在线推理最重要的吞吐优化之一是 batching。和传统批处理不同，LLM 请求长度不一，生成长度不一，需要动态调度。

常见策略：

- Continuous batching：运行中不断把新请求加入 batch，提高 GPU 利用率。
- Prefix caching：相同系统提示词、固定模板或共享上下文可以复用前缀计算。
- 请求队列：按优先级、租户、任务类型做排队和限流。
- 超时控制：超过排队时间或生成时间要失败或降级。
- 最大 token 限制：防止单个请求占用过多资源。

示例配置：

```yaml
serving:
  model_alias: "private_chat"
  max_model_len: 8192
  max_num_batched_tokens: 32768
  max_num_seqs: 64
  request_timeout_ms: 30000
  stream_timeout_ms: 60000
  queue_policy:
    default_priority: "normal"
    max_wait_ms: 3000
    reject_when_queue_full: true
```

高质量回答要说明：batching 能提升吞吐，但会增加排队和首 token 延迟，所以需要根据交互式对话、批量摘要、离线抽取等场景分别配置。

### 6. OpenAI 兼容 API

生产中常把私有模型包装成 OpenAI-compatible API，这样应用层、SDK、网关和评测工具更容易复用。

示例调用：

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://llm-gateway.internal/v1",
    api_key="internal-token",
)

response = client.chat.completions.create(
    model="private_chat",
    messages=[
        {"role": "system", "content": "你是企业知识库助手，只能基于已授权资料回答。"},
        {"role": "user", "content": "请总结本季度客户投诉的主要原因。"},
    ],
    temperature=0.2,
    max_tokens=512,
)

print(response.choices[0].message.content)
```

面试中可以补充：OpenAI 兼容 API 方便迁移，但不要把供应商协议直接扩散到所有业务。更好的方式是由模型网关统一承接协议差异。

### 7. 流式输出

对聊天应用，流式输出能明显改善体感延迟。服务端常用 SSE 返回 token chunk：

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()


async def generate_stream(prompt: str):
    # 实际生产中这里会转发到推理引擎，并处理超时、取消和审计
    for token in ["私", "有", "化", "部", "署"]:
        yield f"data: {token}\n\n"
    yield "data: [DONE]\n\n"


@app.get("/v1/chat/stream")
async def stream_chat(prompt: str):
    return StreamingResponse(
        generate_stream(prompt),
        media_type="text/event-stream",
    )
```

注意点：

- 客户端断开时要取消后端生成，避免浪费 GPU。
- 流式响应也要记录完整输出或采样日志，方便排查。
- 工具调用和结构化输出场景要处理半截 JSON、增量解析和错误恢复。
- 安全审核如果要求完整输出后再放行，就会影响流式体验，需要分级设计。

### 8. 容量规划

容量规划要从业务目标倒推：

1. 峰值 QPS 和平均 QPS。
2. 输入 token 和输出 token 分布。
3. P95 / P99 延迟目标。
4. 并发用户数和最长上下文。
5. 是否需要流式输出。
6. 可接受的排队、拒绝和降级策略。

一个常见面试回答：

> 我不会只问“几张卡能跑”，而是先看请求 token 分布和 SLA。比如对话场景关注 TTFT 和流式速度，批量总结关注吞吐和成本。然后压测不同 batch、上下文长度和并发下的 QPS、P95、显存水位，最后确定 GPU 数量、模型副本数、限流阈值和降级策略。

### 9. 高可用与降级

私有化部署也要按生产系统设计高可用：

- 多副本：同一模型多个推理实例，避免单点。
- 健康检查：探活不只检查端口，还要检查模型是否能完成短推理。
- 熔断：错误率、超时率或显存 OOM 升高时摘除实例。
- 降级：切小模型、缩短上下文、关闭高成本功能、转异步任务。
- 限流：按租户、用户、模型和任务类型限流。
- 灰度：新模型、新量化版本和新 prompt 分批发布。

降级策略示例：

```python
def choose_model(task_type, tenant_level, queue_ms):
    # 高价值租户尽量保质量；普通请求排队过长时切到轻量模型
    if tenant_level == "enterprise" and task_type in {"legal", "finance"}:
        return "private_chat_strong"
    if queue_ms > 2000:
        return "private_chat_fast"
    return "private_chat_balanced"
```

这段代码只是表达路由思想，真实生产中应放在模型网关或配置中心，并记录路由原因。

### 10. 监控指标

私有化推理服务的监控要覆盖业务、服务和 GPU 三层。

| 层次 | 指标 | 作用 |
| --- | --- | --- |
| 业务层 | 请求量、租户、任务类型、成功率、拒绝率 | 判断业务影响 |
| 延迟层 | TTFT、TPOT、总耗时、排队时间、P95/P99 | 判断用户体验 |
| Token 层 | 输入 token、输出 token、tokens/s | 判断吞吐和成本 |
| 资源层 | GPU 利用率、显存、KV Cache 使用率、CPU、网络 | 判断瓶颈 |
| 错误层 | OOM、超时、限流、取消、解析失败 | 定位故障 |
| 质量层 | 答案评分、结构化成功率、人工反馈、坏 Case | 判断模型效果 |

排障顺序通常是：先看错误率和延迟，再拆排队时间、prefill、decode、GPU 水位和请求 token 分布。

### 11. 私有化交付注意事项

私有化交付比内部部署更复杂，因为客户环境往往存在网络、权限、硬件和运维差异。

需要提前确认：

- GPU 型号、显存、驱动、CUDA 版本。
- 是否允许拉取镜像和模型权重。
- 内网域名、证书、代理、防火墙策略。
- 模型许可证和客户数据合规要求。
- 日志是否能采集，是否需要脱敏。
- 离线安装包、回滚包和升级流程。
- 运维手册、容量建议、验收压测标准。

面试中可以强调：私有化交付要把环境差异显式化，最好用容器镜像、Helm Chart、离线包和自动化检查脚本减少人工踩坑。

## 四、常见方案对比

### 1. 公有云 API vs 私有化部署

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 公有云 API | 接入快、质量强、免运维、弹性好 | 数据出域、成本不稳定、供应商依赖 | 原型、中小流量、通用任务 |
| 私有化部署 | 数据可控、可定制、长期成本可能更低 | 运维复杂、质量需评估、硬件投入高 | 敏感数据、大流量、客户私有化 |
| 混合架构 | 质量、成本、合规之间折中 | 路由和治理复杂 | 企业生产系统 |

### 2. 单模型服务 vs 模型网关

单模型服务适合早期验证，但生产中通常需要模型网关：

- 支持多个模型别名。
- 支持灰度、降级和回滚。
- 支持租户级配额和审计。
- 支持统一错误码和指标。
- 支持公有云模型与私有模型混合路由。

回答时可以说：我会先快速起单模型服务验证效果，再在生产化阶段通过模型网关隔离业务和推理引擎。

## 五、高频面试问题与标准答案

### 1. 面试题：如果要把一个 7B 开源模型部署到企业内网，你会怎么设计？

**参考答案：**

我会分五步设计。第一步选模型，确认中文能力、许可证、上下文长度、工具调用能力和业务评测效果。第二步选推理引擎，比如在线服务优先考虑 vLLM 或 TGI，本地轻量场景再考虑 llama.cpp 或 Ollama。第三步做容量估算，不只看 7B FP16 约 14GB 权重显存，还要考虑 KV Cache、上下文长度、并发和运行时冗余。第四步服务化，尽量提供 OpenAI-compatible API，并通过模型网关做鉴权、限流、路由和审计。第五步上线运维，压测 TTFT、TPOT、P95、显存水位，配置健康检查、熔断、降级和监控告警。

### 2. 面试题：为什么模型能加载成功，但并发一上来就 OOM？

**参考答案：**

模型加载成功只说明权重能放进显存，不代表能承载实际请求。线上推理还会占用 KV Cache，KV Cache 会随着 batch size、输入长度、输出长度和并发增长。如果很多用户使用长上下文，显存压力会迅速升高。另外推理框架还有运行时缓存和临时张量。排查时我会看请求 token 分布、max_model_len、max_num_seqs、KV Cache 使用率和显存碎片，然后降低并发、限制上下文、调整 batch 参数，必要时做量化或增加模型副本。

### 3. 面试题：vLLM 为什么适合做在线推理？

**参考答案：**

vLLM 比较适合在线推理，核心原因是它对 LLM 生成过程做了调度和显存优化。PagedAttention 可以更高效地管理 KV Cache，减少显存浪费；continuous batching 可以在服务运行过程中动态合并请求，提高 GPU 利用率；它还提供 OpenAI-compatible API，应用接入成本低。面试中我会补充一点：vLLM 不是所有场景都最优，如果追求 NVIDIA 硬件上的极致性能，可以评估 TensorRT-LLM；如果是边缘设备或 CPU 运行，可以评估 llama.cpp。

### 4. 面试题：量化会带来什么收益和风险？

**参考答案：**

量化最大的收益是降低显存占用和推理成本，让更小的 GPU 也能运行较大的模型，或者在同样硬件上支撑更多副本。风险是模型质量可能下降，尤其是复杂推理、代码生成、数学、结构化输出和安全拒答能力可能受影响。我的做法是：先用业务评测集对比 FP16、INT8、INT4 的质量、延迟和显存，再决定是否上线。不能只因为模型能跑起来就默认量化可用。

### 5. 面试题：如何优化私有化 LLM 的首 token 延迟？

**参考答案：**

首 token 延迟主要由排队、prefill、调度和网络组成。我会先拆指标，看 TTFT 中排队时间占比高还是模型计算占比高。如果排队高，就需要限流、扩容、分模型副本、优化 batch 参数或区分优先级。如果 prefill 高，就关注输入上下文长度、prefix caching、RAG 上下文压缩和长 prompt 模板。如果网络或网关高，就看连接复用、SSE 首包、代理缓冲和跨机房调用。优化时不能只追求吞吐，因为过大的 batch 可能让首 token 变慢。

### 6. 面试题：私有化部署一定比调用云模型便宜吗？

**参考答案：**

不一定。私有化有 GPU、机房、运维、模型调优、监控和故障处理成本。如果调用量小、峰谷明显或模型质量要求很高，公有云 API 可能更划算。私有化更适合数据合规要求强、调用量稳定且较大、有运维能力、模型质量能满足业务的场景。我会用总拥有成本来算，包括硬件折旧、GPU 利用率、人力、失败成本和业务 SLA，而不是只比较单次 token 价格。

### 7. 面试题：如何做私有模型的高可用？

**参考答案：**

我会从多副本、健康检查、熔断、降级和灰度五个方面做。多副本避免单点，健康检查要包含一次轻量推理而不是只检查端口。网关根据错误率、超时率和显存水位摘除异常实例。降级可以切小模型、缩短上下文、关闭高成本功能或转异步。模型升级要按租户或流量灰度，并保留快速回滚能力。同时监控 TTFT、TPOT、P95、OOM、队列长度和 GPU 利用率。

### 8. 面试题：私有化部署如何接入已有 RAG 或 Agent 系统？

**参考答案：**

我会尽量把私有模型接到模型网关后面，而不是让 RAG 或 Agent 直接依赖某个推理引擎。RAG 和 Agent 只使用模型别名，比如 `private_chat`、`private_tool_call`。网关负责把请求路由到私有模型或云模型，并统一鉴权、限流、日志和错误码。这样后续替换模型、量化版本灰度、故障降级都不需要改业务逻辑。对于 Agent，还要重点验证工具调用格式和多轮稳定性，因为很多开源模型在 function calling 上不如闭源模型稳定。

### 9. 面试题：如何压测一个 LLM 推理服务？

**参考答案：**

我会用接近真实业务的数据压测，而不是只用固定短 prompt。压测集要覆盖不同输入长度、输出长度、流式和非流式、普通问答和长文档场景。指标上看 QPS、并发、TTFT、TPOT、P95/P99、成功率、OOM、队列时间、GPU 利用率和显存水位。压测时逐步增加并发，找到延迟拐点和 OOM 边界，再确定限流阈值、模型副本数和降级策略。

### 10. 面试题：客户要求离线私有化交付，你会提前确认什么？

**参考答案：**

我会提前确认硬件、系统、网络、安全和验收标准。硬件包括 GPU 型号、显存、驱动和 CUDA；系统包括容器运行时、Kubernetes 或裸机部署方式；网络包括是否能拉镜像、是否有代理、内网域名和证书；安全包括模型许可证、日志脱敏、数据不出域、权限审计；验收包括压测数据、QPS、P95、并发、可用性和故障恢复要求。最好提供离线安装包、环境检查脚本、回滚方案和运维手册。

## 六、面试答题模板

遇到“如何私有化部署大模型”这类开放题，可以按下面结构回答：

1. **先定目标**：合规、成本、质量、延迟、吞吐、离线环境。
2. **再选模型**：任务匹配、许可证、上下文、中文能力、工具调用。
3. **估算资源**：权重显存、KV Cache、并发、上下文、运行时冗余。
4. **选择引擎**：vLLM/TGI/TensorRT-LLM/llama.cpp，根据场景取舍。
5. **服务化治理**：API、网关、鉴权、限流、路由、审计、降级。
6. **验证上线**：业务评测、压测、监控、灰度、回滚、运维文档。

一句话总结：

> 私有化部署的关键不是把模型跑起来，而是让模型在企业环境中稳定、合规、可观测、可扩展地提供服务。

## 七、实践建议

- 不要只用公开 benchmark 选模型，要建立业务评测集。
- 不要只按权重显存选 GPU，要把 KV Cache 和并发算进去。
- 不要让业务代码直接绑定推理引擎，用模型网关隔离变化。
- 不要上线后才补监控，TTFT、TPOT、队列、OOM 和 GPU 水位必须先接入。
- 不要盲目量化，量化后要重新评估质量和结构化输出稳定性。
- 不要忽略许可证，开源模型不等于可以任意商用和再分发。
- 不要把私有化部署等同于低成本，低成本依赖高利用率和成熟运维。

## 八、一分钟总结

开源大模型私有化部署是 AI 应用生产化的重要能力。面试中要从模型选择、推理引擎、显存估算、KV Cache、动态批处理、OpenAI 兼容 API、流式输出、容量规划、高可用、监控和私有化交付完整回答。最佳表达不是“我会用某个工具部署”，而是“我会根据业务 SLA 和合规要求，把模型部署成一个可治理的生产服务”。
