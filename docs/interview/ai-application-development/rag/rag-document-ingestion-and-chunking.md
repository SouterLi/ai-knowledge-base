## 一、为什么这是高频考点

很多候选人讲 RAG 时会从“用户问题 -> 向量检索 -> LLM 回答”开始，但真实项目里，线上效果往往先输在离线知识处理阶段：

- PDF 解析错乱，表格、页眉、脚注混进正文。
- chunk 切得太碎，答案需要的上下文被拆散。
- chunk 切得太大，Embedding 表示变模糊，召回一堆相似但无用的内容。
- 文档更新后旧索引未删除，用户看到过期政策。
- 权限、版本、来源、页码等 metadata 缺失，无法过滤、溯源和审计。
- 全量重建索引耗时太长，业务无法接受知识更新延迟。

面试官问文档摄取和切分，本质是在考察候选人是否理解：**RAG 的质量不是只由模型决定，而是由知识进入系统时的结构化程度决定。**

一句话回答：

> RAG 文档流水线的目标，是把不稳定、格式各异、持续变化的原始资料，转成可检索、可过滤、可溯源、可增量更新的知识单元。

## 二、核心概念

### 1. 文档摄取（Document Ingestion）

文档摄取是把外部知识源接入 RAG 系统的过程，常见来源包括：

- 文件：PDF、Word、PPT、Markdown、HTML、图片扫描件。
- 系统：Confluence、Notion、飞书文档、语雀、SharePoint、Google Drive。
- 数据库：FAQ、工单、CRM、产品配置、政策条款。
- 代码与日志：代码仓库、接口文档、运行手册、事故复盘。

摄取阶段不只是“上传文件”，还要记录：

| 字段 | 用途 |
| --- | --- |
| `source_uri` | 原始来源，用于溯源和重新同步 |
| `document_id` | 稳定文档标识，用于更新、删除和权限绑定 |
| `tenant_id` | 多租户隔离 |
| `owner` | 责任人和审核人 |
| `version` | 文档版本或更新时间 |
| `acl` | 可见用户、部门、角色 |
| `ingestion_time` | 进入知识库的时间 |

面试要点：没有稳定 ID 和 metadata 的摄取链路，后面很难做增量更新、权限过滤和引用溯源。

### 2. 文档解析（Parsing）

文档解析是把原始格式转成文本和结构化元素。难点在于不同文件格式的信息结构不同：

- PDF 可能是文字层 PDF，也可能是扫描件。
- Word 有标题层级、表格、批注、页眉页脚。
- HTML 有导航栏、广告、脚本、正文。
- PPT 信息分散在文本框、图表和备注里。
- 扫描合同需要 OCR，并且容易识别错数字、日期和条款编号。

解析结果最好不是单纯字符串，而是结构化块：

```json
{
  "document_id": "policy-2026-001",
  "blocks": [
    {
      "type": "heading",
      "level": 2,
      "text": "退款条件",
      "page": 3
    },
    {
      "type": "paragraph",
      "text": "用户在订单支付后 7 天内可申请退款...",
      "page": 3
    }
  ]
}
```

这样后续切分可以利用标题、页码、表格、段落等结构信息，而不是盲目按字符数切。

### 3. 清洗与规范化（Cleaning & Normalization）

清洗的目标是去掉对检索有害的噪声，同时保留能帮助理解和溯源的信息。

常见清洗项：

- 删除页眉页脚、目录重复项、版权声明、导航栏。
- 修复 OCR 空格、断行、乱码和全半角问题。
- 合并被 PDF 换行打断的句子。
- 规范标题层级、列表编号和表格文本。
- 过滤空内容、模板占位符、重复段落。

不要过度清洗。比如合同里的条款编号、表格列名、错误码、产品型号，对检索非常重要，不能当作噪声删掉。

### 4. Chunk

Chunk 是 RAG 检索和上下文注入的基本知识单元。一个 chunk 通常包含：

- 正文文本。
- 标题路径。
- 来源文档。
- 页码或章节位置。
- 权限和租户信息。
- 版本和更新时间。
- hash 或指纹。

示例：

```json
{
  "chunk_id": "policy-2026-001#003",
  "document_id": "policy-2026-001",
  "title_path": ["售后政策", "退款条件"],
  "text": "退款条件：用户在订单支付后 7 天内可申请退款...",
  "page_start": 3,
  "page_end": 3,
  "tenant_id": "tenant_a",
  "acl": ["support", "after_sales"],
  "content_hash": "a6b1..."
}
```

### 5. 索引构建（Indexing）

索引构建是把 chunk 转成可查询结构，通常包括：

1. 写入原文存储：保存完整文档、解析结果和 chunk 文本。
2. 生成 Embedding：批量调用向量模型。
3. 写入向量索引：用于语义召回。
4. 写入关键词索引：用于 BM25、精确匹配、过滤和排序。
5. 写入 metadata 索引：用于权限、租户、版本、时间过滤。
6. 记录构建任务状态：成功、失败、跳过、重试、回滚。

生产环境常见做法是同时保留原文库、chunk 库、向量库和搜索索引，而不是只把向量存起来。

## 三、核心知识点

### 1. 推荐的文档处理流水线

典型链路：

```text
数据源
  -> 连接器同步
  -> 原始文档落库
  -> 文档解析
  -> 清洗规范化
  -> 结构化切分
  -> chunk 质量检查
  -> Embedding 批处理
  -> 向量索引 / 关键词索引 / metadata 索引
  -> 索引发布
  -> 检索评估与线上监控
```

面试回答要强调两个边界：

- 原始文档必须可追溯，方便重新解析和重建索引。
- 索引发布最好是可切换版本，而不是边写边直接污染线上索引。

### 2. 切分策略怎么选

常见切分策略对比：

| 策略 | 适合场景 | 优点 | 风险 |
| --- | --- | --- | --- |
| 固定长度切分 | 快速原型、格式简单文本 | 实现简单 | 容易切断语义 |
| 按标题/段落切分 | Markdown、产品文档、制度文档 | 保留结构 | 超长章节需要二次拆分 |
| 递归切分 | 通用文本 | 兼顾结构与长度 | 参数需要调优 |
| 语义切分 | 长文章、主题变化明显文档 | 边界更自然 | 成本高，稳定性依赖模型 |
| 父子 chunk | 需要精准召回且回答需完整上下文 | 小块召回，大块生成 | 存储和链路更复杂 |
| 表格专用切分 | 报价单、政策表、配置表 | 保留行列语义 | 解析质量要求高 |

推荐表达：

> 我不会只用固定长度切分。优先利用文档结构按标题、段落、表格切分；超长块再递归拆分；对问答需要完整上下文的场景使用父子 chunk；最后通过检索评测调 chunk size、overlap 和 top_k。

### 3. Chunk size 与 overlap 的取舍

`chunk_size` 和 `overlap` 没有通用最优值，要根据文档类型、Embedding 模型和问题类型调。

常见经验：

- FAQ：单条问答通常可以作为一个 chunk，overlap 很少需要。
- 操作文档：按步骤组块，避免把前置条件和操作步骤拆开。
- 政策制度：按条款切分，保留条款编号和上级标题。
- 技术文档：按标题和代码块切分，避免把代码块截断。
- 合同/法务：按条款、定义、例外条件切分，并保留页码和条款号。

典型问题：

- 太小：召回片段缺少答案背景，LLM 只能猜。
- 太大：Embedding 表示平均化，容易召回整段“看起来相关但答不上”的内容。
- overlap 太小：跨段语义断裂。
- overlap 太大：索引膨胀，重复召回，成本升高。

面试中不要报一个固定数字当答案。更好的说法是：

> 我会先按文档结构切，再用评测集调参。指标看 Recall@K、命中片段可回答率、重复率、平均注入 token 和答案引用准确率。

### 4. Metadata 是检索质量和安全的基础

RAG 的 metadata 不只是“额外字段”，而是线上系统的控制面。

必备 metadata：

| 字段 | 作用 |
| --- | --- |
| `tenant_id` | 多租户隔离 |
| `acl` | 权限过滤 |
| `document_id` | 删除、更新、追踪 |
| `chunk_id` | 唯一定位 |
| `source_uri` | 引用溯源 |
| `title_path` | 提升上下文完整性 |
| `page` / `section` | 用户核验 |
| `updated_at` | 时效性排序 |
| `version` | 灰度发布和回滚 |
| `content_hash` | 去重和变更检测 |

高频追问：metadata 过滤是在向量检索前还是后？

实用回答：

- 权限、租户这类硬约束必须前置或在数据库层强制执行，不能先召回再过滤后直接返回。
- 时间、类型、语言等软约束可以作为检索前过滤、检索后 rerank 或混合策略。
- 如果过滤条件太严格导致召回为空，要有可解释的降级，例如提示“你可能没有权限”或“当前范围无结果”，而不是放宽权限。

### 5. 增量更新与删除

企业知识库不是一次性导入，文档会持续新增、修改、删除。

增量更新关键点：

1. **变更检测**：通过更新时间、etag、文件 hash、内容 hash 判断是否变化。
2. **稳定 ID**：同一文档更新后仍能定位旧 chunk。
3. **chunk 级 diff**：只重算变化 chunk，减少 Embedding 成本。
4. **软删除和延迟清理**：先标记不可见，再异步清理向量和索引。
5. **索引版本**：新索引构建完成并验证后再切流。
6. **幂等任务**：重复执行不会生成重复 chunk 或脏索引。

错误做法：

- 文档更新后直接追加新 chunk，不删除旧版本。
- 用自增 ID 做 chunk_id，导致每次重建都无法对齐历史数据。
- 删除文档时只删原文，不删向量索引和关键词索引。
- 索引构建失败一半仍然对线上可见。

### 6. 去重与版本治理

重复内容会造成两个问题：

- 检索结果被同一段内容刷屏，浪费 top_k。
- 统计指标虚高，看起来召回很多，实际信息增量很低。

常见去重层级：

| 层级 | 方法 | 适合问题 |
| --- | --- | --- |
| 文件级 | 文件 hash、source_uri | 重复上传 |
| 段落级 | 文本规范化后 hash | 页眉页脚、模板重复 |
| 语义级 | SimHash、MinHash、Embedding 相似度 | 改写转载、轻微修改 |
| 结果级 | 检索后按 document_id / title_path 合并 | top_k 重复 |

版本治理建议：

- `document_id` 表示业务文档，`version` 表示版本，`chunk_id` 表示某版本下的知识块。
- 检索默认只查当前生效版本。
- 历史版本可用于审计，但不应默认进入在线问答。
- 新版本发布前跑回归评测，重点看高频问答、引用页码和权限过滤。

### 7. 表格、图片和代码块怎么处理

#### 表格

表格不能简单按行拼文本。要保留表头、单位和行列关系。

示例：

```text
表格：会员等级权益
列：等级、月费、客服响应时间、退款政策
行：Pro、99 元、2 小时内、7 天内可退
```

转换成 chunk 时，可以写成：

```text
在“会员等级权益”表中，Pro 等级的月费为 99 元，客服响应时间为 2 小时内，退款政策为 7 天内可退。
```

#### 图片和扫描件

图片需要 OCR 或多模态模型提取文本、图注、流程图关系。关键是保存置信度和页码。

低置信度 OCR 结果不应直接进入高风险问答，可以进入人工审核队列。

#### 代码块

代码文档要避免把函数签名、注释和示例调用拆开。metadata 应包含语言、文件路径、符号名。

```json
{
  "language": "python",
  "file_path": "billing/refund.py",
  "symbol": "create_refund",
  "title_path": ["退款服务", "创建退款单"]
}
```

### 8. Chunk 质量检查

索引前建议做自动质量检查，避免垃圾进索引。

检查项：

- 空文本或极短文本比例。
- 超长 chunk 比例。
- 重复 chunk 比例。
- OCR 乱码比例。
- 缺失 metadata 比例。
- chunk 是否包含标题路径。
- chunk 是否能追溯到原文页码或章节。
- Embedding 失败率和重试次数。

简单规则示例：

```python
def validate_chunk(chunk: dict) -> list[str]:
    errors = []

    text = chunk.get("text", "").strip()
    if len(text) < 20:
        errors.append("文本过短，通常不适合单独入库")
    if len(text) > 3000:
        errors.append("文本过长，可能导致向量语义被稀释")

    for field in ["document_id", "chunk_id", "source_uri", "tenant_id"]:
        if not chunk.get(field):
            errors.append(f"缺少必要元数据：{field}")

    if "page" not in chunk and "section" not in chunk:
        errors.append("缺少页码或章节信息，引用溯源会变差")

    return errors
```

面试时说明：这些规则不能保证语义质量，但能拦住大量工程低级错误。

### 9. 索引发布与回滚

生产系统不要把构建中的索引直接暴露给线上流量。

推荐方式：

```text
index_v1   当前线上版本
index_v2   后台构建中

构建 v2 -> 跑质量检查 -> 跑检索回归 -> 小流量验证 -> 切 alias 到 v2
```

发布要记录：

- 使用的解析器版本。
- 切分策略和参数。
- Embedding 模型版本。
- 索引类型和参数。
- 文档集合版本。
- 评测结果。

这样线上效果变差时，可以定位到底是解析器、切分、Embedding、索引参数还是文档内容变化。

### 10. 评估文档流水线效果

不要只评估最终答案，也要评估摄取和切分本身。

离线指标：

- 解析成功率。
- 有效文本覆盖率。
- 表格保留率。
- OCR 置信度分布。
- chunk 重复率。
- metadata 完整率。
- chunk 平均长度和长度分布。

检索指标：

- Recall@K：答案所在 chunk 是否被召回。
- MRR：第一个正确 chunk 排名。
- 可回答率：召回上下文是否足以回答问题。
- 引用准确率：答案引用是否指向正确页码和章节。
- 重复率：top_k 里重复或近似重复内容比例。

线上指标：

- 无答案率。
- 用户追问率。
- 人工转接率。
- 文档更新到可检索的延迟。
- 因过期知识导致的坏 Case 数。

## 四、参考架构

### 1. 模块拆分

```text
Ingestion Service
  ├── Connector Registry
  ├── Raw Document Store
  ├── Parser Worker
  ├── Cleaner / Normalizer
  ├── Chunker
  ├── Chunk Quality Checker
  ├── Embedding Worker
  ├── Index Writer
  ├── Index Publisher
  └── Ingestion Metadata DB
```

各模块职责：

- **Connector Registry**：管理不同数据源连接器和同步游标。
- **Raw Document Store**：保存原始文件，支持重放和重新解析。
- **Parser Worker**：把 PDF、Word、HTML 等解析成结构化 blocks。
- **Cleaner / Normalizer**：清理噪声，统一文本格式。
- **Chunker**：按结构、长度、语义规则生成 chunk。
- **Chunk Quality Checker**：拦截低质量 chunk。
- **Embedding Worker**：批量向量化，处理限流和重试。
- **Index Writer**：写入向量索引、关键词索引和 metadata。
- **Index Publisher**：完成版本切换、灰度和回滚。
- **Ingestion Metadata DB**：记录任务、版本、错误和构建参数。

### 2. 状态机设计

文档摄取任务建议显式建模状态：

```text
DISCOVERED
  -> DOWNLOADED
  -> PARSED
  -> CLEANED
  -> CHUNKED
  -> VALIDATED
  -> EMBEDDED
  -> INDEXED
  -> PUBLISHED
```

失败状态：

```text
PARSE_FAILED
VALIDATION_FAILED
EMBEDDING_FAILED
INDEX_FAILED
```

状态机的价值：

- 支持断点续跑。
- 支持失败重试。
- 支持定位瓶颈。
- 支持统计每个阶段的失败率。
- 支持把低置信度内容送人工审核。

### 3. 简化伪代码

```python
def ingest_document(doc: RawDocument) -> None:
    # 中文注释：先持久化原文，保证后续解析策略变化时可以重放
    raw_store.save(doc)

    parsed = parser.parse(doc)
    cleaned_blocks = cleaner.normalize(parsed.blocks)
    chunks = chunker.split(
        cleaned_blocks,
        title_path=parsed.title_path,
        metadata=doc.metadata,
    )

    valid_chunks = []
    for chunk in chunks:
        errors = validate_chunk(chunk)
        if errors:
            quality_log.record(chunk["chunk_id"], errors)
            continue
        valid_chunks.append(chunk)

    embeddings = embedding_client.batch_embed([c["text"] for c in valid_chunks])

    # 中文注释：写索引时使用文档版本，避免新旧版本同时污染线上检索
    index_writer.upsert_chunks(
        chunks=valid_chunks,
        embeddings=embeddings,
        index_version=doc.metadata["version"],
    )
```

这段代码面试时重点讲四件事：

1. 原文先落库，后面能重放。
2. 解析结果保留结构，不直接变成大字符串。
3. 入索引前做质量检查。
4. 索引写入带版本，方便发布和回滚。

## 五、常见工程坑

### 1. 只按固定字符数切分

固定长度切分快，但很容易把标题、定义、例外条件和操作步骤拆散。面试中如果只说“每 500 字切一下”，会显得没有做过真实知识库。

更好的做法是：先按标题、段落、表格和列表切，再对超长块递归切。

### 2. 忽略表格和图片

企业文档里的关键信息经常在表格和截图里。只抽正文会导致系统答不上价格、配置、阈值、审批条件等问题。

### 3. 缺少权限 metadata

如果 chunk 没有权限信息，后续很难保证不同租户、部门和角色的数据隔离。不要依赖 Prompt 告诉模型“不要回答无权限内容”，权限必须在检索层过滤。

### 4. 文档更新后旧 chunk 残留

这是 RAG 线上坏 Case 的高发原因。用户问最新政策，系统召回旧版本，答案看似有引用但实际过期。

### 5. 没有构建任务可观测性

摄取链路失败时，如果只知道“知识库没生效”，排查会很慢。每个阶段都要记录耗时、失败原因、输入输出数量和重试次数。

### 6. 过度依赖 LLM 做清洗

LLM 可以辅助结构化和修复格式，但不要让它无约束地“改写知识”。知识库内容要忠实于原文，否则引用溯源会失去可信度。

## 六、高频面试问题与参考答案

### Q1：如何设计一个企业知识库的文档摄取和索引构建流程？

**参考答案：**

我会把它设计成离线或准实时的流水线：首先通过连接器从文件系统、文档平台或数据库同步原始文档，并保存原文、source_uri、document_id、tenant_id、acl、version 等 metadata。然后解析不同格式，把 PDF、Word、HTML、表格、图片 OCR 转成结构化 blocks。接着做清洗规范化，去掉页眉页脚、乱码和重复模板，但保留标题、条款号、表头、页码等关键信息。

切分阶段不会只按固定长度切，而是优先按标题、段落、表格、列表结构切分，超长内容再递归拆分；需要精准召回和完整回答的场景可以用父子 chunk。chunk 生成后做质量检查，包括长度、重复率、metadata 完整率和溯源字段。最后批量生成 Embedding，写入向量索引、关键词索引和 metadata 索引。索引发布采用版本化方式，新版本先跑检索回归和小流量验证，再切 alias 到线上，必要时能回滚。

### Q2：chunk size 应该怎么设置？

**参考答案：**

我不会给一个固定值说适用于所有场景。chunk size 要结合文档结构、问题类型、Embedding 模型上下文长度和最终注入 LLM 的 token 预算来调。

比如 FAQ 可以一条问答一个 chunk；操作手册要把前置条件和步骤放在一起；政策文档适合按条款切；代码文档要避免截断函数和示例。经验上先按结构切分，再对超长块递归拆，最后用评测集看 Recall@K、可回答率、重复率、平均注入 token 和引用准确率。如果召回结果经常缺上下文，说明切得太碎；如果召回片段很长但答不上问题，可能切得太大或主题混杂。

### Q3：为什么 RAG 需要保留 metadata？

**参考答案：**

metadata 是 RAG 的安全、过滤、排序和溯源基础。至少要保留 tenant_id、acl、document_id、chunk_id、source_uri、title_path、page、updated_at、version 和 content_hash。

tenant_id 和 acl 用于权限过滤，必须在检索层执行；document_id 和 chunk_id 用于更新删除；source_uri、page 和 title_path 用于引用溯源；updated_at 和 version 用于处理新旧文档；content_hash 用于去重和增量更新。没有 metadata 的系统，即使向量召回效果不错，也很难上线到企业环境。

### Q4：文档更新后，如何保证检索结果不会召回旧内容？

**参考答案：**

首先要有稳定的 document_id 和版本字段。同步时通过更新时间、etag 或内容 hash 检测变化。文档变化后，可以按 chunk 级 diff 只重建变化部分；如果做不到，也至少按 document_id 删除旧版本 chunk，再写入新版本。

线上检索默认只查当前生效版本。索引发布最好用 alias 或版本切换：新版本在后台构建，完成质量检查和回归评测后再切流。删除文档时不能只删原文，还要删除或标记向量索引、关键词索引和 metadata 索引中的对应 chunk。高风险场景可以保留历史版本用于审计，但不能默认参与问答。

### Q5：PDF 解析质量差会怎么影响 RAG？怎么处理？

**参考答案：**

PDF 解析差会直接影响切分和召回。常见问题包括换行错乱、页眉页脚混入正文、表格列关系丢失、扫描件 OCR 错字、页码缺失。最终表现是召回片段看起来相关但语义不完整，或者引用页码不准确。

处理上要先区分文字层 PDF 和扫描件 PDF。文字层 PDF 用版面解析保留标题、段落、表格和页码；扫描件需要 OCR，并记录置信度。对页眉页脚和目录重复项做规则清洗。表格要保留表头和行列关系，必要时转成自然语言描述。低置信度 OCR 或关键合同条款可以进入人工审核，不要直接进入高风险问答。

### Q6：父子 chunk 是什么？什么时候用？

**参考答案：**

父子 chunk 是把文档切成两种粒度：小 chunk 用于检索，大 chunk 或父章节用于提供上下文。小 chunk 更容易精准匹配用户问题，但可能缺少上下文；父 chunk 能提供完整解释，但直接用于向量召回可能太粗。

例如产品手册中，一个小 chunk 命中“退款时限”，系统可以把它所在的“售后政策”章节作为父 chunk 一起注入给 LLM。适合政策、手册、长文档、代码文档等需要局部命中但回答要完整背景的场景。代价是索引和上下文组装更复杂，要避免把过大的父 chunk 全量塞进 prompt。

### Q7：如何做文档摄取流水线的可观测性？

**参考答案：**

我会按阶段记录指标：同步阶段看新增、修改、删除数量和同步延迟；解析阶段看解析成功率、失败原因、文本覆盖率、OCR 置信度；切分阶段看 chunk 数量、平均长度、超长/过短比例、重复率；索引阶段看 Embedding 成功率、重试次数、索引写入延迟；发布阶段看版本、评测结果和切流状态。

线上还要把坏 Case 关联回 chunk_id、document_id、parser_version、chunker_version 和 embedding_model_version。这样当答案变差时，能判断是文档内容变了、解析器变了、切分参数变了，还是模型和索引参数变了。

### Q8：如何避免重复内容影响召回？

**参考答案：**

我会在多个层级去重。文件级用 source_uri 和文件 hash 识别重复上传；段落级对规范化文本做 hash，去掉页眉页脚和模板重复；语义级可以用 SimHash、MinHash 或 Embedding 相似度识别轻微改写；检索结果级按 document_id、title_path 或内容相似度合并，避免 top_k 被同一段内容刷屏。

但去重不能破坏版本审计。历史版本可以保留在存储层，但默认检索只查当前版本。

## 七、面试速记

- RAG 效果很大程度取决于知识入库质量，不只是模型和向量数据库。
- 摄取时必须保留稳定 ID、来源、版本、权限和页码。
- 解析结果最好是结构化 blocks，不要一开始就压成纯文本。
- 切分优先利用文档结构，固定长度只能作为兜底。
- chunk size 要通过评测调，不要迷信固定数字。
- metadata 是权限过滤、时效排序、引用溯源和增量更新的基础。
- 文档更新要处理旧 chunk 删除、索引版本和发布回滚。
- 表格、图片、代码块需要专门处理，否则企业知识库会漏掉关键答案。
- 入索引前做质量检查，防止垃圾内容污染检索。
- 评估要覆盖解析成功率、metadata 完整率、Recall@K、可回答率和引用准确率。
