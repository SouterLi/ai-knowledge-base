## 一、为什么这是高频考点

普通 RAG 擅长回答“某个片段里直接有答案”的问题，但在下面几类场景里容易失效：

1. 问题需要跨多个文档、多个人物、多家公司或多个事件做关联。
2. 用户问的是“某个组织的整体风险”“一个项目的关键依赖”“某类故障的共性原因”。
3. 文档里充满实体、关系、时间线和层级结构，仅靠向量相似度容易召回碎片化上下文。
4. 面试官希望确认候选人是否理解 RAG 从“文本块检索”升级到“结构化知识检索”的工程代价。

一句话回答：

> GraphRAG 的核心不是把向量数据库换成图数据库，而是在 RAG 链路中显式建模实体、关系、社区和路径，让系统能围绕“关系”和“全局结构”组织上下文。

## 二、核心概念

### 1. GraphRAG

GraphRAG 是一种用图结构增强检索增强生成的方案。它通常会从文档中抽取实体和关系，形成知识图谱，再把图谱检索、图遍历、社区摘要和向量检索结合起来，为 LLM 提供更有结构的上下文。

典型输入不是单个 chunk，而是：

- 实体：人、组织、产品、系统、指标、故障、政策条款等。
- 关系：隶属、依赖、影响、导致、负责、引用、发生于、相似于等。
- 证据：关系来自哪个文档、哪个段落、哪个时间点。
- 摘要：实体摘要、社区摘要、路径摘要。

### 2. 知识图谱

知识图谱可以理解为“实体 + 关系 + 属性 + 证据”的结构化知识网络。

常见表示：

```text
(订单服务)-[:依赖]->(支付服务)
(支付服务)-[:调用]->(风控服务)
(风控服务)-[:产生]->(拦截率升高)
```

面试要点：

- 图谱不是越大越好，关键是实体规范化、关系可信度和可追溯证据。
- 关系要能服务业务问题，不能只抽取“看起来像关系”的三元组。
- 图谱质量会直接影响最终答案质量，错误关系比漏召回更危险。

### 3. 实体抽取与实体消歧

实体抽取是从文本中识别关键对象，实体消歧是把不同写法归并为同一个实体。

例子：

| 文本写法 | 归一化实体 |
| --- | --- |
| GPT-4 Turbo | GPT-4 Turbo |
| gpt4-turbo | GPT-4 Turbo |
| 客服系统 | Customer Support Platform |
| CSP | Customer Support Platform |

高频追问：

- “苹果”到底是水果、公司，还是某个商品名？
- “张三”在多个部门出现时是不是同一个人？
- “订单服务 v2”和“订单服务”要不要合并？

工程上通常需要结合：

- 字典和别名表。
- 规则归一化。
- Embedding 相似度。
- LLM 判断。
- 人工审核高价值实体。

### 4. 关系抽取

关系抽取用于识别实体之间的边。

常见关系类型：

- 组织关系：归属、负责、协作。
- 系统关系：依赖、调用、发布、回滚。
- 因果关系：导致、缓解、触发。
- 时间关系：发生于、早于、晚于。
- 引用关系：文档引用、政策依据、法规条款。

面试中要强调：关系抽取要输出证据，不要只输出边。

```json
{
  "source": "支付服务",
  "relation": "依赖",
  "target": "风控服务",
  "evidence": "支付服务在下单链路中会调用风控服务判断交易风险。",
  "doc_id": "incident_2026_04_12",
  "confidence": 0.86
}
```

### 5. 社区检测与社区摘要

当图谱变大后，可以按实体连接关系做社区检测，例如把同一个业务域、同一个事故链路或同一类政策条款聚合在一起。

社区摘要用于回答“全局问题”：

- “这个系统最大的稳定性风险是什么？”
- “这些投诉主要集中在哪些产品能力？”
- “过去一个季度的故障共性原因是什么？”

注意：社区摘要是预计算的中间产物，适合提升全局问答效率，但必须记录版本和来源，否则很难审计。

### 6. Local Search 与 Global Search

GraphRAG 常见两类检索：

| 检索方式 | 适合问题 | 上下文来源 |
| --- | --- | --- |
| Local Search | 某个实体、关系或路径的具体问题 | 邻居节点、相关边、证据 chunk、路径摘要 |
| Global Search | 全局趋势、主题归纳、风险总结 | 社区摘要、主题摘要、跨社区聚合结果 |

例子：

- Local Search：“支付服务为什么会影响订单成功率？”
- Global Search：“这些故障报告反映了哪些共性架构问题？”

## 三、典型架构

### 1. 离线构建链路

```text
文档接入
  -> 清洗与切分
  -> 实体抽取
  -> 关系抽取
  -> 实体消歧与合并
  -> 图谱入库
  -> 实体/关系/社区摘要生成
  -> 向量索引与图索引同步
```

关键工程点：

1. 抽取任务要可重放：Prompt、模型、输入文档版本都要记录。
2. 图谱更新要增量化：不能每次全量重建。
3. 关系必须带证据：答案里要能引用原文。
4. 图谱和向量索引要保持一致：删除文档时要删除关联节点、边、摘要和向量。

### 2. 在线查询链路

```text
用户问题
  -> 意图识别：实体型 / 关系型 / 全局总结型
  -> 实体链接：识别问题中的实体
  -> 检索策略选择：向量检索 / 图检索 / 混合检索
  -> 图遍历与路径裁剪
  -> 证据 chunk 与摘要组装
  -> LLM 生成
  -> 引用溯源与答案校验
```

面试要点：

- 不要所有问题都走 GraphRAG，简单事实问答用普通 RAG 更便宜。
- 图遍历要限制深度、边类型和候选数量，否则容易引入噪声。
- 最终上下文仍然要回到原文证据，不能只喂“抽取出来的关系”。

### 3. 存储组件选择

常见组合：

| 组件 | 作用 | 示例 |
| --- | --- | --- |
| 对象存储 | 保存原始文档和解析结果 | S3、OSS、MinIO |
| 关系型数据库 | 保存任务、版本、租户、权限、元数据 | PostgreSQL、MySQL |
| 图数据库 | 保存实体、关系和路径查询 | Neo4j、NebulaGraph、Amazon Neptune |
| 搜索引擎 | 关键词检索和过滤 | Elasticsearch、OpenSearch |
| 向量数据库 | 语义召回 | Milvus、Qdrant、pgvector |
| 缓存 | 热门实体、路径和摘要缓存 | Redis |

如果数据规模不大，也可以先用 PostgreSQL 表模拟图结构，避免过早引入图数据库。

## 四、核心知识点

### 1. GraphRAG 解决什么问题

适合 GraphRAG 的问题通常有三个信号：

1. 问题围绕实体和关系，而不是单个文本片段。
2. 答案需要多跳推理或跨文档汇总。
3. 用户需要解释“为什么”和“如何关联”，而不是只要一句事实。

不适合的场景：

- 文档很少，普通全文检索已经足够。
- 业务问题不依赖实体关系。
- 数据频繁变化但没有能力维护图谱一致性。
- 只需要语义搜索，不需要关系推理。

### 2. 图谱构建的质量控制

质量问题主要来自：

- 实体漏抽：关键对象没有进入图谱。
- 实体误合并：两个不同实体被合并。
- 实体重复：同一个实体存在多个节点。
- 关系误抽：模型编造关系。
- 关系过泛：大量“相关于”“涉及”等低价值关系。
- 证据缺失：无法回到原文验证。

常用控制手段：

1. 关系类型白名单：只抽取业务需要的边。
2. 结构化输出校验：JSON Schema 或 Pydantic 校验。
3. 置信度阈值：低置信关系进入人工审核或延迟入库。
4. 证据强约束：没有原文证据的边不入库。
5. 抽样评估：按实体类型、关系类型、数据源分层抽检。
6. 回归评测：构建多跳问答集，观察答案是否稳定。

### 3. 检索策略设计

常见策略：

| 策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 实体邻居检索 | 找到问题实体的一跳或两跳邻居 | 简单稳定 | 可能漏掉远距离关系 |
| 路径检索 | 寻找两个实体之间的路径 | 适合解释关联 | 路径过多时噪声大 |
| 社区摘要检索 | 召回相关社区摘要 | 适合全局总结 | 摘要过期会误导 |
| 向量 + 图混合 | 先向量召回，再图扩展或反过来 | 召回更全面 | 需要排序融合 |
| 元数据过滤 | 按租户、权限、时间、业务域过滤 | 保证安全与相关性 | 过滤过严会召回不足 |

面试中可以说：

> 我会先判断问题类型。具体实体问题走实体链接和邻居检索；两个实体关系问题走路径检索；全局总结问题走社区摘要；不确定时用向量召回兜底，再用图结构扩展候选。

### 4. 混合排序

GraphRAG 通常要融合多种分数：

- 向量相似度。
- BM25 分数。
- 图距离。
- 边置信度。
- 证据新鲜度。
- 权限和业务优先级。
- reranker 分数。

简单融合示例：

```python
def rank_candidate(candidate):
    # 图距离越短越可信，但不能让它压过原文相关性
    graph_score = 1 / (1 + candidate.graph_distance)

    # 新鲜度用于处理政策、事故、价格等时效性强的问题
    freshness_score = min(candidate.days_since_update, 365) / 365
    freshness_score = 1 - freshness_score

    return (
        0.40 * candidate.vector_score
        + 0.25 * candidate.rerank_score
        + 0.20 * graph_score
        + 0.10 * candidate.edge_confidence
        + 0.05 * freshness_score
    )
```

这个公式不是标准答案，面试重点是说明：不同来源的分数要归一化、可解释、可调参，并通过离线评测验证权重。

### 5. 多跳推理

多跳推理是 GraphRAG 的高频考点。

例子：

> “订单成功率下降和风控策略发布有什么关系？”

可能路径：

```text
订单成功率下降
  <- 影响 - 支付失败率上升
  <- 导致 - 风控拦截率升高
  <- 发生于 - 风控策略 v3 发布
```

回答时不能只把路径丢给 LLM，还要提供每条边的证据：

- 哪份事故报告说明支付失败率上升。
- 哪个监控指标说明风控拦截率升高。
- 哪个发布记录说明风控策略 v3 上线。

### 6. 权限与多租户

GraphRAG 比普通 RAG 更容易出现权限泄露。

风险点：

- 两个租户的实体被合并到同一个节点。
- 图遍历跨越了用户无权访问的边。
- 社区摘要混入了用户无权访问的文档。
- 缓存的实体摘要被不同权限用户复用。

工程要求：

1. 节点、边、证据、摘要都要带权限标签。
2. 图遍历前、遍历中、上下文组装时都要做权限过滤。
3. 社区摘要要按权限范围生成，或者只用于内部高权限场景。
4. 缓存 key 必须包含租户、角色、数据范围和版本。

### 7. 更新与一致性

GraphRAG 的难点不只是构建，而是持续更新。

常见问题：

- 文档删除后，实体和关系没有删除。
- 实体摘要还是旧版本。
- 社区结构变化，但社区摘要没有重算。
- 同一个实体的新旧别名没有合并。
- 图索引和向量索引版本不一致。

推荐做法：

- 每条边记录来源文档和抽取任务版本。
- 使用软删除和异步清理任务。
- 为实体摘要、社区摘要保存依赖的节点和边版本。
- 查询时只使用同一数据快照版本。
- 对高价值关系做人工审核或审批流。

## 五、代码与结构化示例

### 1. 抽取三元组的结构化 Prompt

```text
你是企业知识图谱抽取器。请只从原文中抽取明确出现的实体和关系。

要求：
1. 只能输出 JSON。
2. 关系必须来自允许列表：["依赖", "调用", "导致", "缓解", "负责", "发布", "回滚"]。
3. 每条关系必须包含原文证据。
4. 如果证据不足，不要猜测。

输入文本：
{{chunk_text}}

输出格式：
{
  "entities": [
    {"name": "实体名称", "type": "系统|团队|指标|事件|策略"}
  ],
  "relations": [
    {
      "source": "源实体",
      "relation": "关系",
      "target": "目标实体",
      "evidence": "原文证据",
      "confidence": 0.0
    }
  ]
}
```

### 2. 图检索伪代码

```python
def retrieve_with_graph(question, user_scope):
    # 识别问题中的实体，并把别名映射到标准实体
    entities = link_entities(question)

    # 根据问题类型选择检索策略
    intent = classify_question_intent(question)

    if intent == "global_summary":
        candidates = search_community_summaries(question, user_scope)
    elif len(entities) >= 2:
        candidates = search_paths_between_entities(entities, user_scope)
    else:
        candidates = expand_neighbors(entities, max_depth=2, user_scope=user_scope)

    # 补充原文证据，避免只依赖抽取后的边
    evidence_chunks = load_evidence_chunks(candidates, user_scope)

    # 用重排模型控制最终上下文质量
    reranked = rerank(question, evidence_chunks)

    return build_context(reranked, token_budget=6000)
```

### 3. 图数据库查询示例

```cypher
// 查询订单服务两跳内的依赖和故障影响链路
MATCH path = (s:Entity {name: "订单服务"})-[r:DEPENDS_ON|CALLS|CAUSES*1..2]-(n:Entity)
WHERE all(edge IN relationships(path) WHERE edge.tenant_id = $tenant_id)
RETURN path
LIMIT 20
```

面试说明：

- `*1..2` 是深度限制，避免无限扩展。
- `tenant_id` 是权限边界的一部分。
- 真实系统还会加时间范围、实体类型、边置信度和业务域过滤。

## 六、评估指标

### 1. 图谱构建指标

| 指标 | 含义 |
| --- | --- |
| Entity Precision | 抽取出的实体有多少是正确的 |
| Entity Recall | 应抽取实体中有多少被抽到 |
| Relation Precision | 抽取关系有多少是正确的 |
| Relation Recall | 应抽取关系中有多少被抽到 |
| Evidence Coverage | 关系中带可验证证据的比例 |
| Duplicate Entity Rate | 重复实体比例 |
| Wrong Merge Rate | 错误合并实体比例 |

### 2. 检索指标

| 指标 | 含义 |
| --- | --- |
| Path Recall | 正确答案路径是否被召回 |
| Context Precision | 最终上下文中有效证据占比 |
| Multi-hop Recall | 多跳问题所需证据是否完整 |
| Permission Violation Rate | 是否召回无权访问内容 |
| Latency P95 | 图检索和混合检索尾延迟 |

### 3. 生成指标

| 指标 | 含义 |
| --- | --- |
| Answer Faithfulness | 答案是否忠实于证据 |
| Citation Accuracy | 引用是否指向真实证据 |
| Reasoning Completeness | 多跳解释是否缺关键环节 |
| Hallucination Rate | 是否编造不存在关系 |
| User Helpfulness | 用户是否觉得答案有用 |

## 七、常见坑

### 1. 把 GraphRAG 当成“LLM 抽三元组 + Neo4j”

只建图不等于 GraphRAG。真正的难点是实体消歧、证据管理、权限过滤、检索策略、排序融合、图谱更新和评估闭环。

### 2. 关系类型太泛

如果大部分边都是“相关于”“涉及”“提到”，图谱对问答几乎没有帮助。关系类型应该来自业务问题和下游检索需求。

### 3. 只给 LLM 图关系，不给原文证据

抽取结果可能有错。最终答案应优先引用原文证据，图关系用于组织和扩展检索。

### 4. 图遍历不做裁剪

图遍历深度越大，候选噪声越多，延迟越高。一般要限制：

- 最大跳数。
- 边类型。
- 实体类型。
- 时间范围。
- 权限范围。
- top-k 候选数量。

### 5. 忽略摘要版本

社区摘要、实体摘要看起来像“静态知识”，但底层文档变化后必须重算或标记过期。否则会出现引用正确、结论过期的问题。

## 八、高频面试问题与参考答案

### Q1：GraphRAG 和普通 RAG 的区别是什么？

**参考答案：**

普通 RAG 主要围绕文本 chunk 做语义检索和重排，适合答案直接存在于若干片段里的问题。GraphRAG 会把文档中的实体、关系、路径和社区结构建模出来，检索时可以利用图遍历、路径查询和社区摘要。它更适合多跳推理、关系密集型问答和全局总结类问题，但构建和维护成本更高。

---

### Q2：GraphRAG 一定需要图数据库吗？

**参考答案：**

不一定。小规模场景可以用关系型数据库保存节点表和边表，再配合递归查询或应用层遍历。图数据库适合关系多、路径查询频繁、遍历深度复杂的场景。选型关键不是“是否用了图数据库”，而是查询模式、数据规模、权限过滤、运维成本和团队熟悉度。

---

### Q3：GraphRAG 的离线构建链路怎么设计？

**参考答案：**

我会先做文档接入、清洗和切分，然后用规则、模型或 LLM 抽取实体和关系。抽取结果要经过结构化校验、实体消歧、关系置信度过滤和证据绑定，再写入图存储。之后生成实体摘要、社区摘要，并同步构建向量索引。所有任务都要记录文档版本、Prompt 版本、模型版本和抽取任务版本，方便回放和回滚。

---

### Q4：如何降低 LLM 抽取关系时的幻觉？

**参考答案：**

可以从四层控制：第一，Prompt 明确要求只从原文抽取，不允许猜测；第二，关系类型使用白名单，避免泛化关系；第三，结构化输出校验，每条边必须带原文证据和置信度；第四，低置信关系进入人工审核或不入库。上线后还要通过抽样评估和多跳问答回归集持续监控。

---

### Q5：实体消歧怎么做？

**参考答案：**

实体消歧通常结合规则和模型。先做标准化，比如大小写、空格、版本号、别名表；再用上下文 Embedding 判断语义相似；对于高价值实体可以让 LLM 基于上下文判断是否同一实体；最后对关键实体引入人工审核。重要的是保留 alias、source 和 merge history，错误合并要能回滚。

---

### Q6：GraphRAG 如何处理多跳问题？

**参考答案：**

先做实体链接，找出问题中的关键实体；如果有多个实体，就查它们之间的候选路径；如果只有一个实体，就扩展一跳或两跳邻居。路径结果要按边类型、图距离、置信度、时间和权限过滤，再加载每条边对应的原文证据。最终让 LLM 基于“路径 + 证据”生成答案，并输出引用。

---

### Q7：GraphRAG 和知识图谱问答有什么区别？

**参考答案：**

知识图谱问答更依赖结构化图谱本身，答案常来自图查询结果。GraphRAG 则把图谱作为检索增强的一部分，最终仍然会结合原文证据、文本 chunk、摘要和 LLM 生成。GraphRAG 更强调非结构化文档到图结构的自动构建，以及图检索与文本检索的融合。

---

### Q8：如何设计 GraphRAG 的权限控制？

**参考答案：**

节点、边、证据 chunk、实体摘要和社区摘要都要带权限信息。检索时不能只在最后过滤上下文，而要在实体链接、图遍历、证据加载、摘要召回和缓存读取阶段都做权限过滤。多租户场景下实体合并也要受租户边界约束，缓存 key 要包含租户、角色、数据范围和数据版本。

---

### Q9：GraphRAG 的评估怎么做？

**参考答案：**

要分三层评估。第一层评估图谱质量，包括实体准确率、关系准确率、证据覆盖率和错误合并率。第二层评估检索质量，包括路径召回、多跳证据完整性、上下文有效证据占比和权限违规率。第三层评估生成质量，包括忠实度、引用准确率、幻觉率和用户满意度。只看最终答案分数不够，因为无法定位问题出在抽取、检索还是生成。

---

### Q10：什么时候不应该使用 GraphRAG？

**参考答案：**

如果文档规模小、问题主要是单片段事实问答、关系结构不重要，普通 RAG 更简单。另一个不适合的情况是数据变化很快但团队没有能力维护图谱一致性，这会导致图谱和原文不同步。GraphRAG 的收益来自关系结构，如果业务问题不依赖关系，就不应该为了架构复杂度而引入它。

---

### Q11：GraphRAG 如何和向量检索融合？

**参考答案：**

常见做法有两种。第一种是先向量召回相关 chunk，再从 chunk 关联的实体扩展邻居和路径；第二种是先做实体链接和图遍历，再加载相关证据 chunk，并用向量或 reranker 重排。最终排序可以融合向量相似度、图距离、边置信度、证据新鲜度和 reranker 分数。实际选择取决于问题类型和延迟预算。

---

### Q12：社区摘要有什么价值和风险？

**参考答案：**

社区摘要适合回答全局总结类问题，可以把大量实体和关系压缩成主题级上下文，降低在线检索和生成成本。风险是摘要可能过期、过度概括或混入无权限内容。因此社区摘要要保存依赖的数据版本、生成时间、权限范围和来源证据，必要时按租户或权限范围分别生成。

---

## 九、面试回答模板

当面试官问“你会怎么设计 GraphRAG 系统”时，可以按下面结构回答：

1. **先判断必要性**：是否存在多跳、关系密集、全局总结问题。
2. **离线构建**：文档清洗、实体抽取、关系抽取、实体消歧、证据绑定、图谱入库、摘要生成。
3. **在线检索**：意图识别、实体链接、图检索、向量检索、路径裁剪、重排和上下文组装。
4. **质量控制**：关系白名单、结构化校验、证据强约束、抽样评估、回归问答集。
5. **安全治理**：节点、边、证据、摘要全链路权限过滤。
6. **更新机制**：增量更新、版本快照、摘要重算、删除传播。
7. **评估指标**：图谱质量、检索质量、生成忠实度、延迟和成本。

简短版：

> 我会把 GraphRAG 设计成“图谱构建 + 混合检索 + 证据生成 + 质量治理”的闭环。图结构负责组织实体关系和多跳路径，向量检索负责语义召回，最终答案必须回到原文证据，并且全链路要处理权限、版本和评估问题。
