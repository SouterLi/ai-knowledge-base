# AI 应用开发面试主题：Embedding 与向量索引工程

## 主题选择记录

- 本次主题：Embedding 与向量索引工程
- 所属分类：RAG
- 已回顾历史主题：RAG 系统设计、Agent、Prompt 工程、评估与可观测性、安全防护、上下文工程、流式异步、多模态、成本缓存限流、模型网关、工作流编排、微调、MCP、推理性能、数据闭环
- 不重复原因：已有 RAG 文档讲完整检索增强生成链路；本主题聚焦 RAG 链路中最容易被追问的 **Embedding 模型选型、向量索引、元数据过滤、增量更新、容量规划和召回调优**。

## 一、为什么这是高频考点

很多候选人会说“把文档转成向量，存进向量数据库，再相似度搜索”，但面试官继续追问时常见卡点是：

- 为什么召回结果语义相似但答不上问题？
- HNSW、IVF、PQ 这些索引到底在权衡什么？
- metadata 过滤放在向量召回前还是召回后？
- 文档更新、删除和重建索引怎么做？
- 向量维度、top_k、chunk 数量、QPS 和内存成本怎么估算？
- 如何评估 Embedding 或索引调整是否真的有效？

Embedding 与向量索引是 RAG 的“地基”。生成模型再强，如果召回层把错误上下文送进去，最终答案仍会幻觉。面试中要把它讲成一个工程系统，而不是一个数据库 API 调用。

## 二、核心概念

### 1. Embedding

Embedding 是把文本、图片或多模态内容映射成向量的过程。向量空间中距离更近，通常表示语义更相似。

面试中要补一句：Embedding 不是“理解事实正确性”，它只是把输入映射到语义空间。两个句子语义接近，不代表其中一个能回答另一个。

### 2. 向量相似度

常见相似度指标：

| 指标 | 含义 | 适合场景 |
| --- | --- | --- |
| Cosine Similarity | 比较向量方向 | 文本语义检索最常见 |
| Dot Product | 点积，受向量长度影响 | 部分模型训练目标直接优化点积 |
| Euclidean Distance | 欧氏距离 | 图像、聚类或特定向量空间 |

实务中不要随意切换指标。Embedding 模型通常会说明推荐使用 cosine、dot product 还是 L2。索引库的距离配置要和模型训练方式一致。

### 3. 精确检索与近似最近邻

- **精确检索**：逐个计算 query 向量和所有文档向量的距离，结果准确但成本高。
- **近似最近邻**：通过索引结构减少比较次数，牺牲少量召回精度换取低延迟和高吞吐。

生产环境数据量一大，通常使用 ANN（Approximate Nearest Neighbor，近似最近邻）。

### 4. 向量索引

向量索引是为了加速相似向量查找的数据结构。常见类型：

- **HNSW**：图索引，召回质量高、查询快、内存占用较大。
- **IVF**：倒排文件索引，先聚类再在部分簇内搜索，适合大规模数据。
- **PQ / SQ**：量化压缩，用更少内存存向量，通常会损失精度。
- **Flat**：不建近似索引，精确暴力搜索，适合小数据或离线评测基准。

### 5. Metadata 过滤

Metadata 是文档向量以外的结构化字段，例如：

- `tenant_id`
- `user_group`
- `document_id`
- `source`
- `language`
- `created_at`
- `version`
- `acl`

企业 RAG 中 metadata 过滤不是锦上添花，而是权限、安全、时效性和可解释性的基础。

## 三、核心知识点

### 1. Embedding 模型怎么选

重点看这些维度：

1. **语义效果**：是否适配业务语言、领域术语、问答表达方式。
2. **多语言能力**：中文、英文、代码、专有名词是否稳定。
3. **向量维度**：维度越高通常表达能力更强，但存储和计算成本更高。
4. **上下文长度**：单次可编码文本长度，影响 chunk 策略。
5. **吞吐与延迟**：批量导入、在线 query 是否满足 SLA。
6. **成本与部署方式**：API 调用成本、本地部署显存、批处理能力。
7. **版本稳定性**：模型升级后旧向量是否需要重建。

面试回答不要只说“选效果最好的”。生产环境要在效果、延迟、成本、可部署性和版本治理之间取平衡。

### 2. Chunk 与 Embedding 的关系

Embedding 的输入通常不是整篇文档，而是切分后的 chunk。常见问题：

- chunk 太小：语义不完整，召回片段缺少上下文。
- chunk 太大：向量表示变得模糊，召回不准，送入 LLM 的 token 成本高。
- overlap 太小：跨段信息断裂。
- overlap 太大：索引体积膨胀，召回结果重复。

建议面试表达：

> chunk 策略要结合文档结构、业务问题类型和评估集调参，而不是固定 500 字或 1000 token。

### 3. 推荐的向量数据模型

向量库里不要只存向量。更合理的数据结构：

```json
{
  "chunk_id": "doc_123#chunk_008",
  "document_id": "doc_123",
  "tenant_id": "tenant_a",
  "text": "原始 chunk 文本",
  "embedding": [0.12, -0.03, 0.88],
  "metadata": {
    "title": "退款流程说明",
    "section": "售后政策",
    "source": "help_center",
    "language": "zh",
    "version": 3,
    "acl": ["support", "admin"]
  }
}
```

字段设计要支持：

- 权限过滤。
- 文档更新和删除。
- 引用溯源。
- 线上问题排查。
- 按来源、语言、时间范围检索。

### 4. HNSW 面试重点

HNSW（Hierarchical Navigable Small World）可以理解为多层图搜索：

- 上层图连接少，用于快速跳转到大致区域。
- 底层图连接多，用于精细搜索近邻。
- 查询时从高层往低层逐步逼近目标向量。

关键参数：

| 参数 | 含义 | 影响 |
| --- | --- | --- |
| `M` | 每个节点最大连接数 | 越大召回越好，内存越高 |
| `efConstruction` | 建索引时搜索宽度 | 越大索引质量越高，构建越慢 |
| `efSearch` | 查询时搜索宽度 | 越大召回越高，延迟越高 |

面试中要说清楚：HNSW 的调优本质是 **召回率、延迟、内存和构建时间** 的权衡。

### 5. IVF 和 PQ 适合什么场景

当数据量从百万级增长到千万级、亿级，HNSW 内存压力可能变大。这时常见思路：

- IVF：先把向量聚成多个簇，查询时只搜索最相关的若干簇。
- PQ：把高维向量分段量化，用较小编码近似表示原向量。
- IVF + PQ：先粗召回，再用压缩向量快速算距离。

代价是召回精度下降，需要靠更大的候选集、rerank 或混合检索补回来。

### 6. 过滤应该在召回前还是召回后

这是高频追问。

正确回答要分情况：

1. **权限过滤必须尽量前置**：不能先召回无权限内容再交给模型或应用层“过滤掉”，因为敏感内容已经进入检索链路。
2. **高选择性过滤适合前置**：例如只查某个租户、某个知识库、某个文档类型。
3. **复杂业务规则可能后置补充**：例如按时间、点击率、质量分做 rerank，但不能替代权限过滤。
4. **要关注过滤与 ANN 的交互**：过滤条件太严格时，ANN 可能找不到足够候选，需要扩大搜索范围或使用分区索引。

一句话总结：

> 权限和租户过滤要前置，排序和质量增强可以后置；如果前置过滤导致候选不足，就要调整索引分区、扩大搜索参数或走混合检索。

### 7. 向量更新与删除

文档变化后，不能只更新业务数据库。常见策略：

- **新增文档**：解析、切分、生成向量、写入索引。
- **更新文档**：生成新版本 chunk，替换旧版本或标记旧版本失效。
- **删除文档**：删除向量或打 `deleted=true` 软删除标记，并定期 compact。
- **权限变化**：更新 metadata 或重建受影响 chunk 的权限字段。
- **Embedding 模型升级**：通常需要全量重嵌入，不能新旧模型向量直接混用。

面试中可以强调“版本字段”：

```text
document_id + chunk_index + document_version + embedding_model_version
```

这样可以追踪一个召回结果来自哪个文档版本和哪个 Embedding 模型版本。

### 8. 混合检索为什么必要

单纯向量检索对语义相近问题友好，但对这些内容不稳定：

- 错误码。
- 人名、产品名、SKU。
- API 名称。
- 法条编号。
- 代码符号。
- 非常短的查询。

因此企业 RAG 常用混合检索：

```text
query
  -> 向量召回 top_k=50
  -> BM25 召回 top_k=50
  -> 合并去重
  -> Reranker 重排
  -> 取 top_n 进入上下文
```

面试要点：Embedding 不是搜索引擎的全部。关键词检索、metadata 过滤、业务排序和 rerank 共同决定最终上下文质量。

### 9. 容量规划怎么算

粗略估算公式：

```text
向量原始存储 = 向量数量 * 向量维度 * 每个 float 字节数
```

例如：

```text
1,000,000 个 chunk * 1536 维 * 4 字节 ≈ 6 GB
```

但生产环境还要考虑：

- HNSW 图结构额外内存。
- metadata 和原文存储。
- 多副本。
- 索引构建临时空间。
- 版本并存期间的双倍存储。
- 日志、备份和快照。

所以面试中不要只报原始向量大小，要说明索引和副本会显著放大资源需求。

### 10. 召回效果如何评估

离线评估集至少包含：

- query。
- 标准相关文档或 chunk。
- 可接受答案。
- 难例标签，例如短 query、术语、跨章节、多语言。

常见指标：

| 指标 | 说明 |
| --- | --- |
| Recall@K | 正确 chunk 是否出现在前 K 个候选里 |
| Precision@K | 前 K 个候选中相关内容占比 |
| MRR | 第一个正确结果排名越靠前越好 |
| NDCG | 考虑排序位置和相关性等级 |
| Coverage | 有多少问题能召回足够证据 |

不要只看最终答案准确率。最终答案受 LLM、Prompt、rerank、上下文组装影响，不能单独定位 Embedding 和索引问题。

## 四、工程链路示例

### 1. 文档入库流程

```text
文档上传
  -> 权限校验
  -> 文档解析
  -> 结构化切分
  -> chunk 清洗
  -> 批量生成 Embedding
  -> 写入向量库和元数据
  -> 构建或更新索引
  -> 抽样评估召回质量
```

关键点：

- 入库失败要可重试。
- 同一文档重复上传要幂等。
- 原文、chunk、向量和索引状态要能对账。
- 需要记录模型版本、解析版本和切分策略版本。

### 2. 在线检索流程

```text
用户问题
  -> 鉴权和租户识别
  -> query 改写或归一化
  -> 生成 query embedding
  -> metadata 前置过滤
  -> 向量召回 + 关键词召回
  -> 合并去重
  -> rerank
  -> 上下文裁剪
  -> 交给 LLM 生成答案
```

关键点：

- query embedding 要和文档 embedding 使用同一个或兼容模型。
- 检索日志要记录 query、过滤条件、top_k、索引版本和召回分数。
- 不要把低分候选无脑塞进上下文。

### 3. Python 伪代码

```python
from dataclasses import dataclass


@dataclass
class SearchRequest:
    query: str
    tenant_id: str
    user_roles: list[str]
    top_k: int = 20


def search_knowledge_base(request: SearchRequest):
    # 权限条件必须进入检索层，不能等模型生成后再过滤
    filters = {
        "tenant_id": request.tenant_id,
        "acl": {"$overlap": request.user_roles},
        "deleted": False,
    }

    # query 向量模型要与文档入库时的模型版本保持一致
    query_vector = embedding_model.encode(request.query)

    vector_hits = vector_store.search(
        vector=query_vector,
        filters=filters,
        top_k=request.top_k,
        ef_search=128,
    )

    keyword_hits = keyword_store.search(
        query=request.query,
        filters=filters,
        top_k=request.top_k,
    )

    candidates = merge_and_deduplicate(vector_hits, keyword_hits)
    reranked = reranker.rank(request.query, candidates)

    # 只把高相关、可溯源、权限正确的片段交给生成模型
    return reranked[:8]
```

这段代码面试时不需要逐行讲实现，重点是表达三件事：

1. 权限过滤进入检索层。
2. 向量召回和关键词召回并行。
3. 最终上下文经过去重和 rerank。

## 五、常见问题与参考答案

### 1. Embedding 和 Reranker 有什么区别？

Embedding 通常用于第一阶段召回，把 query 和海量 chunk 映射成向量后快速找候选。Reranker 用于第二阶段重排，输入 query 和候选文本，做更精细的相关性判断。

面试回答可以说：Embedding 追求高召回和低延迟，Reranker 追求排序质量。生产系统常用 Embedding 召回几十到几百个候选，再用 Reranker 选出最适合进入上下文的少量片段。

### 2. 为什么向量相似但答案还是错？

常见原因：

- chunk 语义相似但不包含答案。
- query 太短或表达模糊。
- Embedding 模型不理解领域术语。
- top_k 太小，正确片段没召回。
- metadata 过滤错误，把正确文档过滤掉。
- chunk 切分破坏了上下文。
- rerank 或上下文裁剪把正确片段丢了。

不要只怪模型幻觉。要分层排查：query、embedding、索引、过滤、召回、rerank、上下文组装和生成。

### 3. HNSW 为什么内存占用高？

HNSW 不只存向量，还存图结构。每个节点会保存邻居连接，`M` 越大连接越多，召回质量越好，但内存越高。加上 metadata、多副本和索引构建临时空间，实际资源占用会明显高于原始向量大小。

### 4. top_k 设置越大越好吗？

不是。top_k 太小可能漏召回，top_k 太大则会增加延迟、rerank 成本和上下文噪声。合理做法是通过离线评估观察 Recall@K 曲线，找到收益开始变平的位置，再结合线上延迟和成本约束确定默认值。

### 5. Embedding 模型升级要注意什么？

不同 Embedding 模型产生的向量空间通常不兼容，不能把新模型 query 向量拿去搜索旧模型文档向量。升级时要：

1. 新建索引或新建 namespace。
2. 用新模型全量重嵌入文档。
3. 用离线评估集对比 Recall@K、MRR、延迟和成本。
4. 小流量灰度。
5. 保留旧索引用于回滚。

### 6. metadata 过滤为什么不能只放在应用层？

因为如果先召回再过滤，未授权内容已经被检索系统读出，甚至可能进入日志、rerank 或模型上下文。权限控制应该尽量在检索层前置执行，至少保证模型和下游组件看不到无权限内容。

### 7. 向量数据库和 Elasticsearch 是替代关系吗？

不完全是。向量数据库擅长语义相似搜索，Elasticsearch/OpenSearch 擅长关键词、过滤、聚合和成熟运维。很多企业系统会使用混合方案：向量召回处理语义相似，BM25 处理精确词和编号，再合并重排。

### 8. 如何处理非常短的 query？

短 query 信息量不足，例如“退款”“报错 1003”。策略包括：

- 结合会话上下文做 query rewrite。
- 使用关键词召回补强。
- 对产品名、错误码、API 名称做精确匹配。
- 让用户补充范围。
- 根据业务入口增加默认过滤条件。

不要单纯依赖向量相似度。

### 9. 如何判断是 Embedding 不行，还是 chunk 策略不行？

可以做对照实验：

1. 固定 Embedding，比较不同 chunk size、overlap 和结构化切分策略。
2. 固定 chunk，比较不同 Embedding 模型。
3. 使用同一套评估集，分别看 Recall@K、MRR 和错误样例。
4. 人工抽查漏召回 query，判断正确答案是否存在于 chunk 中。

如果正确答案根本不在任何 chunk 中，多半是解析或切分问题；如果答案在 chunk 中但排不上来，才重点看 Embedding、索引和 rerank。

### 10. 向量索引参数怎么调？

先建立 Flat 精确检索或高质量配置作为基准，再调 ANN 参数。以 HNSW 为例：

- 增大 `M`：可能提升召回，但内存增加。
- 增大 `efConstruction`：索引质量提升，构建更慢。
- 增大 `efSearch`：查询召回提升，延迟增加。

调参要用评估集和线上延迟数据，不要凭感觉。

### 11. 为什么要记录 embedding_model_version？

因为向量结果强依赖模型版本。没有版本字段时，线上召回异常很难判断是文档变化、模型升级、索引重建还是切分策略变化导致。版本字段还支持灰度、回滚和双索引对比。

### 12. RAG 召回层有哪些线上监控指标？

建议至少监控：

- query embedding 延迟和失败率。
- 向量检索延迟 P50/P95/P99。
- 候选数量不足比例。
- 平均最高相似度分数。
- top_k 分数分布。
- metadata 过滤命中比例。
- rerank 延迟和失败率。
- 用户点击或采纳的引用片段。
- 无答案率和人工负反馈。

这些指标能帮助定位“没有召回”“召回慢”“召回错”“过滤过严”等问题。

## 六、面试回答模板

当面试官问“你们怎么做向量检索”时，可以按这个结构回答：

1. **数据入库**：文档解析、结构化切分、清洗、批量生成 Embedding、写入向量和 metadata。
2. **索引选择**：小规模用 Flat 做评估基准，生产用 HNSW 或 IVF，根据数据规模、延迟和内存调参。
3. **权限过滤**：租户、角色、文档范围等 metadata 前置过滤。
4. **混合召回**：向量召回解决语义相似，BM25 解决精确词和编号。
5. **重排与裁剪**：合并去重后用 reranker 精排，最终只保留高相关片段。
6. **评估监控**：用 Recall@K、MRR、NDCG 评估召回，用线上日志和坏 Case 反推优化。
7. **版本治理**：记录文档版本、chunk 策略版本、Embedding 模型版本和索引版本，支持灰度与回滚。

## 七、容易踩坑

- 只存向量，不存 chunk 原文和 metadata，导致无法溯源。
- 把权限过滤放到 LLM 输出之后。
- Embedding 模型升级后新旧向量混用。
- top_k 靠感觉设置，没有 Recall@K 曲线。
- 只用向量检索，忽略错误码、产品名、API 名称等精确匹配场景。
- chunk 固定长度切分，破坏标题、表格、列表和代码块结构。
- 没有记录索引版本，线上结果变化无法复现。
- 只看最终答案准确率，不单独评估召回层。

## 八、速记总结

Embedding 与向量索引工程的核心不是“把文本变成向量”，而是围绕召回质量、权限边界、索引性能、版本治理和评估闭环构建可控检索层。

面试中最重要的观点：

- Embedding 负责粗召回，Reranker 负责精排。
- 向量索引调优是召回、延迟、内存和构建成本的权衡。
- 权限和租户过滤必须前置到检索层。
- 企业 RAG 通常需要向量检索和关键词检索结合。
- Embedding 模型、chunk 策略、索引参数都必须通过评估集验证。
- 版本字段是线上排查、灰度和回滚的基础。
